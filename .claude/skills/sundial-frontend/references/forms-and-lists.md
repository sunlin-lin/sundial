## 1. 表單

### 1.1 驗證規則必須來自 OpenAPI schema

必填、長度、數值範圍、格式一律取自 OpenAPI schema 的 `required`／`maxLength`／`minLength`／`minimum`／`maximum`／`pattern`，不得在前端另寫一套數字或正則。前端只允許額外做純體驗性的即時提示，且判定門檻仍必須來自同一份 schema。兩套規則一定會漂移：前端限制 20 字、後端 50 字時，使用者被前端擋住卻不知道其實可以輸入。

後端欄位改名或限制變更時，若前端有引用產生型別，`vue-tsc` 會擋（型別對不上）；「表單規則裡出現字面長度上限與正則字面量」的掃描測試不存在。

### 1.2 送出中防重複點擊

送出按鈕在請求進行中必須 `disabled` 且顯示 loading，禁止只靠「送出後導頁」避免重複送出。後端對同一筆資料的重複操作會以條件式 UPDATE 拒絕第二筆，但使用者會看到一個莫名其妙的錯誤。「帶 `@click` 且觸發 API 的 `el-button` 必須同時綁 `:loading` 或 `:disabled`」這條掃描測試不存在，靠 review。

### 1.3 失敗後的欄位錯誤呈現

`code === '300'` 時，逐筆讀 `errors`，以 `errors[].data.field` 對應回表單欄位就地顯示 `errors[].msg`，並捲動到第一個錯誤欄位；找不到對應欄位的錯誤才用全域提示。**禁止只跳一個 `ElMessage.error('儲存失敗')` 了事。**

`field` 是路徑式（dot-path），陣列以索引表示、0 起算，例如 `items.2.startTime`。**主路徑是解析 dot-path**：拆出路徑段，依段逐層走進表單資料結構，數字段即陣列索引，定位到陣列中第 3 筆的那一格並標紅、捲過去——不是拿整串 `field` 去跟某個扁平欄位名做等值比對。這件事必須寫在一支統一函式內（與 `el-form-item` 的 `prop` 對接），不是各頁自己 `split('.')`。

理由：本系統多處畫面會出現「同一種欄位在陣列中重複出現」的結構。把 `field` 當扁平欄位名處理，`startTime` 在一張五列的表格上指不到任何一列，前端唯一能做的是退化成全域提示「時間格式錯誤」——等於這個 `field` 白給，使用者得自己逐列比對找出是哪一筆錯。

「解析必須經統一函式，禁止頁面自行 `split('.')`」這條掃描測試不存在。目前**沒有現成的統一函式可抄**（`apps/web/src/pages/` 底下還沒有出現需要陣列型欄位錯誤定位的頁面）——新增這類表單時，先確認要不要順手把這支函式建起來放進 `shared/`，而不是各頁各自 `split`。

### 1.4 大型表單的拆分與草稿

「任一失敗整筆取消」的建立流程維持單頁單次送出，但按區塊拆成子元件；可分段獨立更新的編輯流程按分頁拆分，每個分頁獨立送出。**未送出內容一律不做自動儲存草稿**，改為離開有未儲存變更的表單時攔截確認——這類表單可能含敏感個資，暫存 `localStorage` 會把敏感資料留在裝置上，裝置換手即外洩。

## 2. 表格與清單

### 2.1 分頁、排序、篩選參數與後端統一

欄位名固定，禁止各頁自取別名：

| 用途               | Request 欄位                     | Response 欄位                 |
| ------------------ | -------------------------------- | ----------------------------- |
| 目前頁碼（1 起算） | `currentPage`（平鋪）            | `data.pagination.currentPage` |
| 每頁筆數           | `perPage`（平鋪）                | `data.pagination.perPage`     |
| 總筆數             | —                                | `data.pagination.totalCount`  |
| 排序               | `sort: { field, order }`（單欄） | `data.sort`                   |
| 篩選條件           | 平鋪於 request 根層              | `data.search`                 |
| 清單本體           | —                                | `data.data`                   |

**總頁數由前端計算**（`Math.ceil(totalCount / perPage)`），後端不提供也不得要求提供——`totalCount` 與 `totalPages` 並存時只要有一邊算錯，就會出現「共 137 筆、14 頁」但第 14 頁是空的，而兩個數字都來自後端，前端沒有依據判斷該信哪一個。

查詢、排序、分頁一律由後端執行，**前端不得對「當前頁資料」再排序或篩選後呈現**——那會讓使用者看到「這 20 筆之中的排序」，畫面卻顯示「共 340 筆」，排出來的第一名不是全體第一名，而且不會有任何報錯。篩選條件變更一律回到第 1 頁。

⚠️ 「禁止 `.sort(`／`.filter(` 後直接渲染」「禁止出現 `totalPages`／`pageTotal` 等本地欄位名」這兩條掃描測試都不存在，靠 review。

### 2.2 空／載入中／錯誤三態

四態（載入中／有資料／空結果／載入失敗）怎麼做，照現成的列表頁抄（`regulatory/datasets` 的版本清單、`regulatory/sync`）比展開規則省事。這裡只記兩件抄不出來、而且沒有工具擋的事：

- **空結果要分「本來就沒資料」與「篩選後無結果」**，後者要提示可清除篩選。只做一種空狀態的話，使用者篩到沒結果時會以為系統真的沒有任何資料。
- **載入失敗依 `shared/api/load-failure.ts` 的 `LoadFailure` 分兩種**（見 `api-envelope.md` §3）：無權限不給重試鈕、其他給重試。這條分流邏輯是共用函式，不要在頁面裡重寫一次判斷。

⚠️「使用列表資料來源的頁面必須同時出現 error 分支與 empty 分支的渲染」這條掃描測試不存在。

### 2.3 list 回應必須比對 `search`／`sort` 回聲

收到 list 回應後，必須先比對 `data.search` 與 `data.sort` 是否等於「目前畫面上的查詢條件與排序」，不相等就整包丟棄：不寫入 `rows`、不更新 `pagination`、不關閉 loading。這段比對寫在統一的地方，不是各頁自己判斷；**禁止用「後送的一定後到」為前提直接賦值**。

理由：使用者快速切換篩選條件時會連續送出多次請求，而回應到達順序不保證——第一次查詢走到一台比較慢的節點，可能比第三次晚回來。直接賦值的結果是**舊回應蓋掉新回應**：畫面上的篩選器停在 A 條件，列表卻是 B 條件的資料。這種 bug 不會報錯、本機網路太快也測不到，只在客戶端偶發，使用者唯一能得到的結論是「這個系統的數字不能信」。

`shared/api/list-echo.ts` 的 `isListEcho` 是真正落地的那支純函式：

```ts
// ✅ 統一函式：回聲不符就丟棄（client 已拆掉 envelope，回的就是 data）
const page = await api.recordList({ ...search, sort, currentPage, perPage })
if (!isListEcho(page, { ...search, sort })) return // 舊回應，丟掉
rows.value = page.data
pagination.value = page.pagination
```

檔頭記下了「這支為什麼是純函式而不是一個包辦 `rows`／`pagination`／`loading`／`error` 的 composable」：§7.3 的用詞是「統一的列表 composable」，但兩個現成的列表頁（`regulatory/sync` 與 `regulatory/datasets` 的版本清單）在失敗分流、篩選條件形狀上並不相同，硬抽一個共用殼會立刻開始長 `mode` 參數。回聲比對是兩頁逐字相同的那一段，且是純函式、可以逐格測，所以只抽這一段。**新增第三個列表頁時，若又需要一次「四態都要有」的殼，才是重新評估要不要抽 composable 的時機，不要現在先抽。**

⚠️「列表資料的賦值必須發生在回聲比對函式的分支內」這條掃描測試不存在，靠 review——`isListEcho` 本身有單元測試（`shared/api/list-echo.test.ts`），但沒有工具檢查「呼叫端真的有先判斷才賦值」。
