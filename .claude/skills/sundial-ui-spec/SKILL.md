# Sundial UI 定案文件撰寫

## 這份 skill 只講什麼

`docs/ui/` 的 16 份文件體例高度一致，但不是完全一致——直接照抄看到的第一份文件,有相當機率抄到的是特例而不是通則。這份 skill 只做一件事：把 16 份文件逐一讀過之後歸納出「真正共通的規律是什麼、哪裡其實分岔成好幾種寫法、哪裡是單一文件的特例」，讓下一份文件不用重新讀十六遍就能抄對形狀。

畫面本身要寫什麼內容（查詢條件有哪些欄位、狀態機怎麼轉）不是這份 skill 管的事——那是每個畫面各自的產品決策，去讀 `docs/plans/`、跟使用者確認、或讀 `docs/schema/` 對應章節。這份 skill 只管**格式與分工邊界**：這份文件該有哪些章節、界線畫在哪裡、「還沒定案」要怎麼寫才不會被下一個人誤讀成「已經拒絕」或「已經定案」。

## 四種既有體例，不要假裝只有一種

16 份文件不是套同一份模板寫出來的，是同一個人在不同畫面類型上重複做出相近的判斷，結果自然收斂成四種形狀。硬套單一模板去寫第四種畫面，寫出來的東西會比自己判斷更難讀。

## ★ `確認狀態` 記錄的是真的發生過的事，不是套語

每一份既有文件開頭都寫著「本文件內容已由使用者明確同意，列為正式 UI 規劃」。**那句話是在記錄一件真的發生過的事** —— 使用者逐項看過並同意了。

**新寫的文件預設是「尚未確認」。** 照抄那句話等於偽造一個從未發生的確認，而且方向最糟：下一個人會拿它當作可以直接開工的依據，不會回頭問。他不會發現，因為文件之間長得一模一樣。

新建文件時，這一節寫：

```markdown
**尚未經使用者確認。** 本文件是依使用者指示新建的初稿，[哪些部分是自行判斷的]，尚未逐項經過確認。經使用者確認後再改寫本節。
```

使用者確認之後才改成正式的那一句。這條在 `assets/template.md` 也寫了一次 —— 它是這份 skill 唯一一條「照抄既有文件反而會出錯」的地方，所以兩邊都放。

（這條是 `23-ui-daily-attendance-records.md` 初稿實際踩到之後補的：模板原本把「已由使用者明確同意」寫成填空的預設值，等於慫恿寫的人偽造。）

### 第一種：查詢＋列表型（最常見，是「標準形狀」的來源）

代表作：`09-ui-all-attendance.md`（示範最完整）、`12-ui-my-attendance.md`、`08-ui-organization-structure.md`。

章節順序：`確認狀態 → 導覽結構 → 查詢條件 → 列表 → 顯示規則 → 資料責任 → （本輪明確延後）`。

適用條件：畫面的核心是「查一組條件、看一張表」，沒有審核流程，也不橫跨多個實體的建立步驟。最後一節不是必要的——`08` 用的標題是「本輪明確未納入」而不是「本輪明確延後」，`14`（唯一一份零待定的畫面）乾脆沒有這一節，因為真的沒有東西要延後。

### 第二種：申請／簽核流程型

代表作：`17-ui-attendance-correction-approval.md`、`18-ui-overtime-approval.md`、`19-ui-leave-approval.md`、`13-ui-attendance-correction.md`、`14-ui-my-leave.md`、`15-ui-my-overtime.md`。

章節順序沒有固定模板，但重複出現的組件是：`確認狀態 → 導覽（與權限）→ 預設查詢與分頁 → 列表 → 明細 → 狀態操作／核准與退回／撤銷審核結果 → 併發與薪資限制`。這一類文件很少有獨立的「本輪明確延後」節——待定事項多半是行內一句話（例如 `12` 的「是否允許從此處申請補卡或更正尚未定案」），不必為此起一個章節。

這一類文件常常需要**定義一張全新的表**（審核歷程、來源標記這類原本不存在的資料）。`17` 直接在文件裡放了 `attendance_correction_reviews` 的完整欄位表，`16-ui-my-payroll.md` 放了 `payroll_attendance_snapshots` 的完整欄位表——這看起來違反下一節講的分工邊界，但其實是被允許的例外，見下一節說明。

### 第三種：多分頁複雜表單型（目前只有一份先例）

代表作：`20-employee-list.md`——唯一一份用數字編號章節（`## 1. 選單與列表`、`### 2.1 基本資料`）的文件，開頭也不是 `## 確認狀態` 標題，而是檔案最上方一行 `> 狀態：本輪已確認` 的引言區塊，外加 `> 對應 Schema：` 指向相關 Schema 文件。

適用條件：畫面本身是「新增走單頁、修改走多分頁」這種橫跨多個實體、每個分頁邏輯上是獨立子表單的複雜表單，用查詢條件／列表／顯示規則這種單一畫面的骨架硬套會塞不下。這種情況改用編號章節，每個分頁一個章節，最後加一節「已確認規則摘要」條列全部已定案規則——這份摘要在其他三種體例裡都沒有,是這種複雜度才需要的收尾。

**這是體例裡最大的分岔**，不要因為「多數文件用第一種」就假設下一份多分頁表單也該用第一種——當畫面複雜度真的到了「一個分頁就是一個子系統」的程度，抄 `20` 的編號章節比硬套查詢／列表骨架更清楚。

### 第四種：功能範圍總覽型（範圍未收斂成單一畫面）

代表作：`22-ui-shift-settings.md`。

不用查詢條件／列表／顯示規則的骨架，而是依業務功能分類（固定排班、循環排班、班組、換班、代班、待命備勤……）逐類列出已定案規則與尚未定案項目，結尾一節「Schema 對應」同時列出「既有 Schema 可承接的」與「需獨立補充但尚未定案表名的」兩份清單。

適用條件：這份規劃涵蓋的範圍本身還很大、還沒收斂成一個或幾個具體畫面（例如「班別設定與排班模式」實際上涵蓋十幾種排班型態，每種都可能各自需要獨立畫面）。**這種文件的「Schema 對應」節事實上就是第二種體例裡「本輪明確延後」節的功能，只是沒有用那個標題**——判斷一份新文件該不該長這樣，看的是範圍夠不夠大、夠不夠早期，不是看畫面類型的表面相似度。

### 誠實的結論

**這裡沒有一套放諸四海皆準的章節清單。** 唯一在多數文件裡都出現、且措辭穩定的是開頭的確認狀態句式：「本文件內容已由使用者{明確同意／明確確認／要求記錄}，列為正式 {UI／UI、流程與 Schema／功能} 規劃。」——用哪個受詞取決於這份文件除了畫面之外還定案了流程、Schema 還是純功能範圍。`20` 與 payroll 那份沒有這一句，是目前僅有的兩個例外。新文件寫哪一種形狀，看它更接近上面四種裡的哪一種，而不是機械套用某一份模板。

## UI 文件與 Schema 文件的分工邊界

`docs/ui/README.md` 開宗明義：「本目錄只保存畫面、操作流程與已確認的使用規則。資料表欄位、型態、關聯及約束仍以 Schema 文件為準。」具體判準：

**UI 文件可以寫**：畫面上看得到什麼、資料**從哪張表的哪個欄位來**（可以指名欄位，例如「工時：`attendance_results.worked_minutes` 轉換為畫面格式」）、操作流程與狀態轉換、送出前的檢查規則、誰能看誰的資料。

**UI 文件不該寫**：欄位的資料型態、長度、是否為 NULL、索引、外鍵約束、預設值——這些交給 `docs/schema/01`–`06`。

正例（`09-ui-all-attendance.md`）：

> 遲到：`attendance_results.late_minutes`；無則顯示「—」

只講顯示規則與欄位來源，沒有講 `late_minutes` 是不是 `integer`、能不能是 NULL。

反例（不該這樣寫）：

> 遲到：`late_minutes`（`integer`，可為 NULL，索引於 `attendance_results_employee_date_idx`）

這句話把 Schema 文件該負責的型態與索引細節搬進了 UI 文件——下次 Schema 文件改了型態，UI 文件不會跟著改，兩份文件就此各自演化出矛盾版本。

**例外，而且是唯一被容許的例外**：畫面需要一張**目前 Schema 文件裡完全不存在的新表**（例如 `17` 的 `attendance_correction_reviews`、`16` 的 `payroll_attendance_snapshots`）。這種情況下，UI 文件可以先把完整欄位表寫出來——因為這張表是這份 UI 決策的直接產物，等這份 UI 文件定案，就代表這張表也定案了。**但這不是「UI 文件可以定義 Schema」的通則，而是「新表誕生於 UI 決策」的特例**，而且緊接著要做兩件事：

1. 把同一份欄位表**回寫**到對應的 `docs/schema/0X-*.md`（`17` 的 `attendance_correction_reviews` 與 `16` 的 `payroll_attendance_snapshots` 都確實被回寫進了 `docs/schema/03-scheduling-attendance.md` 與 `docs/schema/02-employee-payroll-cost.md`——去核對過，這條規則真的被遵守了）。
2. 修改既有表結構時（例如 `17` 對 `attendance_records` 加欄位）不要在 UI 文件裡重複整張表定義，只點出新增的欄位。

判斷一件事該不該寫進 UI 文件，問自己：「這句話是在講畫面行為，還是在講資料庫怎麼存？」是後者就搬去 Schema 文件，除非它是上面說的「新表誕生」情況。

## 「本輪明確延後」：作用與寫法

這是整套文件體例裡最有價值的機制，值得單獨講清楚——它解決的問題是：**「還沒想清楚」和「已經決定不做」是兩種完全不同的狀態，但兩者在文件裡如果沒被分開寫，下一個讀者無法分辨。**

`09-ui-all-attendance.md` 的寫法是範例：

> 本輪只確認「全體出勤」的查詢與顯示，不確認打卡 GPS 的保存 Schema：
>
> - GPS 必須在打卡時保存。
> - GPS 需能反查為大約地址供本頁顯示。
> - 經度、緯度、定位精準度、反查地址及反查時間等實際欄位，等討論打卡功能時再逐欄確認。
> - 是否顯示地圖、原始經緯度及定位精準度，亦留待打卡與出勤明細畫面討論。
> - **不因本頁需要顯示地址，就自行把未確認欄位補入 `attendance_records`。**

拆解這五句話在做的事：前三句列出「這一輪範圍內、但還沒決定的具體項目」；第四句劃出「這些項目留到哪個場合再決定」；最後一句是**明文禁止下游自行補猜**——這句話不是可有可無的收尾，是這一節真正的價值所在。沒有這句話，下一個實作者遇到「畫面需要顯示地址，但欄位沒定案」的落差時，最自然的反應是自己猜一個欄位名稱填上去，而猜出來的欄位一旦被程式碼引用，就從「暫定」變成「事實上的定案」，覆水難收。

寫這一節時的判準：

- **寫到動作層級，不要寫到功能層級。** `12-ui-my-attendance.md` 的寫法是「目前只能查看；是否允許從此處申請補卡或更正尚未定案」——延後的是「從出勤明細直接跳轉去補卡」這個**捷徑動作**，不是「補打卡」這個**功能**（補打卡功能在 `13` 早就定案且已有獨立導覽項）。如果只寫「補打卡功能尚未定案」，下一個人會誤以為 `13` 也還沒生效，於是重新猜一次已經有答案的東西。
- **不是每份文件都需要獨立成節。** 待定事項只有一兩句時，寫成行內一句話（例如 `11` 的「敏感資料是否遮蔽及遮蔽規則尚未定案」）就夠了，不必為了套模板硬起一個標題。只有當延後的範圍夠大、會被其他文件依賴時（`09` 的 GPS 欄位擋住五個畫面），才值得獨立成一節，因為那時「這裡不得補猜」這句禁止語本身就是重要資訊，值得讓它顯眼。
- **標題可以是「本輪明確延後」也可以是「本輪明確未納入」**（`08` 用的是後者）——用哪個字不重要，重要的是內容具備上面三個要素：具體項目、留待何時何處決定、禁止補猜。

## 文件會漂移，而且沒有工具在擋

`docs/ui/` 沒有任何腳本檢查文件之間是否互相矛盾或過期。以下是查證過的真實案例，修改既有文件時要引以為戒。

**案例一：`09` 的「本輪明確延後」節已經過期。** 它現在仍寫著 GPS 欄位「等討論打卡功能時再逐欄確認」，但打開 `docs/schema/03-scheduling-attendance.md` 會看到一整節「打卡欄位定案（原標『留待打卡功能討論，本輪不得補猜』，此節即該次討論的結果）」——`latitude`／`longitude`／`accuracy_meters`／`address`／`address_resolved_at`／`revoked_at`／`revoked_by`／`revoke_reason`／`revoked_seq` 全部已經定案，連座標的可見範圍規則、併發鎖粒度都寫完了。**`09` 沒有被同步更新**，字面上仍然告訴讀者這些欄位還沒決定。

教訓：**改動一份 UI 文件涉及的定案時，要搜尋其他份文件有沒有引用同一件事。** 這次是 Schema 文件超前 UI 文件；下次也可能反過來。`docs/schema/03` 裡「已確認的『全體出勤』UI」這類小節其實是同一件事在兩個文件各記一份的另一種形式，一樣有漂移風險。

**案例二：`12` 與 `13` 字面上像是互相矛盾，其實不是。** `12`（我的出勤）寫「補卡／更正入口尚未定案」，`13`（補打卡申請）卻已經是獨立導覽項且完全定案。只看標題或粗略掃過內容，很容易誤讀成「補打卡功能到底定案了沒」的衝突。實際讀完才知道 `12` 講的是「從出勤明細直接跳轉去補卡」這一個捷徑動作，跟 `13` 本身是否定案是兩件事——這正是上一節「寫到動作層級」那條規則要防的誤讀。修改任一份文件前，先確認自己講的是同一個動作層級，不要看到「尚未定案」四個字就以為整塊功能都還沒決定。

**案例三：新增文件忘記掛進索引，這件事已經真實發生過，不是假設風險。** `docs/ui/payroll-calculation-settlement.md` 這份文件本身沒有編號（其他都是 `07`–`22`），也**完全沒有被 `docs/ui/README.md` 收錄**——不在任何一個分組底下。它同時是 22 份 UI 文件裡唯一一份全文不指名任何資料表的文件（`docs/plans/00-roadmap.md` 已指出這點）。對應地，`docs/schema/02-payroll-calculation-settlement.md` 也沒有被 `docs/schema/README.md` 的文件清單收錄。這兩個遺漏共同說明一件事：**索引不會自動同步，寫完文件卻忘記掛進索引，不會有任何工具提醒你。**

**案例四：兩份索引各自維護一份 UI 文件清單，分組方式不同。** `docs/ui/README.md` 依選單分組（系統設定／人事作業／總覽／我的資料／簽核）列出連結；`docs/schema/README.md` 也在自己的「文件」清單裡列出全部 `07`–`22`，但單純依編號排序，不分組。新增文件時，兩份索引都要更新——只更新其中一份，另一份就開始跟真實文件清單脫節（`payroll-calculation-settlement.md` 的下場是**兩份都沒更新**，成為兩邊都找不到的孤兒文件）。

## 新增文件的配套

新增一份 UI 定案文件不是寫完 `.md` 就結束，還有三件配套：

1. **檔名編號**：現有編號是 `07`–`22`（`01`–`06` 保留給 `docs/schema/`），下一份接續使用 `23` 起跳。檔名格式沿用既有慣例 `<編號>-ui-<主題英文簡稱>.md`（例外：`20-employee-list.md` 沒有 `ui-` 前綴、`payroll-calculation-settlement.md` 完全沒有編號——這兩個例外不是值得模仿的先例，新文件照 `NN-ui-xxx.md` 的主流格式取名）。

2. **同步掛進兩份索引**：`docs/ui/README.md` 依畫面所屬選單分組（系統設定／人事作業／總覽／我的資料／簽核）加進正確分組；`docs/schema/README.md` 的「文件」清單也要加一行，格式與既有條目一致（連結＋一句話說明這份文件涵蓋什麼）。兩份都要動，見上一節案例四。

3. **導覽結構要與 `apps/web/src/menu/main-menu.ts` 的實際分組核對**。這份文件的導覽結構章節（例如 `人事作業 → 全體出勤` 這種樹狀圖）描述的是**未來要做成什麼樣子**，不代表 `main-menu.ts` 現在就有對應分組——目前 `main-menu.ts` 只有三個分組（`menu.overview`／`menu.system-settings`／`menu.hr-operations`），因為全案只做完 3 個畫面；UI 文件裡的「我的資料」「簽核」這兩個分組現在還不存在於 `main-menu.ts` 裡是正常的，不是文件寫錯。但**分組名稱本身要跟已經出現在 UI 文件裡的既有命名一致**（例如新畫面若屬於「人事作業」，就沿用這個名稱，不要自創「人力資源」之類的同義詞）——等這個分組真的被實作時，這份命名一致性能讓 `main-menu.ts` 直接對得上，不必回頭改文件。

- 導覽結構的分組名稱是否與既有 UI 文件、`main-menu.ts` 已用過的名稱一致？
