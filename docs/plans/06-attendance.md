## 1. 目標

**讓 Dashboard 的「上班打卡」按得下去，而且按下去之後，全體出勤、我的出勤、補打卡申請、補打卡簽核，以及使用者本輪新提出的每日全員打卡明細，五個畫面看得到同一組事實。**

現況：出勤層**一張表都還沒有**。`docs/schema/03` 原本卡在「GPS 座標留待打卡功能討論，本輪不得補猜」，這件事已經在文件層級解決——`attendance_records` 的「打卡欄位定案」節已經把時間、GPS、撤銷四類欄位都定下來了。但欄位定案不等於可以直接開工：欄位定案回答的是「這張表長什麼樣」，沒有回答「兩個人同一秒打卡會怎樣」「誰能撤銷誰的卡」「沒有班表時判定要吐出什麼」「稽核要記到什麼程度」——這四件事字典裡沒有一個字，而它們每一個答錯，都是等到併發測試或稽核掃描器出手才會被發現的錯誤。

## 2. 為什麼這一層值得現在做

出勤判定是加班、請假、薪資結算共同的輸入。roadmap §5 講得很直白：**有人先做排班而跳過打卡，會做出一個「排得出來但驗證不了」的模組**；同理，跳過出勤直接做加班或薪資，會做出一個永遠在等 `attendance_results` 的殼。

而且這是全站唯一一個**同時**要處理「同一端點依呼叫者身分回傳不同欄位」「跨模組併發鎖」「無資料來源時仍要吐出結構完整結果」三件事的模組——前兩層（部門、任職）都各自只踩到其中一項。

## 4. 必須先解決的設計問題

這一節是本計畫的主體。其中兩項是使用者原始已拍板的既有定案（見 §7），多數其餘項目字典與 UI 定案都沒有答案，本計畫逐一定案；§4.2 的座標遮罩規則、§4.3.1 已引用打卡能否撤銷，字典與 UI 原本同樣沒有答案，本輪已由使用者裁示，本計畫據此定案細節（見 §9 的分界說明）。§4.7 是使用者本輪新提出、原始六項 UI 定案都未涵蓋的畫面，一併在本節處理。

### 4.1 沒有班表時，`attendance_results` 要寫出什麼、寫不出什麼

roadmap §3 的處置是「2-D 先做沒有班表時的判定，排班上線後再補對照班表的部分」，但沒有說「沒有班表時的判定」實際上算得出什麼。`attendance_results` 的九個數值欄位全部是**必填 `integer`**，沒有 nullable 這個退路可用，所以「算不出來」必須有一個明確寫入值，不能留白。

**算得出來的（只需要有效打卡事件，不需要班表）：**

- `worked_minutes`：配對到的有效上班卡與下班卡時間差
- 出勤天數（「這天有沒有來」）：由「當天是否存在有效上班卡」推得，屬於彙總層邏輯，不佔 `attendance_results` 的欄位

**算不出來的（需要應上班時間、應下班時間、休息時段才能比較）：**

- `scheduled_minutes`（不知道應該上多少分鐘）
- `late_minutes`、`early_leave_minutes`（沒有基準時間可以比較誰遲到）
- `overtime_minutes`（不知道超過的是不是「預定工時」之外）
- `absence_minutes`（連「這天該不該上班」都不知道，談不上缺勤）

**兩種選擇的後果：**

- **選項 A：算不出來的欄位一律寫 `0`，`result_status_code` 沿用「正常」代碼。** 後果：畫面上「遲到—」與「未排班所以沒算」變成同一個外觀，使用者看到的是一筆看起來完全正常出勤的紀錄；等排班上線後重算，這批舊紀錄與真正「準時」的紀錄在畫面上完全無法區分，而使用者已經看過、記得的是前者。
- **選項 B：算不出來的欄位一律寫 `0`，但 `result_status_code` 使用新代碼（如「未排班待判定」），與「正常」「遲到」「異常」等既有狀態並列。** 後果：全體出勤／我的出勤的狀態欄要多認得一個代碼，UI 定案沒有這個狀態值需要補一筆代碼定義；但換到的是畫面能誠實顯示「這筆還沒有真正判定」，而不是用「正常」冒充。

**本計畫定案：選項 B。** 「看起來完整、實際上算不出遲到早退」正是 roadmap §3 明講要避免的失敗模式，用一個假的「正常」蓋過去只是把這個警告原樣做進系統裡。`result_status_code` 新增 `NO_SCHEDULE` 一項；`scheduled_minutes`／`late_minutes`／`early_leave_minutes`／`overtime_minutes`／`absence_minutes` 全部寫 `0`，`worked_minutes` 依可配對到的有效打卡計算。

**排班上線後怎麼補，才不會變成兩套判定邏輯：** 判定函式從第一天就設計成 `computeAttendanceResult(events, schedule: Schedule | null)` 這一個簽章，`schedule` 為 `null` 時內部直接跳過遲到／早退／應工時分支、只算 `worked_minutes`，回傳 `NO_SCHEDULE`。第 3 層要做的不是「新增一個判定函式」，是把真正的 `Schedule` 物件傳進**同一個**函式——如果排班上線時是另外寫一份「有班表版」的計算器，兩份邏輯字面上不同但語意上必須永遠一致（例如「跨日班的 `work_date` 歸屬」這條規則），維護成本會複製一份。同時要有一支「重算全部 `NO_SCHEDULE` 紀錄」的批次動作，否則排班上線前的歷史紀錄永遠停在未判定狀態。

### 4.2 GPS 座標：明文欄位、型別選擇與可見範圍規則

`docs/dev-standards-backend.md` §5.1 這次改寫，把敏感個資的加密責任從應用層整個搬到資料庫端靜態加密——`employees`／`employee_dependents` 的身分證、生日、電話、Email、地址已經改回明文欄位，`*_encrypted`／`*_hash` 只在過渡期保留供回填核對。`attendance_records` 的座標與反查地址原本比照 `employees` 的 `*_encrypted` 欄位做應用層 `FieldCipher` 加密（見字典「打卡欄位定案」節舊版），這個前提已經不成立，本節據此重新定案。

**欄位改名：`latitude_encrypted`／`longitude_encrypted`／`address_encrypted` 改為明文欄位 `latitude`／`longitude`／`address`。** 三欄的機密性改由資料庫端靜態加密負責（§5.1 講的 `innodb_encrypt_tables`，目前尚未啟用，這是全站現況，不是出勤層獨有的缺口）。**blind index 不再是需要討論的問題：** 應用層加密整個拿掉了，`blindIndex`（HMAC-SHA256 查重複用）自然也沒有存在的位置；但這不影響原本的結論——座標本來就不需要被查詢重複，這一點在應用層加密還存在的舊版就已經成立，現在只是連「要不要建」這個問題本身都不再有意義。

**座標的型別：比照 §4.7 金額規則的判準來判斷，但結論不同。** §4.7 禁止金額用 `number`／`float`，理由是金額要能精確加總、勞健保級距要在邊界值上精確比較，二進位浮點數的捨入誤差在這兩種場景下會變成看得見、對得上／對不上的錯誤（差一塊錢、選錯級距）。座標不落在這個判準裡：

- 座標從來不加總、不與其他座標相減比較、不在任何門檻上做精確判斷（本計畫已確認沒有地理圍欄需求）；它是一個帶測量誤差的物理量，`accuracy_meters` 本身就承認這個誤差是公尺等級。
- 十進位度數轉成 IEEE754 double 的表示誤差落在 10⁻¹¹ 度量級（換算距離遠小於 1 公厘），比 GPS 定位裝置本身的誤差小了六個數量級以上——與金額不同，這裡沒有一個「差一點就對不上」的業務判斷會被這個誤差影響。

**因此：DB 欄位用 `decimal(9,7)`（緯度，±90，小數 7 位約 1.1 公分精度）／`decimal(10,7)`（經度，±180）**——用定點十進位儲存，寫入當下就不留任何二進位捨入的疑慮，這一步與金額的謹慎程度一致；**但 API 回應型別用 JSON `number`，不維持 decimal 字串**——因為輸出後不會再被拿去計算或比對，只用於顯示或未來接地圖，維持字串沒有實質好處，徒增前端每次顯示都要多一層字串轉數字的動作。Drizzle 讀 `decimal` 回傳字串，service 層做一次 `Number(...)` 轉型後直接輸出；這符合 §4.7 原文「禁止 `Number(...)` 後再計算」的字面規定——這裡只是轉型後直接輸出，沒有計算，不是那條規則要擋的情況，但這是一個容易被後人誤讀成「跟金額一樣違規」的地方，實作時建議在轉型那一行留一句註解說明原因，避免下一個人看到 `Number(...)` 反射性地當成違規改掉。

**座標輸出範圍維持前版定案：列表不輸出經緯度，明細輸出。**（見下方「已確認的『全體出勤』」等章節，這條沒有變。）

**座標遮罩規則：使用者本輪裁示選項 B。** 明細不做精度遮罩，改為依呼叫者身分決定回不回座標：

- **看別人的**（`revoke-other` 那批權限、§4.7 每日全員打卡明細、全體出勤明細）→ 要有 `attendance.records.view-all`／`attendance.records.revoke-other` 這一層權限碼才看得到座標。
- **看自己的**（我的出勤明細）→ 一律看得到，不需要額外權限碼。使用者的理由：這是他自己的位置資料，對他自己隱藏保護不了任何人；限制的對象只有「看別人的座標」。

**這是本專案第一次出現「同一支 `get` 端點依呼叫者身分回傳不同欄位」的模式，實作形狀要講清楚：**

- **分支放在 service 層，不是 handler 也不是 repository。** repository 只管查詢，不該知道「呼叫者是誰」這種與資料表無關的上下文；handler 只做 envelope 包裝與呼叫 service，不含業務判斷（§1.8）。§5.2 已經把「是不是本人」「目標是否同公司」這類細粒度判斷放在 service 層——「這筆記錄是不是呼叫者本人的」與「呼叫者是否具備 `view-all`／`revoke-other`」這兩個輸入，service 在做既有的細粒度權限檢查時本來就要處理，組裝回應時追加一步「要不要保留座標欄位」是同一個判斷脈絡的延伸，不是新增一層。
- **回應 schema 怎麼宣告，才能讓前端分辨「沒有權限看」與「這筆打卡本來就沒有 GPS」：** 這兩者不能都表現成 `undefined`，否則畫面會把「你沒權限」顯示成「沒有定位資料」。做法是同時用 `t.Optional` 與 nullable 的組合，讓「鍵不存在」與「鍵存在但值是 `null`」各自對應到不同語意：
  - **有權限、這筆有 GPS** → `latitude`／`longitude` 兩個鍵都存在，值是數字。
  - **有權限、這筆沒有 GPS**（`gps_required=false` 時本來就可能沒收到座標）→ 兩個鍵都存在，值是 `null`。
  - **沒有權限看別人的座標** → 兩個鍵**整個不出現**在回應物件裡（不是出現且值為 `null`，也不是出現且值為 `undefined`）。

  TypeBox 宣告為 `t.Optional(t.Union([t.Number(), t.Null()]))`，對應到生成型別 `latitude?: number | null`；前端判斷用 `'latitude' in record.data`（或依 OpenAPI 生成型別上的可選性）分辨「鍵是否存在」，用 `=== null` 分辨「有沒有 GPS」，兩層判斷不能合併成一個。

- **這個分支沒有工具在擋，寫錯不會有紅字，要靠測試守住。** `check:layers`（見 `sundial-backend` skill）管的是 import 邊界，不管一支端點對不同呼叫者回傳的欄位是否正確；這裡故意提早標出來，避免下一個人以為「型別過了、CI 過了」就等於這條規則有被驗證。Stage 3 的 `get` 端點測試至少要涵蓋三種情境，缺一種就等於沒鎖住這個分支：
  1. 呼叫者查自己的明細 → 回應必須含 `latitude`／`longitude` 鍵。
  2. 呼叫者具備 `view-all`／`revoke-other` 權限查別人的明細 → 回應必須含 `latitude`／`longitude` 鍵。
  3. 呼叫者不具備上述權限查別人的明細 → 斷言回應物件**完全沒有** `latitude`／`longitude` 這兩把鍵（斷言鍵不存在，不是斷言值為 `undefined`——序列化後兩者在 JSON 上看起來一樣，但斷言鍵不存在才是真正鎖住「整個不回傳」這件事，而不是巧合地值剛好是空的）。

`accuracy_meters` 仍然不輸出到全體出勤等清單頁（明細頁可以顯示）。這一欄與座標的差別不再是「有沒有加密」（兩者現在都是明文）——差別是**它本身不透露位置**：知道「這次定位誤差 5 公尺」不會讓人知道人在哪裡，知道經緯度會。地圖顯示仍然不在本計畫範圍——五份 UI 定案都沒有地圖需求，輸出管道存在不代表要求現在就做地圖畫面，那是之後一個新的、明確的前端設計動作。

### 4.3 打卡撤銷的權限：兩條路徑，不是一條路徑加一個條件

字典的 `revoked_by` 只講「撤銷者公司成員」，沒有講「誰能撤銷誰」。UI 只到「員工可以撤銷自己誤打的卡」（10）與「補打卡走另一套審核流程」（13/17）為止，全體出勤／我的出勤都沒有出現「主管幫員工撤銷正常出勤打卡」這種操作——**UI 定案裡沒有「撤銷別人打卡」這個畫面**，但使用者已定案「撤銷要檢查是否有審核權限」，意味著這個能力確實要存在（否則沒有東西好檢查權限）。

**兩種選擇的後果：**

- **選項 A：單一端點 `attendance/records/revoke`，body 帶 `recordId`，service 內部判斷——若這筆記錄的 `employeeId` 對應操作者自己，直接放行（不需要權限碼）；否則要求 `attendance.records.revoke-other` 權限碼。** 後果：一支端點裡混了兩種完全不同的放行條件，日後有人要調整「本人可撤銷的時間窗」時，一不小心會連帶動到「他人撤銷」那個分支的判斷，兩條邏輯掛在同一個函式裡難以各自獨立測試。
- **選項 B：兩支端點。`attendance/records/revoke`（本人，落在已登入群組，權限碼配給「一般員工」預設角色）與 `attendance/records/revoke-other`（他人，權限碼配給人事／主管角色）。** 後果：稽核 `action` 天生就分成兩種字串，日後追查「這筆撤銷是本人操作還是被審核者代撤」不必再解析 body，直接看 `action`；代價是兩支端點的 request schema、錯誤碼清單要各自維護一份，即使多數欄位相同。

**本計畫定案：選項 B。** 這與 §2 權限模型「本人關係一律由 token 推導，不接受請求帶來的識別碼」的既有慣例一致——`revoke` 端點的細粒度檢查是「這筆記錄的 `employeeId` 是不是 token 推出來的本人」，寫不出「撤銷別人」這個輸入；`revoke-other` 才收 `employeeId`／`recordId` 這種可以指到別人的欄位，而它一開始就要求 `attendance.records.revoke-other` 權限碼過關。這與 `sessions-main.logout-all.service.ts`「先做成只能對自己，日後要開放代踢時加新端點」的先例是同一個判準。**`revoke-other` 目前的消費端是 §4.7 新增的「每日全員打卡明細」畫面**——這一頁是使用者本輪新提出的，原本 UI 定案裡沒有「撤銷別人打卡」的畫面，本計畫在 §4.7 把它排進 Stage，不是自己想像出一個新畫面。

#### 4.3.1 本人撤銷與他人撤銷：資料標記與稽核的差異（使用者拍板）

使用者已經拍板兩件事的組合，本計畫據此定案細節：

|                                | 資料處理                                                               | `audit_logs` |
| ------------------------------ | ---------------------------------------------------------------------- | ------------ |
| **本人撤銷**（`revoke`）       | 標記刪除，不再顯示、不再計入出勤判定                                   | **不寫**     |
| **他人撤銷**（`revoke-other`） | 標記作廢（`revoked_at`／`revoked_by`／`revoke_reason`／`revoked_seq`） | **寫**       |

**「本人撤銷＝刪除」是軟刪除，不是實體 `DELETE`。** 這件事沒有選擇餘地：這套系統目前沒有任何一處走實體刪除，全部是軟刪除（`employees.deleted_seq` 即是先例）；而 `attendance_records` 可能已被 `attendance_results`（判定引用的原始事件）或 `attendance_correction_requests.source_id`（核准後建立的正式打卡）引用，實體刪除會讓這些引用指向不存在的列，**而且沒有任何地方會報錯**——外鍵只在寫入當下檢查存在性，不會在之後某一列被刪除時倒回去檢查誰還在引用它。

**本人撤銷要標記在哪個欄位？** `attendance_records` 目前只有 `revoked_at`／`revoked_by`／`revoke_reason`／`revoked_seq` 這一組，沒有 `deleted_at`／`deleted_seq`。

- **選項 A：沿用 `revoke` 那組欄位，本人撤銷與他人撤銷共用同一套標記機制**，來源不必另外存欄位區分：`revoke`（本人）端點的授權範圍本來就限制「只能撤銷 `employeeId` 對應到 token 本人的紀錄」（見下段），寫入時 `revoked_by` 必然等於這筆紀錄所有人自己；`revoke-other` 則必然是別人。事後要分辨這筆是哪一種，比較 `revoked_by` 是否等於這筆紀錄 `employee_id` 目前綁定的 `company_users` 帳號即可，不需要在 `revoke_reason` 塞約定文字去標記來源（文字約定容易漂移，也容易被之後的人忘記遵守）。要不要寫 `audit_logs`，在服務層當下就已經知道——`revoke` 與 `revoke-other` 是兩支不同的 service，各自決定要不要呼叫稽核，不需要靠讀資料列反推。
- **選項 B：另加一組 `deleted_at`／`deleted_seq`，本人撤銷改走這組，`revoked_*` 專屬他人撤銷。** 後果：「這筆是否有效」的判斷從一個條件（`revoked_at IS NULL`）變成兩個獨立條件（`revoked_at IS NULL AND deleted_at IS NULL`），而字典在「有效狀態不另設欄位」那段已經點名過這個模式的風險——多一個獨立的失效開關，就會出現「兩個開關其中一個沒清乾淨」這種**不會報錯**的壞組合。唯一鍵也要面對同一個問題：現有 `UNIQUE(employee_id, work_date, attendance_type_code, revoked_seq)` 只用一個 seq 防止同一天同一種卡出現兩筆有效紀錄；本人撤銷若改記在 `deleted_seq`，這把唯一鍵就必須同時看兩個 seq 才能正確擋下重複，等於重新設計這把鍵。

**定案：選項 A（使用者 2026-08-29 確認）。** 除了上面兩點，還有一個更根本的理由：字典為 `revoked_seq` 寫的註解是「作法與 `employees.deleted_seq` 相同」——字典設計 `attendance_records` 的失效機制時，從一開始就只打算做**一種**「這筆記錄不算數了」的狀態，`revoked_*` 這組欄位本身就是這張表的軟刪除機制，只是命名沿用「撤銷」而不是「刪除」。使用者現在要分辨的是**這一種狀態底下的兩種來源**（誰讓它變成不算數的），不是需要兩種獨立的狀態機制。選項 A 不改字典、不新增欄位、不動唯一鍵，查詢時一次比較就能回答「這是本人撤銷還是他人撤銷」；選項 B 是在一張表已經有一組失效欄位的情況下再疊一組，重新製造字典已經警告過的組合爆炸。（若之後有其他理由需要獨立、不靠比較就能查詢「本人自行刪除」的筆數，選項 B 仍是可行的，只是代價大於選項 A。）

**本人只能撤銷「自己的」打卡，這一條怎麼保證：範圍來自 token 推出的身分，不是 request body。** 比照 `sessions-main.logout-all.service.ts` 的先例——`revoke`（本人）端點的 request body 只帶 `recordId` 與 `reason`，**不接受呼叫端指定 `employeeId`**；service 撈出這筆 `attendance_records` 之後，先比對它的 `employee_id` 是否等於「目前登入身分透過 `company_users → employee_id` 推出的本人」，不相等就視同找不到這筆記錄，比對通過才進入撤銷邏輯。`revoke-other` 才收 `employeeId`／`recordId` 這種可以指到別人的欄位，而它本來就要求 `attendance.records.revoke-other` 權限碼過關——這是把 §4.3 已經定案的「兩條端點」精神，落到程式碼層面要怎麼兌現寫清楚。

**兩種撤銷之後都要重算 `attendance_results`，沒有差別。** 09／10 的驗收明文要求撤銷後重新計算，這條規則不因撤銷者是本人或他人而不同——`revoke` 與 `revoke-other` 兩支 service 在成功標記之後都要呼叫 Stage 4 的重算動作，這與 §5 Stage 5（Dashboard）已經寫的「撤銷後呼叫 Stage 4 的重算」是同一件事；§4.7 新頁用的也是同一支 `revoke-other`，重算邏輯不需要為新頁另外寫一份。

**已引用的打卡能不能撤銷：使用者定案為「不構成限制」，唯一的限制仍是字典原本就有的薪資結算鎖定。** 本計畫上一版曾提出「有待審核的補打卡申請指向它」與「本身是核准補打卡建立出來的」這兩種情況也要擋下撤銷，**這個提案已由使用者推翻**：字典「已確認的 Dashboard 打卡與撤銷」段落原本就寫著「已鎖定日期不得由員工直接撤銷，應改走更正流程」——使用者的判斷是，這一條就是撤銷限制的全部答案，不需要再疊加「引用關係」這一層。

**為什麼不疊加引用關係限制是對的：** 撤銷一張被待審補打卡申請指向的打卡，那張申請確實會失去依據——但「失去依據」是申請流程自己該處理的狀態（申請可以被退回，也可以由員工自行撤回），不需要靠「禁止撤銷」去預防。用禁止撤銷預防的代價是：員工打錯卡、剛好有人在他改回來之前幫他送出了一張補打卡申請，這張卡就此永遠改不了，直到那張申請被處理完為止——這比「申請暫時失去依據、之後被退回或撤回」是更難解的死結。同理，`source_type_code` 為人工補登的打卡本質上就是一筆正常的 `attendance_records`，沒有理由比現場打卡的紀錄更難撤銷；補打卡簽核既有的「撤銷核准」（UI 17）是另一條同樣有效的路徑，但它不是唯一路徑，`revoke`／`revoke-other` 沒有理由對這一類記錄關上門。

**因此撤銷檢查只剩一項：該工作日是否已被薪資結算鎖定。** 判斷依據沿用字典既有的規則（見「已確認的 Dashboard 打卡與撤銷」段落），與 `attendance_correction_requests`／`attendance_correction_reviews` 現有的「已結算月份不得申請」「薪資開始核算後只可查看」是同一條鎖定機制的不同表現，不是為撤銷另外發明一條新規則。

**但這條檢查目前查不到東西：薪資結算模組（第 5 層）還沒有實作。** `payroll_periods.status_code`（尚未生成、已生成、已結算或已撤銷，見 `docs/schema/02-payroll-calculation-settlement.md`）是目前字典裡唯一定義了「這個月份是否已結算」狀態的地方，但這張表**只存在於文件層級的設計**，roadmap 明白列出薪資結算模組尚未開始實作。也就是說，出勤層現在就算寫這段檢查邏輯，也沒有真正的 `payroll_periods` 資料可查——**這條檢查在薪資模組上線前只能是一個固定回傳「未鎖定」的樁（stub）**，不能假裝現在就查得到已結算狀態。誠實的作法是：Stage 3 的 `revoke`／`revoke-other` 先實作這個檢查點的**介面**（例如一個 `isPeriodLocked(companyId, workDate)` 的判斷函式），現階段固定回傳「未鎖定」；第 5 層薪資結算模組上線時，把這支函式接到 `payroll_periods`（依 `work_date` 落在哪一個 `payroll_period_id` 的區間，檢查其 `status_code` 是否為「已結算」），不需要更動呼叫端的邏輯。被擋下來時只有一種情境，訊息要指向正確出路：「這個工作日的薪資已結算，如需更正請改走補打卡流程」。

### 4.4 出勤紀錄掛在員工還是任職上

**字典已經定案，不是開放問題。** `attendance_records` 的欄位清單裡 `employee_id` 與 `employment_id` **都存在、都必填**（`attendance_correction_requests` 同樣兩欄並存，只是型態標「待核對」，見 §6）。這代表字典的答案是「兩者都要」，不是二選一：

- **`employment_id` 是出勤紀錄實際的歸屬單位。** 離職再回任會建立第二筆 `employee_employments`（[05](05-employee-onboarding.md) §7 已定案「回任是新增一筆」），兩段任職各自的出勤紀錄天然分開，不需要額外設計——`employment_id` 必填這件事本身就把「同一人兩段任職的出勤不得混在一起」鎖住了，混進第二段任職的打卡在 `employment_id` 這一欄就會直接指向錯的那一筆。
- **`employee_id` 是查詢便利欄位，不是歸屬單位。** 「我的資料／出勤紀錄」要跨這個人**目前**的任職查（一般情況下一個人只有一段有效任職，但需要用 `employee_id` 才能一次查到「這個人」而不必先知道「他現在哪一段任職」）；全體出勤列表同理，用員工編號／姓名搜尋走的是 `employee_id` 這條線，不是先查任職再查出勤。

**寫入時兩欄從哪裡來：** `employment_id` 由呼叫端在打卡當下依「操作者目前有效任職」查出（同一個 `company_users → employee_id → employee_employments` 路徑，[05] 已經建好），`employee_id` 直接複製自同一筆任職，不是兩個獨立輸入——這樣才能保證不會出現 `employee_id` 與 `employment_id` 對不上號的髒資料。

### 4.5 併發與重複打卡：鎖粒度是任職，唯一鍵已經在字典裡

字典的唯一鍵已經定案：`UNIQUE(employee_id, work_date, attendance_type_code, revoked_seq)`，有效紀錄恆為 `0`。這一條擋得住「同一個人同一個工作日同一種卡重複兩筆有效紀錄」，但擋不住兩個更細的問題：

**問題一：`work_date` 本身要靠配對邏輯決定，而配對邏輯要讀「目前有效的上班卡」——這個讀取如果不上鎖，兩個同時送出的下班打卡請求會同時讀到「還沒有下班卡」，然後都當作有效寫入。** 這與 [05] §4.3、[05](05-employee-onboarding.md) §5 職稱與職務 踩過的坑是同一個坑：MariaDB 預設 `REPEATABLE READ`，一般 `SELECT` 的一致性讀快照在**交易內第一次執行一般 `SELECT`** 的當下建立，鎖定讀（`FOR UPDATE`）不受這份快照約束。如果先做「配對用的一般查詢」再做鎖，鎖拿到之後配對邏輯讀到的仍是鎖定前那份舊快照，兩個交易一樣會同時判定「沒有衝突」而雙雙寫入成功。**`employments/job-position-histories` 與 `labor-pension/main` 都在檔頭把這件事寫成「本交易的第一句資料庫語句」，這裡援用同一個結論。**

**問題二：鎖的粒度要鎖什麼列？** 比照 [05] §4.3 與 `job-title-histories`／`department-histories` 的既有做法，鎖 `employee_employments` 那一列（`SELECT ... FOR UPDATE`，且是本交易第一句）。**不鎖 `attendance_records` 自己的某一列**：與 `job-position-histories` 檔頭說明鎖本表的理由相同——寫入前對「今天這張卡」根本沒有任何一列可鎖，`SELECT ... FOR UPDATE` 對零匹配列的行為依賴索引形狀與隔離等級，不像鎖一張保證存在的任職主檔列那樣可預期。

**本計畫定案：** 打卡（含上班卡與下班卡）交易內第一句是 `findEmploymentForUpdate(tx, companyId, employmentId)`，鎖到手之後才查「目前有效的同工作日同類型打卡」做配對與重複檢查，寫入時仍然保留 `UNIQUE(employee_id, work_date, attendance_type_code, revoked_seq)` 當最後一道保險——**鎖不完美時（例如鎖粒度以外的邊界情況）擋不住的，交給唯一鍵擋，唯一鍵擋不住的意外一律是系統錯誤，不是可以吞掉的業務分支**，這與 [05] §4.3「不完美，但把失敗模式從靜默重疊變成拿不到鎖而失敗」的一貫態度一致。撤銷不需要新的鎖：撤銷是條件式 `UPDATE`（`WHERE revoked_at IS NULL AND id = ?`），影響列數為 0 就回傳衝突（17 明講「兩位審核者同時操作時，第一筆成功後，後送操作必須被拒絕並重新載入狀態」，條件式 `UPDATE` 直接滿足這條，不需要額外上鎖）。

### 4.6 稽核：範圍與欄位等級

`docs/dev-standards-backend.md` 明列「必須寫稽核」的五類：個資異動、金額設定異動、帳號啟停用與密碼重設、角色權限指派撤銷、**審核結果變更**。出勤層要對照著判斷哪些動作落在這五類裡：

- **打卡建立、本人撤銷（`revoke`）：不落在這五類的任何一類，不寫 `audit_logs`。** 打卡不是個資異動（GPS 座標雖然加密，但字典已把它定位成「事件事實」而非個人基本資料），不是金額，不是帳號或角色。本人撤銷依 §4.3.1 是操作者對自己資料的軟刪除，性質上是自我更正，不是「審核」也不是「代人處置」。**而且 `attendance_records` 自己的 `revoked_by`／`revoked_at`／`revoke_reason` 三欄已經完整回答了「系統必須能追蹤撤銷人、撤銷時間及撤銷原因」這條 UI 要求**——這條要求是靠表欄位本身滿足的，不是靠 `audit_logs`。量的考量也還在：全公司每人每天至少兩次打卡，若連建立都寫進全域稽核表，會讓 `audit_logs` 的成長速度遠高於其他任何模組，而這些紀錄的稽核價值已經由 `attendance_records` 自身的欄位提供。
- **他人撤銷（`revoke-other`）：使用者拍板要寫 `audit_logs`（見 §4.3.1）。** 這與本人撤銷不是同一種動作：`revoke-other` 是具審核權限的人對**別人**的出勤事實做出「這筆不算數」的處置，處置對象與決定者是分離的兩個人，且已經有獨立的權限碼 `attendance.records.revoke-other` 把關——這一點與「審核結果變更」類別的共同之處，是兩者都是一個人對另一個人已成立的事實做出改變其效力的決定：補打卡的核准／退回是對「申請」做決定，`revoke-other` 是對「已生效的打卡」做決定，性質相鄰，本計畫比照「審核結果變更」處理，寫入 `audit_logs`。
- **補打卡申請的核准、退回、撤銷核准、撤銷退回：落在「審核結果變更」這一類，必須寫稽核。** 這四個動作改變的是「這個人這一天算不算有出勤」，是薪資結算的輸入，且 `attendance_correction_reviews` 本身雖然是不可變的歷程表，但比照 `employee_job_title_histories` 這類「表自己已經是歷史記錄」的先例——**歷史表不可變，不代表它可以不進 `audit_logs`**：`audit_logs` 服務的是「跨主體、按操作者與時間排序」的查詢，`attendance_correction_reviews` 服務的是「這一筆申請的完整流程」，兩者查詢面向不同，不是同一份資料的重複。

**欄位等級（比照 `employees` 政策表的判準）。以下 `attendance_records` 欄位等級專指會寫入 `audit_logs` 的動作，也就是 `revoke-other`；打卡建立與本人撤銷不寫稽核，不適用這張表：**

```
attendance_records（僅 revoke-other 動作適用）:
  clockedAt:            Value     // 打卡時刻本身，不是個資
  attendanceTypeCode:   Value
  latitude:              Presence  // 位置隱私；記進 audit_logs（不加密、append-only）等於讓稽核旁路了「誰能看座標」這條可見範圍規則
  longitude:             Presence
  address:               Presence
  revokeReason:          Value     // 撤銷原因，供未來查核，記值才有稽核意義

attendance_correction_reviews:
  actionCode:            Value
  reason:                Value     // 退回／撤銷原因，審核依據，記值
```

**`latitude`／`longitude`／`address` 為什麼仍是 `Presence` 而不是 `Value`：判準已經不是「對應 `*_encrypted` 欄位」——這三欄不再是密文欄位，這個舊判準本身已經隨 §4.2 的架構變更失效。** 維持 `Presence` 的理由改寫為：座標與地址是位置隱私，`audit_logs` 是不加密、只能新增、任何具備稽核查看權限的人都能查的全域表；把座標原始值整份記進 `Value` 級，等於在稽核這條路上開了一個後門，讓 §4.2 剛定案的「誰能看到別人座標」可見範圍規則失去意義——查得到 `audit_logs` 的人不需要 `attendance.records.view-all`／`revoke-other` 這個權限碼，就能在稽核紀錄裡看到每一筆他人座標的完整明細。因此這三欄的稽核等級維持 `Presence`（只記錄「這欄有沒有值」，不記錄值本身），這是位置隱私規則對稽核設計提出的要求，不是延用舊判準碰巧得到同樣的結論。

`attendance_settings`（公司打卡規則）落在「金額設定異動」的鄰近類別——雖然不是金額，但 `gps_required`／`allow_employee_cancellation` 這類開關直接決定出勤規則怎麼跑，比照既有對「規則設定類」一律記值的做法，`attendance_settings` 的異動整表 `Value` 級。

### 4.7 新增畫面：每日全員打卡明細（使用者本輪新提出）

**這一頁不在五份既有 UI 定案裡。** 使用者要的是一頁能看到**某一天、全公司所有員工的打卡紀錄**——原始打卡事件本身，不是出勤判定結果；有審核權限的人可以在這一頁對別人的打卡呼叫 `revoke-other`。

**與 09（全體出勤）的分工，以及為什麼不合併：**

- **09 顯示的是判定結果**：一位員工一天一列，資料主要來自 `attendance_results`（工時、遲到、早退、狀態），按年月查詢，服務的是「這個月大家出勤正不正常」這種彙總檢視。09 自己也寫明「主列表顯示出勤判定採用的上班卡與下班卡；完整事件留在明細查看」——也就是說 09 設計上刻意把「完整原始事件」推到明細層級，不塞進月度彙總列表。
- **新頁顯示的是原始事實**：某一天、全公司的 `attendance_records`，一位員工當天可能有多筆（多次進出、已撤銷的、來源各異），服務的是「今天這家公司實際發生了哪些打卡事件、有沒有異常需要處理」這種當天操作情境，且要能直接動用撤銷權限。
- **合併會讓兩種使用情境互相打架**：09 是「按月看彙總結果」的檢視型頁面，新頁是「按天看逐筆事件並可以操作」的工作台型頁面。硬塞進同一頁，要嘛判定結果表被大量原始事件列稀釋掉彙總的可讀性，要嘛操作台要多背一個月份範圍選擇而失去「當天快速掃視」的效率。兩者資料來源（`attendance_results` vs `attendance_records`）、粒度（一人一天一列 vs 一人一天多列）、操作性質（唯讀 vs 可撤銷別人）都不同，維持兩頁分開。

**端點形狀：** 依日期查全公司打卡，需要分頁，不得 N+1。`attendance/records/list-by-date`，body 帶 `{ date, pagination: { page, pageSize }, filters?: { departmentId?, employeeId? } }`（篩選比照 09 的部門＋人員），回傳當天（依查詢者所在公司 Tenant 隔離）所有 `attendance_records`（含已撤銷——審核情境需要看到「這筆本來就已經被撤銷」），一次 JOIN 帶出員工姓名／工號／部門，不得在迴圈內對每一列另外查一次員工資料（`dev-standards-backend.md` §4.5 已有的規則）；索引需以 `(company_id, work_date)` 開頭，否則全公司規模的「某一天」查詢會退化成全表掃描。

**權限碼：** 查看這一頁需要一個查看類權限碼（例如 `attendance.records.view-all`，配人事／主管角色，與 09 全體出勤的查看權限性質相同，實作時可視情況共用或另開，這是實作細節不影響本計畫的分工判斷）；頁面上的撤銷操作沿用 §4.3 已定案的 `attendance.records.revoke-other`。

**排在哪個 Stage：** 見 §5 Stage 6。後端查詢端點（`list-by-date`）本身只讀 `attendance_records`，不依賴判定引擎，可以與 `revoke-other` 同一階段（Stage 3）先做掉；但整頁前端要能操作撤銷並看到 `attendance_results` 隨之重算，必須等判定引擎（Stage 4）與 Dashboard 撤銷流程（Stage 5）都跑得通之後——這與 §6 對 Dashboard／`attendance_results` 順序的判斷是同一個道理：撤銷後重算是這一頁的核心操作，判定引擎不存在，這條驗收就無法通過。

**UI 定案已補齊。** 本計畫只定案上述分工、端點形狀與權限碼，不越權設計畫面版面、欄位排列或互動細節；畫面本身見 [23-ui-daily-attendance-records.md](../ui/23-ui-daily-attendance-records.md)（已經使用者確認）。

### 4.8 地址反查：暫停，服務商未定（使用者 2026-08-29 拍板）

**現況：座標照常存（Stage 3 已完成），`address`／`address_resolved_at` 留 `NULL`。** GPS 反查（座標 → 門牌地址）本輪暫停，服務商不選，其餘照常進行——打卡、撤銷、併發鎖、座標明文儲存與可見範圍規則（§4.2）都不受影響，唯一停下來的是「把座標換算成一段可讀地址」這一步。UI 09 與 23 都已定案「沒有 GPS 或無法取得反查地址時顯示『—』」，因此畫面上的「地點」欄一律顯示「—」，不會因為反查沒做而壞掉或顯示錯誤內容。

#### 一件目前沒有任何地方寫下來的實作細節：Geolocation 權限被拒後不會再跳提示

瀏覽器的定位權限是 per-origin 且會被記住——使用者拒絕過一次之後，之後每次呼叫 `getCurrentPosition` 都直接失敗，且瀏覽器**不會再跳出授權詢問**，除非使用者自己到瀏覽器設定裡把這個網站的定位權限改回來。因此打卡頁的錯誤處理不能只顯示「無法取得定位」這種使用者無法從畫面本身採取行動的訊息，要能引導使用者去瀏覽器設定裡把權限改回來。`attendance_settings.gps_required = false` 的存在，本來就是為了讓「拒絕過定位授權、之後也不會再被詢問」的使用者仍然打得了卡——這件事在字典與 UI 定案裡都沒有一個字提到，屬於前端實作時必須知道、但目前沒有文件記錄的細節，先記在這裡。

## 5. 分階段

roadmap 原始拆法是 2-A（設計）→2-B（settings+records）→2-C（Dashboard）→2-D（results）→2-E（全體/我的出勤）→2-F（補打卡）。**本計畫調整 2-C 與 2-D 的順序**，理由見 §6 對 roadmap 的意見；另外新增一個 roadmap 沒有列出的畫面（每日全員打卡明細，見 §4.7），插入在 2-C 之後、2-E 之前，理由同樣見 §6。以下是實際開發順序。

### Stage 1 — 殘留設計定案回寫文件

把 §4 已經定案的項目（無班表判定內容、座標欄位由密文改為明文與可見範圍規則、撤銷權限碼拆分與兩種撤銷的資料標記差異、已引用的打卡不構成撤銷限制、併發鎖粒度、稽核範圍與欄位等級、每日全員打卡明細的分工與端點形狀）回寫進 `docs/schema/03-scheduling-attendance.md` 對應章節，讓字典不再有「留待打卡功能討論」這類過期文字，也不再保留 `*_encrypted` 這個已經過期的欄位名稱與加密敘述。**輸出是文件，不是程式碼**，與 roadmap 對六塊設計定案的處理方式一致。

### Stage 2 — `attendance_settings`

最小的一張表，且不依賴任何其他新表，先做掉。公司出勤規則的 CRUD，供後續所有階段讀取 `gps_required`／`allow_employee_cancellation`。

### Stage 3 — `attendance_records`：打卡與撤銷

依 §4.5 的鎖與唯一鍵、§4.3／§4.3.1 的兩條撤銷路徑與資料標記差異、§4.3.1 的薪資結算鎖定檢查（先做出介面，固定回傳未鎖定）、§4.2 的座標明文欄位與可見範圍規則建表與五個動作：`create`（含上班卡／下班卡）、`revoke`（本人，軟刪除，不寫稽核）、`revoke-other`（他人，標記作廢並寫 `audit_logs`）、`get`（明細，依呼叫者身分決定回不回座標）、`list-by-date`（依日期查全公司打卡，分頁，供 §4.7 新頁使用）。這一階段**不含前端**，先把資料層、併發與稽核驗收做完。

**驗收**：模擬同一員工同一秒送兩次上班打卡，確認只有一筆有效紀錄成功、另一筆回衝突錯誤，不得兩筆都成功；模擬兩位審核者同時對同一筆記錄呼叫 `revoke-other`，確認只有一筆成功；確認 `revoke-other` 成功後寫入一筆 `audit_logs`，`revoke`（本人）成功後不寫；確認被待審核補打卡申請指向、或由核准補打卡建立的紀錄，一樣能正常呼叫 `revoke`／`revoke-other` 成功（不因引用關係被擋）；確認查自己的明細一定看得到座標，查別人的明細在沒有 `view-all`／`revoke-other` 權限時，回應完全不含 `latitude`／`longitude` 鍵。

### Stage 4 — `attendance_results`：無班表判定引擎

依 §4.1 的定案，實作 `computeAttendanceResult(events, schedule: null)` 與批次重算動作。**排在 Dashboard 前端之前**——這是本計畫對 roadmap 順序的調整，理由見 §6。

### Stage 5 — Dashboard 打卡與撤銷（前後端）

對應 10 的 UI 定案：今日打卡狀態、上班/下班打卡按鈕、撤銷流程。呼叫 Stage 3、4 的動作；撤銷後呼叫 Stage 4 的重算，滿足「撤銷後需重新計算對應的 `attendance_results`」這條驗收。

### Stage 6 — 每日全員打卡明細（前後端，新增畫面）

對應 §4.7：使用者本輪新提出、五份既有 UI 定案都沒有涵蓋的畫面。後端查詢端點（Stage 3 的 `list-by-date`）不依賴判定引擎，其實可以更早做；但整頁前端要能操作 `revoke-other` 並看到 `attendance_results` 隨之更新，必須等 Stage 4（判定引擎）與 Stage 5（Dashboard 的撤銷／重算流程已跑通）都完成——理由與 §6 對 Dashboard／`attendance_results` 順序的判斷相同：這一頁的撤銷驗收同樣要求「撤銷後重新計算」，判定引擎不存在，這條驗收就無法通過。畫面本身依 [23-ui-daily-attendance-records.md](../ui/23-ui-daily-attendance-records.md) 實作。

### Stage 7 — 全體出勤 ⇄ 我的出勤（前後端，可平行）

對應 09、12。兩者都是「查 `attendance_results` 拿判定結果、查 `attendance_records` 拿時間地點來源」的複合查詢，讀取邏輯高度重疊，但一個是公司範圍、一個是本人範圍，權限模型不同，因此仍是兩支端點，只是可以共用同一份 domain 組裝函式。

### Stage 8 — `attendance_correction_requests`：補打卡申請（我的資料，前後端）

對應 13。員工提交、查詢、撤回；核准後建立正式 `attendance_records`（`source_type_code`＝人工補登），呼叫 Stage 4 重算。

### Stage 9 — `attendance_correction_reviews`：補打卡簽核（前後端）

對應 17。核准、退回、撤銷核准、撤銷退回四個動作，依 §4.6 寫稽核；核准／撤銷核准要重算 `attendance_results`。

## 6. 對 roadmap 拆法的意見

roadmap 把 2-C（Dashboard）排在 2-D（`attendance_results`）之前，但 09、10 兩份 UI 定案都明講撤銷之後要「重新計算 `attendance_results`」——**如果照原順序做，Stage 2-C 驗收的那一刻，判定引擎根本還不存在，「重新計算」這條驗收標準無法通過**。這不是可以先擱置、之後再補的細節：Dashboard 的「今日工時」顯示雖然可以現算（上下班卡時間差，不需要判定引擎），但撤銷流程明確要求聯動出勤判定，兩者被同一個 UI 文件綁在一起。

本計畫把 `attendance_results` 的無班表判定引擎（Stage 4）移到 Dashboard 前端（Stage 5）之前，資料層與前端頁面因此變成 3→4→5 而不是 3→5→4。這不是否定 roadmap 的整體判斷（roadmap 把「打卡 Schema」列為整層最重要的定案是對的），只是 2-C／2-D 這兩塊在驗收標準上有互相依賴，原始順序在文字上沒有寫出這個依賴。

**§4.7 新增的「每日全員打卡明細」踩到同一個坑，所以排在同一個位置之後。** 這一頁是使用者本輪才提出的，roadmap 自然沒有排過它，但它的驗收標準（撤銷後重新計算 `attendance_results`）與 Dashboard 一模一樣——只是撤銷的對象從「自己」換成「別人」。如果把這一頁的前端排在判定引擎完成之前，會複製一次 Dashboard 已經踩過的錯：驗收要求的「重算」在那個時間點根本無法通過。本計畫因此把它的前端排在 Stage 6，緊接在 Stage 5（Dashboard）之後、Stage 7（全體出勤／我的出勤）之前；後端查詢端點因為不涉及判定引擎，仍然可以提前併入 Stage 3（與 `revoke-other` 同一階段）先做。

## 7. 已定案的決策

以下三項是使用者已經拍板的既有定案，本計畫據此展開為具體作法：

- **GPS 座標明文儲存，交由資料庫端靜態加密負責，不再有應用層加密與 blind index。** 這是 `docs/dev-standards-backend.md` §5.1 全站架構變更（應用層 `*_encrypted` 欄位加密全面移除，改由資料庫端靜態加密負責）在出勤層的落地：字典的 `latitude_encrypted`／`longitude_encrypted`／`address_encrypted` 三欄本次改名為明文欄位 `latitude`／`longitude`／`address`；原本 §4.2 討論的「建不建 blind index」隨應用層加密一併消失，不再是需要選擇的問題。列表不輸出經緯度、明細輸出經緯度的輸出範圍不變；**座標的遮罩規則本輪由使用者裁示為選項 B**：明細不做精度遮罩，改為依呼叫者身分決定回不回座標（看自己的能看、看別人的需要 `attendance.records.view-all`／`revoke-other` 這一層權限碼），細節見 §4.2。
- **打卡撤銷要檢查是否有審核權限。** 本計畫在 §4.3 定案為兩條端點：`attendance/records/revoke`（本人，權限碼配一般員工角色）與 `attendance/records/revoke-other`（他人，權限碼配人事／主管角色）；`revoke-other` 的消費端是 §4.7 新增的「每日全員打卡明細」畫面。
- **本人撤銷是軟刪除且不寫稽核，他人撤銷標記作廢且要寫 `audit_logs`。** 本計畫在 §4.3.1 定案這條差異的資料處理細節，並建議「沿用 `revoked_*` 既有欄位、不另加 `deleted_at`／`deleted_seq`」（選項 A，理由與選項 B 的取捨見 §4.3.1）。**使用者 2026-08-29 已確認選項 A。**
- **已引用的打卡不構成撤銷限制，唯一限制仍是薪資結算鎖定。** 使用者本輪定案：待審核補打卡申請指向、或本身由核准補打卡建立的打卡，都可以正常走 `revoke`／`revoke-other`；字典既有的「已鎖定日期不得由員工直接撤銷」就是全部答案，不需要為引用關係另外加限制。這條鎖定檢查目前查不到真正資料（薪資結算模組尚未實作），只能先做成固定放行的樁，細節見 §4.3.1。

其餘項目是本計畫新定案（§4.1、§4.4、§4.5、§4.6、§4.7）：無班表時 `attendance_results` 寫入 `NO_SCHEDULE` 狀態而非冒用「正常」；出勤紀錄同時掛 `employee_id`（查詢用）與 `employment_id`（歸屬用），字典已定案，兩者關係在此說明；打卡併發鎖粒度為任職、`FOR UPDATE` 必須是交易第一句；稽核範圍排除打卡建立與本人撤銷、涵蓋他人撤銷與補打卡審核四動作；新增「每日全員打卡明細」畫面的分工、端點形狀、權限碼與所在 Stage。

## 9. 附註：資料字典已定案 vs 本計畫新定案的分界

- **字典已定案，本計畫照抄**：`attendance_records` 全部欄位（含打卡欄位定案節，本次已改為明文欄位，見 §4.2）、`attendance_settings` 全部欄位、`attendance_results` 全部欄位、`work_date` 由配對決定的規則、`revoked_seq` 的唯一鍵形狀、`employee_id`／`employment_id` 並存、「已鎖定日期不得由員工直接撤銷」（§4.3.1 確認這一條就是撤銷限制的全部答案，不需要為引用關係另外加限制）。
- **字典標「型態待恢復」／「待核對」，比照既有慣例補上、不是新設計問題**：`attendance_correction_requests` 的 `id`／`employee_id`／`employment_id`／`reason`／`status_code`，`attendance_correction_requests.reason`。這些欄位的性質（uuid 主鍵、必填外鍵）與 `attendance_records` 逐字一致，本計畫在 Stage 8 建表時直接套用同一套型別，不視為需要使用者拍板的開放問題。
- **字典完全沒有答案，本計畫新定案**：§4.1（無班表判定內容）、§4.2 座標的型別選擇與「依身分決定回不回座標」的實作形狀、§4.3 的撤銷權限碼拆分、§4.3.1 撤銷來源的資料標記建議、§4.5 的鎖粒度、§4.6 的稽核範圍與欄位等級、§4.7 每日全員打卡明細的分工與端點形狀。
- **本輪由使用者裁示、原列為留待裁示的兩項已經解決**：§4.2 座標的遮罩規則（選擇選項 B：不做精度遮罩，依身分決定可見範圍）；§4.3.1 已被補打卡申請引用、或已進入簽核流程的打卡能不能再撤銷（定案為「不構成限制」，唯一限制仍是既有的薪資結算鎖定）。

## 10. UI 定案彼此的落差

- **09（全體出勤）的「本輪明確延後」節已經過期。** 該節仍寫著「打卡 GPS 的實際保存欄位……等討論打卡功能時再逐欄確認」「不因本頁需要顯示地址，就自行把未確認欄位補入 `attendance_records`」，但 `docs/schema/03` 已經在「已確認的『全體出勤』UI」段落註明「打卡 GPS 的實際保存欄位已於後續定案」。03 的引用是對的，09 原文這一節沒有跟著更新，兩份文件字面上互相矛盾——本計畫依 03（較新）為準，但建議之後有人一併把 09 這一節的措辭改掉，否則下一個只讀 09 的人會誤以為 GPS 欄位還沒定案。這一節第 71 行「是否顯示地圖、原始經緯度及定位精準度，亦留待打卡與出勤明細畫面討論」現在已經有了答案——§4.2 已定案明細輸出座標、可見範圍規則也已選定選項 B，但地圖本身仍不在本計畫範圍，09 第 71 行只剩地圖這一半算過期。
- **12（我的出勤）明細查看寫「補卡／更正入口尚未定案」，但 13（補打卡申請）已經是獨立的導覽項目、且已定案。** 這不是真的矛盾——12 講的是「從出勤明細彈窗直接跳轉去補卡」這個捷徑尚未定案，不是「補打卡這個功能」尚未定案——但字面上容易讓人誤讀成兩份文件衝突，本計畫 Stage 7／8 依「12 只查看、13 是獨立入口」的字面分工實作，不做明細跳轉。
