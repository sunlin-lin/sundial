# 實作計畫：班別設定

> Schema 依據：[docs/schema/03-scheduling-attendance.md](../schema/03-scheduling-attendance.md)
> UI 依據：[docs/ui/22-ui-shift-settings.md](../ui/22-ui-shift-settings.md)（已定案）
> 開發規範依據：[dev-standards-backend.md](../dev-standards-backend.md)、[dev-standards-frontend.md](../dev-standards-frontend.md)

## 1. 交付什麼

**班別定義「一天怎麼上班」——幾點到幾點、休息幾段、有薪還無薪、跨不跨日、應工作幾分鐘。**

三張表：

| 表 | 責任 |
|---|---|
| `shift_definitions` | 班別主檔 |
| `shift_work_periods` | 工作時段（一天可多段） |
| `shift_breaks` | 休息時段（可多段，分有薪無薪） |

涵蓋 UI 定案列出的班別形狀：一般班、跨日班、分段班、中空班、多段有薪／無薪休息。

## 2. 為什麼這一塊做得起來，而排班做不起來

**班別只依賴 `companies`，而它已經存在。** 它回答「一天怎麼上班」，與「誰上這個班」完全無關。

排班那一層不行：`employee_schedule_assignments` 與 `employee_schedules` 都需要 `employment_id → employee_employments`，而**那張表還不存在**（目前資料庫 14 張表裡沒有任職表）。

**不得改成綁 `employee_id` 繞過去。** 字典的定案是「離職回任建立新的 `employee_employments`」，而班表綁任職是有意義的：同一個人第二次任職的班表跟第一次是兩回事。綁員工的話，回任那天所有歷史班表會跟新任職混在一起——而那個錯誤要等到有人回任才會出現。

**另一個排班做不起來的理由**：`schedule_rules` 與 `schedule_rule_details` 的**正式欄位從來沒有被寫下來**。`docs/schema/03` 那個標題底下的欄位其實是**指派表**的（`employment_id`／`schedule_rule_id`／`cycle_anchor_date`），而 `employee_schedule_assignments` 標題底下的欄位是**打卡設定**的（`gps_enabled` 那一組）。兩張表標錯了，排班規則只剩一段文字描述。

## 3. 明確不在本計畫內

| 項目 | 為什麼 |
|---|---|
| 排班規則、規則指派、排班期間、每日班表、班表異動 | 見 §2 |
| 班組（A／B／C／D 班） | 字典明列「已確認納入但仍需獨立設計」，且不得塞進班別主檔 |
| 換班、代班、公司停班、待命／備勤 | 同上 |
| **彈性上班區間與核心工時** | 同上，**但這一項兩份文件對不上**，見 §4.3 |
| 出勤判定 | 另一個模組 |

## 4. 三個必須先決定的事

### 4.1 `is_overnight` 與 `required_work_minutes` 是**推導值**，不得由呼叫端送進來

這兩欄都可以從工作時段與休息時段算出來：

- `is_overnight` ＝ 任一工作時段的 `end_day_offset > 0`
- `required_work_minutes` ＝ 各工作時段的 `work_minutes` 總和 － 無薪休息的 `break_minutes` 總和

**它們同時也是資料表上的欄位**，於是有兩份真相。UI 定案已經寫明應工作分鐘是「系統計算的」，但沒有講 `is_overnight`。

**定案：兩者一律由 service 在寫入時計算，request schema 裡根本沒有這兩個欄位。**

不是「收進來再驗算」而是「不收」——收了就得處理「送進來的值跟算出來的不一樣」這種情況，而任何處置（以哪一邊為準）都要有人決定一次；不收就沒有這個問題。

**為什麼要存而不是每次現算**：`attendance_results.scheduled_minutes` 會引用它，而字典的核心原則是「規則改版不得覆蓋歷史」。存下來的是那一版班別當時的應工作分鐘；現算的話，日後改了計算方式（例如有薪休息的認定），所有歷史出勤判定的分母會跟著變。

**不一致的後果具體長這樣**：`is_overnight=false` 但某個時段 `end_day_offset=1`。班別列表上顯示「非跨日」，出勤判定卻按跨日處理——兩邊都不會報錯，而症狀是某些人的工時永遠算錯八小時。

### 4.2 `shift_breaks` 缺一個 `end_day_offset`，跨日班的休息無法表達

`shift_work_periods` 有 `end_day_offset`（跨日班用 1），**但 `shift_breaks` 沒有**。

具體情境：22:00–06:00 的夜班，休息 02:00–03:00。`start_time` 存 `02:00`——**這個 02:00 是班次開始前二十小時，還是開始後四小時？** 從欄位上分不出來。

字典明列跨日班與多段休息都在範圍內，所以這不是「用不到」，是**欄位不足**。

**定案：`shift_breaks` 增補 `start_day_offset` 與 `end_day_offset` 兩欄**（比照 `shift_work_periods` 的作法）。這是本計畫對資料字典的唯一增補，理由如上。

> 為什麼不用「休息一定落在某個工作時段內，所以可以推導」來省掉它：中空班的兩段工作之間本來就有空檔，而那個空檔可能跨過午夜。推導要靠一串條件判斷，而條件判斷寫錯不會報錯。

### 4.3 「彈性及核心工時」兩份文件對不上，需要你裁決

- **資料字典**把「彈性上班區間、核心工時及彈性下班計算」列在「**已確認納入但仍需獨立設計正式 Schema 及流程**」，並明講「上述功能**不能直接塞入 `shift_definitions`**」。
- **UI 定案**卻把「彈性及核心工時設定」寫進班別的新增／修改畫面。

`shift_definitions` 目前只有一個 `is_flexible` 布林，**沒有任何欄位存得下彈性區間與核心工時**。

三條路：

| | 作法 | 代價 |
|---|---|---|
| 甲 | 本輪只做 `is_flexible` 旗標，區間與核心工時另立 | UI 定案的那一段畫面這輪做不出來 |
| 乙 | 現在就把彈性欄位加進 `shift_definitions` | 違反字典明文的「不能直接塞入」 |
| 丙 | 現在設計獨立的彈性設定表 | 字典說「仍需獨立設計」，等於本輪要多做一次設計定案 |

**建議甲。** 字典那句「不能直接塞入」是明文定案，而 UI 文件沒有推翻它——UI 描述的是**畫面上要有這一區**，不是**欄位要放在主檔**。甲把畫面那一段延後，代價最小且不製造要回頭拆的東西。

## 5. 資料表

### 5.1 `shift_definitions`

依字典逐欄，外加軟刪除的配套：

- `UNIQUE(company_id, code, deleted_seq)` — 本表有 `deleted_at` 軟刪除，而 MariaDB 的 UNIQUE 索引中 NULL 互不相等，單純的二欄唯一鍵配上軟刪除會讓「未刪除的資料」失去唯一性（比照 `employees` 的既有作法）。
- `UNIQUE(company_id, id)` — 供 `employee_schedules` 日後建複合外鍵 `(company_id, shift_definition_id)` 指向，理由與 `roles`／`employees` 相同：單欄外鍵會讓 A 公司的班表指向 B 公司的班別，而資料庫完全接受。
- 進 `CompanyScopedTable`。

**`work_type_code` 的代碼值字典沒有定。** 本計畫定為：`1 一般`、`2 輪班`、`3 彈性`、`4 責任制`。理由：這一欄要回答的是「這個班的**工時管理方式**」，而 UI 定案列的「跨日班／分段班／中空班」不是型態而是**形狀**——那些已經由 `end_day_offset` 與時段筆數表達了，做成代碼會是第二份真相（§4.1 同一個問題）。待命班與備勤班不列入，字典明列它們仍需獨立設計。

### 5.2 `shift_work_periods` 與 `shift_breaks`

依字典逐欄，`shift_breaks` 增補兩欄（§4.2）。

**兩張子表都不進 `CompanyScopedTable`**：它們沒有 `company_id`，公司範圍由 `shift_definition_id` 間接決定。存取一律經由主檔的 service，不單獨開端點。

**約束**：

- `UNIQUE(shift_definition_id, sequence_no)`
- 工作時段**不得重疊**（中空班的**空檔**合法，重疊不合法——兩者的差別是有沒有交集）
- 休息時段必須落在某一段工作時段內
- `work_minutes` 與 `break_minutes` 必須等於起訖時間之差（含日偏移）——**由 service 計算，不由呼叫端送**，理由同 §4.1

### 5.3 Migration

```
0017_create_shift_definitions.sql
0018_create_shift_work_periods.sql
0019_create_shift_breaks.sql
0020_seed_permission_codes_shifts.sql
```

權限碼與端點同一批進（這條判準見 [01](01-regulatory-dataset-versioning.md) §3.5 的修訂）。

`modules/shifts/main/`（次目錄名為 `main`：這個子實體就是這個領域本身，§0.2）。

| 端點 | 說明 |

## 7. 「班別被引用後不得覆蓋歷史」這條規則，本輪**不實作**

字典明文：

> 班別被排班引用後，時間、休息及應工作分鐘不得直接覆蓋歷史；現階段採停用舊班別並複製建立新班別，未確認前不自行增加班別版本表。

**本輪不實作那道防護，理由是它現在不可能失敗。** 沒有任何表引用 `shift_definitions`（排班那幾張不存在），所以「這個班別被引用了嗎」這個查詢的答案恆為否。

寫一個永遠回 `false` 的檢查，比不寫更糟：它看起來守著一條規則，實際上一次都擋不到東西，而下一個人會**假設它有效**。這與通用規範 §7.1「永遠是綠的規則比沒有規則更糟」是同一件事。

**因此本輪班別可以自由修改**，這是安全的、也是事實。

**但這是一筆必須被接住的欠帳**：排班模組動工的第一件事就是補上這道防護，否則排班上線那天，改一個班別會靜靜改掉所有歷史班表的應工作分鐘。**要寫進排班的計畫，不是只寫在這裡。**

`/shifts/main/copy` 這一輪就做——它是「停用舊的、複製新的」那個流程的工具，而流程本身不需要防護就能用。

## 8. 前端

UI 定案（`docs/ui/22`）已經給了規格，所以前端這次有依據可循（與法規模組不同）。

`pages/shifts/main/`，URL `/shifts/main`，選單放「人事作業 → 班別設定」。

**列表欄位**（依 UI 定案）：班別代碼、名稱、工作類型、工作時段、休息時段、應工作時數、跨日、彈性、狀態、使用狀況、操作。每頁 20 筆，預設顯示啟用班別。

**「使用狀況」這一欄本輪顯示不出真值**（理由同 §7：沒有東西引用它）。處置：**這一欄本輪不放**，等排班上線再加。放一個恆為「未使用」的欄位，等於在畫面上宣告一件目前為真、日後會悄悄變假的事。

**時間顯示**：走 `shared/format/`（§9.2），不自己 `new Date(`。工作時段與休息時段在列表上是多段的，呈現方式由 `.view.ts` 的純函式決定，不寫在模板裡。
