### 1.2 需要調整的兩處

**一、`/employees/main/create` 要移除。**

## 2. 動工前必須先做設計定案的六塊

**這一節是本文存在的理由。** 這六塊不是「還沒開發」，是**還沒設計**——直接派工開發，做出來的東西一定要重做。

### ① 打卡：`attendance_records` 沒有打卡時間

字典裡那張表的全部欄位：

```
id / employee_id / employment_id / employee_schedule_id
work_date / attendance_type_code / source_type_code / source_id
```

**沒有打卡時間、沒有經緯度、沒有反查地址、沒有撤銷欄位。**

而三份 UI 定案要顯示「上班 08:57、上班地點 ○○」，另一份要求「必須能追蹤撤銷人、撤銷時間及撤銷原因」。四份文件用同一句話帶過：

> 打卡 GPS 的實際保存欄位留待打卡功能討論，**本輪不得補猜**。

**影響範圍最大的一塊**：全體出勤（09）、Dashboard 打卡（10）、我的出勤（12）、補打卡（13）、補打卡簽核（17）全部卡住；而出勤判定是加班、請假、薪資結算的輸入。

**要定案什麼**：打卡時間欄位、GPS 三欄（經緯度、精準度、反查地址）與其可選性、撤銷四欄（撤銷人／時間／原因／有效狀態）、跨日班的 `work_date` 歸屬規則。

### ② 排班規則：兩張表只有名字，而且文件標題錯置

`docs/schema/03` 的 `### schedule_rules / schedule_rule_details` 標題底下，逐欄表格的內容其實是**指派關係**（`employment_id`／`schedule_rule_id`／`cycle_anchor_date`）；而 `### employee_schedule_assignments` 標題底下的欄位是 **`attendance_settings` 的完整複本**。

也就是說：**排班規則主表與明細表的正式欄位從來沒有被寫下來**，指派表的欄位則被放在錯的標題底下。

（兩支獨立閱讀的 agent 得出同樣結論，不是誤讀。）

**要定案什麼**：兩張表的逐欄定義、指派表的正式表名與欄位、以及「做二休二用四日週期表達、不綁星期」怎麼落到 schema 上。

### ③ 薪資三張表被定義了兩次，互斥

`payrolls`、`payroll_periods`、`payroll_details` 在兩份文件各有一版完整定義：

|                   | `02-employee-payroll-cost.md`                                  | `02-payroll-calculation-settlement.md`                                                               |
| ----------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `payrolls`        | `status_code`、`gross/deduction/net_amount`、五個 `*_snapshot` | `payroll_version_id`、`calculation_status_code`、`employer_cost_amount`、`company_total_cost_amount` |
| `payroll_details` | 基本明細                                                       | ＋`temporary_item_batch_id`、`calculated_amount`、`is_overridden`、撤銷欄位                          |

**兩版互不相容，而兩份文件都沒說最終版本是哪一個。** 後者標成「既有表調整」，但沒有說明如何收斂。

**連帶**：`02-payroll-calculation-settlement.md` **不在 `docs/schema/README.md` 的索引裡**——它是唯一一份沒被官方索引收錄的 schema 文件。

### ④ 薪資結算的 UI 定案完全不指名資料表

`docs/ui/payroll-calculation-settlement.md` 是 22 份 UI 文件裡**唯一一份全文不出現任何表名**的。它描述了試算版本、臨時項目批次、結算鎖定、撤銷結算——都是很具體的行為，但沒有任何 schema 對應是由它自己指定的。

**兩個具體缺口**（UI 描述了，schema 沒有位置放）：

- **警告／異常的原因**：`payrolls.calculation_status_code` 只有代碼（正常／警告／異常），**沒有任何欄位或子表保存原因文字**。而畫面要顯示「為什麼這個人是異常」。
- **雇主負擔的逐項明細**：`payroll_details.type_code` 只有 `1 應發`／`2 扣款`，**沒有雇主負擔這一類**。雇主負擔目前只以彙總數字存在，各類保險與勞退分別多少錢**沒有地方放**。`personnel_costs` 是候選但關聯從未被建立。

### ⑤ 班別的六項功能明列「需獨立設計」

字典與 UI 定案兩份文件說法一致，六項都不能塞進 `shift_definitions`：

彈性上班區間／核心工時／彈性下班計算 · 班組（主檔、成員有效期間、主管、規則指派、週期定位） · 換班申請流程 · 代班申請流程 · 公司停班事件 · 待命／備勤

其中 **`schedule_changes` 只承接「已發布班表異動」的歷史，不是換班申請流程本身**——申請、雙方確認、主管審核、雙班表原子異動這四件事沒有表。

### ⑥ 部門的六項待定

刪除規則（有子部門或有成員時怎麼辦） · 停用後既有員工與未來指派的處理 · 部門主管（尚未納入畫面與 schema） · 主管任期與歷史 · 部門排序欄位 · 拖拉調整階層

**部門是建立員工的第一個前置**，所以這六項要在 [05](05-employee-onboarding.md) Stage 1 之前決定——但多數可以定成「本輪不做」，見 §4。

## 3. 開發順序

### 原則

1. **先解鎖，再展開。** 一張表擋住四個模組時，它排在四個模組任何一個之前。
2. **設計定案與開發分開排。** §2 那六塊各自是一次「定案」工作，產出是回寫 schema 文件，不是程式碼。
3. **稽核要走在被稽核的功能前面。** 稽核紀錄只能在事情發生的當下寫，事後補不回來。
4. **同一層內可平行。** 標 ⇄ 的可以同時派工。

---

### 第 0 層：基礎設施（沒有業務依賴，隨時可插）

|         | 內容                                               | 為什麼                                                                                                                  |
| ------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **0-A** | `.dependency-cruiser.cjs` ＋ eslint／prettier 設定 | **`bun run ci` 現在第一步就過不去**，而 18 條分層規則掛在一個不存在的設定檔上——它們是寫在文件上的約定，沒有任何東西在擋 |
| **0-B** | §9.2 兩支掃描（帶時區字串不得上畫面）              | 前端頁面愈多，補的成本愈高                                                                                              |
| **0-C** | 三支端點的 response 契約補 401／403                | `permissions.main.tree`、`company-users.roles.*`                                                                        |

**0-A 愈晚做愈貴**：現在六個模組的規則都還被遵守著，補上去就是全綠；再堆兩個模組才補，會一次冒出一堆違規，而那時要判斷「這是真違規還是規則訂太嚴」困難得多。

### 第 1 層：解鎖建立員工

```
1-A  部門六項待定 → 定案（設計）        ⇄  1-B  稽核 Stage 2（開發）
       ↓                                       ↓
1-C  departments 表 ＋ 模組 ＋ 組織架構頁（開發）
       ↓
1-D  employee_employments ＋ 部門歷史 ＋ 扣繳設定（開發）
       ↓
1-E  交易編排 ＋ onboarding ＋ 移除舊 create（開發）
       ↓
1-F  job_titles ／ job_positions ＋ 兩張歷史表（開發）
       ↓
1-G  員工清單／新增／修改／離職（前後端）
       ↓
1-H  眷屬 ＋ 勞退自願提繳率（開發）
```

**1-A 的建議定案**（多數可以定成「本輪不做」）：

| 項目                   | 建議                                             |
| ---------------------- | ------------------------------------------------ |
| 有子部門或有成員時刪除 | **禁止刪除**，先移轉。最簡單且不會錯             |
| 停用後既有員工         | 停用只影響「能不能被選為新的部門」，不動既有歷史 |
| 部門主管               | **本輪不做**（字典與 UI 都沒有欄位）             |
| 主管任期與歷史         | 同上                                             |
| 部門排序               | **本輪不做**，樹狀顯示按名稱排                   |
| 拖拉調整階層           | **本輪不做**，用「修改上層部門」達成             |

**驗收（1-E）**：故意讓角色指派失敗，確認員工、任職、部門、帳號、扣繳**全部沒有留下**。

### 第 2 層：打卡與出勤（最大的一塊）

```
2-A  打卡 Schema 定案（設計）★ §2①
       ↓
2-B  attendance_settings ＋ attendance_records（開發）
       ↓
2-C  Dashboard 打卡與撤銷（前後端）
       ↓
2-D  attendance_results ＋ 出勤判定計算（開發）
       ↓
2-E  全體出勤 ⇄ 我的出勤（前後端）
       ↓
2-F  補打卡申請 ＋ 補打卡簽核（前後端）
```

**2-A 是整個專案最重要的一次設計定案。** 它擋住五個畫面，而出勤判定是加班、請假、薪資的共同輸入。

**2-D 有一個隱含前置**：出勤判定要比對班表，所以需要 `employee_schedules`——但那在第 3 層。

> **處置**：2-D 先做「沒有班表時的判定」（只看打卡本身），排班上線後再補「對照班表」的部分。**這一段要明確標記**，否則會做出一個看起來完整、實際上算不出遲到早退的判定。

### 第 3 層：排班

```
3-A  排班規則兩張表定案（設計）★ §2②
       ↓
3-B  schedule_rules ＋ schedule_rule_details ＋ 指派表（開發）
       ↓
3-C  schedule_periods ＋ employee_schedules（開發）
       ↓

       ↓
3-F  回頭補 2-D 的「對照班表」判定
```

**3-E 是必須被接住的欠帳**：班別設定那一輪刻意沒做這道防護（沒有東西引用 `shift_definitions`，寫一個永遠回 `false` 的檢查比不寫更糟）。**排班上線那天，改一個班別會靜靜改掉所有歷史班表的應工作分鐘。**

### 第 4 層：加班與請假（可平行）

```
4-A  加班：overtime_requests ＋ approvals ＋ compensations
     ＋ 我的加班申請 ＋ 加班簽核（前後端）
        ⇄

        ⇄
4-C  補休：compensatory_leave_credits ＋ rate_snapshots
     ＋ transactions ＋ allocations
        ↓

```

**4-B 的表定義最完整**（`docs/ui/14` 是唯一一份零待定的 UI 文件），但 **`leave_request_details`、`leave_request_allocations` 有多欄「未明定」**，動工前要補。

**4-C 的 `compensatory_leave_credits` 全部五欄都標「型態待恢復」，`compensatory_leave_allocations` 只有名字。** 這一塊等同 §2 的第七項，只是規模小。

**加班與補休的耦合**：加班核准時二選一（加班費或補休），選補休就要建立補休額度。所以 4-A 與 4-C 實際上要一起做。

## 4.1 已知的技術債（開發過程中撞到的，不擋任何一層）

|                                                       | 內容                                                                                                                                                    | 何時處理                                             |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **`ElOption` 與 `exactOptionalPropertyTypes` 不相容** | Element Plus 2.14.5 的型別宣告缺陷，`value`／`label` 一律報錯，連靜態字面值也是。**兩頁都撞到了**（法規同步、班別設定），兩頁都改用 `ElRadioGroup` 繞過 | 升級 Element Plus 時一併處理。**不要每一頁各自繞**   |
| **「分鐘 → 小時」有兩份實作**                         | 班別頁自己實作了一份（不經 `Number()`），但 §9.2 要求格式化統一在 `shared/format/`                                                                      | 下一次動 `shared/format/` 時搬過去                   |
| **seed 的清理清單曾是第二份副本**                     | `seed-dev.ts` 硬編「要清哪些表」，與 `CompanyScopedTable` 漂移，加 `shift_definitions` 之後 seed 直接壞掉且隔了好幾輪才被發現                           | **已修**：改成由型別釘住的執行期陣列，漏加會編譯不過 |

**第三項的教訓值得留著**：任何「某個事實的第二份清單」都會漂移，而漂移多半沒有症狀——這一次剛好是外鍵擋住才炸出來的，若那張表沒有外鍵，seed 會安靜地留下孤兒資料。

## 5. 這份順序最容易被打破的地方

**一、有人先做薪資。** 它是最有價值的功能，也是依賴最深的：它要出勤結果、核准加班、核准請假、法規資料、員工薪資設定五樣東西。跳過去做只會做出一個永遠在等輸入的殼。

**二、有人先做排班而跳過打卡。** 兩者看起來獨立，實際上出勤判定同時需要班表與打卡，而打卡的 schema 沒定案。先做排班會得到一個「排得出來但驗證不了」的模組。

**三、稽核被往後推。** 每往後推一階段，就有一批異動永久沒有紀錄。這是唯一一種**事後補不回來**的欠帳。

**四、`ci` 一直是紅的。** 現在第一步就過不去（缺 eslint 設定），於是所有人習慣不看它。等真的有東西壞掉時，紅燈已經沒有訊號價值。
