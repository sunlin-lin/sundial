# 實作計畫：法規資料的前端（唯讀）

> 後端依據：[01-regulatory-dataset-versioning.md](01-regulatory-dataset-versioning.md)
> 開發規範依據：[dev-standards-frontend.md](../dev-standards-frontend.md)（§ 編號皆指這份，標明「後端規範」者除外）

## 1. 交付什麼

**把已經同步進系統的政府法規資料呈現出來，供人查看與核對。唯讀，不提供任何修改。**

三件事：

| 要回答的問題 | 頁面 |
|---|---|
| 現在系統裡有哪些法規資料、是哪一版、最後同步是什麼時候 | 資料集總覽 |
| 某一份法規的歷史版本有哪些、某一版的內容長什麼樣 | 資料集內容 |
| 同步有沒有在跑、失敗過幾次、為什麼失敗 | 同步歷程 |

第三個看起來像維運資訊，但它是**人資會問的問題**：「這個月的健保級距對嗎」的答案是「最後一次同步是哪天、成功還是失敗」。同步歷程不是給工程師看的，是給發現薪資算錯的人看的第一站。

## 2. 邊界：唯讀，而且是刻意的

**不提供修改、不提供觸發同步。**

- 同步的觸發由排程負責（[01](01-regulatory-dataset-versioning.md) §7.3）。人工觸發端點依決策 D3 不開放——觸發全平台同步不該由某一家公司的管理者做，而平台管理員這個角色還不存在。
- 補充保險費率（`dataset_code=10`）是唯一人工維護的資料集，它的調整介面同樣屬於平台管理，見 [01](01-regulatory-dataset-versioning.md) §3.1.1。**本計畫不做那個介面**，但總覽要能讓人看出「這一項是人工維護的」——否則它看起來會像一個很久沒同步的資料集。

---

## 2.1 這兩頁不分公司（已定案）

**畫面上沒有公司篩選，也不會因為登入者屬於哪一家公司而看到不同的內容。**

這與後端一致，不是前端自己的簡化：`regulatory_dataset_versions`、`regulatory_records`、`regulatory_sync_logs` **三張表都沒有 `company_id`，都不在 `CompanyScopedTable` 裡**（[01](01-regulatory-dataset-versioning.md) §3.2 (b)）。政府法規是全國一份，勞保投保薪資分級表不會因為公司不同而不同。

**但仍然要登入、仍然走權限碼。** 兩件事要分開：

| | 分不分公司 |
|---|---|
| **資料** | 不分。所有公司看到同一份 |
| **存取** | 分。透過公司成員的角色授權（`regulatory.datasets.*`） |

不做成公開端點的理由：權限碼本來就掛在公司成員身上，而「誰能看系統設定」是各公司自己決定的事。資料不敏感不等於入口要敞開。

**日後不得加公司篩選。** 這一句要留著——看到列表就想加一個公司下拉是很自然的反射，而加下去之後那個篩選條件會一路傳到後端，逼出一個「法規資料要不要分公司」的假問題。公司的選擇（用哪一個職災行業別）在 `company_regulatory_settings`，那是另一張表、另一個畫面。

## 3. 動工前：後端缺一支端點

**目前的四支端點答不出總覽那一頁。**

| 現有端點 | 回答的問題 |
|---|---|
| `/regulatory/datasets/list` | 某**一個**資料集的版本清單 |
| `/regulatory/datasets/get` | 某**一個**版本的 metadata |
| `/regulatory/datasets/resolve` | 某**一個**資料集在某一天適用的版本與內容 |
| `/regulatory/sync/list` | 同步歷程 |

**全部都要先知道 `datasetCode`。** 總覽那一頁要的是「九個資料集各自現在是哪一版」，用現有端點只能打九次 `resolve`——九個請求、九份錯誤要各自處理、而且每一次都會把整份 records 拉回來（勞保那一份就有 97 筆），只為了顯示一行摘要。

**需要新增：`POST /regulatory/datasets/overview`**

- 輸入：基準日（必填，理由同 §4.2——不預設今天）
- 輸出：每個資料集一列，含資料集代碼與名稱、維護方式（自動／人工）、該基準日適用的版本代碼與生效日、筆數、最近一次同步的時間與狀態
- **不回 records**：總覽只要摘要，內容走 `resolve`
- 權限碼 `regulatory.datasets.overview`，要 seed

**這是本計畫的前置**，排在前端任何一行程式碼之前。

## 4. 頁面

依 §0.2「一律兩層，`<段>` 就是 URL 路徑段」：

```
pages/regulatory/datasets/     /regulatory/datasets      總覽 ＋ 單一資料集內容
pages/regulatory/sync/         /regulatory/sync          同步歷程
```

兩段直接對上後端的大目錄與次目錄，不需要另外記一套對照。

### 4.1 `regulatory/datasets`

**總覽**（進頁面的預設狀態）：一列一個資料集。

| 欄 | 來源 | 備註 |
|---|---|---|
| 資料集 | `overview` | 名稱 |
| 維護方式 | `overview` | 自動同步／人工維護 |
| 適用版本 | `overview` | 版本代碼 |
| 生效日 | `overview` | 見 §5.1 |
| 筆數 | `overview` | |
| 最後同步 | `overview` | 時間 ＋ 狀態；人工維護的資料集顯示「不適用」而不是空白 |

**「不適用」不能用空白表達。** 空白會被讀成「同步壞了」或「還沒跑過」，而補充保險費率是**永遠不會有同步紀錄**的——那是規格，不是故障。

**單一資料集**：選一列展開，顯示該資料集的版本清單（`list`，分頁），再選一版顯示內容（`resolve` 或 `get`）。

內容區的欄位**每個資料集都不一樣**（分級表是級距、費率表是行業別與費率、補充保費是三個門檻值）。處理方式見 §5.3。

### 4.2 基準日是必填的查詢條件，不是隱含的今天

總覽與內容都以**法規適用基準日**為準，這一頁必須有一個明確的日期選擇器，**預設今天但要顯示出來**。

後端的 `resolve` 端點就是這樣設計的（[01](01-regulatory-dataset-versioning.md) §4.2）：`asOfDate` 必填、不預設今天。理由在前端這一側同樣成立——薪資結算要補算去年 12 月時，人會來這一頁核對「當時的費率是多少」。若畫面上沒有基準日這個概念，他看到的永遠是今天適用的那一版，而那一版跟他要核對的期間**看起來完全一樣合理**。

### 4.3 `regulatory/sync`

同步歷程列表（`sync/list`，分頁）：資料集、開始時間、結束時間、狀態、收到筆數、失敗原因。

**失敗原因要完整顯示，不要截斷。** 後端在 `error_message` 裡刻意寫了可判讀的內容（缺哪一種身分別、兩邊的 checksum、生效日推導不出來的原因），截斷就等於把那些設計丟掉。

## 5. 顯示規則（這一節是本計畫的重點）

後端花了很多力氣讓數字不失真，前端一行 `Number()` 就能把它全部丟掉。以下三條都是為此。

### 5.1 日期一律顯示西元，不轉民國

政府公告用民國，資料庫存西元。畫面**顯示西元**。

理由不是哪一種比較好，而是**系統其他地方（到職日、離職日、薪資期間、請假日期）全部是西元**。只有法規這一頁用民國的話，讀的人每看一個日期都要先判斷「這一格是哪一種紀年」——而判斷錯的代價是差 1911 年，看起來像資料壞掉。

例外：**同步失敗原因裡的民國年不轉換**，那是後端從政府原文抄出來的，改寫它會讓人對不上公告。

### 5.2 金額與費率禁止經過 `Number()`

**這一條要有檢查擋，不能只靠註解。**

後端的金額與費率一律是 decimal 字串（後端規範 §4.7，逐字寫著「勞健保級距在邊界值上會選錯級距」）。前端顯示時很容易寫成：

```ts
Number(record.data.monthlyContributionWage).toLocaleString()   // ✗
```

那一行看起來完全正常，而且在絕大多數值上都對——直到某個級距的邊界值。

**做法**：`shared/format/` 增加金額與費率的格式化函式（§9.2 要求格式化統一在該目錄），**輸入是字串、輸出是字串**，中間不經過 `number`。千分位靠字串切割，費率的 `0.115 → 11.5%` 靠小數點位移（後端的解析器就是這樣做的，理由相同：`0.29 / 100` 在 JS 裡會得到 `0.0029000000000000002`）。

✅ 掃描規則：`pages/**` 與 `shared/components/**` 禁止對來自 API 的金額／費率欄位使用 `Number(`／`parseFloat(`／`+` 前綴轉型。

### 5.3 每個資料集的內容形狀不同，用資料驅動而不是九個分支

`regulatory_records.data` 的形狀逐資料集不同，後端已經為每一個定了 TypeBox schema（[01](01-regulatory-dataset-versioning.md) §6）。

前端**不要**寫成九個 `v-if`。做法：`.view.ts` 依 `datasetCode` 回傳一份「欄位定義」（欄位鍵、標題的 i18n key、對齊、格式化函式），表格元件吃那份定義。

理由：九個分支的版面會各自漂移（這個表有千分位、那個沒有），而且第十個資料集加進來時要動到模板。欄位定義是資料，加一個資料集就是加一筆。

**這份定義是前端自己的**，不是後端 schema 的複製——後端 schema 管的是「這個值合不合法」，前端定義管的是「這一欄叫什麼、怎麼排、怎麼格式化」。兩者形狀相近但責任不同，硬要共用會逼出一個兩邊都不好用的中間層。

## 6. 權限與選單

**權限碼**（後端已 seed，除了新增的 overview）：

```
regulatory.datasets.list / .get / .resolve / .overview（新增）
regulatory.sync.list
```

依 §4.1，頁面**不得判斷角色**，一律判斷權限碼。沒有 `regulatory.datasets.overview` 的人看不到這個選單項，直接進網址則由路由守衛擋下。

**選單**：`menu/` 是獨立的資料結構（§0.2），加兩筆即可，**不搬任何檔案**。分組放在「系統設定」底下——資料字典 `docs/schema/05` 的分層是「系統設定：角色、權限、帳號；**法規設定：政府資料與公司投保設定**」，兩者並列。

## 7. 型別：這會是第二筆手寫 DTO 的欠帳

**前端規範 §3.2 禁止手寫 DTO**，型別應由 `bun run gen:api` 從 OpenAPI 產生（後端規範 §1.7）。

**但 `gen:api` 目前不存在。** `shared/api/sessions.ts` 已經是手寫的，這一輪會再加一份。

兩個選擇：

| | 作法 | 代價 |
|---|---|---|
| 甲 | 先做 `gen:api`，再做這一頁 | 多一輪前置，但這一頁的型別是產生的 |
| 乙 | 再手寫一份，之後一起換掉 | 這一頁能較快做出來，但欠帳從一份變兩份 |

**已定案：甲。**

決定性的理由不是工作量，是目標本身——**「前後端要能對得起來」如果靠人維護兩份型別，就永遠只是一個努力的方向，不是一個成立的事實。** OpenAPI 產生型別讓它變成機械的：後端改了 schema，前端型別跟著變，對不起來的地方是編譯錯誤而不是執行期的空值。

次要理由：這一頁的型別比登入複雜得多（九種 `data` 形狀、分頁、列表），手寫的量夠大到「之後再換掉」會變成一件沒人想動的事。而 `gen:api` 的前置條件早就齊了——`app/app.ts` 是純組裝、不連資料庫，後端規範 §1.7 那條最麻煩的要求已經滿足。

**連帶還掉舊帳**：`shared/api/sessions.ts` 現在是手寫的，`gen:api` 做完之後換成產生的。

## 8. 分階段

**順序已定案，理由見各階段。**

### Stage 1 — `gen:api` ＋ 端點清單快照

OpenAPI plugin、`gen:api` 指令、產生物列入 `.gitignore`、端點清單快照測試（後端規範 §1.7 標明**必須有**）。

**排第一，不是排在 `overview` 端點後面。** 因為它是「前後端對得起來」這件事本身的機制，而不是一個功能：先有它，`overview` 端點一寫完，前端的型別就是產生出來的，不會有任何一刻存在手寫版本。反過來的話，`overview` 的型別會先被手寫一份，然後多一件要換掉的事。

端點清單快照也在這一階段：spec 是產生物、不進版控，於是**對外契約的變更不會出現在 PR diff 裡**。快照把它拉回來——尤其是「所屬認證群組」那一欄，把一支端點從需驗身分移到公開群組，在 PR 上會是零行變更。

### Stage 0 — 後端 `overview` 端點
見 §3。含權限碼 seed 與測試。**排在 Stage 1 之後**（編號保留是為了標明它屬於後端而非前端）。

### Stage 2 — 顯示規則的基礎建設
`shared/format/` 的金額與費率格式化（§5.2）＋ 它的掃描規則。**排在頁面之前**：反過來的話，頁面會先用 `Number()` 寫出來，之後要逐處改，而漏掉的那幾處不會有任何症狀。

### Stage 3 — `regulatory/datasets`
總覽 → 版本清單 → 版本內容，含基準日選擇器與欄位定義表（§5.3）。

### Stage 4 — `regulatory/sync`
同步歷程列表。

**驗收**：以真實的同步資料（目前資料庫裡有勞保 97 筆、勞退 62 筆、勞就保 28 筆、職災 55 筆、補充保費 3 筆）逐頁核對；基準日改成去年時，顯示的版本要跟著變。

## 9. 不做什麼

| 項目 | 為什麼 |
|---|---|
| 任何修改、觸發同步 | §2 |
| 補充保險費率的調整介面 | 屬於平台管理，而平台管理員不存在（決策 D3） |
| 原始 Snapshot（`raw_data`）檢視 | 端點本來就不回傳它；看原始檔是維運行為，屬於平台管理 |
| 匯出／下載 | 沒有需求；有了再說 |
| 公司投保設定（`company_regulatory_settings`） | 那張表還沒建，見 [01](01-regulatory-dataset-versioning.md) §2 |

## 10. 待定

**`docs/ui/` 沒有這兩頁的規格。** 本計畫是依後端能力與資料字典的分層推出來的，版面細節（欄位順序、預設排序、展開還是換頁）沒有已定案的 UI 文件可依。若日後補了 UI 定案文件，以那份為準。
