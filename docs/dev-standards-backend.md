# Sundial 後端開發規範

適用範圍：`Bun + Elysia + Drizzle ORM + MariaDB`，TypeScript `strict: true`。
本文件規定**程式碼怎麼寫**；**檔案放哪裡由 §0 規定**，那一節是其餘章節的定位基準。資料模型以 [`docs/schema/`](schema/README.md) 為準，畫面行為以 [`docs/ui/`](ui/README.md) 為準。

閱讀方式：每條規則都是「**規則 → 理由（違反會怎樣）**」，容易寫錯的地方附正確／錯誤對照。標記 ✅ 者**可自動化檢查**，括號內為檢查手段；標記 ⚠️ 者**靠 code review 或屬流程建議**，括號內註明；其餘靠 code review。
用語：**必須**＝違反即擋 PR；**禁止**＝同上反向；**建議**＝可用理由推翻但要寫在 PR。

## 0. 模組目錄結構

**這一節必須先讀，因為其餘章節的分層規則全部建立在它定義的目錄與檔名形狀上。** §3.1.1 的「service／domain 不得 import http 層」、§4.4 的「交易邊界屬於 service 層」、§0.4 的「入口檔只做委派」與 `impl/` 的 import 限制——這些規則在工具裡的樣子都是一個 glob（`**/*.service.ts`、`**/*.repository.ts`、`**/impl/**`），glob 命不中，規則就等於不存在。

### 0.1 採縱切（依功能領域分），不採層優先

```text
apps/api/src/modules/<大目錄>/
├─ <次目錄>/
│  ├─ <大目錄>-<次目錄>.routes.ts
│  ├─ <大目錄>-<次目錄>.handler.ts
│  ├─ <大目錄>-<次目錄>.service.ts      入口：每個動作一個函式，一行委派（§0.4）
│  ├─ <大目錄>-<次目錄>.repository.ts   入口：每個動作一個函式，一行委派（§0.4）
│  ├─ impl/                         service／repository 的動作切片（§0.4）
│  │  ├─ <大目錄>-<次目錄>.<動作>.service.ts
│  │  └─ <大目錄>-<次目錄>.<動作>.repository.ts
│  ├─ <大目錄>-<次目錄>.errors.ts
│  ├─ domain/                      零 IO 純函式
│  └─ __tests__/
├─ shared/                          兩個以上次目錄共用時才建
├─ index.ts                         對「其他模組」的唯一出口：只 export service 與 errors（§0.3）
└─ routes.ts                        對「路由組裝點」的唯一出口：只 export routes（§0.3）
```

**為什麼是縱切而不是層優先**（不是「比較好讀」這種可以各說各話的理由）：

- **「層」這個維度已經由檔名後綴表達完了。** `**/*.repository.ts` 在任何目錄結構下都是一個 glob，把所有 repository 集中到一個 `repositories/` 目錄並不會讓工具更容易找到它們——它們本來就找得到。層優先的目錄在這裡是一份**重複的資訊**。
- **功能領域的邊界只有目錄能表達，也只有目錄能被工具強制。** 「跨領域只能走對方的公開介面」這條規則，在縱切結構下是一條 dependency-cruiser 規則（§0.3）；在層優先結構下**寫不出來**——所有 service 都躺在同一個 `services/` 目錄裡，工具沒有任何依據判斷哪一支 service 屬於哪個領域，於是這條規則只剩下 review 能擋。
- **這不是推測。** 本團隊既有的另一套系統採層優先結構，其「不得跨領域直接使用對方的資料存取層」這條規則在該系統的文件中明文記載著「**沒有自動檢查在擋，只能靠 review**」。同一條規則在縱切結構下是一行設定檔。差別不在規則寫得好不好，在於結構讓不讓它被檢查。
- `shared/` **只在兩個以上次目錄真的共用時才建**，不得為了「以後可能會用到」預先建立（同前端規範 §1.5）。

### 0.2 一律兩層目錄，檔名全域唯一

- **一律兩層目錄**：大目錄＝功能領域，次目錄＝子實體。**只有一個子實體時也要有次目錄，沒有例外。**
- **次目錄名 = 該子實體的名稱；當它與大目錄同名（也就是這個子實體就是這個領域本身）時，一律命名為 `main`。** ✅（自製掃描腳本：次目錄名不得與大目錄名相同）
  這條是純比對，不含判斷：只要問「次目錄名跟大目錄名一樣嗎」，一樣就寫 `main`。它刻意**不**規定「每個大目錄都要有一個 `main`」——由平行子實體組成、沒有主體的領域（各子實體都有自己的名字）是正常的，強迫生一個 `main` 只會多一個空殼。
  理由：不訂這條的話，「只有一個子實體時那個目錄叫什麼」會各自發明（`main`／`default`／與大目錄同名／實體單數形），而三段路徑（§1.1）與檔名（下一條）都建立在次目錄名上，名字一亂就沒有一致的推導基礎。
  理由：零例外讓規則只有一種形狀，「這個模組該不該拆次目錄」這個**沒有標準答案**的判斷從流程中消失——與 §1.2「一律 `POST`」是同一種取捨。開了「只有一個子實體時可以扁平」這個口子之後，第二個子實體出現的那天就要整包搬家，而搬家會連帶改動每一個 import，那個 PR 的 diff 大到沒有人看得出裡面有沒有夾帶行為變更。
- **檔名格式一律 `<大目錄>-<次目錄>.<層>.ts`，全域唯一。** 因此**檔名必須等於所在目錄路徑**——搬檔案忘了改名，或改名忘了搬目錄，當場被擋。
  **`impl/` 底下的實作切片（§0.4）沿用同一條規則，只是多一段動作**：`<大目錄>-<次目錄>.<動作>.{service,repository}.ts`。**前綴 `<大目錄>-<次目錄>` 仍必須等於所在次目錄的路徑**（`impl/` 這一段不計入推導），因此切片檔一樣是全域唯一，一樣搬錯就被擋。 ✅（自製掃描腳本：期望檔名**由路徑推導**，不需硬編任何清單；`impl/` 底下額外允許並要求中間那一段動作；掃描器必須自我檢查掃到的檔案數 > 0，見通用規範 §7.2）
  理由：檔名全域唯一，堆疊追蹤、log、編輯器的檔案搜尋才能直接定位到唯一一個檔案。全站有七個 `service.ts` 時，開了七個分頁沒有人分得出哪個是哪個，而錯誤堆疊上那一行檔名等於沒有資訊。
- **檔名白名單**：`modules/` 底下**只允許** `index.ts`、`routes.ts`（此兩者皆為大目錄層，與次目錄同層）、`shared/**`、`<大目錄>-<次目錄>.{routes,handler,service,repository,errors}.ts`、`impl/<大目錄>-<次目錄>.<動作>.{service,repository}.ts`、`domain/**`、`__tests__/**`，出現其餘任何檔名一律失敗。 ✅（自製掃描腳本）
  **`modules/<大目錄>/routes.ts` 是大目錄的第二個出口**，形狀與 `index.ts` 相同、用途完全不同，規則見 §0.3。它同樣是「沒有層後綴的檔案」，因此同樣必須被白名單與 AST 限制管住，否則它會長成 §0.3 針對 `index.ts` 所要防的那個「沒有規則管得到的一層」。
  **`impl/` 底下只允許 `service` 與 `repository` 兩種後綴**，不得出現 `routes`／`handler`／`errors` 的切片——那三種依 §0.4 不拆，出現即代表有人在繞開該節。
  理由必須寫清楚，因為這條看起來像潔癖：**所有分層規則都建立在檔名後綴上**——§3.1.1 的 dependency-cruiser 規則以 `*.service.ts`／`domain/**` 為對象，§0.4 的入口／實作規則以 `*.{service,repository}.ts`／`**/impl/**` 為對象，§1.8.1 的 envelope 掃描以 `*.handler.ts`／`*.routes.ts` 為對象。只要有人把檔案叫 `xxx.manager.ts`，**上述規則會同時失效，而且不會有任何東西報錯**——它們只是靜靜地不再命中任何東西，違規的程式碼一行也不會被掃到，CI 永遠是綠的。白名單的作用，是把「規則沒有命中任何檔案」這種靜默失效，變成一個會紅的檢查。

### 0.3 跨目錄相依：大目錄有兩個出口，`index.ts` 與 `routes.ts`

**一個大目錄對外有且只有兩個出口，各自服務一種呼叫者：`index.ts` 給其他模組，`routes.ts` 給唯一的路由組裝點。** 兩者形狀相同（只允許 re-export）、用途互斥（誰能 import 它們是分開規定的），**不得合併成一個**——合併的後果寫在下方 `routes.ts` 那一條的第二個子項。

- **跨大目錄只能透過對方大目錄的 `index.ts`**，禁止 import 到對方的任何內部檔案。
- **同一大目錄內的次目錄之間可以互相 import**（同一個領域的內部細節本來就該互相知道），但 **`*.repository.ts` 不得被本次目錄以外的任何檔案 import**——跨次目錄要資料，一律走對方的 service。 ✅（dependency-cruiser）
  理由：repository 只負責把資料撈出來，**不含該次目錄的業務規則**（軟刪除判定、公司範圍、狀態過濾）。繞過對方的 service 直接讀它的表，等於把那些規則整組繞掉；而且對方之後改了規則，你這邊不會知道，也不會有任何地方變紅。
- **`index.ts` 只允許 re-export**，不得有任何宣告、常數或函式本體；且**只 export service 與 errors，不 export repository 與 routes**。 ✅（自製掃描腳本：`index.ts` 的 AST 只允許 `export ... from`；被 re-export 的來源檔名後綴必須是 `.service.ts` 或 `.errors.ts`）
  理由有兩層。其一，`index.ts` 是**沒有層後綴的檔案**，所有分層規則都不以它為 `from`——不限制的話它會長成一個沒有任何規則管得到的第六層，而且是最方便亂放東西的那一層（「這段兩邊都要用，先放 index」）。其二，re-export repository 會讓跨模組的一行 import 把資料庫連線一起拖進來，§4.2「裸 db client 限資料存取層」那條 depcruise 規則會被繞過，而繞過的路徑在 import 語句上完全看不出來。
- **`modules/<大目錄>/routes.ts` 是大目錄對「路由組裝點」的唯一出口。** 形狀與 `index.ts` **完全相同**：只允許 `export ... from`，不得有任何宣告、常數或函式本體；被 re-export 的來源檔名後綴**只能是 `.routes.ts`**。 ✅（自製掃描腳本：`routes.ts` 的 AST 只允許 `export ... from`；來源檔名後綴必須是 `.routes.ts`）
  - **只有路由組裝點可以 import 它；`modules/**` 底下任何檔案不得 import 它。** ✅（dependency-cruiser：`modules/*/routes.ts` 的合法 import 者只有唯一的路由組裝點，其餘一律禁止）
    理由：這條是 `routes.ts` 與 `index.ts` 之所以能分開的**執行手段**。少了它，`routes.ts` 就只是「另一個 index」，任何模組都能從它把 HTTP 框架撈進來，下面那條規則會被靜默繞過。
  - **`index.ts` 的規則一字不改：它仍然只 export service 與 errors，仍然不 export routes。** 這一點必須寫清楚，因為「反正都要 export，合成一個檔案不是更簡單嗎」是後人一定會提的問題。
    理由：**讓 `index.ts` 也 export routes 的話，任何模組 import 別人的 service，都會把 HTTP 框架一起拖過大目錄邊界。** 這與上一條「re-export repository 會把 db client 拖過去」**逐字同構**——同一個機制、同一種後果：§3.1.1「service／domain 不得 import http 層」那條 depcruise 規則會被一行看似無害的 `import { xxxService } from '../other'` 繞過，**而且一樣從 import 語句上完全看不出來**。既然理由同構，處置就必須同構：把它拆成第二個出口，而不是放進第一個。
- **入口群組與認證群組不在這兩個出口裡，它們屬於路由組裝點**（§1.9）。模組只透過 `routes.ts` 提供端點，不建立群組、不宣告驗證方式。

### 0.4 實作切片：強制拆分只落在 `service` 與 `repository`

**「要不要拆」不由行數決定，也不由個人判斷決定，而是由「哪一層」決定：`service` 與 `repository` 一律拆，其餘一律不拆。**

- **本節不設任何行數門檻。** 「handler 超過 N 行就拆」「service 入口超過 N 行就拆」這類規則看起來客觀，實際上只是**把判斷從「要不要拆」搬到「這是 14 行還是 16 行」**——判斷沒有被消除，只是換到一個更沒有意義的位置。而且它可以被**沒有改善任何結構**的手法滿足：把兩行併成一行、把註解刪掉、把參數縮成一個物件，門檻就過了，檔案該有多亂還是多亂。改由層決定，「這個檔案該不該拆」就不再是一個問題——同一個問題不會在每次 review 被重新問一次。

| 層 | 拆不拆 | 理由 |
|---|---|---|
| `routes` | **不拆** | 它是這個次實體的**端點目錄**：有哪些端點、各自落在哪個認證群組（§1.9）、收什麼 body。拆掉之後，**就沒有任何一個地方能一眼看完這些**，而「這個次實體對外開了哪些口、哪些口是公開的」正是最需要一次看完的東西 |
| `handler` | **不拆** | 每個函式只做「取出驗證後的 body → 呼叫 service → 把結果收成 `data` 回傳」（§1.8.0 的④與⑥）。**它在結構上不會長大**——沒有可膨脹的內容，拆它只是製造檔案 |
| `service` | **強制拆** | 業務規則會無限成長，**這是唯一會膨脹的層** |
| `repository` | **強制拆** | 查詢會無限成長 |
| `errors` | **不拆** | 它是這個次實體的**錯誤字典**。拆散之後，「哪些錯誤必須刻意含糊」（§3.2）就沒有一個地方能一起看——而那正是最需要並排比對、最不能只看單筆的東西 |

（`domain/` 本來就是目錄，純函式依主題自行分檔，不套用本節的入口／實作形式。）

#### 拆的單位一律是「動作」，但兩層的「動作」不是同一組東西

- **`service` 的動作 ＝ 業務動作。** 多數與端點一對一（§1.1 的動作片段），但**不是必然**：同一段業務邏輯也會被憑證驗證器（§1.9.1）、排程、匯入或其他模組呼叫，那些情境沒有對應的端點。**沒有端點的業務動作一樣放在入口檔**，因為它同樣是這個次實體對外的介面，只是呼叫者不是前端。
  界線是「**有沒有次目錄以外的呼叫者**」：有，就是業務動作，放入口；沒有（只有自己的切片在用），那它是實作細節，應該留在 `impl/` 或抽成 `domain/` 的純函式。 ✅（掃描腳本：入口檔匯出的每個動作都必須有次目錄以外的呼叫端，零呼叫端即失敗）
  理由：把入口限制成「只能是端點」，會讓授權查詢、排程要用的業務邏輯這類東西無處可放——它們的呼叫者不是前端，但它們確實是業務規則，塞進 `impl/` 就繞過了「所有呼叫必須經過入口」那道牆，塞進 middleware 則等於讓入口層直接碰 repository。
- **`repository` 的動作 ＝ 資料存取動作，不是端點動作。** 例如「依名稱查詢是否已存在」本身就是一個 repository 動作，由入口暴露；多個 service 動作各自呼叫它即可，因此**既不需要複製，也不需要切片之間互相依賴**。
  **這一點必須寫清楚，否則一定會被理解成「repository 的切片要與端點一對一」**，而那個誤解會直接長出兩種壞結果二選一：同一段查詢被複製進好幾個切片（改一處漏一處，而且不會有任何地方變紅），或者切片開始互相 import（違反下面第 3 條）。以資料存取動作為單位，這兩條路都不會被走到。

#### 形式：入口檔 ＋ `impl/` 實作檔

```text
modules/<大目錄>/<次目錄>/
├─ <大目錄>-<次目錄>.routes.ts
├─ <大目錄>-<次目錄>.handler.ts
├─ <大目錄>-<次目錄>.service.ts          入口：每個動作一個函式，一行委派
├─ <大目錄>-<次目錄>.repository.ts       入口：每個動作一個函式，一行委派
├─ impl/
│  ├─ <大目錄>-<次目錄>.<動作>.service.ts
│  └─ <大目錄>-<次目錄>.<動作>.repository.ts
├─ <大目錄>-<次目錄>.errors.ts
├─ domain/
└─ __tests__/
```

1. **入口檔只做委派，不得有實作。** `*.service.ts` 與 `*.repository.ts` 的每個匯出函式只有一行：把參數交給 `impl/` 底下對應的實作函式。 ✅（自製掃描腳本：入口檔的匯出函式本體只允許單一 `return`／`await` 委派呼叫，出現條件判斷、迴圈、資料庫呼叫或多段敘述即失敗）
   理由：入口是這個次實體**對外的唯一介面**——打開它就知道這裡有哪些動作、各自收什麼、回什麼，一頁看完。一旦實作開始往入口裡放，這個「一頁看完」的功能就消失了，而它消失得很安靜：檔案只是一天比一天長，沒有任何一天會有人說「就是今天壞的」。

2. **`impl/` 底下的檔案只能被同一個次目錄的入口檔 import，其他任何位置一律禁止。** handler 不行、其他次目錄不行、其他大目錄不行、`shared/` 不行、測試也不行（測試打入口）。 ✅（dependency-cruiser）
   理由要寫清楚，因為這條是整節的**承重牆**：它是「所有呼叫都必須經過入口」的**強制手段**，不是額外的潔癖。少了它，任何人都可以直接 import 到某個實作切片，於是入口就只是裝飾——它宣稱自己是唯一介面，實際上旁邊有一整排沒鎖的側門，而且從 import 語句上看不出來誰走了側門。到那時，「這個動作有哪些呼叫者」這個問題就再也答不出來了。

3. **實作切片之間不得互相 import。** ✅（dependency-cruiser）
   需要共用時**只有兩條路**：
   - **升格成自己的一個動作切片**，由入口暴露，讓上層去組合（repository 尤其常走這條，見上一小節的例子）；
   - **若不碰 IO，抽成 `domain/` 的純函式**。
   理由有兩層。其一，切片互相 import 會在**實作層**長出一張依賴網，而那正是分層一開始想避免的東西——層與層之間的依賴是被規定死的，切片之間的依賴則沒有任何規則管得到，會長成什麼形狀完全看當時誰急著交件。其二，被共用的那個切片會變成一個**沒有名字的隱性介面**：它同時是「某個動作的實作」與「別人依賴的共用元件」，改它的人只會看到前者，於是改壞後者。升格成入口上的一個動作，就是逼這個介面把名字講出來。

4. **檔名規則**（§0.2 已同步）：`impl/` 底下為 `<大目錄>-<次目錄>.<動作>.{service,repository}.ts`，入口檔維持 `<大目錄>-<次目錄>.{service,repository}.ts`。 ✅（自製掃描腳本，見 §0.2）

### 0.5 新增端點的建立順序：由下往上

**`schema` → `repository` → `service` → `errors` → `handler` → `routes`。**

- 理由：依賴方向由下往上，建立順序就跟著由下往上。先寫上層會需要**臆測**下層的介面——service 還沒寫，handler 只能先假設它回什麼；等 service 真的寫出來，形狀對不上就要回頭改 handler，而那次回頭改是純粹白做的工。
- `errors` 排在 service 之後、handler 之前，是因為要宣告哪些錯誤碼，得先知道 service 實際會收集到哪幾種業務拒絕（§3.1.1）；而 handler 與 routes 要宣告的錯誤碼清單（§1.8.3）正是從這裡來的。
- ⚠️（流程建議，非檢查項）：這條規則的產物（schema、各層檔案、錯誤碼清單）都有各自的檢查在管，順序本身沒有檢查，也不該有——它是為了少做白工，不是為了擋 PR。

## 1. API 設計規範

### 1.0 入口（entry point）：本章是「Web 前端」這個入口的契約

**「入口」指的是「誰在呼叫這套系統」。** 本專案目前**只有一種入口**：自家的 Web 前端。本章（§1）與 §2 規定的路徑形狀、`cmd`、request／response envelope、`code` 映射、認證方式（§5.4），全部都是**這一個入口的契約**——不是「全系統唯一的契約」，也不是「所有可能的呼叫者都必須遵守的形狀」。

先寫下這一節，是因為它決定了**現在有哪些話不能寫死**。將來若接上其他入口（對接外部設備、第三方系統、閘道回呼、CLI 或批次／佇列），那些入口的格式**常常由對方訂，我們改不了**；若本文件到處寫著「所有端點一律……」「全站只有一種……」，屆時就只剩兩條路：把對方的格式**硬塞**進我們的信封裡，或**要求對方配合**改他們的規格。**兩條都不可行**——前者產出一個兩邊都不認的畸形契約，後者在商務上根本談不動。因此這一節不是為了預留擴充彈性，是為了**不要現在就把自己堵死**。

- **這不是推測。** 本團隊既有的另一套系統有六種入口：自家前端、內部系統對系統、外部廠商、閘道回呼、CLI、佇列。它們**各自有不同的認證方式、不同的欄位命名慣例、不同的狀態碼體系，四套回應契約絕不混用**，但**全部匯流到同一個業務層**。最極端的一種是閘道回呼：規格完全由對方訂，連信封都沒有——不可能有任何一套自家信封套得上去。

#### 1.0.1 業務層對入口無關，而這正是多入口的支點

- **「service 不得碰 HTTP」不是為了好看，它的目的就是支撐多入口**（既有規則見 §1.8.2、§3.1.1）：同一段業務規則被不同入口呼叫時，**規則只有一份**。多一種入口，多的是一組翻譯層，不是多一份重寫過的規則。
- 反過來說，只要業務層碰了 envelope、碰了 HTTP status、碰了 `cmd`，它就**只能被這一種入口呼叫**。第二種入口出現時，唯一的辦法是把那段規則複製一份改成新格式——然後兩份規則從那天起開始各自演化，而**沒有任何檢查會告訴你它們已經不一樣了**。等到有人發現兩邊算出不同答案，通常已經是對外事故。
- 因此 §3.1.1「service 收集錯誤而不是拋例外、且錯誤分組用具名常數而不是 HTTP 數字」這條規則，**同時也是這一節的實作手段**：具名分組（`Conflict`／`Unprocessable`／`Forbidden`）之所以不直接寫成數字，正是因為「這個分組在某個入口上對應什麼狀態碼」是**入口的事**，不是業務層的事。

#### 1.0.2 新增入口時的規則

新增一種入口時：

- **新入口有自己的路由分組（§1.9，含它自己的認證群組）、自己的翻譯層（入口↔業務層的輸入與輸出轉換）、自己的請求與回應契約。**
- **業務層一行都不改。** 若發現非改不可，那代表既有的業務層已經滲入了入口的細節，**要修的是那個滲入，不是為新入口讓路**。
- **禁止跨入口借用契約。** 不得把某個入口的信封套用到另一個入口，也不得讓一個入口的契約**繼承**另一個入口的契約（不要「基底契約 + 各入口擴充」這種形狀）。
  理由：**對象不同，認證方式、欄位命名慣例、狀態碼體系就全都不同**——它們不是同一個東西的變體，而是各自完整的一套。硬套的後果是**其中一邊的對外契約會錯掉**，而且錯的通常是被迫遷就的那一邊；用繼承串起來則更糟：改共同基底時，你不會知道自己同時改了幾個對外契約，而其中有些的對方**根本不歸我們管**。
  更關鍵的是**外部對接方的格式常常由對方訂**——他們的欄位就叫那個名字、狀態就用那組碼、信封可能根本不存在。這時候「共用信封」不是一個選項，只是一個做不到的假設。 ⚠️（靠 review；目前只有一種入口，尚無第二個契約可資比對。第二種入口出現的當下，「入口 A 的契約模組不得被入口 B import」就成為一條 dependency-cruiser 規則，屆時併入 §8）

#### 1.0.3 現在不建立多入口的目錄結構，只保留概念

**本節到此為止只是概念：不新增任何目錄維度，`modules/<大目錄>/<次目錄>/`（§0.1）維持原樣。**

- 理由：目前**只有一種入口**。預先分出入口維度，結果是每一個模組都多一層**只有一個子項的空目錄**，每個 import 路徑都多一段沒有資訊量的片段——為一個還不存在的東西，讓現在的每一支程式碼都付一點成本。這與 §0.1「`shared/` 只在真的共用時才建」是同一個取捨。
- **重新評估的條件**（出現任一即應重新討論目錄形狀）：確定要接上第二種入口（外部設備、第三方系統、閘道回呼、CLI、批次／佇列皆算）；或某支業務規則已經被兩種不同格式的呼叫者使用。
- **而且屆時要加的東西是明確的**：一組新的路由分組（§1.9 最外層的一個兄弟群組）、一層新的翻譯層、一份新的契約——**業務層不動**。**這正是分層要兌現的地方**：如果那天發現業務層非改不可，那不是分層不夠用，是前面某處已經違反了 §1.0.1，而這一節的存在就是為了讓那個違反在當下就被指出來，而不是等到那天才發現。

### 1.1 路徑命名

**本系統面向 Web 前端這個入口（§1.0）的 API 是 RPC over HTTP，不是 REST。** 這是明確的選擇，不是尚未修正的偏差：不使用 GET、參數全走 request body、request 帶 `cmd` 指令欄位、HTTP status 之外另有一層 envelope `code`——這四點任何一點都足以讓它不是 REST。既然已經偏離，就**一致地偏離**，不要半套：以下規則的共同目的，是讓「一支端點長什麼樣」完全沒有可討論的餘地。

- **所有端點的路徑一律為 `/<大目錄>/<次目錄>/<動作>` 三段**，前兩段**直接鏡射模組目錄結構**（§0.1 的 `modules/<大目錄>/<次目錄>/`），第三段是動作。**三段全部用 kebab-case，且前兩段必須與目錄名完全一致**：

  ```
  POST /<大目錄>/<次目錄>/create
  POST /<大目錄>/<次目錄>/update
  POST /<大目錄>/<次目錄>/delete
  POST /<大目錄>/<次目錄>/list
  POST /<大目錄>/<次目錄>/get
  POST /<大目錄>/<次目錄>/approve
  POST /<大目錄>/<次目錄>/reject
  ```

  **理由：三段是為了讓 URL 與目錄一一對應，不需要任何對照表。** 壓成兩段的話，「大目錄／次目錄」這兩層就得擠進單一個資源名，而**那個壓縮是有損的**——從 URL 上看不出這支端點屬於哪個大目錄，而目錄結構裡它們本來就是分開的兩層。有損之後就必須有人記住或維護「哪個資源名對應哪個目錄」，那份對應**不在任何一份會失敗的檢查裡**，於是它遲早會過期。三段之後，「這支端點的程式碼在哪」與「這個目錄對外開了什麼路徑」兩個方向都是機械推導，兩邊改一邊就會被擋。
  **沒有動作片段的端點不存在**——`POST /<大目錄>/<次目錄>` 這種寫法一律不可，因為它讓 `cmd` 算不出來（§1.3），也讓「這支是建立還是查詢」只能靠 HTTP method 猜。
  ✅（自製掃描腳本：路由路徑必須恰好三段、每段為 kebab-case，且前兩段必須對應到實際存在的 `modules/<大目錄>/<次目錄>/` 目錄，對不上即失敗；掃描器須自我檢查掃到的路由數 > 0）
- **路徑不得帶任何參數。** 沒有 `{id}` 這類路徑參數，也沒有 query string。**所有參數（含識別碼 `id`）一律放 request body**（§1.5）。
  理由：識別碼放路徑等於讓同一支端點的輸入分散在兩個地方，schema 被拆成 `params` 與 `body` 兩份，前端包裝函式與後端驗證都要各自處理兩處；而且輸入永遠不會只有 `id`——很快就會出現「要不要一併帶明細」「要哪個版本的快照」這類條件，那些一定得放 body。統一放 body，**每支端點的輸入永遠只有一包**。
- **動作片段就是這支端點在做什麼**，kebab-case，**沒有預先核准的清單**。`create`／`update`／`delete`／`list`／`get` 涵蓋多數情況，但 `auto-fill`、`allocate`、`archive`、`convert-to-pickup`、`refresh` 這類動作同樣正當——硬塞進五個 CRUD 詞只會塞出更難懂的名字。
  **唯一的約束是：同一件事全站用同一個字。** 不得出現 `list` 與 `lists`、`list` 與 `query` 與 `search` 這種同義或單複數不一致的變體。`/get<次目錄>List`、`/query<次目錄>`、`/doApprove` 這類把目錄名或贅詞塞進動作片段的寫法一律不可——前兩段已經講完「這是誰」，動作片段再講一次只是重複。 ✅（自製掃描腳本：蒐集全站動作片段，出現語意重複的變體即列出供 review）
  理由：要防的是「同一件事三種寫法」——那會讓前端無法用同一套規則推導端點，`cmd` 與權限碼也跟著三種寫法（§1.3、§5.2）。但那個目的用**一致性掃描**就達得到，不需要事前核准。改成封閉字彙表的代價是每個真正需要新動作的端點都要先開一次 PR 改清單，而清單本身沒有任何人能事先想周全——最後不是清單長成一份沒人讀的雜燴，就是開發者把動作硬塞進最接近的既有字彙，兩種結果都比自由命名糟。
- **路徑固定三段，沒有巢狀。** 不會出現第四段，也不會出現「父資源／子資源」串接的形狀。需要表達關聯時改用該子實體自己的端點，關聯條件放 request body：子項清單寫成子實體自己的 `POST /<大目錄>/<次目錄>/list`，body 平鋪帶父資料的識別碼。
  巢狀會讓同一份資料出現多條路徑，權限檢查與快取失效必須逐條重寫，遲早漏掉一條。而且巢狀一旦允許，段數就不再固定，§1.3 的 `cmd` 推導與 §5.2 的權限碼推導都會失去「輸入形狀只有一種」這個前提。
- **認證相關端點沒有例外，一樣是三段、一樣鏡射目錄。** 不存在 `auth` 這種「功能群組」開頭的捷徑路徑：

  | 功能 | 路徑 |
  |---|---|
  | 登入 | `POST /sessions/main/login` |
  | 登出 | `POST /sessions/main/logout` |
  | 換發 token | `POST /sessions/main/refresh` |
  | 登出所有裝置 | `POST /sessions/main/logout-all` |
  | 改密碼 | `POST /credentials/main/update` |
  | 重設密碼 | `POST /credentials/main/reset` |

  這六支端點用到的 `login`／`logout`／`logout-all`／`refresh`／`reset`／`update` 六個動作，都是「這支在做什麼」的直白命名：`login`／`logout` 是這個動作的通用名稱——硬套 `create`／`delete` 並非不精準，而是**語意繞了一圈**：讀的人得先把「登入」轉換成「建立一個 session」才對得上，而規範的目的正是讓端點一眼看懂，**繞路的精準不如直白**；`logout-all` 同理，它與 `logout` 的差別在於刻意不指定目標裝置；`refresh` 不是 update——它產生的是一張新票而不是改舊票；`reset` 不是 update——呼叫者不知道也不需要知道舊值。
  理由：這六支端點在目錄上就是 `modules/sessions/main/` 與 `modules/credentials/main/`，路徑照抄目錄即可，**不需要為認證另訂一套命名**。反過來說，一旦允許「功能群組」當開頭，`report`、`export`、`setting`、`dashboard` 全都會援引同一條，說自己「也是功能群組」，三段鏡射目錄這條規則就只剩下 CRUD 端點還遵守，而**它一旦不是零例外，就不能拿來推導 `cmd` 與權限碼**（§1.3、§5.2）——那兩條檢查的前提正是「路徑形狀只有一種」。**這條規則約束的是前兩段，動作片段仍依上一條各自取最直白的字彙**——登入／登出取 `login`／`logout`（理由見上），改密碼就是**更新**憑證。
- **基礎設施端點（`/health` 之類）不適用本節規範**：不帶 envelope、不帶 `cmd`、不需認證，路徑格式也不受三段規則約束。
  這是**排除適用範圍，不是開例外**——兩者的差別在於：例外會被援引（「既然 `/health` 可以，我這支也可以」），排除則有明確邊界。界線是「**這支端點是不是給本系統前端呼叫的業務端點**」：是，就一律照本節；不是（給 load balancer、監控系統、部署腳本用的維運端點），就不在本節管轄範圍內。這條界線與 §1.0 是同一條：維運端點的呼叫者不是 Web 前端，自然不套用 Web 前端的契約。這類端點必須集中在單一檔案並附註解說明用途（§1.2）。
- **`companyId` 禁止出現在 request body**。公司範圍一律由已驗證的 token 決定（見 §4.2）。
  一旦公司來自客戶端，任何人改一個字串就能讀別家公司的薪資；這是本系統最嚴重的單點風險。 ✅（自製掃描腳本：路由定義的 `body` schema 中出現 `companyId` 即失敗）
  **`companyCode` 不是 `companyId`，這條規則不涵蓋它**：`companyCode` 是使用者在登入頁鍵入、**待伺服器驗證**的字串，只允許出現在登入端點的 body，且它不是公司範圍——公司範圍仍由伺服器推導。兩者的界線與理由見 §4.2。

### 1.2 HTTP method：一律 `POST`

**本入口（§1.0）的所有端點一律使用 `POST`，不使用 `GET`／`PUT`／`PATCH`／`DELETE`。**

理由分兩層：

- **`GET` 用不了**：每個 request 都必須帶 `rqTS`／`cmd`／`locale` 三個基底欄位（§1.3），**GET 沒有 request body，這三欄無處安放**。硬要塞進 query 就等於為讀取端點另開一套參數傳遞方式，envelope 立刻變成兩種形狀，出入口的統一處理（補 `rspTS`／回聲 `cmd`、log 對時）也必須寫兩份。`DELETE` 另有一個獨立問題：**它的 request body 在部分代理與中介層會被丟棄**，同一支端點在開發機正常、過了公司 proxy 就收到空 body，而且是間歇性的。
- **`PUT`／`PATCH` 是「還留著就會出事」**：動作已經寫在路徑裡（§1.1）、參數已經全在 body 裡（§1.5），**HTTP 動詞不再承載任何資訊**。留著多種動詞，只會讓每次新增端點都要多做一次「這支該用哪個」的判斷，而那個判斷**沒有標準答案**——一支 `update` 只改三個欄位算全量還是局部？收斂成一個動詞之前，答案取決於誰寫的；收斂之後，這個問題連問都不會被問到。一律 `POST`，是把一個沒有標準答案的判斷從流程中刪掉。
- **多動詞並存的實際代價，不只是判斷成本。** 動詞是呼叫端**第二個必須記住的維度**，而在本設計中它不承載任何資訊——路徑已經有動作片段、所有參數走 body，`POST` 與 `PATCH` 之間沒有任何行為差異，連「`PATCH` 可以安全重試」這個常見的理由都不成立（HTTP 語意上 `PATCH` 本來就不保證冪等）。而多動詞真正的代價是：**文件或端點清單把動詞寫錯時，照抄的呼叫端與測試會一律 404，且錯誤訊息不會指向真正的原因**——回應只說「這條路徑不存在」，看的人會去確認路徑拼字、確認部署版本、確認路由有沒有註冊，唯獨不會想到路徑是對的、錯的是動詞。動詞只有一種時，這個失敗模式連存在的餘地都沒有。

| 意圖 | 寫法 |
|---|---|
| 查詢列表 | `POST /<大目錄>/<次目錄>/list` |
| 查詢單筆 | `POST /<大目錄>/<次目錄>/get` |
| 建立 | `POST /<大目錄>/<次目錄>/create` |
| 更新 | `POST /<大目錄>/<次目錄>/update` |
| 軟刪除 | `POST /<大目錄>/<次目錄>/delete` |
| **狀態變更（核准、退回、撤銷核准、撤回）** | `POST /<大目錄>/<次目錄>/approve`、`/<大目錄>/<次目錄>/reject`、`/<大目錄>/<次目錄>/revoke-approval`、`/<大目錄>/<次目錄>/withdraw` |

上表每一支的識別碼都在 request body，路徑上一個參數也沒有。

- **禁止註冊 `POST` 以外的路由**（健康檢查等基礎設施端點不在適用範圍內，見 §1.1 末條，且必須集中在單一檔案並附註解）。 ✅（自製掃描腳本：路由註冊出現 `.get(` / `.put(` / `.patch(` / `.delete(` 即失敗，白名單需附註解）
- **禁止在 request body 帶 `status` 欄位**來完成核准或作廢，狀態變更只能走上表的狀態動作端點。
  狀態欄位可寫，等於客戶端可以直接把資料改成任一目標狀態，跳過該轉移應有的前置檢查與必填原因。狀態機一旦破口，後續依賴該狀態的計算全部失準。 ✅（自製掃描腳本：request body schema 內出現 `status` 欄位即失敗，白名單需附註解說明）
- 狀態動作端點必須在 `data` 回傳變更後的完整資源，讓前端不必再打一次查詢端點。
- 規格要求必填原因的動作，`reason` 在 schema 層即設為必填，不得只在 service 檢查。

### 1.3 Request／Response envelope

**本入口（§1.0）只有一種** request 形狀與一種 response 形狀，其下所有端點一致。envelope 由出入口層統一處理，端點自己只管業務欄位與 `data`。**這包信封是「Web 前端」這個入口的契約**——將來若增加入口，那些入口有各自的契約，不套用這一包，也不由這一包繼承而來（§1.0.2）。

#### Request envelope（平鋪，不巢狀）

每個 request 都繼承三個基底欄位，**業務欄位平鋪在同一層**，不另開 `payload`／`params` 之類的巢狀節點：

```json
{
  "rqTS": "2026-04-14T14:30:00+08:00",
  "cmd": "<大目錄>.<次目錄>.list",
  "locale": "zh-TW",
  "keyword": "王",
  "parentId": "..."
}
```

| 欄位 | 型別 | 說明 |
|---|---|---|
| `rqTS` | string | 請求時戳，ISO 8601 **帶時區偏移**（`2026-04-14T14:30:00+08:00`），見 §6.1 |
| `cmd` | string | 指令名稱，**跟著 API 命名走，與路徑一一對應** |
| `locale` | string | 語系（`zh-TW`） |

- `cmd` **必須等於路由路徑的機械轉換結果**，不一致即失敗。 ✅（自製掃描腳本：以路由路徑依下述規則推導期望的 `cmd` 值，與 schema 中宣告的常值比對）

**`cmd` 推導規則：純機械字串轉換。** 取路徑，**去掉開頭的 `/`，把剩下的 `/` 換成 `.`**，其餘一字不改——不做單複數轉換、不轉 camelCase。因為路徑是三段（§1.1），結果一律是 `<大目錄>.<次目錄>.<動作>` 三段。

| 路由 | `cmd` |
|---|---|
| `POST /<大目錄>/<次目錄>/list` | `<大目錄>.<次目錄>.list` |
| `POST /<大目錄>/<次目錄>/approve` | `<大目錄>.<次目錄>.approve` |
| `POST /sessions/main/login` | `sessions.main.login` |
| `POST /credentials/main/update` | `credentials.main.update` |

- **這條規則沒有任何例外分支。** 因為路徑一律是 `/<大目錄>/<次目錄>/<動作>` 三段、沒有路徑參數、沒有巢狀（§1.1），輸入形狀只有一種，轉換函式就只有一行字串處理，**每一支端點都算得出期望值**。
- 原樣轉換的理由：任何「聰明」的轉換都需要額外知識。轉單數要處理不規則變化，而由多個詞組成的複合目錄名，其單數形**沒有唯一答案**（該保持連字號式，還是轉成 camelCase？）；轉 camelCase 又讓 `cmd` 無法反推回路徑。原樣轉換的推導函式只有一行字串處理，**人腦與腳本永遠得到同一個值**，這正是這條檢查能成立的前提——推導規則只要有一絲模稜兩可，腳本就算不出期望值，檢查就寫不出來。
- **同一套轉換也用來推導權限碼（§5.2），因此 `cmd` 與權限碼的字面值相同。** 這不是重複設計：兩者**用途不同**——`cmd` 供追蹤與 log，權限碼供授權——只是**恰好共用同一個機械推導規則**，因為它們要指涉的都是「哪一支端點」。詳見 §5.2。
- 理由（為什麼要檢查）：`cmd` 是 log 與問題追查時唯一好用的關鍵字。**路徑改了但 `cmd` 忘了改，log 就開始騙人**——你在 log 裡搜到的某個 `cmd` 其實是另一支端點打的，追查方向從第一步就錯，而且沒有任何東西會提醒你。
- 平鋪而不巢狀的理由：巢狀之後每支端點都要決定「這個欄位算基底還是業務」，於是同一個 `keyword` 在 A 端點在外層、在 B 端點在 `payload` 內，前端無法用同一個包裝函式送請求。

#### Response envelope

```json
{
  "code": "200",
  "msg": "",
  "errors": [],
  "data": null,
  "rspTS": "2026-04-14T14:30:01+08:00",
  "cmd": "<大目錄>.<次目錄>.list",
  "locale": "zh-TW",
  "expiresIn": 3600,
  "exp": "2026-08-19T18:28:28+08:00"
}
```

| 欄位 | 型別 | 說明 |
|---|---|---|
| `code` | string | 六碼之一，見下表 |
| `msg` | string | 回應訊息 |
| `errors` | array | **僅 `code='300'` 時提供**，見下方 errors 結構 |
| `data` | object \| null | 各 API 自行收窄型別；無資料回 `null` |
| `rspTS` | string | 回應時戳，ISO 8601 帶偏移，**由出口層補上** |
| `cmd` | string | 原樣回傳，出口層補上 |
| `locale` | string | 原樣回傳，出口層補上 |
| `expiresIn` | int \| null | access token 剩餘**秒數**（**滑動視窗**，見下）；**過期判斷唯一依據**；`null` ＝ **本次回應之後客戶端手上沒有有效的 access token**（見下方「兩個來源」） |
| `exp` | string \| null | access token 絕對截止時刻，ISO 8601 帶時區偏移；**僅供 log 與除錯——禁止用於過期判斷，也禁止顯示給使用者**（見下）；`null` 時機同 `expiresIn` |

- **禁止裸陣列**，清單一律包在 `data` 內（見 §1.4）。裸陣列之後要加分頁資訊就是破壞性改版。
- `rspTS`／`cmd`／`locale` **一律由出口層統一補上，禁止各端點自行填寫**。散在各處填的結果是有些端點忘了填，前端的通用處理就得寫「有就用、沒有就算了」的分支，回聲比對（§1.4）也跟著失效。
- **`expiresIn` 是滑動視窗，不是固定到期時間。** 每一次通過憑證驗證的請求都會**續期**，因此**每個回應都必須回傳續期後的剩餘秒數**，而不是「發證當下算出來、之後遞減」的值。前端據此在每次回應覆寫自己的 deadline（前端規範 §3.7），使用者只要還在操作就不會被登出，停止操作滿一個視窗長度才過期。
  理由：若後端只在登入時給一次、之後各回應原樣回傳同一個數字，前端每次覆寫 deadline 就會把 session 無限延長；反之若後端回傳的是遞減值而實際上有續期，前端會提早把人踢出去。兩種錯法都不會有任何錯誤訊息，只會表現為「有時候被登出、有時候登不出」，而且無法重現。**續期與回報必須是同一件事的兩面：只要續期了，就得把新的秒數帶回去。**

**`expiresIn` 與 `exp` 並存，但用途分工必須嚴格。**

| 欄位 | 唯一用途 | 禁止 |
|---|---|---|
| `expiresIn`（int，秒） | **判斷 session 是否過期**。前端收到當下算 `deadline = Date.now() + expiresIn * 1000` 保存，之後一律用 `Date.now()` 與這個 `deadline` 比較（前端規範 §3.7） | — |
| `exp`（string，ISO 8601 帶時區偏移，如 `2026-08-19T18:28:28+08:00`） | **寫進 log 與錯誤回報，供除錯用** | **禁止用於任何過期判斷**（含「快到期」提示的門檻判斷）；**禁止顯示給使用者** |

- 分工的理由是**兩者比較的兩端來源不同**：`exp` 是伺服器算出的截止點，要拿去跟**裝置**的現在時刻比較——兩個時鐘，裝置偏移多少判斷就錯多少。使用者的筆電慢 10 分鐘，session 就會晚 10 分鐘才被判定過期（或早 10 分鐘把人踢出去），而這在伺服器端完全看不出來、也重現不了。`expiresIn` 是相對秒數，**寫入 `deadline` 與讀取比較用的是同一個時鐘**，偏移量在相減時抵銷，時鐘準不準都不影響結果。
- 那為什麼還要 `exp`：**log 對時需要一個絕對時刻**，`expiresIn` 給不出來（它只說「還有 3600 秒」，log 聚合時無法與其他系統的時間軸對齊）。追查「這個 session 到底什麼時候該死」時，log 裡有一個絕對時刻才對得上其他系統的時間軸。**這是 `exp` 的唯一用途。**
- **`exp` 一律不顯示給使用者。** 帶時區偏移的時間字串（`rqTS`／`rspTS`／`exp` 三者）全部只供 log 與除錯，**沒有例外**（§6.1）。畫面若要呈現「還剩多久」，一律由 `expiresIn` 倒數推導——這樣同時避開**時區**（帶偏移的字串會被瀏覽器再換算一次）與**裝置時鐘偏移**（絕對時刻要跟裝置的「現在」比）兩個問題，而顯示一個絕對時刻兩個問題都會踩到。
- ✅（自製掃描腳本／ESLint：前端的 session 過期判斷邏輯中禁止引用 `exp`，且任何顯示路徑——模板、format 函式的輸出——亦禁止引用 `exp`，見前端規範 §3.7、§9.2）

#### HTTP status 與內部 `code` 映射

內部 `code` 是 **string**（不是 int），集中定義為常數：

```ts
export const WebFlowCode = {
  DataSuccess:      '200',  // 正常
  DataInvalid:      '100',  // 資料不正確
  LogicError:       '300',  // 邏輯錯誤（業務規則不允許）
  SystemError:      '400',  // 系統錯誤
  AuthRequired:     '900',  // 無有效身分
  PermissionDenied: '901',  // 有身分但無權限
} as const
```

| HTTP | `code` | 意義 | 前端處置 |
|---|---|---|---|
| 200 | `200` | 正常 | — |
| 400 | `100` | 資料不正確 | 進錯誤回報（代表呼叫端 bug） |
| 401 | `900` | 無有效身分 | 導向登入頁 |
| 403 | `901` | 無權限 | 顯示無權限，**不可**導登入頁 |
| 404 | `400` | 系統錯誤 | 顯示系統錯誤 |
| 409 | `300` | 邏輯錯誤 | 顯示業務訊息，讀 `errors` |
| 422 | `300` | 邏輯錯誤 | 同上 |
| 500 | `400` | 系統錯誤 | 顯示系統錯誤 |

- **不使用的 HTTP status：201、202、429、423。** 建立成功回 200，不回 201。
- **這張表的分類軸不是 HTTP 語意，而是「前端拿到之後該做什麼」。** 這是理解整張表的關鍵：六個 `code` 對應的是六種前端動作（照常處理／進錯誤回報／導登入／顯示無權限／顯示業務訊息／顯示系統錯誤），而不是六種伺服器狀態。因此多個 HTTP status 會映到同一個 `code`（404 與 500 都是 `400`，409 與 422 都是 `300`）——**因為前端對它們該做的事一模一樣**。反過來說，只要前端該做的事不同，`code` 就必須不同。
- **「查無資料」不是 404**，是 **HTTP 200 + `code='200'` + `data: null`**（清單則是空陣列）。`404` 代表**端點不存在**，也就是前端打錯路徑或前後端部署不同步。
  理由：把「查無資料」當 404 之後，前端就無法區分「這組條件確實查不到資料」與「這支 API 根本不在」，而這兩件事的處置完全相反（一個顯示空狀態，一個要告警）。
- **`900` 與 `901` 必須分開。**
  理由：把 403 當 401 處理，會造成**「使用者已登入 → 被踢回登入頁 → 登入完又被踢回」的無限迴圈**——使用者只是點到一個沒權限的功能，結果整個系統看起來像壞了，而且他每次重登都會再遇到一次。
- **`900` 的語意是「前端應導向登入頁」，它的唯一產出者是認證群組的憑證驗證器**（§1.9.1）。service 不得表達「憑證不可用」這件事，`ErrorGroup` 也不為它新增分組（§3.1.1）。
- **登入端點自身的失敗不是 `900`。** 這一點看起來反直覺，但它是**這張表算出來的結果，不是妥協**：本表的分類軸是「前端拿到之後該做什麼」（見上一條），而**使用者已經在登入頁了**——「導向登入頁」對他不是一個動作。他該看到的是「帳號或密碼錯誤」，也就是**顯示業務訊息**，那一格對應的 `code` 是 `300`。
  因此 §3.2 要求的 `auth.invalid-credentials` 走 **422 ＋ `code='300'` ＋ `errors`**。回 `900` 的後果是實的：前端對 `900` 的統一處置是「清掉手上的 token 並導向登入頁」（前端規範 §3.6），於是**登入失敗會觸發一次導向登入頁**——使用者按了登入、畫面閃一下又回到登入頁，錯誤訊息在導向過程中被清掉，他不會知道自己打錯了什麼。
  同一條界線適用於所有「用來取得憑證的端點」：它們**本來就在沒有憑證的情況下被呼叫**，憑證不可用是它們的**輸入**，不是它們的失敗模式。
- **`900` 沒有第二個產出點。** ✅（自製掃描腳本：`WebFlowCode.AuthRequired` 與字面值 `'900'` 只允許出現在憑證驗證器與 envelope 的集中定義檔；出現在 `modules/**` 底下任何檔案即失敗；掃描器須自我檢查掃到的檔案數 > 0）
  理由：`900` 一旦有第二個產出點，「使用者為什麼被踢回登入頁」就再也答不出來了——它可能來自驗證器，也可能來自某一支 service 裡一行「這裡看起來也算沒身分吧」的判斷，而那行判斷不受任何續期規則、任何 `expiresIn` 規則約束。前端只看得到 `900`，看不出是哪一種，於是**「被登出」這個現象變成不可追查**。
- **404 與 500 合併為 `400` 的副作用必須由後端 log 補回。** 前端看不出「打錯端點」與「伺服器爆炸」的差別，因此：
  - 後端 log **必須分類**，至少分 `route_not_found`／`unhandled_exception`／`upstream_timeout` 三類；
  - 回應 header 帶 **`X-Trace-Id`** 供追查，前端在錯誤回報時一併帶上；
  - **404 必須獨立告警，且門檻比 500 低。**
    理由：404 通常代表**前後端部署不同步**（前端已上線、後端還沒，或路徑改名只改了一邊）。這種問題**測試環境測不出來**（兩邊都是最新的），一上線就是整片功能同時死掉，而每一筆都只是「404」這種平常被當成雜訊忽略的東西。門檻設得比 500 低，是因為 500 偶發一兩筆可能只是單一請求出錯，404 偶發一兩筆卻已經代表有一條路徑對不上。

#### `expiresIn` 的兩個來源：續期與發證（都不在 handler）

**`expiresIn`／`exp` 的唯一計算處是「access token 生命週期元件」。** 這個元件有**兩個觸發時機**，兩者共用**同一份實作**、寫進**同一格請求上下文**：

| 來源 | 觸發者 | 時機 | 值 |
|---|---|---|---|
| ① **續期** | 認證群組的憑證驗證器（§1.9.1） | 驗證器驗過了一張 access token | **續期後**的剩餘秒數 |
| ② **發證** | 端點（登入、`refresh`） | 端點簽發了一張**新的** access token | **新 token 的完整壽命秒數** |

- **同一次請求不得同時發生兩者。** 發證端點不經過續期（登入落在公開群組，手上根本沒有 access token 可續；`refresh` 驗的是 refresh token，該群組的續期行為就定義為「不續期，改為發證」，§1.9.1），續期端點不發證（它拿的是既有的票）。**因此不需要任何「誰贏」的判斷**——沒有兩個值同時存在的情境，也就沒有優先序規則要記、沒有「這支端點回的是哪一個」要查。
  這條的價值在於它消滅了一整類 bug：只要允許同一次請求兩者並存，就得有一段仲裁邏輯，而那段邏輯寫錯的表現是「某些端點回的秒數比實際壽命短或長」，前端據此算出的 deadline 跟著錯，而回應在型別上完全合法、測試也不會紅。
- **§1.8.2「handler 不得自行填 `expiresIn`／`exp`」一字不改，而且與②不衝突。** handler 在②裡做的事是「**觸發發證**」——呼叫發證元件，取得一張新票；`expiresIn`／`exp` 兩個 envelope 欄位它**一個也沒碰**，仍然由出口層從請求上下文取值填入（§1.8.2）。「誰簽發 token」與「誰填 envelope 欄位」是兩件事，本節分開的正是這兩件事。
- ✅（自製掃描腳本：`expiresIn:`／`exp:` 的**賦值**只允許出現在「出口層 ∪ 憑證驗證器 ∪ 發證元件」三處，其餘任何位置即失敗；掃描器須自我檢查掃到的檔案數 > 0）
- ✅（dependency-cruiser：**發證能力的介面只能被認證模組 import**——任何其他模組能拿到發證能力，就等於任何端點都能替自己簽一張票）

**續期與處理結果完全無關**——不管資料有沒有找到、request 欄位對不對、業務規則過不過、有沒有權限做這個動作。因此各 `code` 的 `expiresIn` 取值是固定的：

| `code` | 情境 | `expiresIn` |
|---|---|---|
| `200` | 正常（來源①：驗證器續期） | 續期後的秒數 |
| `200` | **發證成功**（來源②：登入、`refresh`） | **新 token 的完整壽命秒數** |
| `200` | **登出成功** | `null` |
| `100` | 資料不正確 | 續期後的秒數 |
| `300` | 邏輯錯誤 | 續期後的秒數 |
| `400` | 系統錯誤 | 續期後的秒數 |
| `901` | 有身分但無權限 | **續期後的秒數**（身分有效，只是這個動作不准） |
| `900` | 無有效身分 | `null` |

- 理由：**憑證驗證在整條鏈的最前面**，驗證過了就代表使用者仍在活動，後面發生什麼都不改變「他還在線上」這個事實。反過來說，若把續期綁在「處理成功」上，使用者連續填錯三次表單就會被登出——他明明一直在操作，系統卻認為他離開了，而且沒有任何錯誤訊息解釋這件事。
- `901` 特別容易被寫成不續期（直覺上「被拒絕」看起來像失敗），但那正是最不該的：使用者點到一個沒權限的功能，等於順便把自己的 session 熬短，下一次真正有權限的操作反而吃到 `900`。
- **`expiresIn: null` 的語意收斂為一句話：本次回應之後，客戶端手上沒有有效的 access token。** 三種情形：未發證的公開端點、`900`、登出成功。
  之所以要收斂成這一句，是因為前端只拿得到這個欄位——它必須能從 `null` 推出一件確定的事。前端收到 `null` **不得**據此判定 session 已失效（公開端點也回 `null`），處置一律照 `code` 走（前端規範 §3.6、§3.7）。
- `exp` 與 `expiresIn` 同步：**兩個來源都必須同時算出兩個欄位**，禁止只更新其中一個。兩者不同步時，log 上的截止時刻與實際被登出的時刻對不上，而追查登出問題時唯一的線索就是 log——線索本身在騙人，等於沒有線索。
- ✅（測試：每個端點的 `901` 案例必須斷言 `expiresIn` 為非 `null` 的正數，`900` 案例必須斷言 `expiresIn` 為 `null`；發證端點的成功案例必須斷言 `expiresIn` 等於設定的完整壽命秒數，登出成功案例必須斷言為 `null`）

#### `errors` 結構

```json
"errors": [
  { "code": "<領域>.balance-insufficient", "msg": "剩餘額度不足", "data": { "field": "days", "remaining": 3, "requested": 5 } }
]
```

| 欄位 | 型別 | 說明 |
|---|---|---|
| `code` | string | 錯誤碼，**語意化命名** |
| `msg` | string | 錯誤訊息 |
| `data` | object | **map/object，不是 list**；慣例帶 `field` 指出出錯位置（**路徑式，見下**），其餘為該錯誤的具體細節 |

**`errors[].data.field` 一律使用路徑式（dot-path），禁止扁平欄位名。**

- 規則：從 request body 根層寫到出錯的那一格，**陣列以索引表示，0 起算**：`items.2.startTime`、`detail.startDate`、`items.0.code`。單層欄位自然退化成 `days` 這種形式，不是例外。
- 理由：本系統多處畫面會出現**「同一種欄位在陣列中重複出現」**的結構。在這些畫面上，`field: "startTime"` 無法回答「是哪一筆的 `startTime`」，前端唯一能做的就是退化成全域提示，等於這個 `field` 白給；使用者面對一張有五列的表格，只被告知「時間格式錯誤」，得自己逐列比對。帶了索引，前端才能定位到**該列該格**並捲過去。
- **後端在驗證迴圈中必須把索引帶進錯誤物件，禁止只丟欄位名。** 這條特別容易違反，因為在迴圈裡加入錯誤的當下手邊只有那一筆物件，索引要刻意從迴圈變數帶進去；漏帶不會有任何錯誤，只是前端從此定位不到。
- **`errors` 是陣列，代表它本來就該裝得下多筆。** 這是 §3.1.1「service 收集錯誤而不是拋例外」的直接後果：迴圈可以整個跑完，五列裡錯了三列就回三筆，使用者一次看到全部。反過來說，若 service 在第一筆不符時就中斷，這個陣列**永遠只會有一個元素**，前端為多筆錯誤寫的定位與捲動邏輯（前端規範 §6.3）也就永遠用不到。
- 需要指出**衝突對象**時，在 `data` 內另外帶其他路徑（例如 `conflictWith: "items.1"`），不要把兩個位置塞進同一個 `field` 字串。
- 完整範例（陣列中第 3 筆的時間區間與第 2 筆重疊）：

```json
"errors": [
  {
    "code": "<領域>.time-range-overlap",
    "msg": "時間區間重疊",
    "data": { "field": "items.2.startTime", "conflictWith": "items.1" }
  }
]
```

- 前端的對應處理（依 dot-path 定位到該列該格，找不到才退全域提示）見前端規範 §6.3。
- 錯誤碼命名 `<領域>.<原因>`，領域用單數名詞、原因用 kebab-case：`auth.invalid-credentials`、`<領域>.already-exists`、`<領域>.period-locked`、`<領域>.balance-insufficient`。**這就是 `errors[].code` 的取值來源**，兩者是同一組字彙、同一份集中定義。
  **錯誤碼的「領域」與路徑的段名是兩套獨立的命名空間**，不必也不應強行對齊：路徑的前兩段必須等於目錄名（§1.1），錯誤碼的領域則是**單數的功能分類**，因此 `auth.invalid-credentials` 是正確的寫法，即使路徑上不存在 `/auth/...`（登入端點是 `POST /sessions/main/login`）。兩者混淆的後果是反過來的：為了配合 `sessions` 而把錯誤碼寫成 `sessions.invalid-credentials`，會讓「憑證錯誤」這個跨端點的語意被綁死在單一個目錄上，改密碼端點（在另一個大目錄底下）要回同一種錯時就無碼可用。
  **禁止編碼式命名**（`SHIP001`、`E4012` 這種）：編碼式要查表才知道是什麼錯，而那張表一定會過期；語意化命名讓 log、告警、前端分支都能一眼看懂。 ✅（型別：錯誤碼集中為 `as const` 聯集型別，加入錯誤時只能用聯集內的值）
- 前端據 `code` 決定行為（focus 欄位、顯示對應文案），據 `msg` 只做 fallback。訊息文案一改前端就壞，是因為有人拿 `msg` 做判斷。
- **`errors` 僅在 `code='300'` 時提供**，其餘 `code` 一律是空陣列。 ✅（型別：envelope 型別以 `code` 判別聯集，`code !== '300'` 時 `errors` 型別為 `[]`）
- **`code='100'` 完全不提供 `errors`。** 這條後人一定會想「順手加一下比較方便」，所以理由寫在這裡：**API 契約已經定義好，送錯代表呼叫端沒照契約來，那是開發期就該發現的問題，不是執行期要引導使用者的問題。** 使用者層級的輸入問題會走 422 → `300`，那裡才有 `errors`。
- **每支端點的 response 定義必須宣告自己會吐出哪些 `errors[].code`，且未宣告者不得在執行期出現**（§1.8.3）。沒宣告的話，前端要處理哪幾種業務錯誤只能靠問人或試出來，而新增一個錯誤碼也不會有任何地方變紅。

### 1.4 List 端點：分頁、排序、篩選

**Request**：基底三欄（§1.3）＋ 搜尋條件平鋪 ＋ `perPage`／`currentPage` 平鋪 ＋ `sort` 物件。

```json
{
  "rqTS": "2026-04-14T14:30:00+08:00",
  "cmd": "<大目錄>.<次目錄>.list",
  "locale": "zh-TW",
  "keyword": "王",
  "parentId": "...",
  "perPage": 20,
  "currentPage": 1,
  "sort": { "field": "createdAt", "order": "desc" }
}
```

- `perPage`：**必填，預設 20**，上限 100。
- `currentPage`：**必填，預設 1**（1 起算）。
- **禁止**在不同端點改叫 `page`、`pageNo`、`size`、`limit`、`offset`。
- `sort`：物件 `{ "field": "createdAt", "order": "asc" | "desc" }`，**不支援多欄排序**。排序欄位**必須白名單**，直接把字串接進 SQL 等於開放 SQL injection 與全表掃描。
- 篩選參數用扁平 camelCase（`status`、`<關聯>Id`、`dateFrom`、`dateTo`、`yearMonth` 這類）。日期區間一律 `xxxFrom` / `xxxTo`（含端點）。
- **列表端點一律分頁，禁止無上限查詢。** 不設限的按月查詢在中型客戶就是數萬列，一次撈完會打爆記憶體並拖垮連線池。

**Response**：`data` 收一層 pagination 結構，**實際清單在 `data.data`**。

```json
"data": {
  "search":     { "keyword": "王", "parentId": "..." },
  "sort":       { "field": "createdAt", "order": "desc" },
  "pagination": { "currentPage": 1, "perPage": 20, "totalCount": 137 },
  "data":       [ ... ]
}
```

- **不提供總頁數**，前端由 `totalCount / perPage` 自行計算。
  理由：兩個數字並存時，只要有一邊算錯（改了 `perPage` 預設值、加了篩選卻沒同步重算），就會出現「共 137 筆、14 頁」但實際只有 13 頁可點的狀況——而且**兩個數字都來自後端，前端沒有任何依據判斷該信哪一個**。只回 `totalCount`，總頁數就只有一個算法、一個出處。
- **`search` 與 `sort` 必須原樣回聲。** 這不是多餘欄位，拿掉會直接產生 race condition：
  使用者快速切換篩選條件時會連續送出多次查詢，而**回應到達順序不保證**——第二次查詢可能比第一次先回來。回聲值讓前端能比對「這包回應是不是我現在畫面上這組條件的結果」，不是的就丟掉。沒有它的話，較慢的舊回應會蓋掉較新的回應，畫面上的資料與篩選條件對不上，而且**沒有任何錯誤**：使用者選了 A 條件卻看到一整片 B 條件的資料，只會認為系統壞了。前端側的規則見前端規範 §7.3。
- **條件變更必須回到第 1 頁**由前端負責；後端在 `currentPage` 超出範圍時回空陣列與正確的 `pagination`，**不得回 404**（404 是端點不存在，見 §1.3）。

### 1.5 所有參數一律走 request body

**先定義本節的定義域：一支端點收到的輸入分成兩類，本節的「參數」只指第一類。** 不先定義的話，「所有參數一律走 body，沒有例外」與「refresh token 走 cookie」（§5.4.3）在字面上就是**兩條各自宣稱沒有例外、卻互相矛盾的規則**，實作者只能違反其中一條，而規範上看不出來哪一條該讓（通用規範 §7.6）。

| 類別 | 定義 | 通道 | 誰驗證 |
|---|---|---|---|
| **業務參數** | 呼叫端用來描述「**這次要做什麼**」的值：識別碼、篩選條件、分頁、排序、要寫入的內容 | **一律走 request body，沒有例外**（下方原規則） | 端點的 body schema（§2） |
| **憑證** | 用來證明「**你是誰**」的值。**定義域是列舉的、封閉的：由伺服器簽發、代表一個已成立身分的票——access token 與 refresh token，就這兩種** | **一律不走 body。** 通道與位置由端點所在的**認證群組**規定（§1.9.1） | 該群組的**憑證驗證器**（§1.9.1） |

- **判準一句話：拿掉它之後，這支端點還知不知道「要做什麼」？** 不知道 → 業務參數；只是不知道「你是誰」 → 憑證。
  這個判準是機械可算的，而且它把邊界畫在正確的地方：`POST /leaves/main/approve` 拿掉 `leaveId` 就不知道要核准哪一筆（業務參數）；拿掉 access token 它仍然知道「要核准 `leaveId` 這一筆」，只是不知道是誰要核准（憑證）。
- **登入端點的公司代號、帳號、密碼三者是「業務參數」，走 body，不是憑證。** 這一點必須明寫，否則「證明你是誰的值」這個描述會把密碼一起吸進憑證那一類，於是登入端點又寫不出來了（通用規範 §7.6：定義域必須可判定、補集必須可枚舉）。
  界線是**「已成立的身分」與「用來成立身分的材料」**：access token／refresh token 是伺服器簽發的、代表身分**已經成立**；公司代號／帳號／密碼是使用者提交、**待伺服器驗證**的材料——它們正是登入這個動作**要處理的內容**（拿掉密碼，登入端點就不知道要驗什麼）。**憑證這一類是封閉列舉的兩項，補集就是其餘一切**，因此不會有第三個東西「不小心也算憑證」。
- **端點不驗證憑證、不宣告憑證、也不讀取憑證。** 端點只從 context 取用**已驗證的身分**（由驗證器放進去的 `userId`／`companyId`／權限碼）。 ✅（自製掃描腳本：`modules/**` 底下禁止讀取 cookie／header／`Authorization`——出現 `cookie`／`headers`／`getCookie` 之類的讀取即失敗；掃描器須自我檢查掃到的檔案數 > 0）
- **憑證不進 body schema、不進 OpenAPI 的 `parameters`、不進端點清單快照的欄位列。** 理由是同一句話：**它不是端點的契約，是群組的契約**。同一支端點搬到另一個認證群組，它的憑證就換了一種，而端點的 request／response 一個字都不必改——會跟著改的東西才屬於端點的契約。
  §1.7「出現任何 `parameters` 即違反 §1.1」**原文不改**：憑證在 OpenAPI 上以 **security scheme** 表達（掛在群組上），不落在 `parameters` 之下，兩條規則沒有重疊。
- **憑證在契約上不是消失，是換一個地方記**：端點清單快照增記一欄「所屬認證群組」（§1.7）——這正是原本 cookie 這個輸入在契約上缺席的補回。

以下是**業務參數**的規則：

- **所有參數一律放 request body，沒有例外。** 識別碼（`id`）、篩選條件、分頁、排序——全部平鋪在 body 裡。**路徑上不會有參數**（§1.1），因此不存在「這個參數該放哪」的判斷。
  這條與 §1.1「路徑不得帶任何參數」是同一件事的兩面：路徑既然固定是 `/<大目錄>/<次目錄>/<動作>` 三段純字面值，能承載參數的地方就只剩 body 一處。好處是**每支端點的輸入永遠只有一包**，schema 只有 `body` 一份（§2），前端的包裝函式也只有一種形狀。
- **禁止使用 query string，也禁止使用路徑參數。** 路由不得宣告 `query` schema，也不得宣告 `params` schema。 ✅（自製掃描腳本：路由定義中出現 `query:` 或 `params:` schema、或路徑字串含 `:` / `{` 即失敗）
  理由（除了 envelope 之外的一條）：query 會被寫進 access log、反向代理 log 與瀏覽器歷史，把事由文字、姓名關鍵字這類個資留在一堆沒人管保存期限的地方。
- **因為不使用 query，query 的字串型別陷阱在本專案不存在**：`?page=abc` 變 `NaN`、`?flag=false` 被 `Boolean()` 判成 `true` 這類問題沒有發生的餘地，也**不需要 `t.Numeric()`／`t.BooleanString()` 這類轉型 schema**。body 是 JSON，`20` 就是 number、`false` 就是 boolean，schema 只做驗證不做轉型。

```ts
// ✅ 正確：JSON body，型別即是型別，schema 只驗證不轉型
body: t.Object({
  ...BaseRequest,                                    // rqTS / cmd / locale
  keyword: t.Optional(t.String({ maxLength: 50 })),
  includeExpired: t.Optional(t.Boolean()),           // 真正的 boolean
  perPage: t.Integer({ minimum: 1, maximum: 100, default: 20 }),
  currentPage: t.Integer({ minimum: 1, default: 1 }),
})
// ❌ 錯誤：本專案不使用 query string
query: t.Object({ page: t.Numeric(), includeExpired: t.BooleanString() })
```

### 1.6 版本策略與不相容變更

- **本入口（§1.0）的 API 路徑不帶版本前綴。** 禁止 `/api/v1/...`、`/v2/...` 這類片段，`/<大目錄>/<次目錄>/<動作>` 就是最終路徑（路徑恆為三段，§1.1）。
  理由：本入口的前後端同 repo、同一批人同時發版，沒有「舊版客戶端長期存活」的情境（**這個前提正是「入口」的屬性，不是全系統的屬性**——換一種入口，呼叫者可能根本不歸我們部署，屆時的版本策略由那個入口自己定，§1.0.2）。版本前綴在這種情況下不是相容性保障，只是每個端點多一段永遠不會遞增的字串；真要遞增時得複製整組路由、測試與權限設定，維護成本直接翻倍。
- 少了版本號這道護欄，**相容性完全靠變更紀律維持**，因此以下分類必須嚴格套用。

**破壞性變更**（符合任一即是）：

- 刪除 request／response 欄位；
- 更改欄位名稱；
- 更改欄位型別（含 `number` ↔ `string`、單筆 ↔ 陣列）；
- 把選填欄位改為必填；
- 縮小允許值範圍（列舉值變少、`maxLength` 變小、數值上下限收窄、格式變嚴）；
- 改變既有 `errors[].code` 的語意，或改變某情境對應的 HTTP status ／ envelope `code`（§1.3 映射）；
- 更改路徑（連帶就是更改 `cmd`，§1.3）。HTTP method 恆為 `POST`（§1.2），不會是變更的來源。

**相容變更**：新增選填欄位、在 response 新增欄位、新增端點、新增列舉值且舊值仍完全支援、放寬既有限制。

- **破壞性變更必須兩步走，禁止一次到位：**
  1. 新舊兩種形式**同時支援**，舊的在 schema 標記 `deprecated`，並在程式碼註明預定移除的條件；
  2. 確認前端全部改用新形式**且已部署**；
  3. 才在獨立的 PR 中移除舊形式。
  理由：前後端不是原子部署，中間一定有時間差。一次到位的破壞性變更，會讓**部署順序決定系統壞多久**——後端先上，所有還在用舊欄位的前端頁面立刻吃 422 或顯示 `undefined`；前端先上，新欄位後端還不認識，一樣壞。差別只在壞的是哪一邊，而不在會不會壞。兩步走則兩種部署順序都是安全的，回退也安全。
- 移除舊形式的 PR **必須在描述指出對應的前端變更與其部署時間**，否則無從判斷第 2 步是否真的完成，「暫時保留」會變成永久保留。

### 1.7 API 契約：OpenAPI，由後端程式碼產生

- **前端與後端即使放在同一個 repo，也是兩個獨立部署的系統，溝通只能透過 HTTP API。** 因此「API 長什麼樣」必須有一份機器可讀、雙方都認的定義，而不是靠口頭或靠讀對方的程式碼。前端禁止 import 後端的任何型別或程式碼（前端規範 §3.5），能跨越這條界線的只有下述產生物。
- **路由宣告的 schema（§2）是契約的唯一真相**；OpenAPI 文件一律**由後端程式碼產生**，禁止另外手寫或手動維護一份 spec 檔。
  理由：手寫的 spec 是第二份真相，跟程式碼必定漂移；漂移之後前端拿到的型別是錯的，而編譯照樣通過，錯誤延到執行期才出現在離成因最遠的地方。
- **每個對外端點都必須宣告完整的 request 與 response schema（§2 第一條），這是整條契約鏈的單點失效。**
  理由：少宣告一個 response schema，產生出來的 OpenAPI 在那個端點就是個空洞（`{}` 或 `unknown`）。前端拿不到型別，唯一的出路是自己手寫一份 interface——於是前端規範 §3.2「禁止手寫 DTO」被迫破例，契約單一來源在那一刻就失效了，而且是從最不起眼的地方失效。 ✅（自製掃描腳本：同 §2，缺任一項即失敗）
- **每個端點在 OpenAPI 上只有 `requestBody`，沒有 `parameters`。** 路徑不帶參數、不用 query（§1.1、§1.5），因此 `parameters` 一律是空的——出現任何 `parameters` 項目就代表有人違反了 §1.1。所有端點都是 `post`，路徑本身沒有 `{}` 模板片段。
  這對前端產生物的意義是：產生出來的 client 函式**每支都只有一個參數**（那包 body），不會有「第一個參數是 id、第二個是 options」這種因端點而異的簽章。
- **envelope 在 OpenAPI 上的表達方式（§1.3、§1.4）：**
  - request：`requestBody` 為 `allOf` [ `BaseRequest`（平鋪的 `rqTS`／`cmd`／`locale`）, 端點自己的平鋪欄位 ]
  - response：`allOf` [ `BaseResponse`, `{ data: 端點的 data schema }` ]
  - list response：`data` 以 `PaginationResponse<T>` 的組合表達（`search`／`sort`／`pagination`／`data`）
  - **實作上這是一個 `envelope(dataSchema)` 包裝函式，不是類別繼承。** 我們是 TypeScript／Elysia，不是 PHP：不要做 `BaseResponse` 基底類別再讓每個端點的 response 去 extends，也不要為每支端點手寫一個 `XxxResponse` 型別。 ✅（自製掃描腳本：路由的 `response` schema 必須是 `envelope(...)` 的呼叫結果，直接寫 `t.Object({ code: ... })` 即失敗）
    理由：繼承會讓每支端點多一個只為了掛 `data` 而存在的型別名稱，改 envelope 時要改的是 N 個子類別而不是一個函式；而包裝函式讓 `data` 的型別自然被泛型帶出去，前端產生的型別直接就是收窄過的形狀。
- **產生流程：**
  - 指令 `bun run gen:api`：載入 Elysia app 定義 → 輸出 `openapi.json` → 由該檔產生前端型別與 API client。
  - **該指令必須能在後端服務未啟動、資料庫未連線的情況下執行**（只 import app 定義，不 `listen`、不連 DB、不跑 migration）。 ✅（CI：在沒有 DB service 的 job 中執行 `bun run gen:api`）
    理由：前端開發者與 CI 只是要一份型別。若必須先起後端與 MariaDB 才能產生，這個指令就會在新人的第一天失敗，結果是「跑不起來，先沿用舊型別」——契約單一來源等於沒有。
  - **產生物（`openapi.json`、前端型別與 client）不進版控**，一律列入 `.gitignore`，需要時重跑 `bun run gen:api` 取得；**禁止手動修改產生物**。
    理由：產生物進版控後必然出現「忘了重跑」的髒 diff，review 時也分不出哪些行是人改的、哪些是機器產的。
- **端點清單快照測試（必須有）**：把所有已註冊路由的 `path`、宣告的 `cmd` 值、**所屬認證群組**與 request body 的必填欄位，以穩定排序序列化成快照檔，**快照檔進版控**；端點有增刪改時測試變紅，必須有人明確更新快照。 ✅（測試：端點清單快照比對）
  **「所屬認證群組」這一欄是憑證在契約上的位置**（§1.5）：憑證不進 body schema、不進 `parameters`，若快照也不記，這支端點「需要什麼憑證、從哪裡收」就**在契約上完全缺席**——搬動一支端點的認證群組（例如把一支原本要驗身分的端點移進公開群組）在 PR diff 上會是零行變更，而那正是最需要被看見的一種變更。記了這一欄，它就是快照上的一行紅綠對照。
  method 不必記錄，因為它恆為 `POST`（§1.2）——記一欄永遠相同的值只會讓快照變大、diff 變吵。**`path` 與 `cmd` 兩欄都要記**，雖然後者可由前者推導（§1.3）：快照的用途是讓契約變更出現在 PR diff 裡，兩欄並列時「路徑改了但 `cmd` 沒改」在快照上就是一行紅綠不對稱，reviewer 一眼看得到，不必等 CI 的一致性檢查。
  理由：code-first 的 spec 是產生物、不進版控，於是**對外契約的變更不會出現在 PR diff 裡**——改一行 schema 就悄悄改了 API，reviewer 什麼也看不到。這正是拿掉版本前綴（§1.6）之後最需要補的洞。快照檔把契約變更重新拉回 diff：路徑改名、欄位從選填變必填、端點被刪掉，都會在 PR 中變成一段紅綠對照，逼出「這是不是破壞性變更、有沒有走兩步走」這個問題。這是替代把關機制，不是加分項。

### 1.8 Response envelope 怎麼產出（唯一入口與分層責任）

§1.3 規定 envelope **長什麼樣**，這一節規定 envelope **由誰、在哪裡產出**。兩件事都要規定，因為格式定得再清楚，只要每個開發者各自手工組那包 JSON，形狀還是會長歪——而且是各歪各的。

#### 1.8.0 一次請求的完整路徑

先把整條路走一遍，後面每一小節都是在講其中一步的規則：

```text
① request body（一份 JSON）
      ▼
② **該端點所在認證群組的憑證驗證器**（§1.9.1）：憑證有效即**續期**（§1.3 來源①）並把已驗證身分放進 context，無效則**就地**回 `900`（不進 handler、不進 service）
      ▼
③ 路由：body schema 驗證（§2；沒有 params／query 可驗，§1.5）——格式與範圍不符即 **400／`code='100'` 且不帶 `errors`**（§1.3），不會進到下一步
      ▼
④ 端點 handler：把驗證後的輸入轉成 service 的輸入型別，呼叫 service
      ▼
⑤ service／domain：只做業務邏輯。**業務規則不符時累積錯誤、不中斷**，全部檢查完成後回傳成功結果或失敗結果（§3.1.1）
      ▼
⑥ 端點 handler：成功則以映射函式把業務資料收成本端點的 `data` 形狀（§2「禁止直接回 Drizzle row」）
      ▼
⑦ envelope 產生函式：包成 envelope，填 `code`／`msg`／`errors`／`data`
   （失敗路徑：邊界層的錯誤映射先把 service 回傳的**整包錯誤集合**映射成 HTTP status ＋ `code` ＋ `errors[]`，再進同一個產生函式；
    真正的意外例外則由統一 error handler 映射成 500 ＋ `code='400'`，同樣進這個產生函式）
      ▼
⑧ 出口層：補上 `rspTS`／`cmd`／`locale`／`expiresIn`／`exp`
      ▼
⑨ 回應
```

**②在③之前，是 §1.3 續期規則的結構性保證**：續期發生在驗證通過的當下，那時候還不知道 body 對不對、資料找不找得到、有沒有權限，所以「續期」與「處理結果」在程式結構上就不可能耦合。這也是為什麼 `100`／`300`／`400`／`901` 全都帶續期後的秒數——它們都是②之後才發生的事。

**②也是這條路徑上唯一會產出 `900` 的一步**（§1.3）。公開群組的端點同樣經過②，只是那個群組的驗證器是「不驗」——**它不是被跳過，是被明確指定為不需要憑證**（§1.9.1、§1.9.2）。而**發證端點**（登入、`refresh`）落在②之後：它們在④～⑥觸發發證元件簽出新票（§1.3 來源②），本身不經過續期。

**三種形狀不可混用**，中間的轉換是刻意的邊界，不是多餘的搬運：

| 形狀 | 用途 | 出現在哪 |
|---|---|---|
| 驗證後的 request 型別 | HTTP 入口 | 端點 handler 開頭 |
| service／domain 的輸入與輸出型別 | 跨層傳遞 | service ↔ domain ↔ repository |
| 端點的 `data` 型別 | HTTP 出口 | 端點 handler 結尾 |

- **禁止把驗證後的 request 型別直接丟進 domain**，也**禁止把 repository／service 的回傳值直接指派給 `data`**。理由與 §2「禁止 `response` 直接回傳 Drizzle 的 row 物件」同源：一旦兩端共用同一個型別，資料表加一個欄位就自動出現在 API 上，而且沒有任何一行程式碼會改變。

#### 1.8.1 唯一產出入口

- **所有回應必須經由統一的 envelope 產生函式產出**（§1.7 的 `envelope(dataSchema)` 及其執行期對應物），**禁止在 handler 或 routes 內以物件字面值手工組 envelope**。handler 只回傳業務資料，由產生函式包成 envelope。 ✅（自製掃描腳本：路由的回傳值必須是 envelope 產生函式的產物；**`*.handler.ts` 與 `*.routes.ts` 兩種檔案**中皆禁止出現含 `code:`／`rspTS:`／`expiresIn:`／`exp:` 的物件字面值）
  **掃描範圍必須含 `*.routes.ts`，這點容易漏。** routes 與 handler 是兩個檔案（§0.1），只掃 handler 的話，**直接手刻在 `*.routes.ts` 裡的 envelope 不會被擋**——而那正是最容易發生的地方：一支「順手回個成功就好」的簡單端點，最可能被寫在路由註冊的當場，連 handler 都不經過。
  理由：手工組的 envelope 會**漏欄位**、會**拼錯欄位名**、會**忘記在錯誤路徑上也包一層**，而這三件事**都不會有任何編譯錯誤**——TypeScript 只知道你回了一個物件，少一個 `locale`、把 `rspTS` 打成 `rspTs`，型別檢查照樣過；測試若只斷言 `data` 的內容，也照樣綠。最後是前端拿到形狀不對的回應才發現，而那時離成因已經很遠，且問題會以「某一支端點的統一處理失效」這種零星形式出現，看起來像前端的 bug。

```ts
// ✅ 正確：handler 只回業務資料，envelope 由產生函式與出口層負責
return ok(toListView(rows, pagination))
// ❌ 錯誤：手工組。少了 locale、rspTS 拼錯，全部靜默通過
return { code: '200', msg: '', errors: [], data: rows, rspTs: now(), expiresIn: 3600 }
```

- **envelope 產生之後禁止再改它的欄位**（不得取得產生結果再賦值 `code`／`errors`／`expiresIn`）。
  理由：`code`、HTTP status 與 `errors` 是由同一次映射一起決定的（§1.3 映射表）。事後只改其中一個，三者就**脫鉤**——出現 HTTP 200 配 `code='300'`、或 `code='300'` 卻沒有 `errors` 這種前端無法處置的組合，而型別上完全合法。要改就回頭改 service 收集到的那筆錯誤（§3.1.1）或映射表。
- **list 端點的 `search`／`sort` 回聲（§1.4）必須由共用的 list 組裝函式從 request 帶回，禁止各端點自行填。**
  理由：這兩段**是最常被忘記填的東西**——留成空物件時後端不會錯、測試若只斷言 `data.data` 也不會紅，但前端的 race condition 防護（前端規範 §7.3）當場失效，而且是靜默失效。交給共用函式，就沒有「忘記」這個選項。

#### 1.8.2 分層責任：誰負責填哪些欄位

| 層 | 負責 | 禁止 |
|---|---|---|
| domain／service 層 | 回傳成功結果（業務資料），或回傳失敗結果（**收集到的錯誤集合**，每筆帶自己的具名錯誤分組與 `errors[].code`，§3.1.1） | **不得碰 envelope 的任何欄位**；不得出現 HTTP 狀態碼字面值與 `WebFlowCode`（§3.1.1）；**不得以拋例外表達業務拒絕**（§3.1.1） |
| 認證群組的**憑證驗證器**（§1.9.1） | 驗證憑證並把已驗證身分放進 context；有效即透過生命週期元件續期（§1.3 來源①） | 不得因後續處理結果而改變是否續期；**`900` 由它就地產出，不交給下游** |
| **access token 生命週期元件**（§1.3） | 算出 `expiresIn`／`exp` 並寫進請求上下文（續期與發證共用同一份實作） | 不得有第二份實作，也不得由呼叫者自行帶入秒數 |
| 端點 handler（路由層） | 宣告本端點的 `data` schema（收窄後的型別，§2）、宣告本端點可能吐出的 `errors[].code` 清單（§1.8.3） | 不得自行設定 `code`／`rspTS`／`cmd`／`locale`／`expiresIn`／`exp`；不得自行組 `errors` |
| 出口層（統一 middleware） | 補上 `rspTS`／`cmd`／`locale`／`expiresIn`／`exp`（§1.3） | — |
| 邊界層錯誤映射（handler 之後、envelope 之前） | 把 service 回傳的**錯誤集合整包**映射成 HTTP status ＋ envelope `code` ＋ `errors[]`（依各筆的錯誤分組與 §1.3 映射表） | 不得自行判斷業務規則成不成立，也不得只取第一筆錯誤 |
| 統一 error handler | 只處理**未攔截的例外**（意外），映射成 500 ＋ `code='400'` 並記錄堆疊（§3.1.2） | 不得用來表達業務拒絕 |

- 這張表的重點是**每個欄位都只有一個地方會寫它**。`rspTS` 只有出口層寫、`errors` 只有邊界層錯誤映射寫、`data` 只有 handler 寫——於是「這個欄位為什麼是這個值」永遠只有一個地方要看，改 envelope 也只要改一處。`expiresIn`／`exp` 同樣如此：**envelope 上的那兩格只有出口層寫**，值則只有生命週期元件算得出來（它的兩個觸發時機寫進的是同一格請求上下文，不是兩格，§1.3）。反過來，只要有一支 handler 自己填了 `code`，出口層與 error handler 的行為就不再是全站一致的，而**沒有任何方式能從外部看出哪幾支端點自己填了**。
- service／domain 不得碰 envelope 的理由與 §3.1 相同，也就是 §1.0.1 那條：**envelope 是「Web 前端」這個入口的東西**，同一段業務邏輯被別的入口呼叫時，那些情境根本沒有這包 envelope。
- **訊息也照同一條規則切：「哪一則訊息」與「哪一種語言」是兩個決定，分屬兩層。**

  | 層 | 決定 | 產物 |
  |---|---|---|
  | service／`*.errors.ts` | **哪一則訊息** | 訊息 **key**（不是字串） |
  | 邊界層錯誤映射 | 把 key 放進 envelope 的 `msg` 與 `errors[].msg` | 仍然是 key |
  | **出口層** | **哪一種語言** | 依 `locale` 把 key 換成該語系的字串 |

  **翻譯只發生在出口層，那是全站唯一一處。** 理由是它就是補 `locale` 的那一層——**整條鏈上只有它知道 `locale`**，翻譯放在任何更早的一層都得把語系再傳一手。往回推的後果是實的：service 一旦產出翻譯後的字串，同一段業務規則被第二種入口（設備、對外 API）呼叫時，那個入口的語系**再也蓋不掉**業務層當初挑的那一種（§1.0.1）；而 `errors[].msg` 若在邊界層就翻好，「同一個錯誤碼在不同端點講不同話」就沒有任何東西擋得住。
  **訊息 key 與錯誤碼刻意是同一個字串**（`auth.invalid-credentials`）：兩者各自維護一份對照時，新增錯誤碼卻忘了加訊息不會有任何地方變紅，使用者看到的是一句空訊息，或更糟——畫面上直接出現那個 key。同一份清單就沒有「只加了一邊」這個選項。 ✅（型別：訊息目錄的 key 即 §1.3 的錯誤碼聯集，`DomainError.msg` 只收 key 不收裸字串）

#### 1.8.3 每支端點必須宣告的內容

**為什麼是「宣告」而不是「寫出來就好」：宣告本身就是契約，端點的業務邏輯一行都還沒寫，`bun run gen:api` 也能產出完整的 OpenAPI。** 這是本節所有要求的來源——把 request／response 定義成獨立於實作的宣告，就得到三件事：

- **前端可以平行開工。** 後端只要先把 `body` schema、`data` schema 與錯誤碼清單宣告好（handler 內容還是 `TODO`），前端就能產生型別與 client、接假資料把畫面做完，不必等後端實作完成，也不必自己手寫 DTO（前端規範 §3.2）。
- **契約先於實作，而不是從實作反推。** 先寫 handler 再回頭「補一下 schema」，補出來的必然是實作剛好回了什麼——包含不小心多回的欄位。先宣告，形狀是被設計出來的，實作只能去符合它。
- **schema 缺漏當場就看得見。** 沒宣告的端點在產生出來的 OpenAPI 上就是個空洞（§1.7），這比在 code review 裡逐支端點檢查可靠。

因此每支端點**必須**宣告：

- **該端點的 `data` schema**（收窄後的型別，不得是 `unknown` 或 Drizzle row，見 §2）。查無資料時 `data` 為 `null`，因此型別是 `T | null`（§1.3）。
- **該端點可能吐出的 `errors[].code` 清單。** 這份清單會進 OpenAPI，讓前端知道要準備哪些文案與處置分支。**未宣告的 error code 不得在執行期出現。** ✅（自製掃描腳本／測試：測試中斷言到的 `errors[].code` 必須在該端點的宣告清單內，不在即失敗）
  理由：沒有這份清單時，前端要處理哪幾種業務錯誤只能靠問人或試出來，而**新增一個錯誤碼不會讓任何地方變紅**——後端加了一個新的業務錯誤碼，前端沒有對應文案，使用者看到的是後端那句給工程師看的 `msg`，或者更糟，什麼都沒看到。把清單釘進契約，新增錯誤碼就必須同時更新宣告，前端也就會在型別上看見它。
- **不會吐出任何業務錯誤的端點，也必須宣告一份空清單**，不可省略不寫。
  理由：省略時「這支端點沒有業務錯誤」與「有人忘了宣告」在契約上長得一模一樣，前端只能一律當作「可能有沒寫出來的錯誤」而退回保守處理，這份清單的價值就沒了。明確寫空清單，是一個可被 review 的決定。
- **每個錯誤碼在宣告時必須同時標明它對應的 HTTP status ＋ envelope `code`**（§1.3 映射表），且**一個錯誤碼只能對應一種**；同一個語意在不同情境要回不同 status 時，**拆成兩個錯誤碼**，不要讓同一個碼有兩種結果。
  理由：前端的處置是綁在 `errors[].code` 上的（前端規範 §3.6、§6.3）。同一個碼有時回 409、有時回 422，前端就無法只憑碼決定要「就地標欄位」還是「請使用者重新載入」，只能兩種都寫、或退化成顯示 `msg`。
- **`data` schema 建議附範例值**（OpenAPI 的 `examples`），讓產生出來的 API 文件對前端可讀。沒有範例的 schema 只說得出型別，說不出「這個欄位長什麼樣」，前端仍然要問人。

#### 1.8.4 成功與失敗走同一個出口

- **錯誤回應同樣經過 envelope 產生函式與出口層，不是另一條路。** 這對**兩種失敗**都成立：service 收集到的業務錯誤（走邊界層錯誤映射）與未攔截的意外例外（走統一 error handler）——兩者都只決定 HTTP status、`code` 與 `errors[]`，其餘欄位一律由同一個出口層補上。
  理由：錯誤路徑另開一條出口，結果就是錯誤回應缺 `cmd`／`locale`／`expiresIn`——**前端的統一處理會剛好在錯誤路徑上失效，而錯誤路徑正是最需要它的時候**：`cmd` 沒回聲，log 追不到是哪支端點錯的；`expiresIn` 沒回，session 過期後的第一個 401 反而讓前端無法更新 deadline；`locale` 沒回，錯誤訊息的語系判斷失準。這些都只在出錯時才發作，因此平常測不到。
- ✅ 這條的落實方式就是 §1.8.1 的同一條檢查：只要 `*.handler.ts`、`*.routes.ts` 與 error handler 都沒有手工組 envelope 的物件字面值，兩條路徑就必然共用同一個出口。

### 1.9 路由檔的分組結構：入口 → 認證方式 → 端點

**路由的巢狀順序固定為兩層分組：先依入口分組，入口內再依認證方式分組，端點註冊在認證群組內。**

```text
入口群組（由 host／domain 決定是哪一個入口，§1.0）
└─ 認證群組（這一整組端點共用的驗證方式）
   └─ 端點（`POST /<大目錄>/<次目錄>/<動作>`）
```

- **最外層依入口分組**，入口由 host／domain 判定。目前只有一種入口（Web 前端，§1.0），因此實際上只有一個入口群組——**但這一層仍然要寫出來**，因為新增入口時加的就是一個同層的兄弟群組，而不是把既有群組拆開重排。（這與 §1.0.3「現在不建立多入口的目錄結構」不衝突：這裡是路由註冊的巢狀層次，不是目錄維度，它不會讓任何模組多出一層空目錄。）
- **入口內依認證方式分組**，端點註冊在認證群組內。
- **入口群組與認證群組一律在唯一的路由組裝點建立。** 模組只透過 `modules/<大目錄>/routes.ts`（§0.3）提供端點，**不建立群組、不宣告驗證方式**。 ✅（dependency-cruiser：只有路由組裝點可以 import `modules/*/routes.ts`；建立群組的 API 只允許出現在路由組裝點）
  理由：群組是**橫跨模組的**東西——同一個認證群組裡會有來自好幾個大目錄的端點。讓模組自己建群組，就會出現「兩個模組各建了一個名字不同、行為相同的群組」，而它們之後各自演化；更糟的是同一個群組被建了兩次、只有其中一次掛上驗證器，那兩批端點在程式碼上看起來一模一樣。集中在一個組裝點，「本系統有哪幾個認證群組」是一個打開檔案就看得完的清單。

#### 1.9.0 身分脈絡由誰建立（本節存在的原因）

**本規範的其餘章節都假設每支端點在一個「已建立的身分脈絡」裡執行**——手上有一張已驗證的 token、有一個 `companyId`、有一組權限碼。§1.3 的續期、§1.5 的「參數一律走 body」、§4.2 的「每次查詢必須帶 `company_id`」、§5.2 的權限碼，全部建立在這個假設上。

**但「誰負責建立那個脈絡」一直沒有被指派。** 這個缺口不是四個獨立的小問題，是同一個缺口的四個切面，而它們的共同症狀是：**照規範寫不出登入這支端點**——

| 切面 | 沒有指派時的死結 | 指派給誰（本節與相關章節） |
|---|---|---|
| `900` 從哪來 | service 要表達「憑證不可用」，但 `ErrorGroup` 沒有這個分組，加一個又違反「業務層不得知道 HTTP 狀態」 | **憑證驗證器**，就地回，service 完全不參與（§1.3、§1.9.1） |
| `expiresIn` 從哪來 | 只有「續期」一個來源，而登入端點沒有票可續，handler 又不得填這個欄位 | **生命週期元件**的第二個觸發時機「發證」（§1.3） |
| 憑證從哪進來 | 「所有參數一律走 body」與「refresh token 走 cookie」互相矛盾 | 憑證不是參數，**通道由認證群組規定**（§1.5、§1.9.1） |
| `companyId` 從哪來 | 「`companyId` 只能來自已驗證的 token」，那**第一次**的 `companyId` 從哪來 | **身分解析查詢 ＋ 發證元件**（§4.2） |

- **這不是「認證端點是特例」，本節也不開任何豁免區。** 這一點必須寫死，因為豁免區的下場是可預測的：`report`／`export`／`dashboard` 會逐一援引它（「我這支也很特殊」），而且它**撐不過第二種入口**——第二種入口有自己的憑證形狀（§1.0.2），豁免區只寫得下第一種。
  正確的形狀是**把責任指派出去**：每一項都有一個具名的元件負責、有一條檢查證明只有那個元件在做。指派完之後，登入端點不再是特例——它只是一支「落在公開群組、會觸發發證元件」的普通端點。
- **這一節就是通用規範 §7.7「不變式規則必須指名 base case 的產出者」在本系統的落地。** 上表每一列都是一條「A 只能來自 B」的不變式，而右欄就是它的 base case 產出者。

#### 1.9.1 認證方式是群組的屬性，不是端點自己宣告的

**這是本節最重要的一條：認證方式寫在群組上，端點本身不宣告任何認證方式。**

- 理由：**認證方式是橫切的**——一整組端點共用同一種驗證，它描述的是「這一批端點怎麼確認來者是誰」，不是某一支端點的個別性質。寫在每支端點上就是把同一件事抄 N 遍，而**重複的東西一定會漏掉某一支**；漏掉的那一支不會報錯、不會少一個檔案、不會讓任何測試變紅——它只是**變成不驗證身分**，而且從程式碼外觀上與其他端點毫無差別。寫在群組上，「漏抄」這個失敗模式就不存在：端點不在群組裡就註冊不進去。
- 端點檔（`*.routes.ts`）內因此看不到任何「這支要不要驗身分」的字眼；要知道一支端點的認證方式，看它落在哪個群組。

**一個認證群組 ＝（憑證來源, 憑證驗證器, 續期行為）三元組。** 三項都必須寫出來，缺一項這個群組就不算被定義：

| 元素 | 內容 | 為什麼必須明寫 |
|---|---|---|
| **憑證來源** | 憑證從哪個通道、哪個位置來（cookie 名稱、header 名稱），或**「無」**（公開群組） | 這是 §1.5 那條「憑證不走 body」的落點：端點不宣告，總得有一個地方宣告 |
| **憑證驗證器** | 驗這個群組憑證的那一個元件 | 沒指名就沒有 `900` 的產出者，也就沒有人負責建立身分脈絡（§1.9.0） |
| **續期行為** | 驗過之後續不續期（§1.3 來源①） | 公開群組不續期、access token 群組續期、`refresh` 群組不續期而是**發證**——三種行為不同，不寫出來就得靠猜 |

- **每個非公開群組必須指定恰好一個憑證驗證器。** 零個代表這組端點實際上不驗身分；兩個代表「哪一個說了算」沒有答案，而兩個驗證器的失敗處置一定會分岔。 ✅（自製掃描腳本：每個非公開群組的驗證器數必須恰好為 1，見 §1.9.2 的同一支檢查）
- **驗證失敗一律就地回應，形狀固定死：HTTP 401 ＋ `code='900'` ＋ `expiresIn: null` ＋ `errors: []`。** 不進 handler、不進 service。
  - **`900` 沒有第二個產出點**（§1.3）。 ✅（自製掃描腳本：`WebFlowCode.AuthRequired` 與字面值 `'900'` 只允許出現在憑證驗證器與 envelope 集中定義檔，出現在 `modules/**` 即失敗）
  - **`ErrorGroup` 因此維持三個值，不新增。** 「憑證不可用」永遠不是業務錯誤，service 不得表達它（§3.1.1）。
  - `errors: []` 是 §1.3 的直接後果（`errors` 只在 `code='300'` 時提供），寫在這裡是因為手刻 401 回應時最容易多塞一筆「請重新登入」進去。
- **公開群組的「驗證器」是「不驗」，這是一個明確的指定，不是留空**（§1.9.2）。差別在於：指定為不驗是一行看得見、可以被質疑的宣告；留空則與「忘了掛」逐字相同。
- **登入端點落在公開群組**——它是用來**取得**憑證的，執行時本來就沒有憑證。它與其他公開端點的唯一差別是它會觸發發證元件（§1.3 來源②），而那是端點自己的業務，不是群組的屬性。

#### 1.9.2 每支端點都必須落在某一個認證群組內

- **不得存在不屬於任何群組的端點。** ✅（自製掃描腳本：逐一展開已註冊的路由，每一條都必須可回溯到一個入口群組與一個認證群組，回溯不到即失敗；**且每個非公開認證群組必須指定恰好一個憑證驗證器**（§1.9.1），零個或兩個以上皆失敗；掃描器須自我檢查掃到的路由數 > 0）
- **公開端點必須放在一個明確命名的公開群組內**（例如一個名字就寫著「不需身分」的群組），**不能靠「沒有加驗證」表示公開**。
  理由必須寫清楚，因為這條看起來只是形式要求：**「忘了加驗證」與「刻意公開」必須長得不一樣。** 兩者長得一樣時，一個沉默的安全漏洞在程式碼上與正常程式碼**逐字相同**——沒有多一行、沒有少一行，review 看不出來，只能逐支去問當初寫的人，而問到的答案還是「應該有吧」。放進具名的公開群組之後，刻意公開是一個**看得見、可以被質疑、可以在 PR 上被要求說明理由**的宣告；忘了放則是一個會失敗的檢查。
- 基礎設施端點（`/health` 之類，§1.1 末條）不在本節適用範圍內，但**必須集中在單一檔案並附註解說明用途**——它們是被排除，不是被遺漏，而「排除」同樣要看得見。

## 2. 輸入與輸出驗證規範

- **每個對外端點都必須宣告 `body`（含基底三欄）與 `response` schema**，`response` 包含成功與各錯誤狀態碼（§1.3 映射表中該端點可能回的每一種）。**只有這兩份，沒有第三份**：不宣告 `params`（路徑不帶參數，§1.1），也不宣告 `query`（不使用 query string，§1.5）。
  少了 request schema，未驗證的字串會一路流到 SQL 與計算邏輯；少了 response schema，加密欄位、`password_hash`、他人資料會在某次 `select *` 重構後靜默外洩，而測試不會變紅。此外，schema 就是對外契約本身（§1.7），缺一項就是 OpenAPI 上的一個空洞，前端會被迫手寫型別。 ✅（自製掃描腳本：掃描所有路由註冊，缺 `body`／`response` 任一項即失敗；出現 `params`／`query` 亦失敗）
  「輸入只有一份 schema」不只是少打幾行字：識別碼放路徑時，同一支端點的輸入會被拆成 `params` 與 `body` 兩份宣告，**必填性、長度限制、共用型別要各自維護一次**，而兩邊漂移不會有任何編譯錯誤——`params.id` 沒套 `Uuid`、`body.id` 套了，於是同一種 id 在不同端點的驗證強度不同，且沒有任何地方看得出來。
- **禁止 `response` 直接回傳 Drizzle 的 row 物件。** 必須經過明確的映射函式挑選欄位。
  資料表加一個欄位就自動出現在 API 上，是個資外洩最常見的路徑。
- **共用欄位型別必須集中定義，禁止就地重寫。** 至少包含：`Uuid`、`IsoDate`（`YYYY-MM-DD`）、`TaipeiDateTime`（`YYYY-MM-DD HH:mm:ss`，不帶時區標記，見 §6.1）、`TransportTS`（ISO 8601 帶時區偏移，僅供 `rqTS`／`rspTS`，見 §6.1）、`Reason`（原因欄位）、`Money`、`Minutes`、`YearMonth`、`BaseRequest`（`rqTS`／`cmd`／`locale`）、`PageRequest`（`perPage`／`currentPage`）、`SortRequest`（`{ field, order }`）、`PaginationResponse`（`search`／`sort`／`pagination`／`data`）。
  理由：同一個「原因」欄位在 A 端點寫 `maxLength: 500`、在 B 端點寫 `maxLength: 200`、在 C 端點忘了寫上限，結果是前端表單限制與後端不一致——使用者在某個畫面填得下的字數，在另一個畫面送出後被 422 退回；更糟的是沒有上限的那個端點，一段 10MB 的字串就能塞爆 `text` 欄位與稽核紀錄。 ✅（自製掃描腳本：路由檔中出現行內 `t.String({ maxLength: ... })` 而非引用共用型別即警告）

```ts
// ✅ 正確：共用型別，一處修改全域生效
body: t.Object({ requestId: Uuid, workDate: IsoDate, reason: Reason })
// ❌ 錯誤：就地重寫，長度限制與別的端點不一致
body: t.Object({ requestId: t.String(), workDate: t.String(), reason: t.String({ maxLength: 200 }) })
```

- 固定代碼欄位（`*_code`、`*_type` 這類）**必須用聯集字面值**驗證，不可只寫 `t.Integer()`。DB 不使用 ENUM（通用規範 §1.4），若應用層再不擋，資料庫最終會出現沒人定義過的代碼值，報表全部對不起來。
- 驗證只負責「格式與範圍」；「數量是否足夠」「當下狀態是否允許這個操作」屬業務規則，必須在 service 層檢查，且**不可只靠 schema**。

## 3. 錯誤處理規範

### 3.1 業務錯誤用「收集」，例外只留給意外

**這是本節的分岔點，兩條路徑必須明確分開：業務拒絕是預期中的結果，走收集；意外是真的出事了，走例外。**

#### 3.1.1 業務錯誤：service 收集，不拋出

- **service 在偵測到業務規則不符時，必須把錯誤「累積」起來而不是立即中斷**；所有檢查跑完之後，若有錯誤就回傳失敗結果，若沒有就回傳成功結果。**禁止以拋例外表達業務拒絕。** ✅（自製掃描腳本：`*.service.ts`／`domain/**` 中，業務規則不符的路徑不得出現 `throw`；`throw` 只允許出現在明確標註為系統錯誤的路徑並附註解說明）
- 錯誤集合的形狀（集中定義，禁止各模組自訂）：

```ts
// 每筆錯誤自帶「分組」與 `errors[].code`，分組是具名常數而不是 HTTP 數字
export const ErrorGroup = { Conflict: 'conflict', Unprocessable: 'unprocessable', Forbidden: 'forbidden' } as const

export type DomainError = {
  group: (typeof ErrorGroup)[keyof typeof ErrorGroup]
  code: ErrorCode          // §1.3 的集中聯集型別
  msg: string
  data?: Record<string, unknown>   // 慣例帶 `field`（dot-path，§1.3）
}
export type ServiceResult<T> = { ok: true; value: T } | { ok: false; errors: DomainError[] }
```

- **`ErrorGroup` 維持三個值，不新增。** 特別是**不得為「憑證不可用／未登入」新增第四個分組**：那件事永遠不是業務錯誤，它由認證群組的憑證驗證器就地處理（§1.9.1），根本走不到 service。
  這條要寫出來，是因為實作認證模組時第一個念頭一定是「登入失敗總該有個 `Unauthorized` 分組吧」。加了之後的後果是實的：**service 從此能表達「你沒有身分」**，於是 `900` 就有了第二個產出點（§1.3），而那個產出點不受續期規則約束、不保證 `expiresIn` 為 `null`、也不保證 `errors` 為空——三條 envelope 規則同時出現一個看不見的破口。而登入失敗本來就有正確的落點：它是**業務訊息**，走 `Unprocessable` → 422／`300`（§1.3、§3.2）。
- **三個理由**（不是風格偏好，每一條都對應一個實際發生過的後果）：
  1. **一次可以回報多筆錯誤。** 拋例外只回報第一筆，使用者修完送出、再被退回、再修——一張表單要修三次才知道總共有幾個問題。而 envelope 的 `errors` 本來就是**陣列**（§1.3），拋例外的模式讓這個陣列永遠只裝得下一個元素，前端為多筆錯誤寫的定位邏輯（前端規範 §6.3）等於白寫。
  2. **每筆錯誤要能各自帶分組與 `errors[].code`，邊界層才決定得了整體回 409 還是 422。** 只有拿到完整集合，邊界層才有依據做這個決定；第一筆就中斷時，那個決定是由「哪一條檢查剛好排在前面」決定的。
  3. **例外是「意外」，業務拒絕不是意外。** 「額度不足」「狀態不符」是業務規則預期中的結果，它們**在設計時就知道會發生**；把預期結果丟進例外路徑，會讓「真的出事了」與「使用者填錯了」在程式結構上長得一模一樣，於是告警要嘛全部關掉、要嘛整天在響。
- **service 與 domain 層禁止出現 HTTP 狀態碼與 `WebFlowCode`**——分組用上面的具名常數表達，數字由邊界層依 §1.3 映射表決定。否則同一段邏輯被別的入口（§1.0）呼叫時無法重用：狀態碼體系是入口的事，寫進業務層就等於把這段規則綁死在一種入口上。 ✅（depcruise：`*.service.ts`／`domain/**` 禁止 import 任何 http／elysia 模組）
- **邊界層（handler 之後、envelope 產生函式之前）把整包錯誤集合映射成 HTTP status ＋ envelope `code` ＋ `errors[]`**（§1.8.2）：集合內出現任一 `Forbidden` 即整體回 403／`901`；否則有 `Conflict` 即 409／`300`，其餘為 422／`300`。**禁止只取第一筆**。
- 每個錯誤碼對應哪一種分組必須在宣告時就固定（§1.8.3「一個錯誤碼只能對應一種 HTTP status ＋ `code`」），不得依情境浮動。
- **`Forbidden` 分組的例外情形要記住：映射成 `901` 之後，envelope 的 `errors` 依 §1.3 一律是空陣列**（`errors` 只在 `code='300'` 時提供）。收集到的那筆錯誤碼**只進 log**，不對前端揭露——前端對 `901` 的處置本來就只有一種（顯示無權限，前端規範 §3.6），不需要細節；而揭露「你是因為不是本人才被擋」本身就是一種資訊外洩（§3.2）。因此 `Forbidden` 與其他兩種分組**不得混在同一次回應裡當成並列的多筆錯誤看待**：只要集合內出現任一 `Forbidden`，整體就是 `901`，其餘錯誤不輸出。

#### 3.1.2 系統錯誤：例外，不攔截

- **系統錯誤**（DB 連線失敗、外部依賴逾時、程式邏輯錯誤）**維持拋例外**，且不攔截、不改寫，交由最外層的統一 error handler 記錄完整堆疊（分類為 `unhandled_exception`，見 §1.3）並回 HTTP 500 ＋ `code='400'` 與一般化訊息。
- **兩條路徑的界線只有一句話：這件事是不是設計時就知道會發生。** 是（額度不足、狀態不符、目標不存在、無權限）→ 收集，走 `300`／`901`；不是（連不上資料庫、陣列越界、不該發生的 `undefined`）→ 例外，走 `400`。
- 這條界線一旦模糊，兩邊會同時壞掉：業務拒絕走例外，`errors` 陣列只剩一筆且告警被業務噪音淹沒；意外走收集，真正的 bug 會被包成一句給使用者看的訊息回 `300`，**堆疊消失、告警不響，而且畫面上看起來像是使用者做錯了什麼**。

#### 3.1.3 「找不到」的處理分兩類

界線是「使用者有沒有嘗試對它做一件事」（§1.3「查無資料不是 404」的細則）：

| 端點類別 | 目標不存在時 | 理由 |
|---|---|---|
| **查詢類**（`list`／`get`） | HTTP 200 ＋ `code='200'` ＋ `data: null`（清單回空陣列），**不算錯誤，不進錯誤集合** | 查詢的語意是「有就給我」，查無此筆是一個**正常且有效的答案**，不是失敗。當成錯誤，前端就得為「這組條件查不到資料」寫錯誤處理 |
| **動作類**（`create` 以外的 `approve`／`reject`／`revoke-approval`／`withdraw`／`update`／`delete` 等對特定目標施加操作者） | `code='300'` 邏輯錯誤 | 使用者**確實嘗試了一個做不到的操作**——他對一筆不存在的資料送出了操作。回 200 等於告訴前端「操作成功了」，畫面會若無其事地更新成完成後的狀態 |

- 動作類的「目標不存在」必須有自己的 `errors[].code`（`<領域>.<目標>-not-found` 形式）並列入該端點的宣告清單（§1.8.3），不得混用「狀態已變更」之類的既有碼——兩者的使用者處置不同（一個要重新載入清單，一個是資料真的沒了）。

### 3.2 錯誤訊息的安全考量

有些錯誤**必須刻意含糊**，這是規格不是疏漏，請在程式碼加註解避免後人「修好」：

| 情境 | 必須回 | 禁止回 |
|---|---|---|
| 登入失敗（**四種原因一律相同**，見下） | **422 ＋ `code='300'` ＋ `errors`**，錯誤碼 `auth.invalid-credentials`「公司代號、帳號或密碼錯誤」 | 「查無此公司」／「查無此帳號」／「密碼錯誤」／「此帳號不屬於這家公司」——任一種可區分即可用來列舉；也**禁止回 `900`**（見下） |
| **查詢類**端點存取不屬於本公司的資料 | **與「查無資料」完全相同**：HTTP 200 ＋ `code='200'` ＋ `data: null`（清單回空陣列） | 403／`901` 或任何回聲該 id 的訊息——403 等於確認「這筆存在，只是不給你看」 |
| **動作類**端點對不屬於本公司的目標施加操作 | **與「目標不存在」完全相同**：同一個 HTTP status、同一個 `code='300'`、同一句 `msg`、同一個 `errors[].code` | 403／`901`，或任何讓「別家的」與「不存在」可以被區分的差異 |
| 忘記密碼／帳號查詢 | 一律回相同成功訊息 | 「此帳號不存在」 |
| 敏感識別值的唯一性檢查 | 只回「無法建立」 | 回聲與哪一筆既有資料重複——等於用建立表單反查他人的敏感識別值 |

**登入失敗的四種原因必須無法區分。** 公司代號不存在、帳號不存在、密碼錯誤、該帳號不屬於這家公司——**一律回同一個 `auth.invalid-credentials`**，同一個 HTTP status、同一個 `code`、同一句 `msg`，且回應時間不得因原因而有可觀察的差異。

- 理由：**否則公司代號就變成一個可枚舉的介面**，任何人（連帳號都不需要）都能用一支登入端點測出系統裡有哪些公司存在。公司名單本身就是客戶名單，它會直接落到競爭對手手上；而「該帳號不屬於這家公司」這一種更糟——它同時洩漏了「這個帳號存在」與「它不在這家公司」，把兩份名單交叉起來。
- **每一次探測在系統看來都是一次普通的登入失敗**，沒有任何一層會告警，log 裡只是一批看起來很平常的 `300`。這與下面「跨公司存取」那條是同一種攻擊，只是發生在登入之前。
- 實作上最容易破口的地方是「先查公司、查不到就早退」這種分段驗證：**四個分支各自 return 的程式碼，回應時間與訊息幾乎不可能完全一致**。正確作法是**以公司代號 ＋ 帳號為單一查詢條件**解析出身分（§4.2「身分解析查詢」），查不到就走與密碼錯誤**同一條**失敗路徑——四種原因走的是同一行程式碼，**想寫出不一致的回應都寫不出來**。
- ✅（測試：四種原因各一條案例，斷言四者的 HTTP status、`code`、`msg`、`errors[].code` **逐項完全相同**；寫成四組各自硬編的期望值即失去意義，必須斷言彼此相等）

**關鍵安全規則：不論查詢類或動作類，「目標不存在」與「目標存在但屬於其他公司」的回應必須完全無法區分——相同的 HTTP status、相同的 `code`、相同的 `msg`、相同的 `errors[].code`。**

- 理由：兩者一旦可區分，**攻擊者拿 id 枚舉就能探測出別家公司有哪些資料存在**。他不需要看到任何內容，「存在」本身就是外洩：資料筆數、變動的時間點、某個人有沒有某一類紀錄，都能從一連串「存在／不存在」推出來。而**每一次探測在系統看來都是一個正常請求**——身分是有效的、格式是對的、回的是一般錯誤，沒有任何一層會告警，log 裡也只是一批看起來很普通的 `300`。
- 實作上最容易破口的地方是「先查再判權限」：`findById(id)` 查到了才發現不同公司，於是拋一個跟「查不到」不同的錯。正確作法是**把 `company_id` 寫進 `WHERE`**（§4.2），讓別家公司的資料在查詢階段就等同於不存在——這樣兩條路徑走的是同一行程式碼，**想寫出不一致的回應都寫不出來**。
- 這條與「動作類回 `300`」不衝突：動作類的兩種情境都回同一個 `300` 與同一個 `errors[].code`（該端點宣告的 not-found 碼），查詢類的兩種情境都回同一個 `200` ＋ `data: null`。**一致性是在同一類端點內部要求的**，不是要求兩類之間相同。
- ✅（測試：每個端點都必須有一條「以 B 公司 token 存取 A 公司資料」的案例，且**斷言其回應與同一端點「目標不存在」案例的回應完全一致**——HTTP status、`code`、`msg`、`errors[].code` 逐項比對，見 §4.2、§7.1）

- 例外訊息與 `errors[].data` **禁止包含**密碼、密碼 hash、完整身分證、完整銀行帳號、加密金鑰、SQL 原文。這些一旦進 log，log 的保存期就變成個資保存期。

### 3.3 禁止吞掉例外

- **禁止空 catch。** 需要忽略時必須註明理由與已知範圍。 ✅（lint：`no-empty` 含 catch；自製規則要求 catch 區塊內至少有一行註解或重拋）

```ts
// ✅ 正確：明說為什麼可以吞
try { await auditLog.write(entry) } catch (e) {
  // 稽核寫入失敗不可讓主要業務操作失敗；改記系統日誌並告警。
  logger.error({ err: e }, 'audit write failed')
}
// ❌ 錯誤：額度扣抵失敗被吞掉，餘額與紀錄不一致且無人知情
try { await deductBalance(...) } catch {}
```

- **禁止 `catch` 後回傳預設值**（`return null`、`return []`）掩蓋錯誤。列表查詢失敗回空陣列，畫面會顯示「查無資料」，比報錯危險得多。
- 重拋時必須保留成因：`throw new UpstreamFailure('...', { cause: e })`，不可只 `throw new Error(String(e))`。**重拋一律是系統錯誤路徑**（§3.1.2）——業務拒絕不走這裡，它在 service 內被收集起來（§3.1.1）。

### 3.4 交易中的錯誤處理

- 交易回呼內**禁止吞例外後繼續使用同一個 tx**。錯誤已使交易進入待回滾狀態，後續寫入不是失敗就是寫進一個注定回滾的交易，結果是「API 回成功、資料沒進去」。
- 交易內**禁止**呼叫外部 HTTP、寄信、寫檔或執行長時間計算。交易期間持有列鎖，一次外部逾時就會連鎖鎖住整張表。
- 需要在成功後才做的副作用（通知、快取失效、重算排程）一律放在交易 commit **之後**。

## 4. 資料庫操作規範

### 4.1 Migration

- 所有 schema 變更**一律走 migration 檔**，與程式碼同一個 PR 進版控。
- **禁止手動連線正式或測試資料庫執行 DDL。** 手改過的資料庫與 migration 歷史分岔後，任何新環境都建不起來，事故當下沒有可信的重建路徑。
- **已套用（已合併進 main）的 migration 檔禁止修改或刪除**，修正一律新增一支。改寫已套用的檔案會讓已跑過的環境永遠不會再執行修正，開發機正常、正式機壞掉。 ✅（CI：比對 PR 對既有 migration 檔的 diff，非新增即失敗）
- 每支 migration **必須可在空資料庫從頭跑到尾**，CI 每次都要跑一遍。
- 新增欄位一律 nullable 或帶 default；對既有大表加 `NOT NULL` 無 default 會直接失敗或鎖表。

### 4.2 多公司資料隔離（最高優先）

- **每一次查詢、更新、刪除都必須帶 `company_id` 條件**，包含子查詢與 JOIN 的每一張帶 `company_id` 的表。
  MariaDB 沒有 Row Level Security，隔離只能由應用層保證。漏掉一次的後果是 A 公司的主管在列表裡看到 B 公司員工的薪資與身分證，且因為查詢「有回資料」，沒有任何錯誤會被觸發——通常是客戶先發現。
- `companyId` **只能來自已驗證的 token／session**，禁止取自 request body 或 header（見 §1.1；路徑上不可能有，因為路徑不帶參數）。**第一次的 `companyId` 從哪來，見本節下方「身分解析查詢」與「寫進 token 的唯一位置」兩段。**
- **建議**：資料存取包一層強制帶入 `company_id` 的封裝，讓「不帶公司條件」寫不出來，而不是靠記憶力。跨公司的平台管理功能走獨立且明確命名的路徑。 ✅（depcruise：限制只有資料存取層可 import 未受限的 db client；自製掃描腳本：`select(...).from(<帶 company_id 的表>)` 的 `where` 未含 `companyId` 即失敗；測試：**每個端點**都要有一條「B 公司 token 存取 A 公司資料」的測試，並斷言其回應與該端點「目標不存在」的案例**逐項完全相同**，見 §3.2）
- 自我參照的父子關聯（`parent_id`）**必須驗證雙方同公司**。跨公司串樹之後，樹狀結構與其統計會把別家公司的資料算進來。

**排除適用範圍：身分解析查詢。** 上面第一條「每次查詢必須帶 `company_id`」**不適用**於「身分解析查詢」——它不是漏帶條件，**它就是產生那個條件的那一步**。沒有這一條，上面那條規則在實作上是循環定義：它保護穩態，卻讓系統無法離開初始狀態（通用規範 §7.7）。

這是排除適用範圍，不是例外——差別在於例外會被援引，排除有明確邊界。邊界寫成**正面的必要條件**，三項全部成立才算數：

1. **必須以公司代號與帳號為條件**（不是「沒有條件」，是換一組條件）；
2. **只能出現在認證模組的 repository**；
3. **回傳欄位只能是公司範圍本身**（`companyId`、`userId` 這類建立脈絡所需的識別），**不得回傳任何業務欄位**。

- ✅（自製掃描腳本：被標記為身分解析查詢的函式必須位於認證模組的 `*.repository.ts`／`impl/**.repository.ts`，其 `where` 必須同時含公司代號與帳號欄位，且 `select` 的欄位列在白名單內；此標記出現在其他模組即失敗）
- 理由（為什麼三項缺一不可）：只寫「不必帶 `company_id`」的話，它就是一個沒有邊界的豁免——下一個人寫一支「先用 email 查使用者再判斷公司」的查詢，也會說自己是身分解析。三項條件把它釘死成**唯一一種形狀**：以公司代號＋帳號查、在認證模組裡、只吐得出公司範圍。第 3 項尤其關鍵：**只要它能回傳業務欄位，它就是一個不帶公司條件的萬用查詢**，而它被放在認證模組裡，離所有「跨公司洩漏」的測試都很遠。

**`companyId` 寫進 access token 的唯一位置是發證元件**（§1.3 來源②）。使用者**在登入時輸入公司代號**，伺服器以「**公司代號 ＋ 帳號 ＋ 密碼**」三者一起驗證後解析出 `companyId`，交給發證元件寫進 claims。任何其他位置都不得寫入或改寫這個 claim。

- **`companyCode` ≠ `companyId`，界線必須寫清楚**，否則這條會被讀成「§1.1 的 `companyId` 禁令被推翻了」：

| | `companyId` | `companyCode` |
|---|---|---|
| 是什麼 | **內部識別碼**，即公司範圍本身 | 使用者鍵入的、**待驗證**的字串 |
| 可否出現在 body | **任何端點都不得出現**（§1.1，既有規則不改） | **只允許出現在登入端點的 body** |
| 信任方向 | 帶 `companyId` 是「**客戶端說了算**」 | 帶 `companyCode` 是「**客戶端提出主張、伺服器驗證**」 |

  差別就在最後一列：`companyCode` 經過「公司代號 ＋ 帳號 ＋ 密碼」三者一起驗證才會被接受，驗完之後**公司範圍仍由伺服器推導**（從解析結果取 `companyId`，不是把 `companyCode` 轉一下就用）。把它當成 `companyId` 的替身直接接進 `WHERE`，等於把第一條規則整組繞掉。
- **access token 的 claims 中 `companyId` 不得為 `null`。** ✅（型別：claims 型別中 `companyId` 為必填非 nullable；測試：發證路徑必須有一條斷言 claims 的 `companyId` 非空）
  理由：**一張沒有公司的票，實質上是一張繞過公司隔離檢查的票**——所有 `WHERE company_id = ?` 會拿到 `null`，查詢要嘛回空、要嘛（在某些寫法下）條件被整個省略，而**它在型別上完全合法**，不會有任何一個地方變紅。允許 `null` 等於在最高優先的安全規則上留一個型別檢查看不見的洞。若某個身分真的沒有公司（跨公司的平台管理），那是**另一種票、另一個認證群組**的事，不是把這一格放成 `null`。

### 4.3 軟刪除

- 有 `deleted_at` 的表，**預設查詢一律加 `IS NULL`**。忘記加，已刪除的資料會重新出現在選單與可選項中，等於刪除從未生效。 ✅（自製掃描腳本：查詢帶 `deleted_at` 欄位的表時，`where` 未出現 `deletedAt` 即失敗；需要含已刪除時以明確的 `includeDeleted` 參數並附註解）
- **禁止對有歷史意義的資料做實體 DELETE**：一律標記撤銷並新增一筆歷程（歷史不可用 UPDATE 或 DELETE 抹除）。
- **軟刪除與唯一鍵的衝突必須明確處理。** MariaDB 的 UNIQUE 索引中 `NULL` 互不相等，因此 `UNIQUE(company_id, code, deleted_at)` 會讓「未刪除的資料」失去唯一性，等於沒擋。本專案採用：唯一鍵改為 `UNIQUE(company_id, code, deleted_seq)`，`deleted_seq` 為 `NOT NULL DEFAULT 0`，軟刪除時同時寫入非零值（如刪除時間戳）。
  不處理的後果二選一：要嘛沿用 `UNIQUE(company_id, code)`，刪掉的代碼永遠不能再用；要嘛把唯一性丟給應用層檢查，併發下兩筆同代碼會同時通過。
- 唯一性檢查**禁止用「先 SELECT 再 INSERT」**取代資料庫唯一鍵。兩個併發請求會同時查到「沒有」，然後都寫進去。正確作法是直接寫入並攔截唯一鍵違反，轉成 409（envelope `code='300'`，並於 `errors` 指出衝突欄位）。

### 4.4 交易邊界

- **交易邊界屬於 service 層**，repository 不自開交易——否則巢狀時無法合併成一個原子操作。
- **同一個業務操作若要寫入多張表，一律必須在同一交易內完成**（跨交易失敗會產生無法自動修復的髒資料）。典型形態有兩種：
  - **一次建立分散在多張表的關聯資料**（主體 + 帳號 + 關聯 + 至少一筆權限指派）：只成功一半會留下「有資料卻無法登入」「有帳號卻沒有任何角色」這種永遠用不了、也沒人會發現的孤兒。
  - **一次狀態變更同時要寫審核歷程、產生衍生資料並更新彙總（或快取）**：只成功一半會讓彙總與明細從此對不起來，而且事後無法自動判斷該補哪一邊。
- **狀態變更必須用條件式 UPDATE**，把「預期的目前狀態」寫進 `WHERE`，並檢查影響列數。

```ts
// ✅ 正確：兩個使用者併發變更同一筆資料時，第二筆影響 0 列 → 收集一筆 Conflict 錯誤（邊界層映射為 409／`code='300'`）
const r = await tx.update(records)
  .set({ status: NEXT_STATUS })
  .where(and(eq(records.companyId, companyId), eq(records.id, id), eq(records.status, EXPECTED_STATUS)))
if (r.affectedRows === 0) {
  errors.push({ group: ErrorGroup.Conflict, code: '<領域>.state-changed', msg: '資料狀態已變更，請重新載入' })
  return { ok: false, errors }   // 不拋例外，§3.1.1
}
// ❌ 錯誤：先讀再寫，兩人同時操作會讓狀態變更的副作用被套用兩次
const row = await findById(id)
if (row.status === EXPECTED_STATUS) await update(id, { status: NEXT_STATUS })
```

### 4.5 索引與 N+1

- 每一張帶 `company_id` 的表，其索引**必須以 `company_id` 開頭**（如 `(company_id, created_at)`、`(company_id, <關聯>_id, status)`）。缺少會讓每次列表查詢退化成全表掃描，資料量成長後同時拖垮所有租戶。
- 新增列表查詢或篩選條件時，**必須在同一個 PR 補上支撐索引**，並在 PR 描述附 `EXPLAIN` 結果。
- **禁止在迴圈中逐筆查詢。** 一頁 20 筆資料各查一次兩張關聯主檔＝41 次往返，看起來只是慢，實際上會在尖峰時段耗盡連線池，讓其他端點一起失敗。 ✅（lint：禁止 `for`／`map` 內出現 await 的 db 呼叫；測試：關鍵列表端點加上查詢次數上限斷言）

```ts
// ✅ 正確：一次撈完再組裝
const rows = await db.select().from(owners).where(and(eq(owners.companyId, cid), inArray(owners.id, ids)))
const byId = new Map(rows.map((r) => [r.id, r]))
// ❌ 錯誤：N+1
for (const row of list) row.owner = await findOwner(row.ownerId)
```

### 4.6 禁止 ORM 關聯查詢，一律顯式 `select` ＋ `join`

- **禁止使用 Drizzle 的 relational query API**（`db.query.*` 搭配 `with`），所有跨表讀取一律以顯式 `select` ＋ `join` 撰寫。 ✅（自製掃描腳本：出現 `db.query.` 或 relational 查詢的 `with:` 選項即失敗；掃描器須自我檢查掃到的檔案數 > 0）
- 理由一：**本系統是重聚合的領域**——一次列表查詢常要跨多張表、套多組條件再彙總。顯式 JOIN 的 SQL 與程式碼幾乎一對一，`EXPLAIN` 直接貼得出來（§4.5 要求 PR 附 `EXPLAIN`），review 時也看得懂查詢實際會掃哪些表、用哪個索引。巢狀 JSON 聚合在多表多條件的情況下，**要另外把實際 SQL 印出來才知道它長什麼樣**——而「要先印出來才知道」等於這段查詢在 review 階段是不可讀的，索引缺漏也就檢查不到。
- 理由二：**relational API 需要另外維護一份關聯宣告**，那是 schema 之外的**第二份真相**。加了外鍵卻忘了補宣告、改了欄位名只改了一邊，都不會有任何地方變紅，兩份定義就這樣慢慢漂移；顯式 JOIN 的關聯條件寫在查詢裡，改錯當場就是查詢結果不對。
- **誠實註明：這條不是因為 N+1。** Drizzle 的 relational API 產生的是**單一查詢**，不是「每個關聯各發一次查詢」那種形態，所以它不會製造 N+1。§4.5「禁止在迴圈中逐筆查詢」另有守備範圍（手寫的逐筆查詢迴圈），兩條規則不重疊，也不互為理由。把理由寫錯的後果是下一個人拿「反正沒有 N+1」推翻這條規則，而真正的理由（可讀性與第二份真相）從來沒被寫下來。

### 4.7 金額與工時的型別

- **金額禁止用 `float`／`double`／JS `number` 運算。** DB 用 `decimal`（依 schema 定義的精度），程式中以整數「分」或 decimal 字串處理。
  浮點誤差在薪資單上就是實發金額差一塊錢對不起來，而勞健保級距在邊界值上會選錯級距，錯的是法定金額。 ✅（型別：金額欄位以 branded type 表示，不可與一般 number 互換；lint：禁止對金額型別使用 `+ - * /` 以外的自製運算函式）
- Drizzle 讀 `decimal` 回傳字串，**禁止 `Number(...)` 後再計算**。轉成 float 的那一刻精度就沒了。
- **工時一律以整數「分鐘」儲存與運算**，只在輸出時換算為小時。用小數小時做加總，8.33 小時這種值會在月結時累積出數十分鐘誤差。
- **四捨五入規則必須集中在單一模組**，且每個呼叫點明確指定用途（金額進位、時薪、比率、工時單位）。散落各處的 `Math.round` 會讓明細加總不等於總額，而每次修都只修到其中一處。

## 5. 安全規範

### 5.1 密碼與敏感個資

- 密碼只保存單向 hash（Argon2id 或 bcrypt cost ≥ 12）。**禁止**保存、log、回傳明碼或 hash；管理者重設密碼要寫稽核，但**內容不得包含密碼與 hash**。
- 身分證、生日、電話、Email、地址、銀行帳號一律存加密欄位（`*_encrypted`），需查詢者另存固定長度 `*_hash`。
  **禁止**新增這些資料的明文欄位或明文索引——一旦資料庫備份外流，加密欄位是唯一的防線。
- 對外回應一律遮罩（身分證僅末 3 碼、帳號僅末 4 碼），完整值只在明確授權的單一端點提供且必寫稽核。 ✅（自製掃描腳本：response schema 中出現 `identityNumber`、`bankAccount`、`passwordHash` 等關鍵字未經遮罩函式即失敗）
- **禁止把敏感值寫進 log 或 `errors[].data`**；log 一律先過欄位遮罩。

### 5.2 權限檢查

- 權限檢查**必須在後端每一個端點執行**，且與 UI 顯示無關。
  前端的隱藏與停用只是體驗優化（前端規範 §4.2）——只靠前端隱藏按鈕，等於權限只擋住不會開 DevTools 的人。
- 路由層做**粗粒度**權限（是否具備該功能權限），service 層做**細粒度**檢查（是否本人、是否在自己的組織範圍內、目標是否同公司、目標當下狀態是否允許）。
  只在路由層檢查，「只能看自己的」這類端點就會變成「只要具備該功能權限就能查任何人的資料」。 ✅（測試：每個端點至少一條「無權限角色被 403」的測試）
- 「本人」關係一律由 token 推導，**禁止**信任請求帶來的識別碼就當成本人。

#### 5.2.1 兩層模型：認證方式由群組決定，權限碼由路徑推導

**「這支端點怎麼確認你是誰」與「這支端點需要什麼權限」是兩件事，各有各的來源，兩件都不是端點自己寫的。**

| 問題 | 答案來自 | 規定於 |
|---|---|---|
| 用哪一種方式驗證身分 | **端點所在的認證群組** | §1.9.1 |
| 需要哪一個權限碼 | **端點的路徑，機械推導** | 本節 |

這取代了「每支端點自行宣告所需權限、公開端點自行宣告為公開」的舊作法。**舊規則要防的事完整保留**——「忘了宣告」與「刻意公開」必須長得不一樣——只是落地方式改成「**必須落在某個群組內**」（§1.9.2）：漏掉的端點不再是「少寫一個欄位」（少寫看不出來），而是「不在任何群組裡」（回溯不到群組即失敗）。

#### 5.2.2 權限碼由路徑推導，禁止手寫

- **權限碼 ＝ 路徑的機械轉換**：`<大目錄>/<次目錄>/<動作>` → `<大目錄>.<次目錄>.<動作>`。轉換規則與 `cmd`（§1.3）**完全相同**：去掉開頭的 `/`，把剩下的 `/` 換成 `.`，其餘一字不改。
- **因此權限碼與 `cmd` 的字面值相同。這是刻意的，不是重複設計，這一點必須講明**，否則後人會以為其中一個是多餘的而想拿掉。兩者**用途完全不同**：`cmd` 進 request／response envelope，供追蹤與 log（§1.3）；權限碼進角色設定與授權判斷，不出現在 envelope 裡。它們只是**恰好都要指涉「哪一支端點」**，於是共用同一個推導規則——共用規則才不會出現「log 上的 `cmd` 與角色設定裡的權限碼指的不是同一支端點」這種對不起來的狀況。
- **禁止手寫權限碼。** ✅（自製掃描腳本：權限碼必須等於該端點路徑的機械轉換結果，不一致即失敗；掃描器須自我檢查掃到的端點數 > 0）
  理由：**手寫的東西會與路徑漂移，推導的不會。** 路徑改名時，手寫的權限碼不會跟著改，也不會有任何地方變紅——結果是角色設定裡授予的那個碼再也對不上任何端點，於是**該權限實際上授不出去（使用者一律 403）**，或者更糟，某個舊碼恰好還被別支端點用著，於是授到了不該授的東西。改成推導之後還多得到一件事：**「這支端點需要什麼權限」從此是算得出來的，不需要查**——看路徑就知道，不必去翻設定、不必問人。
- **多支端點需要「共用權限」時，做法是在角色設定裡授予多個權限碼**，不是讓兩支端點共用同一個碼。
  理由：讓兩支端點共用一個碼，等於在推導規則上開了一個例外，**權限碼就此變回不可推導的**——腳本算不出期望值，上一條的檢查當場失效，而且失效的方式是靜默的（例外分支一旦存在，就沒有人知道還有幾支端點也偷偷共用著）。把「哪些權限要一起給」放在角色設定裡，它本來就是那裡該回答的問題：角色是權限的集合，多給幾個碼是它的日常，不需要動到端點。
- **公開群組（§1.9.2）內的端點沒有權限碼**——它們不需要授權，因此也不參與上面的推導與檢查。這是排除適用範圍，不是例外：界線由「在不在公開群組裡」決定，而那是一個看得見、可被質疑的宣告。

### 5.3 稽核紀錄

- 下列類別的操作**必須寫稽核**：個人與敏感個資的異動、金額相關設定的異動、帳號的啟用停用與密碼重設、角色與權限的指派與撤銷，以及所有會改變審核結果的操作。
- 每筆至少記錄：操作者、操作時間、操作類型、資料主體、異動前後差異、必要時的生效日。缺少「異動前值」的稽核在爭議發生時完全無法舉證，等於沒寫。
- 稽核與業務資料**必須在同一交易內寫入**（除非該操作明定稽核失敗不可阻斷，見 §3.3 範例，此時必須告警）。
- 稽核紀錄**只能新增**，禁止修改與刪除。

### 5.4 認證機制：access token + refresh token 雙票

**本系統面向 Web 前端這個入口（§1.0）採用兩張票的認證機制。**（認證方式是入口的屬性——將來若增加入口，那個入口的認證方式由它自己定，不套用本節。）這是為了同時滿足兩件互相衝突的事：**access token 要短命**（被偷走的價值才低），但**使用者不能每天被迫重新登入**（這是員工每天都要用的內部系統，把登入擋在每天第一個操作前面，等於天天多一道摩擦）。單一張票無法兼顧——壽命短就天天登入，壽命長就等於把一張長期有效的鑰匙放在瀏覽器裡。

#### 5.4.1 兩張票的分工

| | 用途 | 壽命 |
|---|---|---|
| **access token** | **每次請求攜帶**，用於身分驗證；envelope 的 `expiresIn` 反映的就是它的剩餘秒數 | **滑動視窗 2 小時**，每次通過憑證驗證即續期（續期規則見 §1.3，此處不重複）；**且可即時撤銷**（§5.4.6） |
| **refresh token** | **只用於 `POST /sessions/main/refresh`** 換發新的 access token，不得用於其他任何端點 | **30 天** |

- refresh token **只認一個端點**。它出現在 `/sessions/main/refresh` 以外的任何請求上都應被視為錯誤，而不是「順便也能用」。理由：兩張票的價值差異全部建立在「refresh token 的使用面極小」這件事上——一旦它也能當 access token 用，就只是一張 30 天壽命的 access token，短命那一半的設計當場失效。
- access token 的續期不需要 refresh token 參與：只要人還在操作，滑動視窗就會一直往後推，`/sessions/main/refresh` 只在**停止操作超過一個視窗**之後才會被用到。

#### 5.4.2 輪替與偷用偵測（不可省略）

本系統**不做敏感操作的重新驗證**（§5.4.4），因此以下機制是偵測「票被偷」的**唯一防線**，不是加分項：

- **每次 refresh 時，refresh token 也一併換新，舊的立即作廢。** 也就是說每一張 refresh token 都是**一次性使用**：`/sessions/main/refresh` 回傳的是「新的 access token ＋ 新的 refresh token」，而不是只換 access token。
- **已作廢的 refresh token 再次被使用 → 一律視為外洩 → 該使用者的所有 refresh token 全部作廢，強制重新登入。** 不是只擋下這一次請求，是整條鏈作廢。
- 理由（為什麼重複使用等於外洩）：**正常的 client 不會重複使用同一張已經換掉的票**——它換完就把舊的丟了，手上永遠只有最新的一張。舊票再次出現，代表**同一張票有第二方持有**：不是攻擊者拿舊票來換（此時真正的使用者手上是新票），就是攻擊者已經換過而真正的使用者拿著舊票來（此時被偷的事實更明確）。兩種情形都無法從單次請求判斷誰是誰，也不需要判斷——**兩邊一起作廢、要求重新登入**，被偷的一方最多是重登一次，攻擊者則失去全部存取權。
- 這條之所以不能省略：沒有輪替，一張 30 天的 refresh token 被偷走之後，**攻擊者可以安靜地用滿 30 天，而系統與使用者都不會察覺任何異常**——每次 refresh 在 log 上都是一個完全正常的請求。加上輪替，偷用會在**下一次任一方 refresh 時**立刻暴露。
- **refresh token 必須存在伺服器端且可主動撤銷。** 不得做成純自帶簽章（stateless JWT）而無撤銷清單——那樣既無法作廢舊票（輪替偵測就無從實作），也無法支援「登出所有裝置」（`POST /sessions/main/logout-all`）。
  **access token 同樣必須可即時撤銷**，見 §5.4.6：本節的「全鏈作廢、強制重新登入」是**當下生效**，不是「等這一張 access token 自己過期」。
- 偵測到重複使用時**必須寫稽核與告警**（§5.3、§1.3 的 log 分類），這是少數「系統自己能發現的安全事件」，靜靜作廢等於浪費了這個訊號。
- ✅（測試：必須包含「以已作廢的 refresh token 呼叫 `/sessions/main/refresh` → 該使用者所有 refresh token 全鏈作廢、後續請求一律 `900`」的案例；以及「正常輪替後舊票不可再用」的案例）

#### 5.4.3 儲存方式

| 票 | 存放位置 |
|---|---|
| **refresh token** | **httpOnly + Secure + SameSite=Lax cookie**，JS 讀不到 |
| **access token** | **前端記憶體**（模組層變數／store），**不進 `localStorage`／`sessionStorage`** |

- 理由：**兩張票若同時被 XSS 拿走，5.4.2 的偷用偵測也救不回來**——攻擊者手上有 access token 可以直接打 API，有 refresh token 可以自己輪替，他甚至可能比真正的使用者更早 refresh，於是被作廢、被要求重登的是**使用者本人**。因此重點是讓兩張票不可能同時落入同一個 XSS payload：`httpOnly` 讓 refresh token 對 JS 不可見，記憶體則讓 access token 隨分頁關閉即消失，且不會躺在任何一個可被 `localStorage.getItem` 一次撈走的地方。
- access token 存記憶體的代價是**重新整理頁面後 access token 就沒了**，這是可接受的：cookie 裡的 refresh token 還在，前端啟動時打一次 `/sessions/main/refresh` 就換回來，使用者無感。反過來把它存進 `localStorage` 換取「重整不掉線」，等於為了省一支請求把票放在 XSS 一行程式碼就能讀到的地方。
- **`SameSite` 定案為 `Lax`，不是 `Strict`。** 兩者的差別只有一處：`Strict` 比 `Lax` 多擋的，是「**從其他站台以 top-level GET 導航進來時帶 cookie**」這一種情形。而本系統**所有端點都是同源的 POST XHR**（§1.2、§1.5），**一支 GET 端點都沒有**——`Lax` 對同源請求、對所有 POST XHR 一律照常帶上 cookie，**改成 `Lax` 沒有任何一支端點的行為會改變**。也就是說 `Strict` 在這裡多買到的安全性趨近於零。
- **代價卻是實的，而且會在未來才發作。** 目前不做 Email／通訊軟體通知，但**未來可能會做**——一旦做了，通知裡會附「前往簽核」這類連結，使用者從外部信件或訊息點進來就是一個**跨站的 top-level GET 導航**。在 `Strict` 之下，那第一個請求不會帶上 refresh token cookie，於是**使用者明明還登入著，卻被導去登入頁**；而這種問題不會有錯誤訊息，只會表現成「從信裡點進來每次都要重登，直接開瀏覽器就不用」。
  真正的問題是**修它的時機**：這種「未來做通知功能時要記得回來改 cookie 屬性」的待辦一定會被忘記，因為做通知功能的人不會想到問題出在半年前定的 cookie 設定上，他只會看到一個「有時候要重登」的怪現象，而查到 `SameSite` 要花掉的時間遠比一開始就選對貴。**用趨近於零的安全性去換一個注定會被忘記的未來待辦，不划算**——因此定案為 `Lax`。
- **`None` 則明確排除**：它需要放行跨站帶 cookie，本系統沒有任何需要那樣做的情境。
- **仍未決的只剩一點，已收斂進 §9**：若前後端改為**不同源部署**，`Lax` 同樣送不出 cookie，屆時必須放寬並**補上 CSRF token**（放寬 SameSite 的同時就把 CSRF 防線一起放掉了）。同源部署下不需要 CSRF token，因為 `Lax` 已擋住跨站的 POST。

#### 5.4.4 明確記錄「決定不做」：敏感操作的重新驗證（step-up authentication）

**本系統不做敏感操作的重新驗證。** 查看薪資、查看個資這類敏感操作，**不會**要求使用者重新輸入密碼或做第二因素驗證。這是明確的決定，不是還沒做完的項目——寫在這裡是為了讓後人知道它被考慮過、被否決過，以及否決的代價是什麼。

- **後果必須明說：所有資料都在同一個登入態下。** 只要人已登入，**能做最日常的操作，就能看到權限範圍內最敏感的資料**。裝置借給同事、午休離座沒鎖螢幕、瀏覽器留在共用電腦上——這些情境下，取得畫面的人拿到的是全部權限範圍內的資料，而不只是他原本要用的那一項。這不是理論風險：全體員工每天都會在各種裝置上使用本系統，正是最容易發生「借一下」的場景。
- 因此 **§5.4.2 的輪替偵測、「登出所有裝置」（`POST /sessions/main/logout-all`）與 §5.4.5 的「改密碼作廢所有 session」是唯一防線，不得省略**。第一項處理票被偷，第二項處理裝置失控，第三項是使用者懷疑帳號被盜時的第一直覺動作——沒有 step-up 的情況下，這三者失去任何一個都沒有替代品。
  **而這三項的效力全部建立在 §5.4.6「access token 即時撤銷」之上**：撤銷若不是即時的，三者都只是「過一陣子才生效」，而使用者按下去的當下就已經不再警戒了。
- **重新評估的條件**（出現任一即應重新討論導入 step-up）：客戶或稽核明確要求；系統開始承載薪資以外更敏感的資料（例如完整銀行帳號的直接查看、跨公司的平台管理功能）；出現實際的越權查看事件；或導入行動裝置／外網存取，登入態離開公司內網環境。
- 前端規範同步：前端**不得**實作任何「敏感操作需重新驗證」的流程或提示（前端規範 §4.2、§4.3 的停用與提示規則已足夠表達「不允許」，不需要再多一層驗證）。

#### 5.4.5 改密碼與重設密碼必須作廢所有 session

**`POST /credentials/main/update`（改密碼）與 `POST /credentials/main/reset`（重設密碼）成功後，必須作廢該使用者的所有 refresh token，強制所有裝置重新登入。** 這不是選項，也不是「之後再看要不要做」。

- **作廢範圍包含執行操作的當前裝置，沒有例外。** 該使用者當下所有有效的 refresh token 一律作廢，使用者（含剛剛才輸入過密碼的那個裝置）必須重新登入。不得以「只作廢比密碼變更時間早的票」之類的近似作法取代，也不得在同一次回應中替當前裝置換發新票。
  - **理由**：留一個例外，就要多一段「哪一張票是當前這張」的判斷邏輯；而那段邏輯寫錯的後果是**「以為作廢了、其實沒有」**——沒有效果卻讓人放心，比什麼都沒做更危險。一律作廢沒有這個判斷，也就沒有寫錯的空間。省下的那次重新登入，換不到這個風險。
- **理由（為什麼這條在本系統特別重要）**：本系統**不做敏感操作的重新驗證**（§5.4.4），登入態一旦被別人取得就等於全部權限。而**使用者懷疑帳號被盜時，第一直覺就是去改密碼**——這幾乎是唯一一個一般使用者自己想得到、也做得到的自救動作。若改完密碼舊 session 仍然活著，**他做的事等於完全沒有效果，而他會以為自己已經處理好了**：攻擊者手上那張 refresh token 照樣可以繼續輪替下去，而使用者不再警戒、也不會再去按「登出所有裝置」。**沒有效果還讓人放心，比什麼都沒做更危險。**
- 管理者重設密碼（`/credentials/main/reset`）同樣適用，且理由更直接：會走到這條路徑的情境本來就常是「帳號出事了」或「員工離職／裝置回收」，此時最不該發生的就是舊裝置還連得上。
- 作廢事件必須寫稽核（§5.3），與密碼變更同一交易（§4.4）——密碼改了但票沒作廢，或票作廢了但密碼沒改，兩種半套狀態都不可出現。
- ✅（測試：必須包含「A 裝置呼叫 `/credentials/main/update` 成功後，B 裝置持有的 refresh token 立即失效——以該票呼叫 `/sessions/main/refresh` 回 `900`，且 B 裝置後續請求一律 `900`」；`/credentials/main/reset` 比照一條。另須斷言 **A 裝置自己原有的 refresh token 同樣失效**，以該票呼叫 `/sessions/main/refresh` 一樣回 `900`）

#### 5.4.6 access token 必須可即時撤銷（沒有殘留視窗）

**「作廢」在本系統一律指「即時」：撤銷之後的下一個請求就必須回 `900`，不存在任何「最長還有 N 分鐘／N 小時仍然有效」的殘留視窗。**

- **憑證驗證器（§1.9.1）每一個請求都必須檢查該 session 的撤銷狀態，不做跨請求快取。** 不得以「access token 是短命的自帶簽章票，過期自然就失效了」取代這項檢查。 ✅（測試：撤銷（登出／改密碼／輪替偵測觸發）後，**持同一張仍在有效期內的 access token 的下一個請求**必須回 `900`，不得先成功再失敗）
- **理由一：額外成本接近零。** 驗證器**本來就必須每個請求查一次「這個使用者有哪些權限碼」**（§5.2 的粗粒度權限檢查建立在這上面）——撤銷狀態搭同一次查詢一起取回，多的是一個欄位，不是多一次往返。所以這裡沒有「為了安全犧牲效能」的取捨可談，取捨本身不存在。
- **理由二：加了 TTL 快取之後，「已被撤銷的權限還能再用幾秒」會變成一個沒有人說得準的數字。** 它是快取 TTL？是 TTL 減去上次查詢到現在的時間？多個節點各有各的快取時是哪一個？沒有人答得出來，而**它會被寫進安全說明裡當成一句「幾乎是即時的」**。
- **理由三（這一條才是決定性的）：那個視窗在測試裡永遠是 0 秒，只在正式環境發作。** 測試中撤銷與下一個請求之間隔不到一毫秒，快取還沒被填進去或剛好被清掉，**測試會全綠**；正式環境有持續流量把快取填滿、有多個節點各自持有副本，於是「登出後還能操作幾秒」真的發生，而且**沒有任何一條測試涵蓋它**。一個只在正式環境成立、且無法被測試證偽的安全行為，等於沒有這個行為。
- 連帶結論：§5.4.2（輪替偵測觸發的全鏈作廢）、§5.4.5（改密碼作廢所有 session）與 §5.4.7（登出）**三者的作廢一律是即時的**，它們的測試斷言（「後續請求一律 `900`」）字面上就是這個意思，不得以「下次 refresh 時才生效」的近似作法滿足。

#### 5.4.7 登出必須作廢整條輪替鏈

**refresh token 一次性輪替（§5.4.2）會產生一串票：`T1 → T2 → T3 → …`。登出必須作廢整條鏈，不是只作廢手上那一張。**

- **理由要寫清楚，因為兩種做法在多數情況下看起來一模一樣**：任何時刻只有最新那張是活的，所以「作廢手上這張」與「作廢整條鏈」在單分頁情境下效果相同。**差別出在「手上的票不是最新那張」的時候**——多分頁是本系統的日常：A 分頁已經 refresh 過、鏈走到 `T4`，B 分頁手上還是 `T3`。
  此時 B 分頁按下登出，只作廢單張的做法**廢掉的是早就已經失效的 `T3`，而 `T4` 還活著**：畫面乾淨地回到登入頁，**session 卻沒有斷**。這正是 §5.4.5 已經警告過的那件事——**「以為作廢了、其實沒有」，沒有效果卻讓人放心，比什麼都沒做更危險**。
- **`refresh_tokens` 必須有一個代表「一次登入」的欄位**（一條輪替鏈共用同一個值，輪替時原樣沿用），讓「這次登入」在資料上真的存在。作廢與撤銷一律以這個欄位為單位。
  理由：沒有這個欄位，「整條鏈」在資料上是**推不出來的**——只能靠「前一張是誰」逐張回溯，而回溯要嘛在輪替時把舊列刪掉就斷了，要嘛就得保留全部歷史再走一遍鏈。把「一次登入」寫成一個欄位，作廢就是一次條件更新，也讓「登出所有裝置」（作廢該使用者的所有鏈）與「登出這台裝置」（作廢這一條鏈）變成同一種操作的兩個範圍。
- 這與 §5.4.5「改密碼作廢所有 session」不重疊：那一條的範圍是**該使用者的所有鏈**，本條的範圍是**當前這一條鏈**。
- ✅（測試：必須包含「**以鏈中的舊票登出後，最新票也失效**」——先輪替到 `T4`，再以 `T3` 呼叫 `/sessions/main/logout`，然後斷言以 `T4` 呼叫 `/sessions/main/refresh` 回 `900`，且該 session 的 access token 後續請求一律 `900`（§5.4.6））

## 6. 時間與時區規範

**全系統一律使用台北時間（`Asia/Taipei`, UTC+8），不做任何時區換算。** 資料庫、後端、API 傳輸、前端看到的是同一個牆鐘時間字串。

- 營運時區固定 `Asia/Taipei`，定義為單一常數，**禁止**在各處寫死字串或依賴伺服器時區。伺服器多半跑在 UTC，用 `new Date().getHours()` 做時間判定，台北早上 9 點會被當成凌晨 1 點。
- **資料庫連線 session 時區固定 `+08:00`**；`datetime` 欄位存的就是**台北牆鐘時間**，`date` 欄位存台北的日曆日。兩者都不做換算。
  理由（為什麼不存 UTC）：本系統只服務單一時區的客戶。全程台北時間，讓「時刻」「歸屬日期」「時段分鐘數」三者天然一致，換算這件事從流程中被移除，也就沒有漏換算的可能。反之存 UTC 時，每一次讀寫都多一次換算，只要有一處漏掉，就會出現「時刻對、日期差一天」這種只在深夜與月底發作的錯誤，而錯的是法定工時與薪資。
- **應用程式啟動時必須比對資料庫時區，不一致就拒絕啟動。** 啟動自檢讀取連線的 session 時區（`@@session.time_zone` 或等效查詢），不等於 `+08:00` 即中止程序，並輸出實際讀到的值。 ✅（啟動自檢，CI 亦跑一次）
  理由：DB 或連線參數的時區被誤設時，所有寫入的時間會**靜靜偏移**——沒有例外、沒有錯誤訊息、沒有測試會變紅，資料照樣寫得進去。等到有人察覺，已經有數個月的出勤與薪資是錯的，而且分不出哪幾筆需要修。啟動就擋下來，是唯一能在事故發生**之前**攔住它的位置；讓服務起不來，遠比讓它算錯薪資便宜。

### 6.1 API 傳輸格式（前後端必須一致）

**同一個 payload 裡會同時出現兩種時間格式，判準必須寫死，這裡是唯一的定義處。**

| 類型 | 格式 | 判準 |
|---|---|---|
| **傳輸層時戳**（`rqTS`／`rspTS`，§1.3） | ISO 8601 **帶時區偏移**：`2026-04-14T14:30:00+08:00` | **機器用的**，給 log 對時、算往返延遲，**不顯示給使用者** |
| **業務時間**（`datetime`） | `YYYY-MM-DD HH:mm:ss`，台北時間，**不帶任何時區標記** | **要顯示、要計算的**，前端不做任何換算 |
| **業務日期**（`date`） | `YYYY-MM-DD` | 同上 |
| 月份 | `YYYY-MM` | 同上 |
| 不含日期的時刻 | `HH:mm`；跨午夜以「當日第幾分鐘」整數表示（`09:00`／`1560`） | 同上 |

判準只有一句話：**這個時間會不會出現在畫面上？** 會 → 業務時間格式；只給機器看 → 傳輸層時戳格式。

- **業務時間欄位禁止帶 `Z`、禁止帶 `+08:00`、禁止使用 ISO 8601 帶時區的形式（`2026-08-26T09:30:00+08:00`）、禁止傳 epoch 數字或其他本地格式字串。** ✅（自製掃描腳本：業務欄位的 schema 不得使用帶時區偏移的格式；時間欄位必須引用共用型別 `TaipeiDateTime`／`IsoDate`，出現行內 `t.String()` 或以 `toISOString()` 產出對外業務時間即失敗）
  理由：字串一旦帶了時區標記，前端 `new Date('2026-08-26T09:30:00+08:00')` 會依**瀏覽器**時區再換算一次並顯示換算後的結果——使用者把筆電時區設成東京，整批時間就多一小時，而系統任何一處都不會報錯。不帶標記時，前端拿到的字串就是要顯示的字串，前後端看到的是同一組數字，「再換算一次」這個失敗模式在格式層就被消除。
- **反過來，`rqTS`／`rspTS`／`exp` 必須帶時區偏移。** `rqTS`／`rspTS` 的用途是跨機器對時（比對前端送出、後端收到、後端回應三個時間點），`exp` 的用途是在 log 上標示 session 截止時刻；三者都需要一個絕對參考點，不帶偏移的時戳在 log 聚合時無法與其他系統的時間軸對齊。**這三欄是唯三允許帶偏移的欄位**，且**禁止拿它們當業務時間計算**——`rqTS` 是「請求發出的時刻」，不是「該筆業務事件發生的時刻」，兩者在網路重試或前端排隊時會差好幾秒。
  **帶時區偏移的時間字串一律不上畫面，沒有例外**：`rqTS`／`rspTS`／`exp` 三者**都只供 log 與除錯**，一個都不顯示給使用者。`exp` 另外**仍禁止用於任何過期判斷**（§1.3）——換句話說，`exp` 在前端只剩下「寫進錯誤回報與 log」一種用途。畫面若需要呈現剩餘時間，一律由 `expiresIn` 倒數推導（前端規範 §3.7）。
  理由：這條規則的判準就是上表那句「這個時間會不會出現在畫面上？」。只要有**任何一個**帶偏移的欄位被允許顯示，判準就從「格式決定用途」退化成「要看是哪一欄」，而那正是會被記錯的東西——下一個人看到 `exp` 可以顯示，很自然就會想「那 `rspTS` 應該也可以」。零例外，這條規則才不需要被記住。
- 傳輸層時戳的共用型別為 `TransportTS`（`rqTS`／`rspTS`／`exp` 共用），業務時間為 `TaipeiDateTime`／`IsoDate`（§2），一律附 `pattern` 驗證；禁止就地重寫。三者**不可互相代入**，型別上就要分開。前端的顯示格式規範見前端規範 §9.2，兩者必須一致。
- Session 到期資訊回傳 `expiresIn`（相對秒數，過期判斷與倒數顯示的唯一依據）與 `exp`（絕對時刻，僅供 log 與除錯）兩個欄位，分工與理由見 §1.3。

### 6.2 「現在」必須由呼叫端注入

- **「今天」「現在」禁止由底層函式自行取得，必須由呼叫端傳入。** 統一以可注入的 clock 提供 `now()`／`today()`／`minuteOfDay()`（回傳值一律為台北時間），業務程式碼**禁止直接 `new Date()`／`Date.now()`**。
  理由：底層自己抓時間，跨日、月底、閏年、到期日這類與日期相關的邏輯**根本無法測試**——你不能為了跑一條測試把機器時間調到 2 月 29 日。這類 bug 只會在真正的月底當天出現在正式環境。 ✅（lint：業務程式碼禁止 `new Date()` / `Date.now()`，僅 clock 模組例外）

```ts
// ✅ 正確：時間由呼叫端傳入，測試可任意指定
function isWithinWindow(window: TimeWindow, minuteOfDay: number): boolean
// ❌ 錯誤：無法測試跨日與月底
function isWithinWindow(window: TimeWindow): boolean { const now = new Date() /* ... */ }
```

- 跨午夜的時段以「當日第幾分鐘」表示，允許超過 1440（隔日）。用 `HH:mm` 字串比大小，跨午夜時段的結束時刻會小於開始時刻，時長算成負數。

## 7. 測試規範

### 7.1 一定要寫的測試

- **所有金額、時間長度、額度與法規級距的計算邏輯**：必須有單元測試，且**必須包含邊界值**（期間的起訖、跨日、閏年、剛好用盡的臨界值、級距上下限、最小計算單位）。這些算錯不是體驗問題，是法定金額算錯。
- **所有對外端點**：至少涵蓋成功（200／`200`）、業務規則不允許（422 或 409／`300`，並斷言 `errors[].code`）、無權限（403／`901`，並斷言 `expiresIn` 非 `null`）、**目標不存在**、**跨公司存取** 五條。斷言必須同時檢查 HTTP status 與 envelope 的 `code`，只檢查其中一項會漏掉映射寫錯的情況。
  - 「目標不存在」的期望值依端點類別而定（§3.1.3）：查詢類是 200／`200` ＋ `data: null` 或空清單，動作類是 `300` ＋ 該端點宣告的 not-found 錯誤碼。
  - **「跨公司存取」不是獨立斷言一組期望值，而是斷言它與「目標不存在」那一條的回應逐項相同**（HTTP status、`code`、`msg`、`errors[].code`）。寫成兩組各自硬編的期望值時，日後有人改了其中一條的訊息，兩邊就悄悄分岔而測試依然全綠——那正是 §3.2 要防的事。
- **多筆業務錯誤**：有兩條以上業務規則的端點，至少要有一條「一次違反兩條規則」的測試，並斷言 `errors` **同時回傳兩筆**、各自的 `code` 都在宣告清單內。
  理由：這是唯一能證明 service 真的在收集而不是在第一筆就中斷的方式（§3.1.1）。只回一筆時，回應在型別上完全合法、HTTP status 也對，沒有任何其他檢查抓得到——而使用者要修幾次表單才知道全部問題，正是這條規則存在的原因。
- **所有狀態機轉移**：每個不允許的轉移都要有一條測試證明會被拒絕（例如已進入終態的資料不得再被變更、前置狀態不成立時不得轉移）。
- **併發衝突**：狀態變更類端點至少一條「兩個使用者對同一筆資料同時操作，第二筆被拒」的測試。

### 7.2 不必寫的測試

- 純轉發的 mapper、Drizzle schema 定義、常數表、框架本身的行為。這些改壞了型別檢查就會擋下，測試只是重複描述實作。

### 7.3 測試不可繞過正式流程

- **禁止在測試中直接改資料庫欄位來製造前置狀態**，凡是有對應正式流程（API 或 service 函式）者一律走該流程。

```ts
// ❌ 錯誤：直接關掉強制改密碼旗標。哪天這道閘門壞了，測試依然全綠。
await db.update(users).set({ mustChangePassword: false }).where(eq(users.id, id))
// ✅ 正確：走正式的變更密碼流程，順便驗證那道閘門還活著
await api.post('/credentials/main/update', { currentPassword, newPassword })
```

- 例外：製造「無法由正式流程產生」的髒資料（例如舊版遺留狀態）時可直接寫入，但**必須註明理由**。
- **禁止 mock 掉被測邏輯本身**。把額度計算 mock 起來去測那支呼叫它的端點，測到的只有 mock。

### 7.4 測試資料隔離

- 每個測試**自建自己的公司與員工**，用隨機後綴避免代碼碰撞；**禁止**多個測試共用同一筆 fixture 再互相修改——那會產生只在特定執行順序下失敗的測試，最後大家改成「重跑一次就好」。
- 測試資料庫由 migration 建立（與正式同一套），**禁止**另外維護一份測試用 schema——兩份會分岔，而分岔的那一刻測試就不再保證正式環境可用。
- **禁止在測試中連線正式或共用開發資料庫。** ✅（測試啟動時檢查連線字串，非測試庫即中止）
- 每個測試以交易包住並在結束時回滾，或以「新公司」隔離；**禁止 truncate 全庫**（會炸掉平行執行的其他測試）。

### 7.5 覆蓋率門檻的路徑必須自檢

通用規範 §7.5 只對純計算邏輯按路徑設 ≥ 90% 門檻。**按路徑設定的門檻有一個靜默失效模式，必須另外擋：**

- **覆蓋率設定中的每一組路徑（glob）都必須有「匹配數 > 0」的自檢**，匹配到 0 個檔案時應該讓 CI 失敗，而不是通過。 ✅（CI：讀覆蓋率設定，逐條 glob 展開並斷言命中檔案數 > 0）
  理由：glob 一旦匹配不到任何檔案——目錄搬家、模組改名、次目錄拆開（§0.2）、`.ts` 換位置——覆蓋率工具會**算出「這組路徑 100% 通過門檻」並靜靜通過**，門檻等於消失，而 CI 全綠。這與通用規範 §7.2 對掃描器的要求是同一件事：**設定裡的門檻只有在真的命中檔案時才存在**，而「有沒有命中」本身必須是一個會失敗的斷言。
  這條在本專案特別容易發作，因為 §0 的目錄規則會讓純計算邏輯集中在 `modules/*/*/domain/**`——那是一個**含兩層萬用字元**的路徑，任何一層的結構調整都可能讓它整組失準。

## 9. 尚待拍板（實作前請確認）

1. 軟刪除唯一鍵採 `deleted_seq NOT NULL DEFAULT 0`（§4.3）——需回寫資料模型文件，因為這是新增欄位。
2. 稽核日誌表名與逐欄定義尚未定案，§5.3 只規定內容要求，實作前需先定表。
3. 帳號鎖定與密碼複雜度尚未定案，§5.1 未涵蓋。「登出所有裝置」的**機制**已定於 §5.4.2（refresh token 伺服器端可撤銷）＋ `POST /sessions/main/logout-all`，**改密碼／重設密碼後自動作廢所有 session 已定案**（§5.4.5）；尚未定案的只剩**手動觸發的政策**：誰可以對誰執行 `logout-all`（本人以外，管理者能不能踢掉某位員工的所有裝置）。
4. **前後端不同源部署時需補 CSRF token（§5.4.3）**：cookie 屬性已定案為 `httpOnly + Secure + SameSite=Lax`。同源部署下 `Lax` 已擋住跨站 POST，不需要 CSRF token；但若前後端改為**不同源部署**（不同網域或不同子網域），`Lax` 會讓 cookie 送不出去，屆時必須放寬 `SameSite` 並**補上 CSRF token**——放寬的同時就把 CSRF 防線一起放掉了。這一項待部署拓樸確定。
5. refresh token 的具體壽命 30 天（§5.4.1）與 access token 的 2 小時滑動視窗（§5.4.1、§1.3）為初始值，上線後可依實際登出頻率調整；調整時**兩個數字要一起看**，不可只改其中一個。（**壽命縮短不再是撤銷的替代手段**——撤銷一律即時，見 §5.4.6。）
6. `refresh_tokens` 需要一個代表「**一次登入**」的欄位（一條輪替鏈共用，§5.4.7）——**規則已定案**，待辦的只有欄位名與型別，且需回寫資料模型文件，因為這是新增欄位。同一份文件也需記錄「撤銷狀態」要能被憑證驗證器**與權限碼查詢同一次取回**（§5.4.6 的成本論證建立在這件事上），這會影響該表與權限查詢的索引設計。
