# Sundial 後端開發規範

適用範圍：`Bun + Elysia + Drizzle ORM + MariaDB`，TypeScript `strict: true`。
本文件規定**程式碼怎麼寫**，不規定檔案放哪裡。資料模型以 [`docs/schema/`](schema/README.md) 為準，畫面行為以 [`docs/ui/`](ui/README.md) 為準。

閱讀方式：每條規則都是「**規則 → 理由（違反會怎樣）**」，容易寫錯的地方附正確／錯誤對照。標記 ✅ 者**可自動化檢查**，括號內為檢查手段；其餘靠 code review。
用語：**必須**＝違反即擋 PR；**禁止**＝同上反向；**建議**＝可用理由推翻但要寫在 PR。

## 1. API 設計規範

### 1.1 路徑命名

**本系統的 API 是 RPC over HTTP，不是 REST。** 這是明確的選擇，不是尚未修正的偏差：不使用 GET、參數全走 request body、request 帶 `cmd` 指令欄位、HTTP status 之外另有一層 envelope `code`——這四點任何一點都足以讓它不是 REST。既然已經偏離，就**一致地偏離**，不要半套：以下規則的共同目的，是讓「一支端點長什麼樣」完全沒有可討論的餘地。

- **所有端點的路徑一律為 `/<資源>/<動作>` 兩段**，資源片段用**複數 kebab-case**，動作片段用 **kebab-case**：

  ```
  POST /<資源>/create
  POST /<資源>/update
  POST /<資源>/delete
  POST /<資源>/list
  POST /<資源>/get
  POST /<資源>/approve
  POST /<資源>/reject
  ```

  單複數混用會讓前端無法用同一套命名推導端點，最後每個端點都要查文件。**沒有動作片段的端點不存在**——`POST /<資源>` 這種寫法一律不可，因為它讓 `cmd` 算不出來（§1.3），也讓「這支是建立還是查詢」只能靠 HTTP method 猜。
- **路徑不得帶任何參數。** 沒有 `{id}` 這類路徑參數，也沒有 query string。**所有參數（含識別碼 `id`）一律放 request body**（§1.5）。
  理由：識別碼放路徑等於讓同一支端點的輸入分散在兩個地方，schema 被拆成 `params` 與 `body` 兩份，前端包裝函式與後端驗證都要各自處理兩處；而且輸入永遠不會只有 `id`——很快就會出現「要不要一併帶明細」「要哪個版本的快照」這類條件，那些一定得放 body。統一放 body，**每支端點的輸入永遠只有一包**。
- **動作片段優先取自基本字彙**：`create`、`update`、`delete`、`list`、`get`，以及狀態動作 `approve`／`reject`／`revoke-approval`／`withdraw`。`/get<資源>List`、`/query<資源>`、`/doApprove` 這類把資源名或贅詞塞進動作片段的寫法一律不可。
  **確實沒有合適的字彙時才可自創**，但必須做到兩件事：(a) **把新動作加進這份字彙表**（與程式中的集中定義同步）；(b) **在 PR 描述中說明為什麼現有字彙不適用**。字彙表是一份**可增長的清單，不是封閉集合**——但每次增長都是一個被 review 過的決定，不是某支端點順手發明的。
  理由：動作若開放自由發揮而不留紀錄，同一件事會出現 `/list`、`/query`、`/search` 三種寫法，前端無法用同一套規則推導端點，`cmd` 也跟著三種寫法（§1.3）。優先使用既有字彙，是讓「猜得到」成為常態；有條件開放自創，是承認少數動作（例如 `refresh`、`reset`）確實無法塞進五個 CRUD 詞裡，硬塞只會塞出更難懂的名字。 ✅（自製掃描腳本：路由路徑的動作片段必須出現在集中定義的字彙表中，不在即失敗——新增動作要先改字彙表，這個改動本身就會出現在 PR diff 裡）
- **路徑固定兩段，沒有巢狀。** 需要表達關聯時改用獨立資源的端點，關聯條件放 request body：子項清單寫成獨立資源的 `POST /<子資源>/list`，body 平鋪帶父資源的識別碼。
  巢狀會讓同一份資料出現多條路徑，權限檢查與快取失效必須逐條重寫，遲早漏掉一條。
- **認證相關端點沒有例外，一律對應到真正的複數資源。** 不存在 `auth` 這種「功能群組」開頭的路徑：

  | 功能 | 路徑 |
  |---|---|
  | 登入 | `POST /sessions/login` |
  | 登出 | `POST /sessions/logout` |
  | 換發 token | `POST /sessions/refresh` |
  | 登出所有裝置 | `POST /sessions/logout-all` |
  | 改密碼 | `POST /credentials/update` |
  | 重設密碼 | `POST /credentials/reset` |

  這六支端點用到的 `login`／`logout`／`logout-all`／`refresh`／`reset` 五個動作，**依上一條的規則已正式列入動作字彙表**（第六支的 `update` 本來就在基本字彙裡）。它們都是「確實沒有合適字彙」的案例：`login`／`logout` 是這個動作的通用名稱——硬套 `create`／`delete` 並非不精準，而是**語意繞了一圈**：讀的人得先把「登入」轉換成「建立一個 session」才對得上，而規範的目的正是讓端點一眼看懂，**繞路的精準不如直白**；`logout-all` 同理，它與 `logout` 的差別在於刻意不指定目標裝置；`refresh` 不是 update——它產生的是一張新票而不是改舊票；`reset` 不是 update——呼叫者不知道也不需要知道舊值。
  理由：`auth` 不是一組可列舉的東西——你數不出「有幾個 auth」，它是一個功能分類的標籤。一旦為它開了口子，接下來 `report`、`export`、`setting`、`dashboard` 全都會援引同一條，用「這也是功能群組」合理化各種不複數的路徑，`/<資源>/<動作>` 這條規則就只剩下 CRUD 端點還遵守。**`sessions` 與 `credentials` 都是精準的複數名詞**：session 是可列舉的（一個裝置一張、可以逐一撤銷），credential 也是（密碼是使用者的一份憑證）。**這條規則約束的是資源片段，動作片段仍依上一條各自取最直白的字彙**——登入／登出取 `login`／`logout`（理由見上），改密碼就是**更新**憑證。規則零例外，路徑就永遠推導得出來。
- **基礎設施端點（`/health` 之類）不適用本節規範**：不帶 envelope、不帶 `cmd`、不需認證，路徑格式也不受 `/<資源>/<動作>` 約束。
  這是**排除適用範圍，不是開例外**——兩者的差別在於：例外會被援引（「既然 `/health` 可以，我這支也可以」），排除則有明確邊界。界線是「**這支端點是不是給本系統前端呼叫的業務端點**」：是，就一律照本節；不是（給 load balancer、監控系統、部署腳本用的維運端點），就不在本節管轄範圍內。這類端點必須集中在單一檔案並附註解說明用途（§1.2）。
- **`companyId` 禁止出現在 request body**。公司範圍一律由已驗證的 token 決定（見 §4.2）。
  一旦公司來自客戶端，任何人改一個字串就能讀別家公司的薪資；這是本系統最嚴重的單點風險。 ✅（自製掃描腳本：路由定義的 `body` schema 中出現 `companyId` 即失敗）

### 1.2 HTTP method：一律 `POST`

**本系統所有端點一律使用 `POST`，不使用 `GET`／`PUT`／`PATCH`／`DELETE`。**

理由分兩層：

- **`GET` 用不了**：每個 request 都必須帶 `rqTS`／`cmd`／`locale` 三個基底欄位（§1.3），**GET 沒有 request body，這三欄無處安放**。硬要塞進 query 就等於為讀取端點另開一套參數傳遞方式，envelope 立刻變成兩種形狀，出入口的統一處理（補 `rspTS`／回聲 `cmd`、log 對時）也必須寫兩份。`DELETE` 另有一個獨立問題：**它的 request body 在部分代理與中介層會被丟棄**，同一支端點在開發機正常、過了公司 proxy 就收到空 body，而且是間歇性的。
- **`PUT`／`PATCH` 是「還留著就會出事」**：動作已經寫在路徑裡（§1.1）、參數已經全在 body 裡（§1.5），**HTTP 動詞不再承載任何資訊**。留著多種動詞，只會讓每次新增端點都要多做一次「這支該用哪個」的判斷，而那個判斷**沒有標準答案**——一支 `update` 只改三個欄位算全量還是局部？收斂成一個動詞之前，答案取決於誰寫的；收斂之後，這個問題連問都不會被問到。一律 `POST`，是把一個沒有標準答案的判斷從流程中刪掉。

| 意圖 | 寫法 |
|---|---|
| 查詢列表 | `POST /<資源>/list` |
| 查詢單筆 | `POST /<資源>/get` |
| 建立 | `POST /<資源>/create` |
| 更新 | `POST /<資源>/update` |
| 軟刪除 | `POST /<資源>/delete` |
| **狀態變更（核准、退回、撤銷核准、撤回）** | `POST /<資源>/approve`、`/<資源>/reject`、`/<資源>/revoke-approval`、`/<資源>/withdraw` |

上表每一支的識別碼都在 request body，路徑上一個參數也沒有。

- **禁止註冊 `POST` 以外的路由**（健康檢查等基礎設施端點不在適用範圍內，見 §1.1 末條，且必須集中在單一檔案並附註解）。 ✅（自製掃描腳本：路由註冊出現 `.get(` / `.put(` / `.patch(` / `.delete(` 即失敗，白名單需附註解）
- **禁止在 request body 帶 `status` 欄位**來完成核准或作廢，狀態變更只能走上表的狀態動作端點。
  狀態欄位可寫，等於客戶端可以直接把資料改成任一目標狀態，跳過該轉移應有的前置檢查與必填原因。狀態機一旦破口，後續依賴該狀態的計算全部失準。 ✅（自製掃描腳本：request body schema 內出現 `status` 欄位即失敗，白名單需附註解說明）
- 狀態動作端點必須在 `data` 回傳變更後的完整資源，讓前端不必再打一次查詢端點。
- 規格要求必填原因的動作，`reason` 在 schema 層即設為必填，不得只在 service 檢查。

### 1.3 Request／Response envelope

全站**只有一種** request 形狀與一種 response 形狀，所有端點一致。envelope 由出入口層統一處理，端點自己只管業務欄位與 `data`。

#### Request envelope（平鋪，不巢狀）

每個 request 都繼承三個基底欄位，**業務欄位平鋪在同一層**，不另開 `payload`／`params` 之類的巢狀節點：

```json
{
  "rqTS": "2026-04-14T14:30:00+08:00",
  "cmd": "<資源>.list",
  "locale": "zh-TW",
  "keyword": "王",
  "parentId": "..."
}
```

| 欄位 | 型別 | 說明 |
|---|---|---|
| `rqTS` | string | 請求時戳，ISO 8601 **帶時區偏移**（`2026-04-14T14:30:00+08:00`），見 §6.1 |
| `cmd` | string | 指令名稱，**跟著 API 命名走，與路徑一一對應** |
| `locale` | string | 語系（`zh-TW`） |

- `cmd` **必須等於路由路徑的機械轉換結果**，不一致即失敗。 ✅（自製掃描腳本：以路由路徑依下述規則推導期望的 `cmd` 值，與 schema 中宣告的常值比對）

**`cmd` 推導規則：純機械字串轉換。** 取路徑，**去掉開頭的 `/`，把剩下的 `/` 換成 `.`**，其餘一字不改——不做單複數轉換、不轉 camelCase。

| 路由 | `cmd` |
|---|---|
| `POST /<資源>/list` | `<資源>.list` |
| `POST /<資源>/approve` | `<資源>.approve` |
| `POST /sessions/login` | `sessions.login` |
| `POST /credentials/update` | `credentials.update` |

- **這條規則沒有任何例外分支。** 因為路徑一律是 `/<資源>/<動作>` 兩段、沒有路徑參數、沒有巢狀（§1.1），輸入形狀只有一種，轉換函式就只有一行字串處理，**每一支端點都算得出期望值**。
- 原樣轉換的理由：任何「聰明」的轉換都需要額外知識。轉單數要處理不規則變化，而由多個詞組成的複合資源名，其單數形**沒有唯一答案**（該保持連字號式，還是轉成 camelCase？）；轉 camelCase 又讓 `cmd` 無法反推回路徑。原樣轉換的推導函式只有一行字串處理，**人腦與腳本永遠得到同一個值**，這正是這條檢查能成立的前提——推導規則只要有一絲模稜兩可，腳本就算不出期望值，檢查就寫不出來。
- 理由（為什麼要檢查）：`cmd` 是 log 與問題追查時唯一好用的關鍵字。**路徑改了但 `cmd` 忘了改，log 就開始騙人**——你在 log 裡搜到的某個 `cmd` 其實是另一支端點打的，追查方向從第一步就錯，而且沒有任何東西會提醒你。
- 平鋪而不巢狀的理由：巢狀之後每支端點都要決定「這個欄位算基底還是業務」，於是同一個 `keyword` 在 A 端點在外層、在 B 端點在 `payload` 內，前端無法用同一個包裝函式送請求。

#### Response envelope

```json
{
  "code": "200",
  "msg": "",
  "errors": [],
  "data": null,
  "rspTS": "2026-04-14T14:30:01+08:00",
  "cmd": "<資源>.list",
  "locale": "zh-TW",
  "expiresIn": 3600,
  "exp": "2026-08-19T18:28:28+08:00"
}
```

| 欄位 | 型別 | 說明 |
|---|---|---|
| `code` | string | 六碼之一，見下表 |
| `msg` | string | 回應訊息 |
| `errors` | array | **僅 `code='300'` 時提供**，見下方 errors 結構 |
| `data` | object \| null | 各 API 自行收窄型別；無資料回 `null` |
| `rspTS` | string | 回應時戳，ISO 8601 帶偏移，**由出口層補上** |
| `cmd` | string | 原樣回傳，出口層補上 |
| `locale` | string | 原樣回傳，出口層補上 |
| `expiresIn` | int \| null | Session 剩餘**秒數**（**滑動視窗**，見下）；**過期判斷唯一依據**；`null` = 本次請求未經 Session 授權 |
| `exp` | string \| null | Session 絕對截止時刻，ISO 8601 帶時區偏移；**僅供 log 與除錯——禁止用於過期判斷，也禁止顯示給使用者**（見下）；`null` 時機同 `expiresIn` |

- **禁止裸陣列**，清單一律包在 `data` 內（見 §1.4）。裸陣列之後要加分頁資訊就是破壞性改版。
- `rspTS`／`cmd`／`locale` **一律由出口層統一補上，禁止各端點自行填寫**。散在各處填的結果是有些端點忘了填，前端的通用處理就得寫「有就用、沒有就算了」的分支，回聲比對（§1.4）也跟著失效。
- **`expiresIn` 是滑動視窗，不是固定到期時間。** 每一次通過 Session 授權的請求都會**續期**，因此**每個回應都必須回傳續期後的剩餘秒數**，而不是「發證當下算出來、之後遞減」的值。前端據此在每次回應覆寫自己的 deadline（前端規範 §3.7），使用者只要還在操作就不會被登出，停止操作滿一個視窗長度才過期。
  理由：若後端只在登入時給一次、之後各回應原樣回傳同一個數字，前端每次覆寫 deadline 就會把 session 無限延長；反之若後端回傳的是遞減值而實際上有續期，前端會提早把人踢出去。兩種錯法都不會有任何錯誤訊息，只會表現為「有時候被登出、有時候登不出」，而且無法重現。**續期與回報必須是同一件事的兩面：只要續期了，就得把新的秒數帶回去。**

**`expiresIn` 與 `exp` 並存，但用途分工必須嚴格。**

| 欄位 | 唯一用途 | 禁止 |
|---|---|---|
| `expiresIn`（int，秒） | **判斷 session 是否過期**。前端收到當下算 `deadline = Date.now() + expiresIn * 1000` 保存，之後一律用 `Date.now()` 與這個 `deadline` 比較（前端規範 §3.7） | — |
| `exp`（string，ISO 8601 帶時區偏移，如 `2026-08-19T18:28:28+08:00`） | **寫進 log 與錯誤回報，供除錯用** | **禁止用於任何過期判斷**（含「快到期」提示的門檻判斷）；**禁止顯示給使用者** |

- 分工的理由是**兩者比較的兩端來源不同**：`exp` 是伺服器算出的截止點，要拿去跟**裝置**的現在時刻比較——兩個時鐘，裝置偏移多少判斷就錯多少。使用者的筆電慢 10 分鐘，session 就會晚 10 分鐘才被判定過期（或早 10 分鐘把人踢出去），而這在伺服器端完全看不出來、也重現不了。`expiresIn` 是相對秒數，**寫入 `deadline` 與讀取比較用的是同一個時鐘**，偏移量在相減時抵銷，時鐘準不準都不影響結果。
- 那為什麼還要 `exp`：**log 對時需要一個絕對時刻**，`expiresIn` 給不出來（它只說「還有 3600 秒」，log 聚合時無法與其他系統的時間軸對齊）。追查「這個 session 到底什麼時候該死」時，log 裡有一個絕對時刻才對得上其他系統的時間軸。**這是 `exp` 的唯一用途。**
- **`exp` 一律不顯示給使用者。** 帶時區偏移的時間字串（`rqTS`／`rspTS`／`exp` 三者）全部只供 log 與除錯，**沒有例外**（§6.1）。畫面若要呈現「還剩多久」，一律由 `expiresIn` 倒數推導——這樣同時避開**時區**（帶偏移的字串會被瀏覽器再換算一次）與**裝置時鐘偏移**（絕對時刻要跟裝置的「現在」比）兩個問題，而顯示一個絕對時刻兩個問題都會踩到。
- ✅（自製掃描腳本／ESLint：前端的 session 過期判斷邏輯中禁止引用 `exp`，且任何顯示路徑——模板、format 函式的輸出——亦禁止引用 `exp`，見前端規範 §3.7、§9.2）

#### HTTP status 與內部 `code` 映射

內部 `code` 是 **string**（不是 int），集中定義為常數：

```ts
export const WebFlowCode = {
  DataSuccess:      '200',  // 正常
  DataInvalid:      '100',  // 資料不正確
  LogicError:       '300',  // 邏輯錯誤（業務規則不允許）
  SystemError:      '400',  // 系統錯誤
  AuthRequired:     '900',  // 無有效身分
  PermissionDenied: '901',  // 有身分但無權限
} as const
```

| HTTP | `code` | 意義 | 前端處置 |
|---|---|---|---|
| 200 | `200` | 正常 | — |
| 400 | `100` | 資料不正確 | 進錯誤回報（代表呼叫端 bug） |
| 401 | `900` | 無有效身分 | 導向登入頁 |
| 403 | `901` | 無權限 | 顯示無權限，**不可**導登入頁 |
| 404 | `400` | 系統錯誤 | 顯示系統錯誤 |
| 409 | `300` | 邏輯錯誤 | 顯示業務訊息，讀 `errors` |
| 422 | `300` | 邏輯錯誤 | 同上 |
| 500 | `400` | 系統錯誤 | 顯示系統錯誤 |

- **不使用的 HTTP status：201、202、429、423。** 建立成功回 200，不回 201。
- **這張表的分類軸不是 HTTP 語意，而是「前端拿到之後該做什麼」。** 這是理解整張表的關鍵：六個 `code` 對應的是六種前端動作（照常處理／進錯誤回報／導登入／顯示無權限／顯示業務訊息／顯示系統錯誤），而不是六種伺服器狀態。因此多個 HTTP status 會映到同一個 `code`（404 與 500 都是 `400`，409 與 422 都是 `300`）——**因為前端對它們該做的事一模一樣**。反過來說，只要前端該做的事不同，`code` 就必須不同。
- **「查無資料」不是 404**，是 **HTTP 200 + `code='200'` + `data: null`**（清單則是空陣列）。`404` 代表**端點不存在**，也就是前端打錯路徑或前後端部署不同步。
  理由：把「查無資料」當 404 之後，前端就無法區分「這組條件確實查不到資料」與「這支 API 根本不在」，而這兩件事的處置完全相反（一個顯示空狀態，一個要告警）。
- **`900` 與 `901` 必須分開。**
  理由：把 403 當 401 處理，會造成**「使用者已登入 → 被踢回登入頁 → 登入完又被踢回」的無限迴圈**——使用者只是點到一個沒權限的功能，結果整個系統看起來像壞了，而且他每次重登都會再遇到一次。
- **404 與 500 合併為 `400` 的副作用必須由後端 log 補回。** 前端看不出「打錯端點」與「伺服器爆炸」的差別，因此：
  - 後端 log **必須分類**，至少分 `route_not_found`／`unhandled_exception`／`upstream_timeout` 三類；
  - 回應 header 帶 **`X-Trace-Id`** 供追查，前端在錯誤回報時一併帶上；
  - **404 必須獨立告警，且門檻比 500 低。**
    理由：404 通常代表**前後端部署不同步**（前端已上線、後端還沒，或路徑改名只改了一邊）。這種問題**測試環境測不出來**（兩邊都是最新的），一上線就是整片功能同時死掉，而每一筆都只是「404」這種平常被當成雜訊忽略的東西。門檻設得比 500 低，是因為 500 偶發一兩筆可能只是單一請求出錯，404 偶發一兩筆卻已經代表有一條路徑對不上。

#### `expiresIn` 的續期時機（在 middleware 層，與處理結果無關）

**續期發生在身分驗證的 middleware 層：只要 token 在有效期內且驗證通過，就續期。** 續期與後續處理結果**完全無關**——不管資料有沒有找到、request 欄位對不對、業務規則過不過、有沒有權限做這個動作。

因此各 `code` 的 `expiresIn` 取值是固定的：

| `code` | 意義 | `expiresIn` |
|---|---|---|
| `200` | 正常 | 續期後的秒數 |
| `100` | 資料不正確 | 續期後的秒數 |
| `300` | 邏輯錯誤 | 續期後的秒數 |
| `400` | 系統錯誤 | 續期後的秒數 |
| `901` | 有身分但無權限 | **續期後的秒數**（身分有效，只是這個動作不准） |
| `900` | 無有效身分 | `null` |

- 理由：**身分驗證在整條鏈的最前面**，身分驗證過了就代表使用者仍在活動，後面發生什麼都不改變「他還在線上」這個事實。反過來說，若把續期綁在「處理成功」上，使用者連續填錯三次表單就會被登出——他明明一直在操作，系統卻認為他離開了，而且沒有任何錯誤訊息解釋這件事。
- `901` 特別容易被寫成不續期（直覺上「被拒絕」看起來像失敗），但那正是最不該的：使用者點到一個沒權限的功能，等於順便把自己的 session 熬短，下一次真正有權限的操作反而吃到 `900`。
- `900` 是唯一回 `null` 的情況，因為此時根本沒有一個有效身分可以續期。前端收到 `null` **不得**據此判定 session 已失效（未經 Session 授權的公開端點也回 `null`），處置一律照 `code` 走（前端規範 §3.6、§3.7）。
- `exp` 與 `expiresIn` 同步：續期時兩個欄位一起重算，禁止只更新其中一個。兩者不同步時，log 上的截止時刻與實際被登出的時刻對不上，而追查登出問題時唯一的線索就是 log——線索本身在騙人，等於沒有線索。
- ✅（測試：每個端點的 `901` 案例必須斷言 `expiresIn` 為非 `null` 的正數，`900` 案例必須斷言 `expiresIn` 為 `null`）

#### `errors` 結構

```json
"errors": [
  { "code": "<領域>.balance-insufficient", "msg": "剩餘額度不足", "data": { "field": "days", "remaining": 3, "requested": 5 } }
]
```

| 欄位 | 型別 | 說明 |
|---|---|---|
| `code` | string | 錯誤碼，**語意化命名** |
| `msg` | string | 錯誤訊息 |
| `data` | object | **map/object，不是 list**；慣例帶 `field` 指出出錯位置（**路徑式，見下**），其餘為該錯誤的具體細節 |

**`errors[].data.field` 一律使用路徑式（dot-path），禁止扁平欄位名。**

- 規則：從 request body 根層寫到出錯的那一格，**陣列以索引表示，0 起算**：`items.2.startTime`、`detail.startDate`、`items.0.code`。單層欄位自然退化成 `days` 這種形式，不是例外。
- 理由：本系統多處畫面會出現**「同一種欄位在陣列中重複出現」**的結構。在這些畫面上，`field: "startTime"` 無法回答「是哪一筆的 `startTime`」，前端唯一能做的就是退化成全域提示，等於這個 `field` 白給；使用者面對一張有五列的表格，只被告知「時間格式錯誤」，得自己逐列比對。帶了索引，前端才能定位到**該列該格**並捲過去。
- **後端在驗證迴圈中必須把索引帶進錯誤物件，禁止只丟欄位名。** 這條特別容易違反，因為在迴圈裡拋錯的當下手邊只有那一筆物件，索引要刻意從迴圈變數帶進去；漏帶不會有任何錯誤，只是前端從此定位不到。
- 需要指出**衝突對象**時，在 `data` 內另外帶其他路徑（例如 `conflictWith: "items.1"`），不要把兩個位置塞進同一個 `field` 字串。
- 完整範例（陣列中第 3 筆的時間區間與第 2 筆重疊）：

```json
"errors": [
  {
    "code": "<領域>.time-range-overlap",
    "msg": "時間區間重疊",
    "data": { "field": "items.2.startTime", "conflictWith": "items.1" }
  }
]
```

- 前端的對應處理（依 dot-path 定位到該列該格，找不到才退全域提示）見前端規範 §6.3。
- 錯誤碼命名 `<領域>.<原因>`，領域用單數名詞、原因用 kebab-case：`auth.invalid-credentials`、`<領域>.already-exists`、`<領域>.period-locked`、`<領域>.balance-insufficient`。**這就是 `errors[].code` 的取值來源**，兩者是同一組字彙、同一份集中定義。
  **錯誤碼的「領域」與路徑的「資源」是兩套獨立的命名空間**，不必也不應強行對齊：路徑的資源必須是複數且可列舉（§1.1），錯誤碼的領域則是**單數的功能分類**，因此 `auth.invalid-credentials` 是正確的寫法，即使路徑上不存在 `/auth/...`（登入端點是 `POST /sessions/login`）。兩者混淆的後果是反過來的：為了配合 `sessions` 而把錯誤碼寫成 `sessions.invalid-credentials`，會讓「憑證錯誤」這個跨端點的語意被綁死在單一資源上，改密碼端點要回同一種錯時就無碼可用。
  **禁止編碼式命名**（`SHIP001`、`E4012` 這種）：編碼式要查表才知道是什麼錯，而那張表一定會過期；語意化命名讓 log、告警、前端分支都能一眼看懂。 ✅（型別：錯誤碼集中為 `as const` 聯集型別，拋錯時只能用聯集內的值）
- 前端據 `code` 決定行為（focus 欄位、顯示對應文案），據 `msg` 只做 fallback。訊息文案一改前端就壞，是因為有人拿 `msg` 做判斷。
- **`errors` 僅在 `code='300'` 時提供**，其餘 `code` 一律是空陣列。 ✅（型別：envelope 型別以 `code` 判別聯集，`code !== '300'` 時 `errors` 型別為 `[]`）
- **`code='100'` 完全不提供 `errors`。** 這條後人一定會想「順手加一下比較方便」，所以理由寫在這裡：**API 契約已經定義好，送錯代表呼叫端沒照契約來，那是開發期就該發現的問題，不是執行期要引導使用者的問題。** 使用者層級的輸入問題會走 422 → `300`，那裡才有 `errors`。
- **每支端點的 response 定義必須宣告自己會吐出哪些 `errors[].code`，且未宣告者不得在執行期出現**（§1.8.3）。沒宣告的話，前端要處理哪幾種業務錯誤只能靠問人或試出來，而新增一個錯誤碼也不會有任何地方變紅。

### 1.4 List 端點：分頁、排序、篩選

**Request**：基底三欄（§1.3）＋ 搜尋條件平鋪 ＋ `perPage`／`currentPage` 平鋪 ＋ `sort` 物件。

```json
{
  "rqTS": "2026-04-14T14:30:00+08:00",
  "cmd": "<資源>.list",
  "locale": "zh-TW",
  "keyword": "王",
  "parentId": "...",
  "perPage": 20,
  "currentPage": 1,
  "sort": { "field": "createdAt", "order": "desc" }
}
```

- `perPage`：**必填，預設 20**，上限 100。
- `currentPage`：**必填，預設 1**（1 起算）。
- **禁止**在不同端點改叫 `page`、`pageNo`、`size`、`limit`、`offset`。
- `sort`：物件 `{ "field": "createdAt", "order": "asc" | "desc" }`，**不支援多欄排序**。排序欄位**必須白名單**，直接把字串接進 SQL 等於開放 SQL injection 與全表掃描。
- 篩選參數用扁平 camelCase（`status`、`<關聯>Id`、`dateFrom`、`dateTo`、`yearMonth` 這類）。日期區間一律 `xxxFrom` / `xxxTo`（含端點）。
- **列表端點一律分頁，禁止無上限查詢。** 不設限的按月查詢在中型客戶就是數萬列，一次撈完會打爆記憶體並拖垮連線池。

**Response**：`data` 收一層 pagination 結構，**實際清單在 `data.data`**。

```json
"data": {
  "search":     { "keyword": "王", "parentId": "..." },
  "sort":       { "field": "createdAt", "order": "desc" },
  "pagination": { "currentPage": 1, "perPage": 20, "totalCount": 137 },
  "data":       [ ... ]
}
```

- **不提供總頁數**，前端由 `totalCount / perPage` 自行計算。
  理由：兩個數字並存時，只要有一邊算錯（改了 `perPage` 預設值、加了篩選卻沒同步重算），就會出現「共 137 筆、14 頁」但實際只有 13 頁可點的狀況——而且**兩個數字都來自後端，前端沒有任何依據判斷該信哪一個**。只回 `totalCount`，總頁數就只有一個算法、一個出處。
- **`search` 與 `sort` 必須原樣回聲。** 這不是多餘欄位，拿掉會直接產生 race condition：
  使用者快速切換篩選條件時會連續送出多次查詢，而**回應到達順序不保證**——第二次查詢可能比第一次先回來。回聲值讓前端能比對「這包回應是不是我現在畫面上這組條件的結果」，不是的就丟掉。沒有它的話，較慢的舊回應會蓋掉較新的回應，畫面上的資料與篩選條件對不上，而且**沒有任何錯誤**：使用者選了 A 條件卻看到一整片 B 條件的資料，只會認為系統壞了。前端側的規則見前端規範 §7.3。
- **條件變更必須回到第 1 頁**由前端負責；後端在 `currentPage` 超出範圍時回空陣列與正確的 `pagination`，**不得回 404**（404 是端點不存在，見 §1.3）。

### 1.5 所有參數一律走 request body

- **所有參數一律放 request body，沒有例外。** 識別碼（`id`）、篩選條件、分頁、排序——全部平鋪在 body 裡。**路徑上不會有參數**（§1.1），因此不存在「這個參數該放哪」的判斷。
  這條與 §1.1「路徑不得帶任何參數」是同一件事的兩面：路徑既然固定是 `/<資源>/<動作>`，能承載參數的地方就只剩 body 一處。好處是**每支端點的輸入永遠只有一包**，schema 只有 `body` 一份（§2），前端的包裝函式也只有一種形狀。
- **禁止使用 query string，也禁止使用路徑參數。** 路由不得宣告 `query` schema，也不得宣告 `params` schema。 ✅（自製掃描腳本：路由定義中出現 `query:` 或 `params:` schema、或路徑字串含 `:` / `{` 即失敗）
  理由（除了 envelope 之外的一條）：query 會被寫進 access log、反向代理 log 與瀏覽器歷史，把事由文字、姓名關鍵字這類個資留在一堆沒人管保存期限的地方。
- **因為不使用 query，query 的字串型別陷阱在本專案不存在**：`?page=abc` 變 `NaN`、`?flag=false` 被 `Boolean()` 判成 `true` 這類問題沒有發生的餘地，也**不需要 `t.Numeric()`／`t.BooleanString()` 這類轉型 schema**。body 是 JSON，`20` 就是 number、`false` 就是 boolean，schema 只做驗證不做轉型。

```ts
// ✅ 正確：JSON body，型別即是型別，schema 只驗證不轉型
body: t.Object({
  ...BaseRequest,                                    // rqTS / cmd / locale
  keyword: t.Optional(t.String({ maxLength: 50 })),
  includeExpired: t.Optional(t.Boolean()),           // 真正的 boolean
  perPage: t.Integer({ minimum: 1, maximum: 100, default: 20 }),
  currentPage: t.Integer({ minimum: 1, default: 1 }),
})
// ❌ 錯誤：本專案不使用 query string
query: t.Object({ page: t.Numeric(), includeExpired: t.BooleanString() })
```

### 1.6 版本策略與不相容變更

- **API 路徑不帶版本前綴。** 禁止 `/api/v1/...`、`/v2/...` 這類片段，`/<資源>/<動作>` 就是最終路徑（路徑恆為兩段，§1.1）。
  理由：本系統前後端同 repo、同一批人同時發版，沒有「舊版客戶端長期存活」的情境。版本前綴在這種情況下不是相容性保障，只是每個端點多一段永遠不會遞增的字串；真要遞增時得複製整組路由、測試與權限設定，維護成本直接翻倍。
- 少了版本號這道護欄，**相容性完全靠變更紀律維持**，因此以下分類必須嚴格套用。

**破壞性變更**（符合任一即是）：

- 刪除 request／response 欄位；
- 更改欄位名稱；
- 更改欄位型別（含 `number` ↔ `string`、單筆 ↔ 陣列）；
- 把選填欄位改為必填；
- 縮小允許值範圍（列舉值變少、`maxLength` 變小、數值上下限收窄、格式變嚴）；
- 改變既有 `errors[].code` 的語意，或改變某情境對應的 HTTP status ／ envelope `code`（§1.3 映射）；
- 更改路徑（連帶就是更改 `cmd`，§1.3）。HTTP method 恆為 `POST`（§1.2），不會是變更的來源。

**相容變更**：新增選填欄位、在 response 新增欄位、新增端點、新增列舉值且舊值仍完全支援、放寬既有限制。

- **破壞性變更必須兩步走，禁止一次到位：**
  1. 新舊兩種形式**同時支援**，舊的在 schema 標記 `deprecated`，並在程式碼註明預定移除的條件；
  2. 確認前端全部改用新形式**且已部署**；
  3. 才在獨立的 PR 中移除舊形式。
  理由：前後端不是原子部署，中間一定有時間差。一次到位的破壞性變更，會讓**部署順序決定系統壞多久**——後端先上，所有還在用舊欄位的前端頁面立刻吃 422 或顯示 `undefined`；前端先上，新欄位後端還不認識，一樣壞。差別只在壞的是哪一邊，而不在會不會壞。兩步走則兩種部署順序都是安全的，回退也安全。
- 移除舊形式的 PR **必須在描述指出對應的前端變更與其部署時間**，否則無從判斷第 2 步是否真的完成，「暫時保留」會變成永久保留。

### 1.7 API 契約：OpenAPI，由後端程式碼產生

- **前端與後端即使放在同一個 repo，也是兩個獨立部署的系統，溝通只能透過 HTTP API。** 因此「API 長什麼樣」必須有一份機器可讀、雙方都認的定義，而不是靠口頭或靠讀對方的程式碼。前端禁止 import 後端的任何型別或程式碼（前端規範 §3.5），能跨越這條界線的只有下述產生物。
- **路由宣告的 schema（§2）是契約的唯一真相**；OpenAPI 文件一律**由後端程式碼產生**，禁止另外手寫或手動維護一份 spec 檔。
  理由：手寫的 spec 是第二份真相，跟程式碼必定漂移；漂移之後前端拿到的型別是錯的，而編譯照樣通過，錯誤延到執行期才出現在離成因最遠的地方。
- **每個對外端點都必須宣告完整的 request 與 response schema（§2 第一條），這是整條契約鏈的單點失效。**
  理由：少宣告一個 response schema，產生出來的 OpenAPI 在那個端點就是個空洞（`{}` 或 `unknown`）。前端拿不到型別，唯一的出路是自己手寫一份 interface——於是前端規範 §3.2「禁止手寫 DTO」被迫破例，契約單一來源在那一刻就失效了，而且是從最不起眼的地方失效。 ✅（自製掃描腳本：同 §2，缺任一項即失敗）
- **每個端點在 OpenAPI 上只有 `requestBody`，沒有 `parameters`。** 路徑不帶參數、不用 query（§1.1、§1.5），因此 `parameters` 一律是空的——出現任何 `parameters` 項目就代表有人違反了 §1.1。所有端點都是 `post`，路徑本身沒有 `{}` 模板片段。
  這對前端產生物的意義是：產生出來的 client 函式**每支都只有一個參數**（那包 body），不會有「第一個參數是 id、第二個是 options」這種因端點而異的簽章。
- **envelope 在 OpenAPI 上的表達方式（§1.3、§1.4）：**
  - request：`requestBody` 為 `allOf` [ `BaseRequest`（平鋪的 `rqTS`／`cmd`／`locale`）, 端點自己的平鋪欄位 ]
  - response：`allOf` [ `BaseResponse`, `{ data: 端點的 data schema }` ]
  - list response：`data` 以 `PaginationResponse<T>` 的組合表達（`search`／`sort`／`pagination`／`data`）
  - **實作上這是一個 `envelope(dataSchema)` 包裝函式，不是類別繼承。** 我們是 TypeScript／Elysia，不是 PHP：不要做 `BaseResponse` 基底類別再讓每個端點的 response 去 extends，也不要為每支端點手寫一個 `XxxResponse` 型別。 ✅（自製掃描腳本：路由的 `response` schema 必須是 `envelope(...)` 的呼叫結果，直接寫 `t.Object({ code: ... })` 即失敗）
    理由：繼承會讓每支端點多一個只為了掛 `data` 而存在的型別名稱，改 envelope 時要改的是 N 個子類別而不是一個函式；而包裝函式讓 `data` 的型別自然被泛型帶出去，前端產生的型別直接就是收窄過的形狀。
- **產生流程：**
  - 指令 `bun run gen:api`：載入 Elysia app 定義 → 輸出 `openapi.json` → 由該檔產生前端型別與 API client。
  - **該指令必須能在後端服務未啟動、資料庫未連線的情況下執行**（只 import app 定義，不 `listen`、不連 DB、不跑 migration）。 ✅（CI：在沒有 DB service 的 job 中執行 `bun run gen:api`）
    理由：前端開發者與 CI 只是要一份型別。若必須先起後端與 MariaDB 才能產生，這個指令就會在新人的第一天失敗，結果是「跑不起來，先沿用舊型別」——契約單一來源等於沒有。
  - **產生物（`openapi.json`、前端型別與 client）不進版控**，一律列入 `.gitignore`，需要時重跑 `bun run gen:api` 取得；**禁止手動修改產生物**。
    理由：產生物進版控後必然出現「忘了重跑」的髒 diff，review 時也分不出哪些行是人改的、哪些是機器產的。
- **端點清單快照測試（必須有）**：把所有已註冊路由的 `path`、宣告的 `cmd` 值與 request body 的必填欄位，以穩定排序序列化成快照檔，**快照檔進版控**；端點有增刪改時測試變紅，必須有人明確更新快照。 ✅（測試：端點清單快照比對）
  method 不必記錄，因為它恆為 `POST`（§1.2）——記一欄永遠相同的值只會讓快照變大、diff 變吵。**`path` 與 `cmd` 兩欄都要記**，雖然後者可由前者推導（§1.3）：快照的用途是讓契約變更出現在 PR diff 裡，兩欄並列時「路徑改了但 `cmd` 沒改」在快照上就是一行紅綠不對稱，reviewer 一眼看得到，不必等 CI 的一致性檢查。
  理由：code-first 的 spec 是產生物、不進版控，於是**對外契約的變更不會出現在 PR diff 裡**——改一行 schema 就悄悄改了 API，reviewer 什麼也看不到。這正是拿掉版本前綴（§1.6）之後最需要補的洞。快照檔把契約變更重新拉回 diff：路徑改名、欄位從選填變必填、端點被刪掉，都會在 PR 中變成一段紅綠對照，逼出「這是不是破壞性變更、有沒有走兩步走」這個問題。這是替代把關機制，不是加分項。

### 1.8 Response envelope 怎麼產出（唯一入口與分層責任）

§1.3 規定 envelope **長什麼樣**，這一節規定 envelope **由誰、在哪裡產出**。兩件事都要規定，因為格式定得再清楚，只要每個開發者各自手工組那包 JSON，形狀還是會長歪——而且是各歪各的。

#### 1.8.0 一次請求的完整路徑

先把整條路走一遍，後面每一小節都是在講其中一步的規則：

```text
① request body（一份 JSON）
      ▼
② 身分驗證 middleware：token 有效即**續期**（§1.3），無效則就地回 `900`
      ▼
③ 路由：body schema 驗證（§2；沒有 params／query 可驗，§1.5）——格式與範圍不符即 422／`code='300'`，不會進到下一步
      ▼
④ 端點 handler：把驗證後的輸入轉成 service 的輸入型別，呼叫 service
      ▼
⑤ service／domain：只做業務邏輯。成功回業務資料；失敗以具名錯誤類別拋出領域錯誤（§3.1）
      ▼
⑥ 端點 handler：以映射函式把業務資料收成本端點的 `data` 形狀（§2「禁止直接回 Drizzle row」）
      ▼
⑦ envelope 產生函式：包成 envelope，填 `code`／`msg`／`errors`／`data`
   （失敗路徑：統一 error handler 先把領域錯誤映射成 HTTP status ＋ `code` ＋ `errors[]`，再進同一個產生函式）
      ▼
⑧ 出口層：補上 `rspTS`／`cmd`／`locale`／`expiresIn`／`exp`
      ▼
⑨ 回應
```

**②在③之前，是 §1.3 續期規則的結構性保證**：續期發生在驗證通過的當下，那時候還不知道 body 對不對、資料找不找得到、有沒有權限，所以「續期」與「處理結果」在程式結構上就不可能耦合。這也是為什麼 `100`／`300`／`400`／`901` 全都帶續期後的秒數——它們都是②之後才發生的事。

**三種形狀不可混用**，中間的轉換是刻意的邊界，不是多餘的搬運：

| 形狀 | 用途 | 出現在哪 |
|---|---|---|
| 驗證後的 request 型別 | HTTP 入口 | 端點 handler 開頭 |
| service／domain 的輸入與輸出型別 | 跨層傳遞 | service ↔ domain ↔ repository |
| 端點的 `data` 型別 | HTTP 出口 | 端點 handler 結尾 |

- **禁止把驗證後的 request 型別直接丟進 domain**，也**禁止把 repository／service 的回傳值直接指派給 `data`**。理由與 §2「禁止 `response` 直接回傳 Drizzle 的 row 物件」同源：一旦兩端共用同一個型別，資料表加一個欄位就自動出現在 API 上，而且沒有任何一行程式碼會改變。

#### 1.8.1 唯一產出入口

- **所有回應必須經由統一的 envelope 產生函式產出**（§1.7 的 `envelope(dataSchema)` 及其執行期對應物），**禁止在 handler 內以物件字面值手工組 envelope**。handler 只回傳業務資料，由產生函式包成 envelope。 ✅（自製掃描腳本：路由的回傳值必須是 envelope 產生函式的產物；handler 檔案中禁止出現含 `code:`／`rspTS:`／`expiresIn:` 的物件字面值）
  理由：手工組的 envelope 會**漏欄位**、會**拼錯欄位名**、會**忘記在錯誤路徑上也包一層**，而這三件事**都不會有任何編譯錯誤**——TypeScript 只知道你回了一個物件，少一個 `locale`、把 `rspTS` 打成 `rspTs`，型別檢查照樣過；測試若只斷言 `data` 的內容，也照樣綠。最後是前端拿到形狀不對的回應才發現，而那時離成因已經很遠，且問題會以「某一支端點的統一處理失效」這種零星形式出現，看起來像前端的 bug。

```ts
// ✅ 正確：handler 只回業務資料，envelope 由產生函式與出口層負責
return ok(toListView(rows, pagination))
// ❌ 錯誤：手工組。少了 locale、rspTS 拼錯，全部靜默通過
return { code: '200', msg: '', errors: [], data: rows, rspTs: now(), expiresIn: 3600 }
```

- **envelope 產生之後禁止再改它的欄位**（不得取得產生結果再賦值 `code`／`errors`／`expiresIn`）。
  理由：`code`、HTTP status 與 `errors` 是由同一次映射一起決定的（§1.3 映射表）。事後只改其中一個，三者就**脫鉤**——出現 HTTP 200 配 `code='300'`、或 `code='300'` 卻沒有 `errors` 這種前端無法處置的組合，而型別上完全合法。要改就回頭改領域錯誤或映射表。
- **list 端點的 `search`／`sort` 回聲（§1.4）必須由共用的 list 組裝函式從 request 帶回，禁止各端點自行填。**
  理由：這兩段**是最常被忘記填的東西**——留成空物件時後端不會錯、測試若只斷言 `data.data` 也不會紅，但前端的 race condition 防護（前端規範 §7.3）當場失效，而且是靜默失效。交給共用函式，就沒有「忘記」這個選項。

#### 1.8.2 分層責任：誰負責填哪些欄位

| 層 | 負責 | 禁止 |
|---|---|---|
| domain／service 層 | 只回業務資料，或以具名錯誤類別拋出領域錯誤（§3.1） | **不得碰 envelope 的任何欄位**；不得出現 HTTP status 與 `WebFlowCode`（§3.1） |
| 身分驗證 middleware | 驗證 token；有效即續期並算出續期後的 `expiresIn`／`exp`（§1.3） | 不得因後續處理結果而改變是否續期 |
| 端點 handler（路由層） | 宣告本端點的 `data` schema（收窄後的型別，§2）、宣告本端點可能吐出的 `errors[].code` 清單（§1.8.3） | 不得自行設定 `code`／`rspTS`／`cmd`／`locale`／`expiresIn`／`exp`；不得自行組 `errors` |
| 出口層（統一 middleware） | 補上 `rspTS`／`cmd`／`locale`／`expiresIn`／`exp`（§1.3） | — |
| 統一 error handler | 將領域錯誤映射成 HTTP status ＋ envelope `code` ＋ `errors[]`（§1.3 映射表） | — |

- 這張表的重點是**每個欄位都只有一個地方會寫它**。`rspTS` 只有出口層寫、`errors` 只有 error handler 寫、`data` 只有 handler 寫——於是「這個欄位為什麼是這個值」永遠只有一個地方要看，改 envelope 也只要改一處。反過來，只要有一支 handler 自己填了 `code`，出口層與 error handler 的行為就不再是全站一致的，而**沒有任何方式能從外部看出哪幾支端點自己填了**。
- service／domain 不得碰 envelope 的理由與 §3.1 相同：同一段業務邏輯會被排程、匯入、worker 呼叫，那些情境根本沒有 envelope。

#### 1.8.3 每支端點必須宣告的內容

**為什麼是「宣告」而不是「寫出來就好」：宣告本身就是契約，端點的業務邏輯一行都還沒寫，`bun run gen:api` 也能產出完整的 OpenAPI。** 這是本節所有要求的來源——把 request／response 定義成獨立於實作的宣告，就得到三件事：

- **前端可以平行開工。** 後端只要先把 `body` schema、`data` schema 與錯誤碼清單宣告好（handler 內容還是 `TODO`），前端就能產生型別與 client、接假資料把畫面做完，不必等後端實作完成，也不必自己手寫 DTO（前端規範 §3.2）。
- **契約先於實作，而不是從實作反推。** 先寫 handler 再回頭「補一下 schema」，補出來的必然是實作剛好回了什麼——包含不小心多回的欄位。先宣告，形狀是被設計出來的，實作只能去符合它。
- **schema 缺漏當場就看得見。** 沒宣告的端點在產生出來的 OpenAPI 上就是個空洞（§1.7），這比在 code review 裡逐支端點檢查可靠。

因此每支端點**必須**宣告：

- **該端點的 `data` schema**（收窄後的型別，不得是 `unknown` 或 Drizzle row，見 §2）。查無資料時 `data` 為 `null`，因此型別是 `T | null`（§1.3）。
- **該端點可能吐出的 `errors[].code` 清單。** 這份清單會進 OpenAPI，讓前端知道要準備哪些文案與處置分支。**未宣告的 error code 不得在執行期出現。** ✅（自製掃描腳本／測試：測試中斷言到的 `errors[].code` 必須在該端點的宣告清單內，不在即失敗）
  理由：沒有這份清單時，前端要處理哪幾種業務錯誤只能靠問人或試出來，而**新增一個錯誤碼不會讓任何地方變紅**——後端加了一個新的業務錯誤碼，前端沒有對應文案，使用者看到的是後端那句給工程師看的 `msg`，或者更糟，什麼都沒看到。把清單釘進契約，新增錯誤碼就必須同時更新宣告，前端也就會在型別上看見它。
- **不會吐出任何業務錯誤的端點，也必須宣告一份空清單**，不可省略不寫。
  理由：省略時「這支端點沒有業務錯誤」與「有人忘了宣告」在契約上長得一模一樣，前端只能一律當作「可能有沒寫出來的錯誤」而退回保守處理，這份清單的價值就沒了。明確寫空清單，是一個可被 review 的決定。
- **每個錯誤碼在宣告時必須同時標明它對應的 HTTP status ＋ envelope `code`**（§1.3 映射表），且**一個錯誤碼只能對應一種**；同一個語意在不同情境要回不同 status 時，**拆成兩個錯誤碼**，不要讓同一個碼有兩種結果。
  理由：前端的處置是綁在 `errors[].code` 上的（前端規範 §3.6、§6.3）。同一個碼有時回 409、有時回 422，前端就無法只憑碼決定要「就地標欄位」還是「請使用者重新載入」，只能兩種都寫、或退化成顯示 `msg`。
- **`data` schema 建議附範例值**（OpenAPI 的 `examples`），讓產生出來的 API 文件對前端可讀。沒有範例的 schema 只說得出型別，說不出「這個欄位長什麼樣」，前端仍然要問人。

#### 1.8.4 成功與失敗走同一個出口

- **錯誤回應同樣經過 envelope 產生函式與出口層，不是另一條路。** error handler 只負責決定 HTTP status、`code` 與 `errors[]`，其餘欄位一律由同一個出口層補上。
  理由：錯誤路徑另開一條出口，結果就是錯誤回應缺 `cmd`／`locale`／`expiresIn`——**前端的統一處理會剛好在錯誤路徑上失效，而錯誤路徑正是最需要它的時候**：`cmd` 沒回聲，log 追不到是哪支端點錯的；`expiresIn` 沒回，session 過期後的第一個 401 反而讓前端無法更新 deadline；`locale` 沒回，錯誤訊息的語系判斷失準。這些都只在出錯時才發作，因此平常測不到。
- ✅ 這條的落實方式就是 §1.8.1 的同一條檢查：只要 handler 與 error handler 都沒有手工組 envelope 的物件字面值，兩條路徑就必然共用同一個出口。

## 2. 輸入與輸出驗證規範

- **每個對外端點都必須宣告 `body`（含基底三欄）與 `response` schema**，`response` 包含成功與各錯誤狀態碼（§1.3 映射表中該端點可能回的每一種）。**只有這兩份，沒有第三份**：不宣告 `params`（路徑不帶參數，§1.1），也不宣告 `query`（不使用 query string，§1.5）。
  少了 request schema，未驗證的字串會一路流到 SQL 與計算邏輯；少了 response schema，加密欄位、`password_hash`、他人資料會在某次 `select *` 重構後靜默外洩，而測試不會變紅。此外，schema 就是對外契約本身（§1.7），缺一項就是 OpenAPI 上的一個空洞，前端會被迫手寫型別。 ✅（自製掃描腳本：掃描所有路由註冊，缺 `body`／`response` 任一項即失敗；出現 `params`／`query` 亦失敗）
  「輸入只有一份 schema」不只是少打幾行字：識別碼放路徑時，同一支端點的輸入會被拆成 `params` 與 `body` 兩份宣告，**必填性、長度限制、共用型別要各自維護一次**，而兩邊漂移不會有任何編譯錯誤——`params.id` 沒套 `Uuid`、`body.id` 套了，於是同一種 id 在不同端點的驗證強度不同，且沒有任何地方看得出來。
- **禁止 `response` 直接回傳 Drizzle 的 row 物件。** 必須經過明確的映射函式挑選欄位。
  資料表加一個欄位就自動出現在 API 上，是個資外洩最常見的路徑。
- **共用欄位型別必須集中定義，禁止就地重寫。** 至少包含：`Uuid`、`IsoDate`（`YYYY-MM-DD`）、`TaipeiDateTime`（`YYYY-MM-DD HH:mm:ss`，不帶時區標記，見 §6.1）、`TransportTS`（ISO 8601 帶時區偏移，僅供 `rqTS`／`rspTS`，見 §6.1）、`Reason`（原因欄位）、`Money`、`Minutes`、`YearMonth`、`BaseRequest`（`rqTS`／`cmd`／`locale`）、`PageRequest`（`perPage`／`currentPage`）、`SortRequest`（`{ field, order }`）、`PaginationResponse`（`search`／`sort`／`pagination`／`data`）。
  理由：同一個「原因」欄位在 A 端點寫 `maxLength: 500`、在 B 端點寫 `maxLength: 200`、在 C 端點忘了寫上限，結果是前端表單限制與後端不一致——使用者在某個畫面填得下的字數，在另一個畫面送出後被 422 退回；更糟的是沒有上限的那個端點，一段 10MB 的字串就能塞爆 `text` 欄位與稽核紀錄。 ✅（自製掃描腳本：路由檔中出現行內 `t.String({ maxLength: ... })` 而非引用共用型別即警告）

```ts
// ✅ 正確：共用型別，一處修改全域生效
body: t.Object({ requestId: Uuid, workDate: IsoDate, reason: Reason })
// ❌ 錯誤：就地重寫，長度限制與別的端點不一致
body: t.Object({ requestId: t.String(), workDate: t.String(), reason: t.String({ maxLength: 200 }) })
```

- 固定代碼欄位（`*_code`、`*_type` 這類）**必須用聯集字面值**驗證，不可只寫 `t.Integer()`。DB 不使用 ENUM（通用規範 §1.4），若應用層再不擋，資料庫最終會出現沒人定義過的代碼值，報表全部對不起來。
- 驗證只負責「格式與範圍」；「數量是否足夠」「當下狀態是否允許這個操作」屬業務規則，必須在 service 層檢查，且**不可只靠 schema**。

## 3. 錯誤處理規範

### 3.1 領域錯誤 vs 系統錯誤

- **領域錯誤**（額度不足、狀態不符、無權限）必須用具名錯誤類別拋出，帶 `code` 與可選 `data`，由統一的 error handler 轉成 HTTP status ＋ envelope 的 `code`／`errors`（§1.3 映射表）。
  **service 與 domain 層禁止出現 HTTP 狀態碼與 `WebFlowCode`**，否則同一段邏輯被排程或 worker 呼叫時無法重用。 ✅（depcruise：`*.service.ts`／`domain/**` 禁止 import 任何 http／elysia 模組）
- **系統錯誤**（DB 連線失敗、程式 bug）不攔截、不改寫，交由最外層 handler 記錄完整堆疊（分類為 `unhandled_exception`，見 §1.3）並回 HTTP 500 ＋ `code='400'` 與一般化訊息。
- **「找不到」的處理分兩類，界線是「使用者有沒有嘗試對它做一件事」**（§1.3「查無資料不是 404」的細則）：

| 端點類別 | 目標不存在時 | 理由 |
|---|---|---|
| **查詢類**（`list`／`get`） | HTTP 200 ＋ `code='200'` ＋ `data: null`（清單回空陣列），**不拋錯** | 查詢的語意是「有就給我」，查無此筆是一個**正常且有效的答案**，不是失敗。當成錯誤，前端就得為「這組條件查不到資料」寫錯誤處理 |
| **動作類**（`create` 以外的 `approve`／`reject`／`revoke-approval`／`withdraw`／`update`／`delete` 等對特定目標施加操作者） | `code='300'` 邏輯錯誤 | 使用者**確實嘗試了一個做不到的操作**——他對一筆不存在的資料送出了操作。回 200 等於告訴前端「操作成功了」，畫面會若無其事地更新成完成後的狀態 |

- 動作類的「目標不存在」必須有自己的 `errors[].code`（`<領域>.<目標>-not-found` 形式）並列入該端點的宣告清單（§1.8.3），不得混用「狀態已變更」之類的既有碼——兩者的使用者處置不同（一個要重新載入清單，一個是資料真的沒了）。

### 3.2 錯誤訊息的安全考量

有些錯誤**必須刻意含糊**，這是規格不是疏漏，請在程式碼加註解避免後人「修好」：

| 情境 | 必須回 | 禁止回 |
|---|---|---|
| 登入失敗 | `auth.invalid-credentials`「帳號或密碼錯誤」 | 「查無此帳號」／「密碼錯誤」——可用來列舉有效帳號 |
| **查詢類**端點存取不屬於本公司的資料 | **與「查無資料」完全相同**：HTTP 200 ＋ `code='200'` ＋ `data: null`（清單回空陣列） | 403／`901` 或任何回聲該 id 的訊息——403 等於確認「這筆存在，只是不給你看」 |
| **動作類**端點對不屬於本公司的目標施加操作 | **與「目標不存在」完全相同**：同一個 HTTP status、同一個 `code='300'`、同一句 `msg`、同一個 `errors[].code` | 403／`901`，或任何讓「別家的」與「不存在」可以被區分的差異 |
| 忘記密碼／帳號查詢 | 一律回相同成功訊息 | 「此帳號不存在」 |
| 敏感識別值的唯一性檢查 | 只回「無法建立」 | 回聲與哪一筆既有資料重複——等於用建立表單反查他人的敏感識別值 |

**關鍵安全規則：不論查詢類或動作類，「目標不存在」與「目標存在但屬於其他公司」的回應必須完全無法區分——相同的 HTTP status、相同的 `code`、相同的 `msg`、相同的 `errors[].code`。**

- 理由：兩者一旦可區分，**攻擊者拿 id 枚舉就能探測出別家公司有哪些資料存在**。他不需要看到任何內容，「存在」本身就是外洩：資料筆數、變動的時間點、某個人有沒有某一類紀錄，都能從一連串「存在／不存在」推出來。而**每一次探測在系統看來都是一個正常請求**——身分是有效的、格式是對的、回的是一般錯誤，沒有任何一層會告警，log 裡也只是一批看起來很普通的 `300`。
- 實作上最容易破口的地方是「先查再判權限」：`findById(id)` 查到了才發現不同公司，於是拋一個跟「查不到」不同的錯。正確作法是**把 `company_id` 寫進 `WHERE`**（§4.2），讓別家公司的資料在查詢階段就等同於不存在——這樣兩條路徑走的是同一行程式碼，**想寫出不一致的回應都寫不出來**。
- 這條與「動作類回 `300`」不衝突：動作類的兩種情境都回同一個 `300` 與同一個 `errors[].code`（該端點宣告的 not-found 碼），查詢類的兩種情境都回同一個 `200` ＋ `data: null`。**一致性是在同一類端點內部要求的**，不是要求兩類之間相同。
- ✅（測試：每個端點都必須有一條「以 B 公司 token 存取 A 公司資料」的案例，且**斷言其回應與同一端點「目標不存在」案例的回應完全一致**——HTTP status、`code`、`msg`、`errors[].code` 逐項比對，見 §4.2、§7.1）

- 例外訊息與 `errors[].data` **禁止包含**密碼、密碼 hash、完整身分證、完整銀行帳號、加密金鑰、SQL 原文。這些一旦進 log，log 的保存期就變成個資保存期。

### 3.3 禁止吞掉例外

- **禁止空 catch。** 需要忽略時必須註明理由與已知範圍。 ✅（lint：`no-empty` 含 catch；自製規則要求 catch 區塊內至少有一行註解或重拋）

```ts
// ✅ 正確：明說為什麼可以吞
try { await auditLog.write(entry) } catch (e) {
  // 稽核寫入失敗不可讓主要業務操作失敗；改記系統日誌並告警。
  logger.error({ err: e }, 'audit write failed')
}
// ❌ 錯誤：額度扣抵失敗被吞掉，餘額與紀錄不一致且無人知情
try { await deductBalance(...) } catch {}
```

- **禁止 `catch` 後回傳預設值**（`return null`、`return []`）掩蓋錯誤。列表查詢失敗回空陣列，畫面會顯示「查無資料」，比報錯危險得多。
- 重拋時必須保留成因：`throw new Conflict('...', '...', { cause: e })`，不可只 `throw new Error(String(e))`。

### 3.4 交易中的錯誤處理

- 交易回呼內**禁止吞例外後繼續使用同一個 tx**。錯誤已使交易進入待回滾狀態，後續寫入不是失敗就是寫進一個注定回滾的交易，結果是「API 回成功、資料沒進去」。
- 交易內**禁止**呼叫外部 HTTP、寄信、寫檔或執行長時間計算。交易期間持有列鎖，一次外部逾時就會連鎖鎖住整張表。
- 需要在成功後才做的副作用（通知、快取失效、重算排程）一律放在交易 commit **之後**。

## 4. 資料庫操作規範

### 4.1 Migration

- 所有 schema 變更**一律走 migration 檔**，與程式碼同一個 PR 進版控。
- **禁止手動連線正式或測試資料庫執行 DDL。** 手改過的資料庫與 migration 歷史分岔後，任何新環境都建不起來，事故當下沒有可信的重建路徑。
- **已套用（已合併進 main）的 migration 檔禁止修改或刪除**，修正一律新增一支。改寫已套用的檔案會讓已跑過的環境永遠不會再執行修正，開發機正常、正式機壞掉。 ✅（CI：比對 PR 對既有 migration 檔的 diff，非新增即失敗）
- 每支 migration **必須可在空資料庫從頭跑到尾**，CI 每次都要跑一遍。
- 新增欄位一律 nullable 或帶 default；對既有大表加 `NOT NULL` 無 default 會直接失敗或鎖表。

### 4.2 多公司資料隔離（最高優先）

- **每一次查詢、更新、刪除都必須帶 `company_id` 條件**，包含子查詢與 JOIN 的每一張帶 `company_id` 的表。
  MariaDB 沒有 Row Level Security，隔離只能由應用層保證。漏掉一次的後果是 A 公司的主管在列表裡看到 B 公司員工的薪資與身分證，且因為查詢「有回資料」，沒有任何錯誤會被觸發——通常是客戶先發現。
- `companyId` **只能來自已驗證的 token／session**，禁止取自 request body 或 header（見 §1.1；路徑上不可能有，因為路徑不帶參數）。
- **建議**：資料存取包一層強制帶入 `company_id` 的封裝，讓「不帶公司條件」寫不出來，而不是靠記憶力。跨公司的平台管理功能走獨立且明確命名的路徑。 ✅（depcruise：限制只有資料存取層可 import 未受限的 db client；自製掃描腳本：`select(...).from(<帶 company_id 的表>)` 的 `where` 未含 `companyId` 即失敗；測試：**每個端點**都要有一條「B 公司 token 存取 A 公司資料」的測試，並斷言其回應與該端點「目標不存在」的案例**逐項完全相同**，見 §3.2）
- 自我參照的父子關聯（`parent_id`）**必須驗證雙方同公司**。跨公司串樹之後，樹狀結構與其統計會把別家公司的資料算進來。

### 4.3 軟刪除

- 有 `deleted_at` 的表，**預設查詢一律加 `IS NULL`**。忘記加，已刪除的資料會重新出現在選單與可選項中，等於刪除從未生效。 ✅（自製掃描腳本：查詢帶 `deleted_at` 欄位的表時，`where` 未出現 `deletedAt` 即失敗；需要含已刪除時以明確的 `includeDeleted` 參數並附註解）
- **禁止對有歷史意義的資料做實體 DELETE**：一律標記撤銷並新增一筆歷程（歷史不可用 UPDATE 或 DELETE 抹除）。
- **軟刪除與唯一鍵的衝突必須明確處理。** MariaDB 的 UNIQUE 索引中 `NULL` 互不相等，因此 `UNIQUE(company_id, code, deleted_at)` 會讓「未刪除的資料」失去唯一性，等於沒擋。本專案採用：唯一鍵改為 `UNIQUE(company_id, code, deleted_seq)`，`deleted_seq` 為 `NOT NULL DEFAULT 0`，軟刪除時同時寫入非零值（如刪除時間戳）。
  不處理的後果二選一：要嘛沿用 `UNIQUE(company_id, code)`，刪掉的代碼永遠不能再用；要嘛把唯一性丟給應用層檢查，併發下兩筆同代碼會同時通過。
- 唯一性檢查**禁止用「先 SELECT 再 INSERT」**取代資料庫唯一鍵。兩個併發請求會同時查到「沒有」，然後都寫進去。正確作法是直接寫入並攔截唯一鍵違反，轉成 409（envelope `code='300'`，並於 `errors` 指出衝突欄位）。

### 4.4 交易邊界

- **交易邊界屬於 service 層**，repository 不自開交易——否則巢狀時無法合併成一個原子操作。
- **同一個業務操作若要寫入多張表，一律必須在同一交易內完成**（跨交易失敗會產生無法自動修復的髒資料）。典型形態有兩種：
  - **一次建立分散在多張表的關聯資料**（主體 + 帳號 + 關聯 + 至少一筆權限指派）：只成功一半會留下「有資料卻無法登入」「有帳號卻沒有任何角色」這種永遠用不了、也沒人會發現的孤兒。
  - **一次狀態變更同時要寫審核歷程、產生衍生資料並更新彙總（或快取）**：只成功一半會讓彙總與明細從此對不起來，而且事後無法自動判斷該補哪一邊。
- **狀態變更必須用條件式 UPDATE**，把「預期的目前狀態」寫進 `WHERE`，並檢查影響列數。

```ts
// ✅ 正確：兩個使用者併發變更同一筆資料時，第二筆影響 0 列 → 回 409（`code='300'`）要求重新載入
const r = await tx.update(records)
  .set({ status: NEXT_STATUS })
  .where(and(eq(records.companyId, companyId), eq(records.id, id), eq(records.status, EXPECTED_STATUS)))
if (r.affectedRows === 0) throw new Conflict('<領域>.state-changed', '資料狀態已變更，請重新載入')
// ❌ 錯誤：先讀再寫，兩人同時操作會讓狀態變更的副作用被套用兩次
const row = await findById(id)
if (row.status === EXPECTED_STATUS) await update(id, { status: NEXT_STATUS })
```

### 4.5 索引與 N+1

- 每一張帶 `company_id` 的表，其索引**必須以 `company_id` 開頭**（如 `(company_id, created_at)`、`(company_id, <關聯>_id, status)`）。缺少會讓每次列表查詢退化成全表掃描，資料量成長後同時拖垮所有租戶。
- 新增列表查詢或篩選條件時，**必須在同一個 PR 補上支撐索引**，並在 PR 描述附 `EXPLAIN` 結果。
- **禁止在迴圈中逐筆查詢。** 一頁 20 筆資料各查一次兩張關聯主檔＝41 次往返，看起來只是慢，實際上會在尖峰時段耗盡連線池，讓其他端點一起失敗。 ✅（lint：禁止 `for`／`map` 內出現 await 的 db 呼叫；測試：關鍵列表端點加上查詢次數上限斷言）

```ts
// ✅ 正確：一次撈完再組裝
const rows = await db.select().from(owners).where(and(eq(owners.companyId, cid), inArray(owners.id, ids)))
const byId = new Map(rows.map((r) => [r.id, r]))
// ❌ 錯誤：N+1
for (const row of list) row.owner = await findOwner(row.ownerId)
```

### 4.6 金額與工時的型別

- **金額禁止用 `float`／`double`／JS `number` 運算。** DB 用 `decimal`（依 schema 定義的精度），程式中以整數「分」或 decimal 字串處理。
  浮點誤差在薪資單上就是實發金額差一塊錢對不起來，而勞健保級距在邊界值上會選錯級距，錯的是法定金額。 ✅（型別：金額欄位以 branded type 表示，不可與一般 number 互換；lint：禁止對金額型別使用 `+ - * /` 以外的自製運算函式）
- Drizzle 讀 `decimal` 回傳字串，**禁止 `Number(...)` 後再計算**。轉成 float 的那一刻精度就沒了。
- **工時一律以整數「分鐘」儲存與運算**，只在輸出時換算為小時。用小數小時做加總，8.33 小時這種值會在月結時累積出數十分鐘誤差。
- **四捨五入規則必須集中在單一模組**，且每個呼叫點明確指定用途（金額進位、時薪、比率、工時單位）。散落各處的 `Math.round` 會讓明細加總不等於總額，而每次修都只修到其中一處。

## 5. 安全規範

### 5.1 密碼與敏感個資

- 密碼只保存單向 hash（Argon2id 或 bcrypt cost ≥ 12）。**禁止**保存、log、回傳明碼或 hash；管理者重設密碼要寫稽核，但**內容不得包含密碼與 hash**。
- 身分證、生日、電話、Email、地址、銀行帳號一律存加密欄位（`*_encrypted`），需查詢者另存固定長度 `*_hash`。
  **禁止**新增這些資料的明文欄位或明文索引——一旦資料庫備份外流，加密欄位是唯一的防線。
- 對外回應一律遮罩（身分證僅末 3 碼、帳號僅末 4 碼），完整值只在明確授權的單一端點提供且必寫稽核。 ✅（自製掃描腳本：response schema 中出現 `identityNumber`、`bankAccount`、`passwordHash` 等關鍵字未經遮罩函式即失敗）
- **禁止把敏感值寫進 log 或 `errors[].data`**；log 一律先過欄位遮罩。

### 5.2 權限檢查

- 權限檢查**必須在後端每一個端點執行**，且與 UI 顯示無關。
  前端的隱藏與停用只是體驗優化（前端規範 §4.2）——只靠前端隱藏按鈕，等於權限只擋住不會開 DevTools 的人。
- 路由層做**粗粒度**權限（是否具備該功能權限），service 層做**細粒度**檢查（是否本人、是否在自己的組織範圍內、目標是否同公司、目標當下狀態是否允許）。
  只在路由層檢查，「只能看自己的」這類端點就會變成「只要具備該功能權限就能查任何人的資料」。 ✅（自製掃描腳本：每個路由必須套用權限 guard，未宣告即失敗；測試：每個端點至少一條「無權限角色被 403」的測試）
- 「本人」關係一律由 token 推導，**禁止**信任請求帶來的識別碼就當成本人。

### 5.3 稽核紀錄

- 下列類別的操作**必須寫稽核**：個人與敏感個資的異動、金額相關設定的異動、帳號的啟用停用與密碼重設、角色與權限的指派與撤銷，以及所有會改變審核結果的操作。
- 每筆至少記錄：操作者、操作時間、操作類型、資料主體、異動前後差異、必要時的生效日。缺少「異動前值」的稽核在爭議發生時完全無法舉證，等於沒寫。
- 稽核與業務資料**必須在同一交易內寫入**（除非該操作明定稽核失敗不可阻斷，見 §3.3 範例，此時必須告警）。
- 稽核紀錄**只能新增**，禁止修改與刪除。

### 5.4 認證機制：access token + refresh token 雙票

**本系統採用兩張票的認證機制。** 這是為了同時滿足兩件互相衝突的事：**access token 要短命**（被偷走的價值才低），但**使用者不能每天被迫重新登入**（這是員工每天都要用的內部系統，把登入擋在每天第一個操作前面，等於天天多一道摩擦）。單一張票無法兼顧——壽命短就天天登入，壽命長就等於把一張長期有效的鑰匙放在瀏覽器裡。

#### 5.4.1 兩張票的分工

| | 用途 | 壽命 |
|---|---|---|
| **access token** | **每次請求攜帶**，用於身分驗證；envelope 的 `expiresIn` 反映的就是它的剩餘秒數 | **滑動視窗 2 小時**，每次通過身分驗證即續期（續期規則見 §1.3，此處不重複） |
| **refresh token** | **只用於 `POST /sessions/refresh`** 換發新的 access token，不得用於其他任何端點 | **30 天** |

- refresh token **只認一個端點**。它出現在 `/sessions/refresh` 以外的任何請求上都應被視為錯誤，而不是「順便也能用」。理由：兩張票的價值差異全部建立在「refresh token 的使用面極小」這件事上——一旦它也能當 access token 用，就只是一張 30 天壽命的 access token，短命那一半的設計當場失效。
- access token 的續期不需要 refresh token 參與：只要人還在操作，滑動視窗就會一直往後推，`/sessions/refresh` 只在**停止操作超過一個視窗**之後才會被用到。

#### 5.4.2 輪替與偷用偵測（不可省略）

本系統**不做敏感操作的重新驗證**（§5.4.4），因此以下機制是偵測「票被偷」的**唯一防線**，不是加分項：

- **每次 refresh 時，refresh token 也一併換新，舊的立即作廢。** 也就是說每一張 refresh token 都是**一次性使用**：`/sessions/refresh` 回傳的是「新的 access token ＋ 新的 refresh token」，而不是只換 access token。
- **已作廢的 refresh token 再次被使用 → 一律視為外洩 → 該使用者的所有 refresh token 全部作廢，強制重新登入。** 不是只擋下這一次請求，是整條鏈作廢。
- 理由（為什麼重複使用等於外洩）：**正常的 client 不會重複使用同一張已經換掉的票**——它換完就把舊的丟了，手上永遠只有最新的一張。舊票再次出現，代表**同一張票有第二方持有**：不是攻擊者拿舊票來換（此時真正的使用者手上是新票），就是攻擊者已經換過而真正的使用者拿著舊票來（此時被偷的事實更明確）。兩種情形都無法從單次請求判斷誰是誰，也不需要判斷——**兩邊一起作廢、要求重新登入**，被偷的一方最多是重登一次，攻擊者則失去全部存取權。
- 這條之所以不能省略：沒有輪替，一張 30 天的 refresh token 被偷走之後，**攻擊者可以安靜地用滿 30 天，而系統與使用者都不會察覺任何異常**——每次 refresh 在 log 上都是一個完全正常的請求。加上輪替，偷用會在**下一次任一方 refresh 時**立刻暴露。
- **refresh token 必須存在伺服器端且可主動撤銷。** 不得做成純自帶簽章（stateless JWT）而無撤銷清單——那樣既無法作廢舊票（輪替偵測就無從實作），也無法支援「登出所有裝置」（`POST /sessions/logout-all`）。
- 偵測到重複使用時**必須寫稽核與告警**（§5.3、§1.3 的 log 分類），這是少數「系統自己能發現的安全事件」，靜靜作廢等於浪費了這個訊號。
- ✅（測試：必須包含「以已作廢的 refresh token 呼叫 `/sessions/refresh` → 該使用者所有 refresh token 全鏈作廢、後續請求一律 `900`」的案例；以及「正常輪替後舊票不可再用」的案例）

#### 5.4.3 儲存方式

| 票 | 存放位置 |
|---|---|
| **refresh token** | **httpOnly + Secure + SameSite=Lax cookie**，JS 讀不到 |
| **access token** | **前端記憶體**（模組層變數／store），**不進 `localStorage`／`sessionStorage`** |

- 理由：**兩張票若同時被 XSS 拿走，5.4.2 的偷用偵測也救不回來**——攻擊者手上有 access token 可以直接打 API，有 refresh token 可以自己輪替，他甚至可能比真正的使用者更早 refresh，於是被作廢、被要求重登的是**使用者本人**。因此重點是讓兩張票不可能同時落入同一個 XSS payload：`httpOnly` 讓 refresh token 對 JS 不可見，記憶體則讓 access token 隨分頁關閉即消失，且不會躺在任何一個可被 `localStorage.getItem` 一次撈走的地方。
- access token 存記憶體的代價是**重新整理頁面後 access token 就沒了**，這是可接受的：cookie 裡的 refresh token 還在，前端啟動時打一次 `/sessions/refresh` 就換回來，使用者無感。反過來把它存進 `localStorage` 換取「重整不掉線」，等於為了省一支請求把票放在 XSS 一行程式碼就能讀到的地方。
- **`SameSite` 定案為 `Lax`，不是 `Strict`。** 兩者的差別只有一處：`Strict` 比 `Lax` 多擋的，是「**從其他站台以 top-level GET 導航進來時帶 cookie**」這一種情形。而本系統**所有端點都是同源的 POST XHR**（§1.2、§1.5），**一支 GET 端點都沒有**——`Lax` 對同源請求、對所有 POST XHR 一律照常帶上 cookie，**改成 `Lax` 沒有任何一支端點的行為會改變**。也就是說 `Strict` 在這裡多買到的安全性趨近於零。
- **代價卻是實的，而且會在未來才發作。** 目前不做 Email／通訊軟體通知，但**未來可能會做**——一旦做了，通知裡會附「前往簽核」這類連結，使用者從外部信件或訊息點進來就是一個**跨站的 top-level GET 導航**。在 `Strict` 之下，那第一個請求不會帶上 refresh token cookie，於是**使用者明明還登入著，卻被導去登入頁**；而這種問題不會有錯誤訊息，只會表現成「從信裡點進來每次都要重登，直接開瀏覽器就不用」。
  真正的問題是**修它的時機**：這種「未來做通知功能時要記得回來改 cookie 屬性」的待辦一定會被忘記，因為做通知功能的人不會想到問題出在半年前定的 cookie 設定上，他只會看到一個「有時候要重登」的怪現象，而查到 `SameSite` 要花掉的時間遠比一開始就選對貴。**用趨近於零的安全性去換一個注定會被忘記的未來待辦，不划算**——因此定案為 `Lax`。
- **`None` 則明確排除**：它需要放行跨站帶 cookie，本系統沒有任何需要那樣做的情境。
- **仍未決的只剩一點，已收斂進 §9**：若前後端改為**不同源部署**，`Lax` 同樣送不出 cookie，屆時必須放寬並**補上 CSRF token**（放寬 SameSite 的同時就把 CSRF 防線一起放掉了）。同源部署下不需要 CSRF token，因為 `Lax` 已擋住跨站的 POST。

#### 5.4.4 明確記錄「決定不做」：敏感操作的重新驗證（step-up authentication）

**本系統不做敏感操作的重新驗證。** 查看薪資、查看個資這類敏感操作，**不會**要求使用者重新輸入密碼或做第二因素驗證。這是明確的決定，不是還沒做完的項目——寫在這裡是為了讓後人知道它被考慮過、被否決過，以及否決的代價是什麼。

- **後果必須明說：所有資料都在同一個登入態下。** 只要人已登入，**能做最日常的操作，就能看到權限範圍內最敏感的資料**。裝置借給同事、午休離座沒鎖螢幕、瀏覽器留在共用電腦上——這些情境下，取得畫面的人拿到的是全部權限範圍內的資料，而不只是他原本要用的那一項。這不是理論風險：全體員工每天都會在各種裝置上使用本系統，正是最容易發生「借一下」的場景。
- 因此 **§5.4.2 的輪替偵測、「登出所有裝置」（`POST /sessions/logout-all`）與 §5.4.5 的「改密碼作廢所有 session」是唯一防線，不得省略**。第一項處理票被偷，第二項處理裝置失控，第三項是使用者懷疑帳號被盜時的第一直覺動作——沒有 step-up 的情況下，這三者失去任何一個都沒有替代品。
- **重新評估的條件**（出現任一即應重新討論導入 step-up）：客戶或稽核明確要求；系統開始承載薪資以外更敏感的資料（例如完整銀行帳號的直接查看、跨公司的平台管理功能）；出現實際的越權查看事件；或導入行動裝置／外網存取，登入態離開公司內網環境。
- 前端規範同步：前端**不得**實作任何「敏感操作需重新驗證」的流程或提示（前端規範 §4.2、§4.3 的停用與提示規則已足夠表達「不允許」，不需要再多一層驗證）。

#### 5.4.5 改密碼與重設密碼必須作廢所有 session

**`POST /credentials/update`（改密碼）與 `POST /credentials/reset`（重設密碼）成功後，必須作廢該使用者的所有 refresh token，強制所有裝置重新登入。** 這不是選項，也不是「之後再看要不要做」。

- **作廢範圍包含執行操作的當前裝置，沒有例外。** 該使用者當下所有有效的 refresh token 一律作廢，使用者（含剛剛才輸入過密碼的那個裝置）必須重新登入。不得以「只作廢比密碼變更時間早的票」之類的近似作法取代，也不得在同一次回應中替當前裝置換發新票。
  - **理由**：留一個例外，就要多一段「哪一張票是當前這張」的判斷邏輯；而那段邏輯寫錯的後果是**「以為作廢了、其實沒有」**——沒有效果卻讓人放心，比什麼都沒做更危險。一律作廢沒有這個判斷，也就沒有寫錯的空間。省下的那次重新登入，換不到這個風險。
- **理由（為什麼這條在本系統特別重要）**：本系統**不做敏感操作的重新驗證**（§5.4.4），登入態一旦被別人取得就等於全部權限。而**使用者懷疑帳號被盜時，第一直覺就是去改密碼**——這幾乎是唯一一個一般使用者自己想得到、也做得到的自救動作。若改完密碼舊 session 仍然活著，**他做的事等於完全沒有效果，而他會以為自己已經處理好了**：攻擊者手上那張 refresh token 照樣可以繼續輪替下去，而使用者不再警戒、也不會再去按「登出所有裝置」。**沒有效果還讓人放心，比什麼都沒做更危險。**
- 管理者重設密碼（`/credentials/reset`）同樣適用，且理由更直接：會走到這條路徑的情境本來就常是「帳號出事了」或「員工離職／裝置回收」，此時最不該發生的就是舊裝置還連得上。
- 作廢事件必須寫稽核（§5.3），與密碼變更同一交易（§4.4）——密碼改了但票沒作廢，或票作廢了但密碼沒改，兩種半套狀態都不可出現。
- ✅（測試：必須包含「A 裝置呼叫 `/credentials/update` 成功後，B 裝置持有的 refresh token 立即失效——以該票呼叫 `/sessions/refresh` 回 `900`，且 B 裝置後續請求一律 `900`」；`/credentials/reset` 比照一條。另須斷言 **A 裝置自己原有的 refresh token 同樣失效**，以該票呼叫 `/sessions/refresh` 一樣回 `900`）

## 6. 時間與時區規範

**全系統一律使用台北時間（`Asia/Taipei`, UTC+8），不做任何時區換算。** 資料庫、後端、API 傳輸、前端看到的是同一個牆鐘時間字串。

- 營運時區固定 `Asia/Taipei`，定義為單一常數，**禁止**在各處寫死字串或依賴伺服器時區。伺服器多半跑在 UTC，用 `new Date().getHours()` 做時間判定，台北早上 9 點會被當成凌晨 1 點。
- **資料庫連線 session 時區固定 `+08:00`**；`datetime` 欄位存的就是**台北牆鐘時間**，`date` 欄位存台北的日曆日。兩者都不做換算。
  理由（為什麼不存 UTC）：本系統只服務單一時區的客戶。全程台北時間，讓「時刻」「歸屬日期」「時段分鐘數」三者天然一致，換算這件事從流程中被移除，也就沒有漏換算的可能。反之存 UTC 時，每一次讀寫都多一次換算，只要有一處漏掉，就會出現「時刻對、日期差一天」這種只在深夜與月底發作的錯誤，而錯的是法定工時與薪資。
- **應用程式啟動時必須比對資料庫時區，不一致就拒絕啟動。** 啟動自檢讀取連線的 session 時區（`@@session.time_zone` 或等效查詢），不等於 `+08:00` 即中止程序，並輸出實際讀到的值。 ✅（啟動自檢，CI 亦跑一次）
  理由：DB 或連線參數的時區被誤設時，所有寫入的時間會**靜靜偏移**——沒有例外、沒有錯誤訊息、沒有測試會變紅，資料照樣寫得進去。等到有人察覺，已經有數個月的出勤與薪資是錯的，而且分不出哪幾筆需要修。啟動就擋下來，是唯一能在事故發生**之前**攔住它的位置；讓服務起不來，遠比讓它算錯薪資便宜。

### 6.1 API 傳輸格式（前後端必須一致）

**同一個 payload 裡會同時出現兩種時間格式，判準必須寫死，這裡是唯一的定義處。**

| 類型 | 格式 | 判準 |
|---|---|---|
| **傳輸層時戳**（`rqTS`／`rspTS`，§1.3） | ISO 8601 **帶時區偏移**：`2026-04-14T14:30:00+08:00` | **機器用的**，給 log 對時、算往返延遲，**不顯示給使用者** |
| **業務時間**（`datetime`） | `YYYY-MM-DD HH:mm:ss`，台北時間，**不帶任何時區標記** | **要顯示、要計算的**，前端不做任何換算 |
| **業務日期**（`date`） | `YYYY-MM-DD` | 同上 |
| 月份 | `YYYY-MM` | 同上 |
| 不含日期的時刻 | `HH:mm`；跨午夜以「當日第幾分鐘」整數表示（`09:00`／`1560`） | 同上 |

判準只有一句話：**這個時間會不會出現在畫面上？** 會 → 業務時間格式；只給機器看 → 傳輸層時戳格式。

- **業務時間欄位禁止帶 `Z`、禁止帶 `+08:00`、禁止使用 ISO 8601 帶時區的形式（`2026-08-26T09:30:00+08:00`）、禁止傳 epoch 數字或其他本地格式字串。** ✅（自製掃描腳本：業務欄位的 schema 不得使用帶時區偏移的格式；時間欄位必須引用共用型別 `TaipeiDateTime`／`IsoDate`，出現行內 `t.String()` 或以 `toISOString()` 產出對外業務時間即失敗）
  理由：字串一旦帶了時區標記，前端 `new Date('2026-08-26T09:30:00+08:00')` 會依**瀏覽器**時區再換算一次並顯示換算後的結果——使用者把筆電時區設成東京，整批時間就多一小時，而系統任何一處都不會報錯。不帶標記時，前端拿到的字串就是要顯示的字串，前後端看到的是同一組數字，「再換算一次」這個失敗模式在格式層就被消除。
- **反過來，`rqTS`／`rspTS`／`exp` 必須帶時區偏移。** `rqTS`／`rspTS` 的用途是跨機器對時（比對前端送出、後端收到、後端回應三個時間點），`exp` 的用途是在 log 上標示 session 截止時刻；三者都需要一個絕對參考點，不帶偏移的時戳在 log 聚合時無法與其他系統的時間軸對齊。**這三欄是唯三允許帶偏移的欄位**，且**禁止拿它們當業務時間計算**——`rqTS` 是「請求發出的時刻」，不是「該筆業務事件發生的時刻」，兩者在網路重試或前端排隊時會差好幾秒。
  **帶時區偏移的時間字串一律不上畫面，沒有例外**：`rqTS`／`rspTS`／`exp` 三者**都只供 log 與除錯**，一個都不顯示給使用者。`exp` 另外**仍禁止用於任何過期判斷**（§1.3）——換句話說，`exp` 在前端只剩下「寫進錯誤回報與 log」一種用途。畫面若需要呈現剩餘時間，一律由 `expiresIn` 倒數推導（前端規範 §3.7）。
  理由：這條規則的判準就是上表那句「這個時間會不會出現在畫面上？」。只要有**任何一個**帶偏移的欄位被允許顯示，判準就從「格式決定用途」退化成「要看是哪一欄」，而那正是會被記錯的東西——下一個人看到 `exp` 可以顯示，很自然就會想「那 `rspTS` 應該也可以」。零例外，這條規則才不需要被記住。
- 傳輸層時戳的共用型別為 `TransportTS`（`rqTS`／`rspTS`／`exp` 共用），業務時間為 `TaipeiDateTime`／`IsoDate`（§2），一律附 `pattern` 驗證；禁止就地重寫。三者**不可互相代入**，型別上就要分開。前端的顯示格式規範見前端規範 §9.2，兩者必須一致。
- Session 到期資訊回傳 `expiresIn`（相對秒數，過期判斷與倒數顯示的唯一依據）與 `exp`（絕對時刻，僅供 log 與除錯）兩個欄位，分工與理由見 §1.3。

### 6.2 「現在」必須由呼叫端注入

- **「今天」「現在」禁止由底層函式自行取得，必須由呼叫端傳入。** 統一以可注入的 clock 提供 `now()`／`today()`／`minuteOfDay()`（回傳值一律為台北時間），業務程式碼**禁止直接 `new Date()`／`Date.now()`**。
  理由：底層自己抓時間，跨日、月底、閏年、到期日這類與日期相關的邏輯**根本無法測試**——你不能為了跑一條測試把機器時間調到 2 月 29 日。這類 bug 只會在真正的月底當天出現在正式環境。 ✅（lint：業務程式碼禁止 `new Date()` / `Date.now()`，僅 clock 模組例外）

```ts
// ✅ 正確：時間由呼叫端傳入，測試可任意指定
function isWithinWindow(window: TimeWindow, minuteOfDay: number): boolean
// ❌ 錯誤：無法測試跨日與月底
function isWithinWindow(window: TimeWindow): boolean { const now = new Date() /* ... */ }
```

- 跨午夜的時段以「當日第幾分鐘」表示，允許超過 1440（隔日）。用 `HH:mm` 字串比大小，跨午夜時段的結束時刻會小於開始時刻，時長算成負數。

## 7. 測試規範

### 7.1 一定要寫的測試

- **所有金額、時間長度、額度與法規級距的計算邏輯**：必須有單元測試，且**必須包含邊界值**（期間的起訖、跨日、閏年、剛好用盡的臨界值、級距上下限、最小計算單位）。這些算錯不是體驗問題，是法定金額算錯。
- **所有對外端點**：至少涵蓋成功（200／`200`）、業務規則不允許（422 或 409／`300`，並斷言 `errors[].code`）、無權限（403／`901`，並斷言 `expiresIn` 非 `null`）、**目標不存在**、**跨公司存取** 五條。斷言必須同時檢查 HTTP status 與 envelope 的 `code`，只檢查其中一項會漏掉映射寫錯的情況。
  - 「目標不存在」的期望值依端點類別而定（§3.1）：查詢類是 200／`200` ＋ `data: null` 或空清單，動作類是 `300` ＋ 該端點宣告的 not-found 錯誤碼。
  - **「跨公司存取」不是獨立斷言一組期望值，而是斷言它與「目標不存在」那一條的回應逐項相同**（HTTP status、`code`、`msg`、`errors[].code`）。寫成兩組各自硬編的期望值時，日後有人改了其中一條的訊息，兩邊就悄悄分岔而測試依然全綠——那正是 §3.2 要防的事。
- **所有狀態機轉移**：每個不允許的轉移都要有一條測試證明會被拒絕（例如已進入終態的資料不得再被變更、前置狀態不成立時不得轉移）。
- **併發衝突**：狀態變更類端點至少一條「兩個使用者對同一筆資料同時操作，第二筆被拒」的測試。

### 7.2 不必寫的測試

- 純轉發的 mapper、Drizzle schema 定義、常數表、框架本身的行為。這些改壞了型別檢查就會擋下，測試只是重複描述實作。

### 7.3 測試不可繞過正式流程

- **禁止在測試中直接改資料庫欄位來製造前置狀態**，凡是有對應正式流程（API 或 service 函式）者一律走該流程。

```ts
// ❌ 錯誤：直接關掉強制改密碼旗標。哪天這道閘門壞了，測試依然全綠。
await db.update(users).set({ mustChangePassword: false }).where(eq(users.id, id))
// ✅ 正確：走正式的變更密碼流程，順便驗證那道閘門還活著
await api.post('/credentials/update', { currentPassword, newPassword })
```

- 例外：製造「無法由正式流程產生」的髒資料（例如舊版遺留狀態）時可直接寫入，但**必須註明理由**。
- **禁止 mock 掉被測邏輯本身**。把額度計算 mock 起來去測那支呼叫它的端點，測到的只有 mock。

### 7.4 測試資料隔離

- 每個測試**自建自己的公司與員工**，用隨機後綴避免代碼碰撞；**禁止**多個測試共用同一筆 fixture 再互相修改——那會產生只在特定執行順序下失敗的測試，最後大家改成「重跑一次就好」。
- 測試資料庫由 migration 建立（與正式同一套），**禁止**另外維護一份測試用 schema——兩份會分岔，而分岔的那一刻測試就不再保證正式環境可用。
- **禁止在測試中連線正式或共用開發資料庫。** ✅（測試啟動時檢查連線字串，非測試庫即中止）
- 每個測試以交易包住並在結束時回滾，或以「新公司」隔離；**禁止 truncate 全庫**（會炸掉平行執行的其他測試）。
