# UI 與流程設計：我的資料／補打卡申請

## 確認狀態

本文件內容已由使用者明確同意，列為正式 UI、流程與 Schema 規劃。

## 導覽結構

```text
我的資料
├─ 個資
├─ 出勤紀錄
└─ 補打卡申請
```

本頁只能查看及申請目前登入員工本人的補打卡資料。

## 查詢與列表

查詢條件：

- 年月預設當月，可切換其他年月。
- 狀態可選全部、待審核、已核准、未核准、已撤回。
- 進入頁面立即載入當月全部申請。

| 申請日期 | 補卡日期 | 類型 | 申請補登時間 | 原因 | 狀態 | 操作 |
|---|---|---|---|---|---|---|

- 類型為上班或下班。
- 狀態為待審核、已核准、未核准或已撤回。
- 操作提供查看；待審核申請另提供撤回。
- 日期預設由新到舊排列。

## 新增申請

| 欄位 | 必填性 | 說明 |
|---|---|---|
| 補卡日期 | 必填 | 缺少打卡的工作日期 |
| 補卡類型 | 必填 | 上班或下班；兩種卡分開申請 |
| 申請補登時間 | 必填 | 實際應打卡的日期與時間 |
| 申請原因 | 必填 | 未能正常打卡的原因 |

選擇日期後顯示當日班別、預定上下班時間、有效上下班卡、缺少類型及月份是否已結算。

### 送出檢查

- 不可選擇未來日期。
- 原因必填。
- 已有有效打卡的類型不可重複申請。
- 同一工作日、同一類型已有待審核申請時，不可重複送出。
- 補卡時間需符合上下班基本先後關係。
- 跨日班以班表工作日期作為補卡日期，但下班時間可以落在隔日。
- 已結算月份不能申請；前端停用，後端亦須拒絕。

## 狀態與處理

### 待審核

- 尚未建立正式打卡。
- 員工可以撤回。
- 審核資訊顯示「—」。

### 已核准

- 核准後才建立正式 `attendance_records`。
- 來源標示為人工補登。
- 建立後重新計算 `attendance_results`。
- 審核意見可填，不強制。

### 未核准

- 不建立正式打卡。
- 審核意見必填。
- 不提供複製後重新送出功能。
- 原申請與結果保留。

### 已撤回

- 只有待審核申請可以撤回。
- 撤回後不建立正式打卡，且不得再送交審核。
- 申請紀錄保留，不得 DELETE。
- 不產生審核者及審核時間。

## 月份結算

- 已結算月份不能新增補打卡申請。
- 結算前若仍有待審核補卡申請，應阻止結算。
- 待審核申請必須先完成審核或由員工撤回。
- 結算完成後不另設出勤更正流程。

## 申請明細

顯示申請時間、補卡工作日期、類型、申請補登時間、原因、班別、原有效打卡、狀態、審核者、審核時間、審核意見、核准後正式打卡及撤回資訊。

## GPS

- 補打卡為事後申請，不要求 GPS。
- 不建立或偽造經緯度及大約地址。
- 核准後正式打卡來源為人工補登。
- 本人出勤及全體出勤的地點顯示「—」。

## 資料流程

```text
attendance_correction_requests
→ 審核
→ 核准後建立 attendance_records
→ 重新計算 attendance_results
→ 更新本人與全體出勤
```

申請本身不是正式打卡。
