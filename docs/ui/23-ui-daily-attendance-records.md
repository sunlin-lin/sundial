# UI 設計規劃：每日全員打卡明細

## 確認狀態

**尚未經使用者確認。** 本文件是依使用者指示新建的初稿，畫面、查詢條件、列表呈現、撤銷流程與顯示規則都是本文件自行判斷的結果，**尚未逐項經過確認**。其餘 UI 文件的「已由使用者明確同意」是記錄一件真的發生過的事，不可照抄。經使用者確認後再改寫本節。

本頁是使用者在打卡與出勤實作計畫（[06-attendance.md](../plans/06-attendance.md) §4.7）中新提出的畫面，五份既有出勤相關 UI 定案（09、10、12、13、17）都未涵蓋。分工理由、端點形狀與權限碼已在該計畫定案，本文件只補上畫面、查詢條件、列表呈現、撤銷操作流程與顯示規則，不重新定義分工。

## 與「全體出勤」的分工（承接計畫定案，不重新討論）

- **[09 全體出勤](09-ui-all-attendance.md)** 看的是**判定結果**：一位員工一天一列，資料主要來自 `attendance_results`，按年月查詢。
- **本頁** 看的是**原始事實**：某一天、全公司的 `attendance_records`，一位員工當天可能有多筆（多次進出、已撤銷的、來源各異），可以直接對別人的打卡執行撤銷。
- 兩頁不合併，理由見計畫 §4.7：兩者資料來源、粒度（一人一天一列 vs 一人一天多列）、操作性質（唯讀 vs 可撤銷別人）都不同。

## 導覽結構

> 選單位置：`人事作業 → 每日打卡明細`

```text
人事作業
├─ 員工清單
├─ 組織架構
├─ 全體出勤
├─ 每日打卡明細
├─ 特休／補休贈與
└─ 班別設定
```

進入本頁需要 `attendance.records.view-all` 權限碼；沒有這個權限碼看不到選單項目，也不能直接呼叫 `attendance/records/list-by-date`。頁面內的撤銷操作另外檢查 `attendance.records.revoke-other`（見下方「撤銷操作」），兩個權限碼各自把關，只有查看權限的人進得了頁面但看不到撤銷按鈕。

## 查詢條件

| 查詢條件   | 規則                                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 日期       | 必選；預設今天。查單一天，不支援日期區間                                                                                             |
| 部門       | 可選全部部門或指定部門，比照 09                                                                                                      |
| 人員       | 可依員工編號或姓名搜尋及選擇，比照 09                                                                                                |
| 部門＋人員 | 可同時套用；選定部門後，人員選項只顯示該部門員工，比照 09                                                                            |
| 狀態       | 全部（預設）／只看有效／只看已撤銷。預設「全部」，因為審核情境需要看到「這筆本來就已經被撤銷」（計畫 §4.7 明文要求列表含已撤銷紀錄） |

條件變更回到第 1 頁；查詢、排序、分頁由後端處理（`attendance/records/list-by-date`，帶 `pagination: { page, pageSize }`）。

## 列表

一筆 `attendance_records` 一列，不是一人一天一列——同一位員工同一天可能出現多列。

| 欄位     | 顯示內容／來源                                                     |
| -------- | ------------------------------------------------------------------ |
| 員工編號 | 員工主檔，JOIN 帶出，不得逐列查詢                                  |
| 姓名     | 員工主檔，JOIN 帶出                                                |
| 部門     | 該日有效的員工部門資料，JOIN 帶出                                  |
| 打卡類型 | `attendance_records.attendance_type_code`（上班／下班）            |
| 打卡時間 | `attendance_records.clocked_at`                                    |
| 地點     | GPS 反查後的大約地址（`attendance_records.address`），不顯示經緯度 |
| 來源     | `attendance_records.source_type_code`（現場打卡／人工補登）        |
| 狀態     | 有效／已撤銷（`attendance_records.revoked_at IS NULL` 判斷）       |
| 操作     | 「查看明細」；有效紀錄且操作者具備撤銷權限時另有「撤銷」           |

### 排序

預設先依員工（工號）排序，同一員工當天的多筆打卡再依打卡時間由早到晚排列。這頁的情境是審核者要在同一個人一天內的多筆打卡之間來回比對前後關係（例如判斷哪一筆下班卡對應哪一筆上班卡、哪一筆是重打的），依員工分組比純粹依時間排列更符合這個操作方式；「今天全公司發生了哪些事件」的時間軸瀏覽需求可以之後再議，本輪先滿足審核情境。

### 已撤銷紀錄的呈現

已撤銷的列整列以灰階文字呈現，狀態欄顯示「已撤銷」，操作欄不出現「撤銷」按鈕（已經撤銷的紀錄不能再撤銷一次）。已撤銷紀錄預設就顯示在列表中，不用另一個開關才看得到——「狀態」查詢條件的「只看已撤銷」是給審核者專門檢視撤銷紀錄用的篩選，不是控制顯不顯示的開關；兩者是不同的操作目的，不應該合併成同一個控制項。

撤銷人、撤銷時間、撤銷原因不放進主列表欄位（欄位數已經不少，且平時不需要一直看見），改為並入「查看明細」帶出的內容，見下一節。

## 明細

點擊「查看明細」開啟明細（彈窗或側邊抽屜，形式留給實作決定），顯示：

- 員工、部門、打卡類型、打卡時間、來源
- 座標與定位精準度：`attendance_records.latitude`／`longitude`／`accuracy_meters`，可見範圍規則見下方「座標顯示規則」
- 反查地址與反查完成時間：`attendance_records.address`／`address_resolved_at`
- 撤銷資訊（僅已撤銷紀錄顯示）：撤銷人、撤銷時間（`revoked_at`）、撤銷原因（`revoke_reason`）

## 座標顯示規則

明細顯示座標，列表不顯示——這一條沿用計畫 §4.2 與 09 既有的輸出範圍定案，本頁不重新開放列表顯示經緯度。

明細畫面必須能分辨三種情況，三種文字不得相同：

| 情況                                                                | 畫面顯示                                                         |
| ------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 有權限看座標，這筆有 GPS                                            | 顯示實際經緯度數值與定位精準度                                   |
| 有權限看座標，這筆本來就沒有 GPS                                    | 顯示「本筆未取得定位」（不是空白，也不是與下一種情況相同的文字） |
| 沒有 `attendance.records.view-all`／`revoke-other` 權限看別人的座標 | 顯示「無權限檢視座標」（明確告知是權限問題，不是資料問題）       |

前端判斷依 API 回應決定顯示哪一種：後端依計畫 §4.2 的約定，「沒有權限」時回應物件裡完全不含 `latitude`／`longitude` 這兩把鍵，「有權限但沒有 GPS」時兩把鍵存在且值為 `null`——前端用鍵是否存在分辨第三種情況，用值是否為 `null` 分辨第二種情況，不得把兩者合併成同一個判斷或同一段顯示文字。反查地址與反查完成時間不受此規則限制（不是座標，全公司角色只要有查看權限就能看到，與 09 列表顯示大約地址的規則一致）。

## 撤銷操作

只有具備 `attendance.records.revoke-other` 權限的操作者，在「有效」狀態的紀錄上才看得到「撤銷」按鈕。這是計畫 §4.3 定案的「他人撤銷」路徑（`attendance/records/revoke-other`），不是 Dashboard 上員工撤銷自己打卡的 `revoke`——本頁的撤銷永遠是操作者對別人的打卡做出的處置。

```text
點擊「撤銷」
→ 顯示這筆打卡的員工、打卡類型、打卡時間與地點（不需要重新叫出整份明細）
→ 填寫撤銷原因（必填，attendance_records.revoke_reason）
→ 再次確認
→ 呼叫 attendance/records/revoke-other
→ 成功後：這一列的狀態變更為「已撤銷」、灰階呈現、操作欄的「撤銷」按鈕消失
```

### 規則

- 撤銷原因必填，比照 Dashboard（10）與補打卡簽核（17）既有的撤銷／退回原因必填慣例。
- 撤銷不得 DELETE；標記作廢（`revoked_at`／`revoked_by`／`revoke_reason`／`revoked_seq`），原始紀錄保留可查。
- 撤銷成功會寫入 `audit_logs`（計畫 §4.3.1、§4.6 已定案：他人撤銷與本人撤銷不同，他人撤銷一律寫稽核）——這是本頁與 Dashboard 自行撤銷最大的差別，畫面上不需要特別提示「這會被記錄」，但實作不能省略這一步。
- 撤銷後這一天的 `attendance_results` 會被重新計算（沿用 09／10 已定案的規則，他人撤銷與本人撤銷在這一點沒有差別）。重算是背景動作，撤銷操作本身成功即代表這一列狀態已更新，不需要讓使用者等待判定結果重算完成才顯示撤銷成功。
- 該工作日若已被薪資結算鎖定，前端停用「撤銷」按鈕；若後端仍拒絕（併發或前端狀態過期），顯示訊息：「這個工作日的薪資已結算，如需更正請改走補打卡流程」（計畫 §4.3.1 定案的唯一限制與訊息文案）。**這條檢查目前是樁，永遠回傳「未鎖定」**——薪資結算模組（第 5 層）尚未實作，本頁不因此另外設計一套「檢查中」或「暫時無法判斷」的畫面狀態，等薪資模組上線後這條檢查會自然生效，不需要改動本頁。
- 已引用該筆紀錄的待審核補打卡申請、或本身由核准補打卡建立的紀錄（來源為人工補登），都可以正常撤銷，不因此多一層確認或警告文字（計畫 §4.3.1 明文定案：引用關係不構成撤銷限制）。
- 兩位操作者同時對同一筆紀錄撤銷時，第一筆成功、第二筆送出時應被拒絕並重新載入該筆狀態（比照 17 對併發衝突的既有處理方式）。
- 一次只能撤銷一筆，本輪不提供批次撤銷（見下方「本輪明確延後」）。

## 顯示規則

- 同一位員工同一天可能出現多筆有效或已撤銷的打卡，列表以逐筆事件呈現，不做任何彙總或去重。
- 來源（現場打卡／人工補登）一律顯示；兩種來源在本頁的可撤銷性完全相同，畫面不需要因來源不同而改變操作或加註警告。
- 沒有 GPS（`attendance_settings.gps_required = false` 時本來就可能沒收到座標）不視為異常，列表與明細都不得因此顯示成錯誤或警示樣式。
- 本頁不顯示對應 `attendance_results` 的判定狀態（例如是否為 `NO_SCHEDULE`）——本頁的資料層是原始事件，維持與判定結果分開的分工（見「與『全體出勤』的分工」一節），避免兩種資料來源混在同一張表裡讓使用者誤以為兩者是同一件事。

## 資料責任

- 列表與明細的打卡本體資料全部來自 `attendance_records`，不讀取 `attendance_results`。
- 部門顯示應依查詢日期對應的有效部門資料，不應只取員工目前部門而改變歷史畫面，比照 09。
- 成員資料與打卡紀錄需限制在目前公司 Tenant；查詢索引以 `(company_id, work_date)` 開頭（計畫 §4.7 已定案），避免全公司規模的「某一天」查詢退化成全表掃描。
- 一次查詢以 JOIN 帶出員工姓名、工號、部門，不得在迴圈內對每一列另外查一次員工資料。

## 本輪明確延後

本輪只確認查詢、列表呈現與撤銷操作流程，以下項目本輪不做，也不得由下游自行補做：

- **批次撤銷。** 本輪只支援逐筆撤銷，比照 17（補打卡簽核）第一版逐筆審核、不提供批次核准的既有判斷；若之後要做批次撤銷，需要另外討論一次送出多筆時的併發與稽核記錄方式，不是現有 `revoke-other` 單筆流程的簡單延伸。
- **地圖顯示原始座標。** 計畫 §4.2、§8 已明確排除地圖需求，本頁的座標可見範圍規則只回答「顯不顯示數值」，不涉及地圖，本輪不因為本頁需要顯示座標就自行加一個地圖元件。
- **從本頁直接建立補打卡申請的捷徑。** 延後的是「在這一頁上直接跳轉去補登一筆打卡」這個捷徑動作，不是補打卡功能本身——補打卡申請（13）與補打卡簽核（17）都已經是獨立且完全定案的畫面，本頁沒有必要重複提供入口。
- **本頁是否顯示對應 `attendance_results` 的判定狀態（含 `NO_SCHEDULE`）供審核參考。** 本輪選擇不顯示（見「顯示規則」），但如果之後認為審核者需要在看原始事件的同時知道當天判定狀態，這是需要另外決定顯示位置與欄位形狀的新設計，不是在現有欄位表裡直接加一欄就能解決。
- **匯出或列印。** 本輪未提出這個需求，不因為這是一份逐筆列表就假設需要匯出功能。
