# UI 設計規劃：總覽 Dashboard 與打卡撤銷

## 確認狀態

本文件內容已由使用者明確同意，列為正式 UI 與操作規劃。

## 預設進入頁面

使用者進入公司後，預設顯示「總覽」Dashboard；上下班打卡放在總覽的主要區域。

```text
總覽
人事作業
├─ 員工清單
├─ 組織架構
└─ 全體出勤
系統設定
└─ 權限／角色
```

## 今日打卡

- 顯示目前日期與時間。
- 顯示今日班別及預定上下班時間。
- 尚未上班時顯示「上班打卡」。
- 完成上班後顯示有效上班時間，並開放「下班打卡」。
- 完成下班後顯示上下班時間與今日工時。
- 沒有有效上班卡時，不得先打下班卡。
- 操作按鈕依狀態只顯示下一個有效動作：上班打卡 → 下班打卡 → 今日打卡完成。

打卡時嘗試取得 GPS，並顯示反查後的大約地址；因 `attendance_settings.gps_required = false`，定位失敗時仍可打卡，但需顯示未取得位置。

## 撤銷打卡

上班卡與下班卡都可以撤銷，因員工可能誤打卡。

```text
點擊撤銷
→ 顯示該筆打卡時間與大約地址
→ 填寫撤銷原因
→ 再次確認
→ 將該筆紀錄標記為已撤銷
→ 重新計算今日打卡及出勤狀態
```

### 規則

- 上班卡與下班卡都可撤銷。
- 撤銷原因必填。
- 撤銷不得 DELETE；原始打卡紀錄必須保留。
- 已撤銷紀錄不參與有效工時與出勤計算。
- 撤銷後可重新打卡。
- 已存在下班卡時，不能直接撤銷其前面的上班卡；需先撤銷下班卡，避免留下無法配對的下班事件。
- 已進入出勤或薪資鎖定的日期，不允許員工直接撤銷，應改走補登／更正申請。
- 系統必須能追蹤撤銷人、撤銷時間及撤銷原因。
- 「全體出勤」主列表只呈現有效打卡；出勤明細仍可查看已撤銷事件。
- 撤銷後需重新計算對應的 `attendance_results`，但不得無痕覆蓋已鎖定歷史。

## 與現有 Schema 的關係

- 本流程符合 `attendance_settings.allow_employee_cancellation`。
- 正式事件保存在 `attendance_records`；撤銷不物理刪除。
- 撤銷後重新產生或更新出勤判定，由 `attendance_results` 負責結果，不反向改寫原始事實。
- 撤銷人、撤銷時間、撤銷原因及事件有效狀態的正式欄位名稱與型態尚未逐欄確認；本文件只確認資料責任與規則，不自行補猜 Schema。
- GPS 保存欄位仍留待打卡 Schema 逐欄討論。
