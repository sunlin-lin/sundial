# UI 設計規劃：組織架構

## 確認狀態

本文件內容已由使用者明確同意，列為正式 UI 規劃。

## 導覽結構

> 選單位置：`人事作業 → 組織架構`


```text
人事作業
├─ 員工清單
└─ 組織架構
```

## 主畫面

組織架構採同一頁左右分欄，不使用一般平面表格：

- 左側：部門樹狀列表。
- 右側：所選部門的查看與修改區。
- 頁面上方提供「新增部門」。
- 選取部門後提供「新增下層」，自動以目前部門作為上層部門。

採樹狀列表是因部門具有父子階層，能直接呈現 `departments.parent_id` 的組織關係；一般表格較難閱讀多層組織。

## 列表

| 畫面內容 | 資料來源／規則 |
|---|---|
| 部門階層 | `departments.parent_id` |
| 部門名稱 | `departments.name` |
| 展開／收合 | 只影響畫面顯示，不修改資料 |
| 成員人數 | 由員工目前有效的部門歷史紀錄計算，不存入 `departments` |
| 選取部門 | 在右側載入該部門資料 |

## 新增部門

- 「新增部門」建立根部門，上層部門預設為空。
- 「新增下層」建立目前選取部門的子部門，上層部門預先帶入目前部門。

| UI 欄位 | Schema 對應 | 必填性 | 規則 |
|---|---|---|---|
| 部門名稱 | `departments.name` | 必填 | 顯示名稱 |
| 部門代碼 | `departments.code` | 必填 | 公司內使用的部門代碼 |
| 上層部門 | `departments.parent_id` | 根部門選填／下層必填 | 只能選擇同一公司的部門 |
| 部門說明 | `departments.description` | 選填 | 部門用途說明 |

建立時由系統帶入 `company_id`、初始 `status` 及建立時間，不要求使用者輸入系統欄位。

## 修改部門

| UI 欄位 | Schema 對應 | 規則 |
|---|---|---|
| 部門名稱 | `departments.name` | 可修改 |
| 部門代碼 | `departments.code` | 可修改；仍須符合公司內代碼規則 |
| 上層部門 | `departments.parent_id` | 可調整，但不得選擇自己或自己的下層 |
| 狀態 | `departments.status` | 可啟用或停用 |
| 部門說明 | `departments.description` | 可修改 |

右側提供「儲存修改」、「取消」及「刪除部門」。

## 刪除與停用

- 刪除沿用 `departments.deleted_at`，採 Soft Delete。
- 不得把部門移到其他公司的組織樹。
- 是否允許刪除仍有子部門或有效員工的部門，後續需再確認具體阻擋或移轉流程；本輪不自行定案。
- 停用部門後如何處理既有員工及未來指派，後續另行確認。

## 本輪明確未納入

- 部門主管尚未納入畫面與 Schema。
- 主管是否需要任期及歷史紀錄尚未討論完成。
- 部門排序欄位尚未確認。
- 拖拉調整組織階層尚未確認。
- 成員人數不是 `departments` 的新欄位。
