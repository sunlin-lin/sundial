# UI 設計規劃：全體出勤

## 確認狀態

本文件內容已由使用者明確同意，列為正式 UI 規劃。

## 導覽結構

> 選單位置：`人事作業 → 全體出勤`


```text
人事作業
├─ 員工清單
├─ 組織架構
└─ 全體出勤
```

## 查詢條件

| 查詢條件 | 規則 |
|---|---|
| 年月 | 必選；按月顯示出勤資料 |
| 部門 | 可選全部部門或指定部門 |
| 人員 | 可依員工編號或姓名搜尋及選擇 |
| 部門＋人員 | 可同時套用；選定部門後，人員選項只顯示該部門員工 |

## 列表

一位員工一天一列。

| 欄位 | 顯示內容／來源 |
|---|---|
| 員工編號 | 員工主檔 |
| 姓名 | 員工主檔 |
| 部門 | 該日有效的員工部門資料 |
| 日期 | 出勤工作日 |
| 上班 | 出勤判定採用的上班打卡時間 |
| 上班地點 | 上班 GPS 反查後的大約地址 |
| 下班 | 出勤判定採用的下班打卡時間 |
| 下班地點 | 下班 GPS 反查後的大約地址 |
| 工時 | `attendance_results.worked_minutes` 轉換為畫面格式 |
| 遲到 | `attendance_results.late_minutes`；無則顯示「—」 |
| 早退 | `attendance_results.early_leave_minutes`；無則顯示「—」 |
| 狀態 | 出勤判定結果；同日可同時呈現多項狀態 |
| 來源 | 打卡、人工補登、請假、排班或系統判定等實際來源 |

## 顯示規則

- 同一天可能同時有遲到與早退，或同時有請假與出勤，因此狀態不得在 UI 假設為單一互斥值。
- 同一天若有多次打卡，主列表顯示出勤判定採用的上班卡與下班卡；完整事件留在明細查看。
- 主列表不直接顯示經緯度。
- 上班與下班位置分開顯示，因兩次打卡位置可能不同。
- 大約地址只代表 GPS 反查位置，不宣稱為精確門牌。
- 沒有 GPS 或無法取得反查地址時顯示「—」。
- GPS 未提供不得直接判定為出勤異常，因目前已確認 `attendance_settings.gps_required = false`。

## 資料責任

- 工時、遲到、早退及出勤計算結果主要來自 `attendance_results`。
- 上下班時間、來源及位置來自正式打卡事件，不存入 `attendance_results`。
- 部門篩選與顯示應依查詢日期對應的有效部門資料，不應只取員工目前部門而改變歷史畫面。
- 成員資料與出勤結果需限制在目前公司 Tenant。

## 本輪明確延後

本輪只確認「全體出勤」的查詢與顯示，不確認打卡 GPS 的保存 Schema：

- GPS 必須在打卡時保存。
- GPS 需能反查為大約地址供本頁顯示。
- 經度、緯度、定位精準度、反查地址及反查時間等實際欄位，等討論打卡功能時再逐欄確認。
- 是否顯示地圖、原始經緯度及定位精準度，亦留待打卡與出勤明細畫面討論。
- 不因本頁需要顯示地址，就自行把未確認欄位補入 `attendance_records`。
