# 前端開發規範

適用於 Sundial 前端：Vue 3（Composition API + `<script setup>`）、TypeScript 嚴格模式、Vue Router、Pinia、Element Plus、Tailwind CSS v4、Vite、axios。

本文規定**程式碼怎麼寫**，以及**檔案放哪裡**：目錄與檔名的形狀見 §0，頁面私有 vs 共用區的界線見 §1.5。畫面規格見 [`docs/ui/`](./ui/README.md)，資料欄位以 [`docs/schema/`](./schema/README.md) 為準。

**標記**：✅ = 可自動化檢查，違反時 CI 應該是紅的，不靠 code review 抓。沒有 ✅ 的條文靠 review 把關（需要特別提醒 reviewer 看什麼時標 ⚠️），因此每條都必須寫清楚「違反會發生什麼」，才有辦法在 review 中被指認。全文採「**規則 → 理由 → 範例**」，範例只出現在容易寫錯處。

## 0. 目錄結構與檔案配置

**這一節必須先讀，因為本文其餘章節的掃描規則幾乎全部以本節定義的目錄與檔名形狀為條件。** §1.5 的跨頁面邊界檢查、§3.6 的「頁面不得出現 `code` 常值」、§4.1 的「頁面不得判斷角色」、§7.3 的回聲比對、§9.2 的「format 模組以外禁止 `new Date(`」——這些規則在工具裡的樣子都是一個 glob（`pages/*/*/*.page.vue`、`pages/*/*/*.view.ts`）。**glob 命不中，規則就等於不存在，而且不會有任何東西報錯**：它們只是靜靜地不再命中任何檔案，CI 永遠是綠的（通用規範 §7.1）。

### 0.1 目錄總覽

```text
apps/web/src/
├─ main.ts
├─ App.vue
├─ api/generated/                       OpenAPI 產生物（不進版控，見 §3.2）
├─ pages/
│  └─ <段1>/<段2>/                      固定兩層；兩段就是 URL 路徑段（§0.2）
│     ├─ <段1>-<段2>.page.vue           路由目標，必要
│     ├─ <段1>-<段2>.route.ts           路由宣告，必要（§0.12）
│     ├─ <段1>-<段2>.view.ts            呈現決策純函式（§1.3 的 (1)(2)）
│     ├─ <段1>-<段2>.actions.ts         動作可用性純函式（§1.3 的 (3)）
│     ├─ <段1>-<段2>.payload.ts         表單值 → 送出 payload（§1.3 的 (4)）
│     ├─ <段1>-<段2>.<角色>.test.ts     測試與被測檔同層（§0.6）
│     └─ components/PascalCase.vue      本頁私有子元件（§1.5）
├─ menu/                                選單資料結構；改選單不搬檔案（§0.2）
├─ layouts/
├─ router/registry.ts                   唯一可以 import pages/ 的地方（§0.11）
├─ stores/                              扁平，不得有子目錄（§0.8）
└─ shared/                              兩個以上頁面實際共用時才移入（§1.5）
   ├─ api/                              統一 HTTP client（§3.1）
   ├─ format/                           統一格式化函式（§9.2）
   ├─ permission/                       權限原語（§4.1）
   ├─ components/                       共用元件（PascalCase）
   └─ design/                           設計 token（§5.2）
```

本節一律以 `<段1>`／`<段2>`／`<主題>` 這種佔位符表達，**不列舉任何具體畫面或功能**——具體有哪些頁面由畫面規格決定（`docs/ui/`），寫進規範就會過期（通用規範 §8）。

### 0.2 頁面一律兩層，`<段>` 就是 URL 路徑段

**規則**

- **`pages/` 底下一律兩層目錄，零例外。** 某個 `<段1>` 目前只有一個子頁面時也要有 `<段2>`。
- **這兩層的語意是「URL 路徑段」，不是導覽分組。** `.route.ts` 宣告的 `path` **必須以 `/<段1>/<段2>` 開頭**，其後只允許接路由參數段（例如 `/<段1>/<段2>/:id`）。 ✅（掃描測試：由頁面目錄推導期望前綴，`path` 不以該前綴開頭即失敗；前綴由路徑推導，不硬編任何清單）
  之所以是「開頭」而非「完全相等」：前端的 URL 與後端的 API 路徑是兩回事。後端所有參數走 request body、路徑不帶參數（後端規範 §1.1），但**瀏覽器 URL 必須能被書籤、被分享、重新整理後回到同一筆資料**，所以識別碼要出現在網址裡。允許接參數段的同時仍然保住推導性——前兩段永遠算得出來，參數段只是尾巴。
- **`<段1>` 與 `<段2>` 同名時，第二層一律寫 `main`**（比照後端規範 §0.2，兩邊同一條規則同一種寫法）。 ✅（掃描測試：第二層目錄名不得與第一層相同）
- **選單是一份獨立的資料結構（`menu/`），不是目錄結構。** 導覽的分組、排序、層級全部寫在那份資料裡；**選單改版不得造成任何檔案搬動**。

**理由（本節最重要的一條）**　把目錄綁在導覽分組上，是把**便宜且可變**的東西當成**昂貴且難改**的東西的組織依據。導覽分組是 UX 產物，改版是常態，成本應該接近零；目錄是程式碼產物，搬動成本高（連帶改 import、改檔名、動到 git 歷史）。兩者綁在一起的可預測後果是：**第一次導覽改版時二選一——搬目錄（連帶改 URL 與四個角色檔的檔名），或不搬（目錄從此與選單矛盾，而且矛盾只會愈積愈多）**。綁 URL 之後這個兩難消失：純選單改版零檔案搬動；而真的要改 URL 時才搬目錄——**改 URL 本來就該是有成本、要被看見的破壞性變更**（舊網址失效、書籤失效），讓它需要一個明顯的 PR 是正確的，不是缺點。

**深度必須固定的第二個理由**　§1.5 的跨頁面邊界檢查必須從檔案路徑算出「這個檔案屬於哪一個頁面」，也就是**頁面根目錄**。深度固定為 2 時這是一行字串運算；深度浮動時工具沒有依據判斷該取幾段，該檢查會**靜默停止命中**——不報錯、不失敗，只是不再擋任何東西（通用規範 §7.1：永遠是綠的規則比沒有規則更糟）。§0.9 的去重鍵、§0.11 的頁面目錄相依規則也全部建立在同一個推導上。

### 0.3 檔名由路徑推導，且前綴全域唯一

**規則**

- 頁面目錄下的角色檔一律 `<段1>-<段2>.<角色>.{vue,ts}`，**前綴必須等於所在目錄路徑**。因此搬檔案忘了改名、或改名忘了搬目錄，當場被擋。 ✅（掃描測試：期望前綴**由路徑推導**，不需硬編清單；掃描器必須自我檢查掃到的頁面目錄數 > 0，見通用規範 §7.2）
- **另加一條「前綴全域唯一」檢查。** ✅（掃描測試：所有頁面目錄推導出的前綴集合不得有重複值）

**理由**　檔名等於路徑，是為了讓**檔名全域唯一**——堆疊追蹤、log、編輯器分頁上那一行檔名才有資訊。全站有七個 `view.ts` 時，開七個分頁沒人分得出哪個是哪個。

全域唯一必須**另外檢查**，因為「檔名等於路徑」這一條擋不住它：目錄名本身允許 kebab-case，所以 `pages/a-b/c/` 與 `pages/a/b-c/` 會推導出**同一個前綴 `a-b-c`**。兩邊各自都通過「檔名等於路徑」，檔名卻在全域撞了，而撞掉的正是這條規則唯一想換到的東西。

**kebab 與 PascalCase 的分界線**（與通用規範 §1.1 的例外子句對應）：

| 對象 | 慣例 | 為什麼 |
|---|---|---|
| **被路由掛載的檔案**：`.page.vue` / `.route.ts` / `.view.ts` / `.actions.ts` / `.payload.ts` | kebab-case，**檔名由路徑推導** | 它們不是被 import 的元件，`.page.vue` 是由 `.route.ts` 動態載入的路由目標，不出現在任何模板標籤中；檔名要能與 URL 對得起來 |
| **被模板使用的元件**：`components/` 底下與 `shared/components/` | `PascalCase.vue` | 它會以 `<PascalCase />` 出現在模板裡，檔名與標籤名一致才找得到 |

### 0.4 頁面目錄的檔案白名單 ✅

**規則**　`pages/<段1>/<段2>/` 底下**只允許**以下檔案，出現其餘任何檔名一律失敗：

- `<段1>-<段2>.page.vue`（**必要，恰好一個**）
- `<段1>-<段2>.route.ts`（**必要，恰好一個**）
- `<段1>-<段2>.view.ts`、`<段1>-<段2>.actions.ts`、`<段1>-<段2>.payload.ts`（選用，**有內容才建，不得建空殼**）
- `<段1>-<段2>.<主題>.{view,actions}.ts`（主題拆分檔，見 §0.7）
- `<段1>-<段2>.<角色>.test.ts`（測試與被測檔同層，見 §0.6；**不得有 `__tests__/` 子目錄**）
- `components/**/*.vue`（PascalCase，本頁私有子元件）

**理由**　既有的多條掃描規則——§3.6 禁止頁面出現 `'900'` / `'901'` / `'300'` 等 `code` 常值、§4.1 禁止頁面出現角色判斷、§7.3 的列表回聲比對、§9.2 禁止 `new Date(`——**全部以「頁面程式碼」的 glob 為條件**。只要有人在頁面目錄放一個 `helpers.ts` 把邏輯搬進去，**那些規則會同時失去對那段程式碼的命中，而且沒有任何東西會報錯**：檔案還在、程式還跑、CI 全綠。白名單的作用，就是把「規則沒有命中任何檔案」這種靜默失效，變成一個會紅的檢查。

「不得建空殼」則是為了讓角色檔的存在**有意義**：一個到處都是空 `payload.ts` 的專案，等於把「這一頁有沒有把 payload 組裝抽出去」這個訊號洗掉。

### 0.5 角色檔與 §1.3 四類邏輯的對照

**規則**　§1.3 列了四類必須抽出 `.vue` 的邏輯，每一類都必須有對應的角色檔：

| 角色檔 | 對應 §1.3 |
|---|---|
| `.view.ts` | (1) 列怎麼組（單位換算、零值／空值呈現、衍生欄位）、(2) 狀態顯示什麼文字與色彩 token |
| `.actions.ts` | (3) 動作可用性（資料狀態 + 前置狀態 + 權限） |
| `.payload.ts` | (4) 表單值 → 送出 payload（日期格式化、空字串轉 `null`、單位換算） |

**理由**　沒有家的那一類，會留在 `.vue` 的送出函式裡——而 §1.3 本身沒有 ✅ 標記，**「對應的角色檔存在」是 §1.3 唯一可能被自動化的落腳點**。少一個角色檔，等於一開始就放棄四分之一。第 (4) 類尤其不能放棄：payload 組裝的錯誤（日期少補一段、空字串沒轉 `null`）不會報錯，只會讓後端收到一個形狀合法但語意錯誤的值。

### 0.6 測試檔與被測檔同層

**規則**　測試檔直接放在被測檔旁邊（`<段1>-<段2>.view.test.ts` 緊鄰 `<段1>-<段2>.view.ts`），**不使用 `__tests__/` 子目錄**。命名沿用通用規範 §1.1「被測檔同名 + `.test.ts`」。

**理由**　「改一支純函式 → 改它的測試」是本專案最高頻的編輯迴圈（§8 已把重心全押在純函式測試上）。在這個迴圈中插一層目錄跳轉，是**每天付、換不到東西**的成本——`__tests__/` 的價值在於「檔案多到需要收納」，而一個頁面目錄最多只有三、四個可測檔案，不需要目錄來收納。（後端的 `__tests__/` 是另一回事：那裡一個次目錄底下的檔案數量與種類都更多。）

### 0.7 `view` / `actions` 過大時的處置

**規則**

- **不做「入口檔 + `impl/`」**（與後端規範 §0.4 不同）。
- **但「不拆入口」不等於「沒有拆的規則」**：`.view.ts` / `.actions.ts` 過大時，**按主題拆成平鋪的兄弟檔**——`<段1>-<段2>.<主題>.view.ts`、`<段1>-<段2>.<主題>.actions.ts`。不建 `impl/`、不設入口委派。 ✅（§0.4 的白名單即涵蓋此形狀；頁面目錄下出現 `impl/` 即失敗）
- **§1.2 的行數上限延伸適用到 `.view.ts` / `.actions.ts` / `.payload.ts`，上限為 150 行**（與 §1.2 的 `.vue` script 上限同值）。 ✅（ESLint `max-lines`，對 `pages/**/*.{view,actions,payload}.ts` 設 overrides）
- **拆到三個以上互不共用狀態的主題時，那是「這個畫面在做三件事」的訊號，應拆成兩條以上的路由**（同 §6.4 對可分段流程的處置）。 ⚠️（review）

**為什麼不照抄後端的 `impl/`**　後端的 `impl/` 是一道**承重牆**：入口檔存在的目的是「所有呼叫必須經過它」，`impl/` 底下的檔案只能被同次目錄的入口檔 import（後端規範 §0.4），因為那裡真的有側門（別的模組直接摸進去）。前端的角色檔**只有一個消費者**——同目錄那支 `.page.vue`（§0.11 已經用相依規則保證了這件事）。沒有側門，就沒有牆要承；照抄只會多一層每次都要點兩下才到得了實作的目錄。

**為什麼行數上限必須延伸**　§1.2 的行數上限只管 `.vue`，而 §1.3 的作用**正是把邏輯從 `.vue` 擠進 `view.ts`**。兩條規則合起來的可預測後果是——`.vue` 永遠守在上限內、看起來非常合規，`view.ts` 變成新的堆放處，而且**沒有任何檢查會紅**。這不是假設，這是兩條規則的算術結果。

### 0.8 `stores/` 一律扁平

**規則**

- **`stores/` 底下不得有子目錄。** ✅（目錄掃描）
- **檔案數上限為 8，超過即紅**；錯誤訊息必須直接指向 §2.1 的三項判準（跨頁共用／有生命週期／不是可重取的清單快照）。 ✅（掃描測試）
  8 是寫死在掃描器裡的硬值，不是建議值。訂成「建議」在 CI 裡沒有任何對應物，等於沒有這條檢查；要調整就改掃描器裡那個數字，而改它會出現在 PR diff 裡，正好逼出「為什麼需要第 9 個 store」這個問題。

**理由**　§2.1 已經用規則把「能進 store 的東西」封頂在個位數。所以扁平不只是「目前夠用」——**目錄一旦開始分層，就代表數量已經超過 §2.1 允許的量，而分層會把那個訊號藏起來**。`stores/<主題>/…` 這種分層看起來很整齊，實際上是「有人把列表快照放進全域 store」這個 §2.1 明文禁止的失敗模式已經發生了。分層在這裡不只是無用，是**主動遮蔽一個已知的失敗模式**；上限則是讓那個訊號變成一個會紅的檢查，而不是等某次 review 有人剛好想起 §2.1。

### 0.9 `shared/` 的兩個致命細節

**規則**

- **`shared/` 底下禁止 `index.ts` barrel**（`shared/format/index.ts`、`shared/index.ts` 皆不得存在），一律 import 到具體檔案。 ✅（掃描測試：`shared/**/index.ts` 存在即失敗）
- **§1.5「兩個以上使用者」的去重鍵必須是「頁面根目錄」（`pages/` 底下深度 2），不是檔案。** ✅（掃描測試：計數前先把來源檔路徑正規化成頁面根目錄；全域基礎設施——layout、router、統一 client——各算一個來源）

**barrel 的理由**　barrel 會讓所有 import 變成 `from '@/shared'`，於是「誰用了哪一個模組」在相依分析與計數掃描上**一起報廢**——每個模組看起來都有很多使用者，因為工具只看得到「有人 import 了 shared」。§1.5「共用區的模組必須有兩個以上使用者」那條規則會整條歸零，**而且全綠**。最危險的地方在於：引入 barrel 的那個 PR 看起來只是「順手整理一下 import」，diff 乾淨、行為不變，沒有任何理由擋它。

**去重鍵的理由**　以檔案為單位計數時，**同一頁的 `.page.vue` 與 `.view.ts` 就是兩個來源**——規則當場失效，任何一個模組只要被一頁用兩次就算「共用」。而且失效是看不出來的：報告裡的數字全部 ≥ 2，跟真正通過長得一模一樣。

**這條規則的已知上限（誠實寫下）** ⚠️　作者為了讓檢查變綠，可以在第二個頁面塞一個沒必要的 import，掃描分辨不出來。寫下來的目的，是讓 review 知道要看的是**「第二個使用者是不是真的」**，而不是「有沒有兩個」——後者機器已經看過了，人再看一次是零產出。

**刪頁面時檢查變紅是預期行為** ⚠️　刪掉一個頁面之後，某個共用模組可能掉到只剩一個使用者而讓 §1.5 的檢查變紅。**正確處置是把該模組移回僅存的那個頁面目錄**（回到 §1.5 的預設位置），不是去找第二個假用戶，也不是去改掃描器的門檻。這條要寫出來，因為紅燈出現的時機（刪頁面的 PR）離規則的本意很遠，第一次遇到的人多半會以為是掃描器壞了。

### 0.10 不設手寫的 API 包裝層

**規則**　**不建立手寫的 `api/<領域>/*.api.ts` 包裝樹**；`api/` 底下只有 `generated/`。頁面直接使用 `api/generated/` 的產生函式（呼叫仍然全部經過統一 client，見 §3.1）。 ✅（目錄掃描：`api/` 底下只允許 `generated/`）

**理由**　後端規範 §1.7 已定案產生物是「型別**與 API client**」，而且因為所有端點都是 `POST`、無路徑參數、無 query（後端規範 §1.2），**產生的 client 函式每一支都只有一個參數、簽章統一、回傳型別已經收窄**。在這種形狀上再手寫一層包裝，得到的是**一份手工維護的後端結構副本**：每支端點多一個要維護的函式、每次後端加端點要同步補、還要滿足 §8.2「API 函式必須有呼叫端」的掃描（於是又多出一批只為了讓掃描通過而存在的轉呼叫），而換到的是零——包裝層沒有增加任何型別安全，也沒有隱藏任何會變的東西。這也正好違反 §3.2 的整個論證：**不要手抄後端契約**，包裝樹就是把契約的結構抄一遍。

### 0.11 單向分層相依 ✅

**規則**　相依方向固定如下，違反即失敗。 ✅（dependency-cruiser）

```text
shared/                不得 import  pages/、stores/、layouts/
stores/                不得 import  pages/、layouts/
api/                   只能 import  api/generated/、shared/api/
router/                是唯一可以 import pages/ 的地方
pages/<段1>/<段2>/     內的檔案只能被同目錄、以及 router/registry.ts import
全樹                   禁止循環相依
```

（最後一條頁面規則與 §1.5 的「禁止跨頁面目錄 import」是同一條規則的兩面：§1.5 說的是「頁面 A 不得 import 頁面 B」，這裡補上「除了 router 之外也沒有別人可以 import 頁面」。）

**理由**　目前除了 `pages/` 之外**完全沒有方向約束**，而缺方向約束的兩個後果都不會在本機發作：

- **循環相依**：Vite 對循環 import 大多不報錯，症狀是「某個模組在初始化時是 `undefined`」，只在特定進入順序下發作——直接開某一頁會壞、從別頁導過去就正常。**本機開發通常碰不到**（HMR 的載入順序與 production build 不同），而 production 的 chunk 切分一改，發作的頁面就換一批。
- **`shared/` 反向相依**：`shared/format/` 一旦能 import `stores/`，「這個格式化函式在哪些情境下能用」就變成**不可回答的問題**——它現在依賴登入狀態，在登入前呼叫會拿到什麼沒有人說得準，而型別上完全看不出來。同理，`stores/` 能 import `pages/` 之後，刪一頁會把 store 一起弄壞。

### 0.12 `.route.ts` 的硬規則

**規則**

1. **只能以 `() => import('./<段1>-<段2>.page.vue')` 惰性載入頁面元件，禁止靜態 import。** ✅（掃描測試：`.route.ts` 不得出現對 `.page.vue` 的靜態 `import` 語句）
2. **`.route.ts` 與 `.page.vue` 必須雙向成對**：同層有 `.route.ts` 就必須有 `.page.vue`，反之亦然。 ✅（純路徑比對）
3. **`.route.ts` 內的動態 import 字面量必須指向同目錄的 `.page.vue`，禁止出現 `../`。** ✅（純路徑比對）

**理由**

1. 靜態 import 會讓路由 registry 的 eager glob 把**全站每一支 `.page.vue` 拉進入口 chunk**，而**沒有任何檢查會紅**——型別對、測試綠、畫面一切正常，唯一的症狀是 bundle 從幾百 KB 變成幾 MB，而那個數字沒有人在每次 PR 上看。**這是本節最大的單一風險**，也是唯一一條「寫錯了完全不影響正確性、只影響所有人每天的載入時間」的規則。
2. 少了 `.page.vue` 的 `.route.ts` 會在點進去時才炸；少了 `.route.ts` 的 `.page.vue` 是一支**永遠不會被載入的死檔**，而 §8.2 的路由可達性掃描看不到它（它不在 registry 裡，見下）。
3. 擋住複製貼上忘了改路徑。兩條路由指向同一個 `.page.vue` 時，兩頁都「有路由」、可達性掃描也是綠的，**但其中一頁的使用者永遠打不開**——他點選單、網址變了、畫面卻是另一頁。

**registry 的自我檢查** ✅

- **registry 載入後的路由數，必須與以檔案系統獨立掃描到的 `.route.ts` 數相等**，且兩個數字必須由**兩種不同機制**產生（一邊是實際 import registry 之後數它註冊了幾條，另一邊是掃檔案系統）。**用兩個 glob 互比是無效的**——兩個一起寫錯就一起綠。registry 載入結果為 0 時必須直接失敗（通用規範 §7.2）。

**與 §8.2 路由可達性掃描的分工**　§8.2 的**輸入是 registry**：registry 漏收了誰，它就看不到誰，因此對那個頁面**永遠是綠的**。這條檢查補的是「檔案系統 → registry」那一段。兩段串起來才是完整的鏈：**檔案存在 → 有被註冊 → 註冊後可達**。少了前面那一段，一支新加的頁面只要忘了讓 registry 收進去，全套檢查沒有一條會紅，而它在使用者眼中就是「這個功能不存在」——正是 §8.2 理由段所說本專案真正的失敗模式。

## 1. 元件撰寫

### 1.1 一律 `<script setup lang="ts">`，props/emits 用型別宣告 ✅

**規則**　所有 `.vue` 使用 `<script setup lang="ts">`；禁止 Options API 與 `defineComponent`。`defineProps<T>()` / `defineEmits<T>()` 一律泛型宣告，預設值走 `withDefaults`；禁止 `defineProps({ foo: { type: Object } })` 這種執行期寫法。

**理由**　混用兩種寫法後，「這個值從哪來」要先讀懂寫法才讀得懂邏輯。少了 `lang="ts"` 的區塊 `vue-tsc` 不檢查，型別錯誤直接進 production。執行期宣告只能表達 `Object`，傳進來的到底是哪一種物件編譯器分不出來，欄位打錯要到畫面空白才發現。

**檢查**　ESLint 禁止 Options API 用法；CI 跑 `vue-tsc --noEmit`。

```ts
// ✅
const props = withDefaults(defineProps<{ record: RecordDetail; readonly?: boolean }>(), { readonly: false })
const emit = defineEmits<{ confirm: [id: string]; cancel: [id: string, reason: string] }>()

// ❌ record 是 Object；cancel 少傳 reason 不會報錯
const props = defineProps({ record: Object, readonly: Boolean })
const emit = defineEmits(['confirm', 'cancel'])
```

### 1.2 元件職責上限 ✅（部分）

**規則**　`<script setup>` 超過 150 行或 `<template>` 超過 200 行必須拆分。以下情況無論行數都必須拆：同一元件同時負責「查詢條件／列表／明細彈窗」三件事以上；元件內有兩組以上互不相干的 loading／error 狀態；模板出現三層以上 `v-if` 巢狀。

**理由**　一個明細彈窗若要同時呈現多種來源的資料，本身就是一頁的量。塞在同一檔案裡，改「列表篩選」會動到「明細預覽」的 ref —— 兩個不相干的需求共用同一份狀態，改 A 壞 B。

**檢查**　行數上限用 lint（`max-lines`、模板深度規則）；語意判準靠 review。

### 1.3 呈現決策必須抽成純函式

**規則**　以下四類邏輯不得寫在 `.vue` 內（模板或 `computed` 都不行），必須抽成不依賴 Vue 的純 TS 函式：(1) 表格列怎麼組 —— 單位換算、零值或空值的呈現方式、衍生欄位的推導；(2) 狀態顯示什麼文字與顏色 token；(3) 按鈕何時可按 —— 由資料本身的狀態 + 相關的前置狀態 + 權限共同決定；(4) 表單值轉送出 payload —— 日期格式化、空字串轉 `null`、單位換算。**四類各自該放進哪一個角色檔，見 §0.5 的對照表**（(1)(2) → `.view.ts`、(3) → `.actions.ts`、(4) → `.payload.ts`）。

**理由**　`.vue` 在本專案不做元件測試（見第 8 節），邏輯留在模板或 `computed` 就等於零測試覆蓋。而這四類正好最容易出錯又最不容易一眼看出錯：「某個狀態下本該停用的操作還亮著」不會報錯，只會讓使用者按下去吃一個 403。抽成純函式後，「狀態 × 前置狀態 × 權限」的操作矩陣可以逐格寫成測試。

```ts
// ✅ 純 TS，可逐格測整張操作矩陣
export function availableActions(
  status: RecordStatus, locked: boolean, can: (p: Permission) => boolean,
): RecordAction[] { /* ... */ }

// ❌ 埋在模板裡，永遠不會有測試碰到它
<el-button v-if="row.status === 1 && !locked && isManager">執行</el-button>
```

### 1.4 模板中禁止複雜運算式 ✅

**規則**　模板內只允許屬性存取、單一函式呼叫、單一比較。禁止巢狀三元、算術、字串拼接與格式化、`.filter().map()` 鏈。

**理由**　同 1.3：模板運算式沒有測試、沒有型別窄化，出錯時堆疊指向模板編譯結果而非原始碼。

**檢查**　ESLint `vue/no-complex-template-expression` 設為 error。

```vue
<!-- ✅ --> <span>{{ formatWorkedHours(row.workedMinutes) }}</span>
<!-- ❌ --> <span>{{ row.workedMinutes ? (row.workedMinutes / 60).toFixed(1) + ' 小時' : '—' }}</span>
```

### 1.5 頁面私有的東西放頁面自己的目錄，共用區要先有第二個使用者 ✅

**規則**　某個頁面私有的呈現邏輯（1.3 抽出來的純函式）與子元件，一律放在**該頁面自己的目錄底下**。**只有在被兩個以上的頁面實際共用時，才移入共用區**（共用元件／共用 composable／共用 format 目錄）。移入時才改 import，不預先放。

**理由**　「先放共用區以備不時之需」是共用區變成垃圾場的標準路徑。東西一旦放進共用區，三件事同時發生：**沒有人知道它還有沒有人用**（刪不掉，因為不確定）、**沒有人敢改它**（可能有別人在用），以及**它會開始長參數**——第二個頁面來用時加一個 `mode`，第三個再加一個 `compact`，最後那個「共用元件」的內部是一堆 `v-if`，比兩份各自單純的實作加起來還難讀。而放在頁面目錄下的東西，界線是清楚的：只有這一頁在用，改它只會影響這一頁，刪這一頁時它跟著一起刪掉。

第二個使用者出現時才移入，成本也不高——那時候你**已經知道**兩邊真正共用的是哪一部分，抽出來的介面是被兩個真實案例驗證過的，而不是憑想像先設計一個。

**定位：前端的模組邊界粒度在「頁面目錄」，不在領域。**　因此前端**不設頁面層以外的出口檔**（不做 `index.ts` barrel，見 §0.9），跨頁面共用一律是「移進 `shared/`」這一種形狀，沒有第二種。

這個理由必須寫對：**前端沒有可被繞過的規則層。** 後端之所以需要大目錄的 `index.ts` 當唯一出口（後端規範 §0.3），是因為那裡真的有東西可繞——繞過對方的 service 直接讀 repository，會把軟刪除判定、公司範圍、狀態過濾整組繞掉，而且繞掉的部分在 import 語句上看不出來。前端的 `api/generated/` 是**純傳輸層**，沒有這種藏在層裡的規則可繞，多設一層出口檔換不到任何保護，只換到 §0.9 描述的計數失效。

**不要**把這條理由寫成「前端是單一部署物所以不需要邊界」——那句話不成立（§0.11 的分層相依就是邊界），而且它會被拿去否決別的邊界規則。

**檢查**　dependency-cruiser 禁止跨頁面目錄的 import（頁面 A 的目錄不得被頁面 B 的檔案 import，要共用就先移進共用區；完整的相依方向見 §0.11）；掃描測試斷言共用區的每個模組**至少有兩個不同的使用者**，只有一個使用者即失敗——**去重鍵是「頁面根目錄」而不是檔案，定義與已知上限見 §0.9**（全域基礎設施——layout、router、統一 client——各算一個來源；含掃描器自我檢查，見 general 規範 §7.2）。

## 2. 狀態管理

### 2.1 進 Pinia 的判準

**規則**　同時滿足三點才進 store，否則留在元件內的 `ref`：(1) 跨頁共用 —— 至少兩個路由讀同一份；(2) 有生命週期 —— 需在登入時建立、登出或切換公司時清除；(3) 不是可重取的清單快照。本專案符合的大致只有：登入身分與所屬公司、權限碼集合、全域偏好、跨頁共用的主檔字典（下拉選單用）。

**理由**　把列表資料放進全域 store 是本專案最容易犯的過度設計。清單一旦進 store 就產生「誰負責清掉它」的問題：從列表進明細再返回，看到的是上一次的舊資料；切換公司後沒清，看到別家公司的資料。留在元件內時，元件卸載即消失，這類 bug 從結構上不存在。

```ts
// ✅ 查詢條件與結果留在頁面元件內，換頁重來一次
const rows = ref<RecordRow[]>([])
// ❌ 列表結果進全域 store，離開頁面沒人清
export const useRecordStore = defineStore('record', () => ({ list: ref<Record[]>([]) }))
```

### 2.2 store 的命名與結構 ✅（部分）

**規則**　一律 setup store；store id 與檔名同名，小寫單數領域名詞（`auth`、`permission`、`directory`），composable 命名 `useXxxStore`。對外只暴露 `readonly` 狀態與具名 action，禁止把可寫 `ref` 直接 return。每個 store 必須提供 `reset()`，並在登出與切換公司時被呼叫。

**理由**　狀態能從任何元件直接賦值時，「這個值為什麼變了」要全域搜尋才答得出來。沒有 `reset()`，切換公司會殘留上一家公司的權限碼 —— 畫面會出現使用者在新公司沒有的按鈕。

**檢查**　命名與 setup 寫法用 lint；`reset()` 存在性用掃描測試（每個 `defineStore` 回傳物件必須含 `reset`）。

## 3. API 呼叫

### 3.1 所有 HTTP 必須經過統一 client ✅

**規則**　元件、store、composable 一律禁止 `import axios`，所有請求走專案唯一的 HTTP client。

**理由**　token 附加、request envelope 的三個基底欄位（`rqTS` / `cmd` / `locale`，見後端規範 §1.3）、依 `code` 的統一分支處理（見 3.6）、`expiresIn` 的換算與保存（見 3.7）、後端錯誤格式轉成前端錯誤型別 —— 這幾件事若散落各頁，任一項要改就得改遍全站，而漏改的那幾頁不會編譯失敗，只會在 token 過期或後端回非 `200` 時默默壞掉。

**補充**　client 必須替所有請求自動補上 `rqTS`（送出當下的時間）、`cmd`（該端點的指令名，由產生的 API client 帶入）、`locale`，**頁面程式碼不得自己組這三個欄位**；也不得自己拆 envelope —— client 對外**只回 `data`，失敗時拋型別化錯誤**（見 3.3、3.6），頁面碰不到原始的 `rspTS` / `locale` / `msg`。envelope 一旦在頁面裡被手動拆解，後端加一個欄位就要改 N 處。

**產生的 API client 必須注入統一 client ✅**　OpenAPI 產生器的 fetcher／httpClient **必須注入本專案的統一 client**：產生的函式只負責型別、路徑與序列化，**實際傳輸一律交給統一 client**。**禁止使用產生器的預設 fetcher。**

**檢查的對象是「產生出來的 client」，不是「產生器的設定檔」。** 原文寫的是後者，那是假設用第三方產生器（`openapi-fetch` 之類）、而它有一個設定檔可以掃。本專案沒有：型別由 `openapi-typescript` 產（純轉譯、無執行期行為），client 由 `gen:api` 自己的樣板產，統一 client 的注入點是那支腳本裡寫死的一行——沒有設定檔可掃。

改成掃**產物**反而更強：設定檔對不對是間接證據，產物裡有沒有 `fetch(` 是直接證據。判準三條：產生的 client 必須 import 統一 client；不得出現 `fetch(`／`axios`／`XMLHttpRequest`／`sendBeacon`；**端點函式的數量必須等於統一 client 呼叫的次數**（兩個數字用兩種方式數，避免一起寫錯一起變綠）。 ✅（自製掃描腳本，含自我檢查）

**理由**　本節規定所有 HTTP 呼叫必須經過統一 client——token 附加、401 refresh 的 single-flight 收斂、envelope 拆解、依 `code` 分支（3.6）、`deadline` 覆寫（3.7）全部做在那裡。用預設 fetcher 的請求會**繞過這一整套**，而且**在本機開發時完全看不出來**：access token 在有效期內不會過期，所以 refresh 那條路徑要等兩、三個小時後才會被走到——那時候通常已經上線了，症狀是「某幾個畫面隔一段時間就會莫名其妙被登出或整片空白」，而那幾個畫面的程式碼看起來跟其他畫面沒有兩樣。§3.2 禁止手寫 DTO、§0.10 禁止手寫包裝層之後，產生器設定是唯一還能決定「請求實際怎麼送出去」的地方，它必須被寫死。

**token 的存放（後端規範 §5.4.3 是唯一定義處）**　本系統採 access token + refresh token 雙票：

- **access token 一律只存在前端記憶體**（統一 client 或 session 模組的模組層變數／store），**禁止寫入 `localStorage` 與 `sessionStorage`**，也禁止寫進 cookie。
- **refresh token 前端完全碰不到**——它由後端以 `httpOnly + Secure + SameSite=Lax` cookie 下發（屬性定案理由見後端規範 §5.4.3），JS 讀不到也寫不到。前端不得有任何讀寫 refresh token 的程式碼。
- access token 過期時，由**統一 client 呼叫 `POST /sessions/refresh` 換發並重試原請求**，這件事只做在 client 內、頁面完全無感；頁面也不得自行呼叫 refresh 端點。**重新整理頁面後 access token 會消失是預期行為**，前端啟動時打一次 refresh 換回來即可。

**理由**　兩張票若同時被 XSS 拿走，後端的偷用偵測（後端規範 §5.4.2）也救不回來——攻擊者可能比使用者本人更早 refresh，被強制登出的反而是使用者。`httpOnly` 讓 refresh token 對 JS 不可見，記憶體讓 access token 不會躺在 `localStorage.getItem` 一行就能撈走的地方；把 access token 存進 `localStorage` 換取「重整不掉線」，等於為了省一支請求把票放在 XSS 最容易讀到的位置。refresh 集中在 client 內做，則是因為散在各頁時會出現多支請求同時觸發 refresh，而 refresh token 是一次性的（後端規範 §5.4.2）——**併發 refresh 會讓第二支拿著已作廢的票，直接觸發全鏈作廢，使用者莫名其妙被登出**。

**並行的 refresh 必須收斂成單一 promise（single-flight）✅**　access token 過期時，**第一支**遇到過期的請求負責發出 `POST /sessions/refresh`，其餘同時遇到過期的請求一律 **await 同一個 promise**，拿到結果後各自重試自己的原請求；**不得各自發出 refresh 請求**，也不得用「先搶先做、後到的直接失敗」代替等待。refresh 完成（成功或失敗）後才可清掉那個共用 promise，讓下一輪重新開始。

**理由**　後端的 refresh token 是一次性輪替＋偷用偵測（後端規範 §5.4.2），規則本身是對的，但**這是少數「規則正確卻極容易實作錯」的地方**：一個頁面初始化時同時打三支查詢很常見，三支同時撞到 access token 過期也很常見，各自去 refresh 的話第二、第三支拿的是**已經被第一支換掉的舊票**，後端依規定判定為外洩 → 全鏈作廢 → 使用者在一次完全正常的開頁動作中被踢回登入頁。而且**錯誤現場當場消失**：使用者重登之後一切正常，log 上只看得到一次「偷用偵測」，沒有人重現得出來。

**檢查**　ESLint `no-restricted-imports` 禁止 `axios`，僅 client 檔案本身例外；**掃描產生出來的 client**（見下）；掃描測試禁止全站出現 `localStorage` / `sessionStorage` 存取 token 的程式碼（key 含 `token` / `auth` 者一律失敗），並禁止 client 以外的檔案出現 `sessions.refresh` / `/sessions/refresh`。**single-flight 用單元測試證明**：對統一 client 寫測試，mock 底層請求，同時發出三支都會遇到 access token 過期的請求，斷言 (a) 底層實際只被打出**一次** `/sessions/refresh`，(b) 三支請求最終都拿到成功結果。這是全文少數不靠靜態掃描、而是靠行為斷言的檢查——因為「有沒有收斂」看程式碼形狀看不出來，只看得出跑起來發了幾次。

```ts
// ✅ 共用同一個 in-flight promise，完成後才清掉
let refreshing: Promise<void> | null = null
function refreshOnce(): Promise<void> {
  refreshing ??= doRefresh().finally(() => { refreshing = null })
  return refreshing
}
// ❌ 每支過期的請求各自 refresh：第二支拿舊票 → 後端判定外洩 → 全鏈作廢
if (isExpired) { await doRefresh(); return retry(req) }
```

### 3.2 API 型別一律由 OpenAPI 產生，禁止前端手寫 DTO interface ✅

**規則**　請求與回應型別一律使用**由後端 OpenAPI 產生的型別與 client**（`bun run gen:api` 產出，spec 由後端路由 schema 產生，見後端規範 §1.7）。禁止在前端宣告任何描述 API 形狀的 `interface` / `type`，禁止用 `as any`、`as unknown as T` 繞過，也禁止手動修改產生物（產生物不進版控，改了下次重跑就沒了）。

**理由**　手寫 DTO 的本質是把後端契約複製一份。後端把某個單一欄位改成一張關聯表之後，前端那份副本仍然編譯得過，錯誤延後到執行期畫面顯示 `undefined` 才爆，而且爆在離改動最遠的地方。用產生型別的目的，就是讓這種改動**在 CI 編譯階段就紅**：後端 schema 一改，重新產生的型別就對不上前端的用法。「產生」而非「共用」也很關鍵——前端拿到的是 API 對外形狀，不是後端的內部型別（見 3.5）。

**檢查**　`vue-tsc`；lint 禁止 `as any`；掃描測試禁止前端出現以 `Response` / `Request` / `Dto` 結尾的本地型別宣告。

### 3.3 載入中／錯誤狀態統一處理

**規則**　每次非同步取數一律用三態表示（`loading` / `error` / `data`），且由統一 composable 產生，不各頁自己拼 `ref(false)`。錯誤必須是 client 轉換後的型別化錯誤（含 envelope 的 `code`、`msg`，以及 `code === '300'` 時的 `errors` 陣列），不得是原始 `AxiosError`。

**理由**　各頁自己管 `loading` 時最常漏的是「失敗時忘了關」—— 使用者看到永遠轉不停的圈。直接用 `AxiosError` 則會讓畫面出現 `Request failed with status code 422`，對 HR 使用者完全不可讀。

### 3.4 `onMounted` 內禁止未捕捉的 async ✅

**規則**　`onMounted` 的 callback 不得為 `async`，也不得呼叫回傳 promise 而未處理的函式；初始載入呼叫「內部已完整處理成功／失敗／結束」的載入函式。

**理由**　`onMounted(async () => ...)` 拋出的例外是 unhandled rejection，Vue 的 `errorHandler` 抓不到，畫面停在 loading，console 只有一行紅字，使用者看到空白頁且沒有重試入口。

**檢查**　ESLint `no-floating-promises` 與 `no-misused-promises`（需 type-aware lint）。

```ts
// ✅ load() 內部自行 try/catch 並設定 error 狀態
onMounted(() => { void load() })
// ❌
onMounted(async () => { rows.value = await fetchLeaveRequests(query) })
```

### 3.5 禁止 import 後端的任何型別或程式碼 ✅

**規則**　前端**不得以任何形式** import 後端 workspace（`apps/api`）的型別、常數、工具函式或任何模組——不得跨 workspace import、不得用相對路徑上溯、不得經由第三個套件轉手 re-export。唯一允許跨越這條界線的東西，是 `bun run gen:api` 由 OpenAPI 產生的型別與 API client（見 3.2）。

**理由**　前後端即使在同一個 repo，也是兩個獨立部署的系統，溝通只能透過 API，所以 API 格式的定義才是唯一該共享的東西。一旦前端 import 得到後端的程式碼，「編譯通過」就不再代表「API 相容」——前端拿後端的內部型別編譯成功，實際跑起來卻是透過 HTTP 收到另一種形狀的資料（後端 response 有映射函式挑欄位，內部型別跟對外形狀本來就不同）。連帶的三個後果：後端一次內部重構就讓前端 build 失敗，兩邊被綁成必須同時改；Drizzle row 型別、DB 連線設定這類伺服器端才有的東西可能被打包進**公開的**前端 bundle；以及界線一旦破一個口，之後「順手 import 一下」會迅速蔓延，等到要拆分部署時已經拆不開。

**檢查**　dependency-cruiser 禁止前端 workspace → `apps/api` 的任何相依（含傳遞相依）；ESLint `no-restricted-imports` 禁止 `@sundial/api*` 與含 `apps/api` 的路徑；產生物目錄為唯一例外。

### 3.6 一律依 `code` 分支，不看 HTTP status ✅

**規則**　所有回應處置一律依 envelope 的 `code`（後端規範 §1.3）決定，且**只在統一 client 內做一次**，頁面不得自行判斷 HTTP status（`err.response.status === 401` 之類一律禁止）。

| `code` | 處置 |
|---|---|
| `200` | 正常，回 `data` 給呼叫端 |
| `900` | **導向登入頁**（帶回跳網址） |
| `901` | **顯示「無權限」，絕對不可導登入頁** |
| `300` | 業務錯誤：讀 `errors`，逐筆顯示 `msg`，並依 `errors[].data.field` 的 dot-path 定位到該列該格標紅（見 6.3） |
| `100` | 一律當**系統錯誤**：進錯誤回報，**不對使用者顯示細節** |
| `400` | 一律當**系統錯誤**：進錯誤回報，**不對使用者顯示細節** |

**理由**

- **`code` 的分類軸是「前端拿到之後該做什麼」，不是 HTTP 語意**（後端規範 §1.3）。所以照 `code` 分支永遠只有六條路，照 HTTP status 分支則要自己把 404 與 500、409 與 422 合併，每一頁合併一次、每一頁都可能合錯。
- **`901`（403）若比照 `900`（401）導向登入頁，會產生無限迴圈**：使用者明明已登入，點到一個沒權限的功能就被踢回登入頁，登入成功後回到原頁又被踢回。使用者會認為整個系統壞掉，而且他重登幾次就遇到幾次。這正是後端把「無身分」與「有身分但無權限」分成兩個 `code` 的原因，前端**必須**把這兩條路分開走。
- **`100` 代表呼叫端沒照契約送資料，那是我們的 bug，不是使用者的操作問題。** 後端在 `100` 時不提供 `errors`（後端規範 §1.3），因此前端也沒有東西可以顯示給使用者——把它當系統錯誤送進錯誤回報，才會有人去修；當成表單錯誤顯示，只會讓使用者對著一個他改不動的欄位反覆嘗試。使用者層級的輸入問題會以 `300` 回來。
- **「查無資料」在查詢類與動作類端點的回法不同，前端不必也不該自己判斷是哪一種**（後端規範 §3.1）：查詢類（`list` / `get`）回 `200` + `data: null` 或空清單，**不是錯誤**，必須走空狀態畫面（7.2）；動作類（`approve` / `delete` / `update` 等）的目標不存在則回 `300`，走一般業務錯誤處理，顯示 `errors[].msg`（6.3）。兩者都已經由 `code` 分好了，照 `code` 分支就自然正確——**禁止**再多寫一層「這是不是找不到」的判斷。

**收到回應時的順序：先無條件覆寫 session `deadline`，再依 `code` 分支。**　`100` / `300` / `400` / `901` 的回應都帶續期後的 `expiresIn`（後端規範 §1.3），把覆寫寫在成功分支裡會讓使用者每遇到一次錯誤就少活一次續期（詳見 3.7）。

**檢查**　ESLint `no-restricted-syntax` 禁止 client 以外的檔案出現 `.response.status` / `statusCode` 比較；掃描測試禁止頁面程式碼出現 `'900'` / `'901'` / `'300'` 等 `code` 常值（分支只能在 client 與錯誤處理模組內）。

### 3.7 Session 到期一律用 `expiresIn` 換算，`exp` 不得上畫面 ✅

**規則**　收到回應時，若 `expiresIn` 不為 `null`，**當下**計算並保存 `deadline = Date.now() + expiresIn * 1000`；之後判斷是否接近／已過期一律用 `Date.now()` 與這個 `deadline` 比較。**禁止**把 `rspTS` 或任何其他來自伺服器的絕對時戳拿來當基準。`expiresIn === null` 表示本次請求未經 Session 授權，**不得**據此判定 session 已失效（會把公開端點的回應誤判成登出）。

**envelope 同時帶 `expiresIn` 與 `exp`，兩者用途不可互換**（後端規範 §1.3）：

| 欄位 | 前端唯一用途 | 禁止 |
|---|---|---|
| `expiresIn`（int，秒） | 算 `deadline`，並以它做**所有**過期／快到期判斷 | — |
| `exp`（string，ISO 8601 帶偏移，如 `2026-08-19T18:28:28+08:00`） | **只有一個**：寫進錯誤回報／log 供除錯 | **禁止出現在任何過期判斷邏輯中**——不得拿去跟 `Date.now()` 或 `new Date()` 比較、不得用來算 `deadline`、不得當「快到期」提示的門檻；**也禁止出現在任何顯示路徑上**——不得進模板、不得成為 format 函式的輸出 |

**理由**　`exp` 比較的兩端**來源不同**：截止點來自伺服器，「現在」來自使用者的裝置。裝置時鐘偏移多少，判斷就錯多少——使用者的筆電慢 10 分鐘，session 就會晚 10 分鐘才被判定過期（或早 10 分鐘就把人踢出去），而伺服器端完全看不出來，也重現不了。`expiresIn` 則是**寫入與讀取用同一個時鐘**：`deadline` 由 `Date.now()` 算出、又拿 `Date.now()` 去比，偏移量在相減時抵銷，時鐘準不準都不影響結果。

**`exp` 連顯示都不行。**　帶時區偏移的時間字串（`rqTS` / `rspTS` / `exp`）**一律不上畫面，沒有例外**（後端規範 §6.1、9.2）。顯示一個絕對到期時刻會同時踩到兩個問題：**時區**——帶 `+08:00` 的字串一旦進 `new Date()`／`dayjs()` 就會依瀏覽器時區再換算一次，使用者把筆電時區設成東京，畫面上的到期時刻就多一小時；**裝置時鐘偏移**——就算原樣印出字串不做換算，那個時刻對使用者仍是拿來跟他自己那個可能不準的時鐘對照的。而 `expiresIn` 的倒數兩個問題都不存在。

**畫面需要呈現剩餘時間時，一律由 `expiresIn` 倒數推導**（`deadline - Date.now()`，見下），顯示成「將於 12 分鐘後到期」這種**相對**說法，不要顯示絕對時刻。相對說法在時鐘不準的裝置上依然是對的，因為它自始至終沒有跨越兩個時鐘。

零例外的理由：只要 `exp` 被允許顯示，規則就從「帶偏移的字串不上畫面」退化成「要看是哪一欄」，而那正是會被記錯的東西——下一個人看到 `exp` 可以顯示，很自然會覺得 `rspTS` 也可以。這條也特別容易被違反，因為 `exp` 看起來「比較直觀」，而錯誤的判斷邏輯在開發者自己的機器上永遠是對的（時鐘準），只在客戶端偶發，且症狀是「有時候被登出、有時候登不出」。

**`expiresIn` 是滑動視窗（sliding window），不是固定到期時間。**　每一次通過**身分驗證**的請求都會**續期**，後端在**每個回應**都回傳續期後的剩餘秒數（後端規範 §1.3）。因此：

- **每收到一個 `expiresIn` 就無條件覆寫 `deadline`**，不要保留「第一次拿到的那個 deadline」、不要取兩者的較小值、不要以為後端在騙人而自己遞減。上面的規則本來就是這樣寫的，這裡只是把語意講明：覆寫不是防禦性寫法，而是**唯一正確**的寫法。
- **`901`（有身分但無權限）的回應也會帶續期後的 `expiresIn`，同樣要覆寫 `deadline`。** 續期發生在後端的身分驗證 middleware，與後續處理結果無關（後端規範 §1.3），所以 `100`／`300`／`400`／`901` 全都帶新的秒數。**只有 `900` 是 `null`**（沒有有效身分可續）。
  這點必須寫死，因為 3.6 把 `901` 導向「顯示無權限」那條分支，很容易順手寫成「錯誤分支就不更新 session」——結果使用者每點一次沒權限的功能，就等於少活一次續期，最後在一連串正常操作中莫名其妙被登出。**覆寫 `deadline` 的動作要放在 client 收到回應的共同路徑上，在依 `code` 分支之前，不是放在成功分支裡。**
- **倒數 UI（若有）只能是 `deadline - Date.now()` 的即時投影，禁止自己跑一個每秒 −1 的計數器當作真相，也禁止改用 `exp` 顯示絕對到期時刻。** 自己遞減的計數器在使用者持續操作時會一路數到 0，然後把還活著的 session 判成過期，把人踢出去；而 `deadline` 本身就是 `expiresIn` 推導出來的，每收到一個回應就被覆寫，投影自然跟著滑動視窗走。
- 因為是滑動視窗，「快到期」的提示只有在**使用者停止操作**時才會出現；本機開著頁面猛點是永遠測不到過期的，測試要靠停手等待或直接餵假的 `expiresIn`。

滑動視窗語意要寫死，則是因為把它誤當固定到期會寫出兩種都不報錯的倒數邏輯：一種是只認第一次的 deadline，使用者明明一直在操作卻被強制登出，且**每次都在登入後固定時間發作**，看起來像後端 session 設太短；另一種是本地每秒遞減而不理會回應，症狀相同但更難查，因為後端 log 上那個 session 根本還沒過期。把語意寫在這裡，後人就不必從行為反推規格。

**檢查**　ESLint `no-restricted-syntax`／掃描測試：session 模組的過期判斷邏輯中禁止出現 `exp`；**掃描測試禁止任何顯示路徑引用 `exp`**——`.vue` 模板與 `<script setup>` 一律不得出現 `exp`，format 模組不得有任何以 `exp` 為輸入或輸出的函式（讀取 `exp` 只允許出現在錯誤回報／log 的程式碼路徑）；9.2 的「format 模組以外禁止 `Date.now(`」規則需將 session 模組列為例外並標註用途；掃描測試禁止 session 相關程式碼出現 `new Date(` 解析伺服器時戳。

## 4. 權限與畫面

### 4.1 權限判斷只能用單一組原語 ✅

**規則**　全站只透過 `can(code)` / `canAny(codes)` / `canAll(codes)` / `scope(resource)` 判斷權限，權限碼是型別化聯集而非字串。禁止在頁面內讀角色名稱、比較 `role.code === 'HR_MANAGER'`、`roles.includes(...)`、`user.isAdmin`。

**理由**　本系統的權限模型是「角色 → 小權限」多對多，角色由各公司自訂、可新增可刪除。前端若認角色而不認權限碼，客戶新增一個角色時，要在全站每一處角色比較加上新角色名 —— 而沒有任何檢查會告訴你漏了哪一處。認權限碼則新角色只要在後端勾選權限，前端零改動。

**檢查**　權限碼型別化後拼錯即編譯失敗；掃描測試禁止頁面程式碼出現 `role` / `isAdmin` 的條件判斷。

```ts
const canApprove = can('<資源>.approve')                              // ✅
const canApprove = auth.user.roles.some(r => r.code === 'MANAGER')     // ❌
```

### 4.2 前端隱藏 ≠ 權限控制

**規則**　前端的 `v-if="can(...)"` 只是體驗優化。每一支被隱藏按鈕對應的 API，後端必須各自檢查權限與業務狀態；前端不得以「按鈕已隱藏」為由省略送出前檢查，也不得把前端的權限判斷結果送給後端當授權依據。

**理由**　前端 bundle 是公開的，權限碼集合在瀏覽器裡可改。後端規範 §5.2 已明訂權限與業務狀態必須在後端每一支端點各自檢查：前置狀態已不允許時仍被送出的請求，必須由後端拒絕。併發情境（兩個使用者對同一筆資料同時操作）前端無論如何也判斷不了，只有後端擋得住。

**本系統不做敏感操作的重新驗證（step-up authentication）**——查看薪資、查看個資等敏感操作**不會**要求重新輸入密碼。這是已定案的決定（後端規範 §5.4.4），因此前端**不得**實作任何「請再次輸入密碼以繼續」的流程、彈窗或提示，也不得自行為某些頁面加上二次確認密碼。要限制某個操作，唯一的手段是 4.3 的隱藏／停用＋說明，實際把關一律在後端。代價已記在後端規範 §5.4.4：所有資料都在同一個登入態下，取得登入態就取得該使用者全部權限範圍內的資料——這使得使用者只剩兩個自救手段：**「登出所有裝置」**與**改密碼**（後端規範 §5.4.5 已定案：改密碼成功即作廢該使用者的所有 refresh token，**含目前這台裝置在內，一律被踢下線**）。兩者的入口都**必須做在使用者找得到的地方**（帳號設定），不可只留給管理者；改密碼頁也**必須明白告知「所有裝置都將被登出，包含目前這一台，需重新登入」**，否則使用者不會知道自己剛剛已經處理掉了被盜的 session，還會繼續找別的辦法。

**改密碼成功後，client 必須立即清掉記憶體中的 access token 並導回登入頁。** 不得停留在原頁面繼續發請求——那些請求一定會回 `900`，使用者看到的會是一連串莫名其妙的錯誤，而不是一句「請重新登入」。

### 4.3 無權限時：隱藏 vs 停用 vs 提示

**規則**

| 情況 | 表現 | 例 |
|---|---|---|
| 使用者**永遠**不會有此權限 | **隱藏**，路由不進選單，直接進入導向 403 | 沒有該功能權限的人看不到整組選單 |
| 有權限但**當下狀態**不允許 | **停用 + tooltip 說明原因** | 某個前置狀態使該操作不再允許 → 該操作鈕停用，並說明是哪個前置狀態擋住了 |
| 有權限但資料未就緒 | **停用 + loading**，不顯示錯誤 | 所需資料仍在計算中 |

禁止以停用取代隱藏（滿畫面永遠按不了的按鈕）、以隱藏取代停用（按鈕突然消失，使用者不知發生什麼事）、無說明的停用。

**理由**　停用而不說明時，使用者唯一的行動是打電話問客服。本系統的操作限制幾乎都是狀態性的，說明原因才能讓使用者自行判斷下一步（例如去請有權限的人先解除那個前置狀態），而不是卡在原地。

## 5. 樣式

### 5.1 Tailwind 與 Element Plus 的分工

**規則**　版面與間距（排版、grid/flex、寬高、gap、padding、對齊）用 Tailwind utility class；互動控制項（表單元件、表格、彈窗、下拉、日期選擇、訊息、分頁）用 Element Plus，不得自幹。不得用 Tailwind 重刻 Element Plus 元件的內部外觀；不得為了排版在 Element Plus 元件上疊 `style`，排版一律用外層容器的 utility class。

**理由**　自幹表單控制項會失去 Element Plus 的鍵盤操作、表單驗證整合與無障礙屬性，而這些在大量表單的 HR 系統是每天在用的功能。反過來用 `el-row/el-col` 做整頁版面，則會讓兩套響應式斷點打架。

### 5.2 顏色、間距、字級一律走 token ✅

**規則**　禁止 inline style 寫死色碼、禁止 CSS 出現字面色碼、禁止魔術數字尺寸（`style="width:317px"`）。顏色、間距、字級、圓角、陰影一律用設計 token（Tailwind v4 `@theme` CSS 變數）。狀態色必須有具名 token，不得各頁自選相近顏色。

**理由**　同一種狀態在 A 頁是 `#e6a23c`、在 B 頁是 `#f0a020`，使用者看到兩種橘色，而沒有人說得出哪個才對。要調主題色或做深色模式時，寫死的色碼一個都改不到。

**檢查**　stylelint 禁止字面色碼；掃描測試禁止 `.vue` 出現含 `#` 或 `px` 的 `style="` 屬性。

### 5.3 覆寫 Element Plus 樣式的允許方式 ✅

**規則**　**允許**改 Element Plus 的 CSS 變數（`--el-color-primary` 等，全域統一設定一次），或透過元件提供的 `class` / `popper-class` 加上自訂 class。**禁止** `!important`、禁止堆疊選擇器提高權重（`.page .el-table tr td.cell span {...}`）、禁止 `:deep()` 穿透到 `.el-input__inner` 這類非公開內部結構。

**理由**　權重 hack 與內部 class 都綁在 Element Plus 的實作細節上。升級小版本、內部 DOM 一改，樣式無聲失效 —— 不編譯失敗、沒有測試變紅，只有畫面歪掉，通常在客戶那邊才被發現。`!important` 則讓後續任何合法覆寫失效，下一個人只能再疊一個 `!important`。

**檢查**　stylelint 禁 `!important`；掃描測試禁止出現 `:deep(.el-`。

### 5.4 響應式與最小支援寬度

**規則**　最小支援寬度 **1280px**。手機端只需支援員工本人的日常自助操作（少數幾個畫面），斷點以 Tailwind `md` 為界。其餘管理類頁面不保證手機可用，但**必須**讓寬表格在窄螢幕內水平捲動，不得讓整頁橫向溢出。

**理由**　員工用手機做本人的日常自助操作是必要場景，管理者用手機維護設定不是；不劃線就得為每張表格做卡片式 fallback，成本花在沒人走的路徑上。整頁橫向溢出則會讓固定側欄與表頭錯位，比單純截斷更難用。

## 6. 表單

### 6.1 驗證規則必須來自 OpenAPI schema ✅

**規則**　必填、長度、數值範圍、格式一律取自 OpenAPI schema 中的 `required`、`maxLength`／`minLength`、`minimum`／`maximum`、`pattern`（同 3.2 的產生來源），不得在前端另寫一套數字或正則。前端只允許額外做純體驗性的即時提示（例如輸入時就提醒而非等到送出），且**判定門檻仍必須來自同一份 schema**。

**理由**　兩套規則一定會漂移。前端限制 20 字、後端 50 字時，使用者被前端擋住卻不知道其實可以輸入；反過來則是填完按送出才吃 422。在多區塊、欄位數量大的表單上，這種白費特別痛。而後端本來就把這些限制集中定義在共用欄位型別裡（後端規範 §2），前端再抄一次的唯一結果就是抄錯或忘了跟改。

**檢查**　驗證規則由 OpenAPI schema 產生，後端欄位改名或限制變更時前端編譯失敗（`vue-tsc`）；掃描測試禁止表單規則中出現字面長度上限與正則字面量。

### 6.2 送出中防重複點擊 ✅

**規則**　送出按鈕在請求進行中必須 `disabled` 且顯示 loading；禁止只靠「送出後導頁」避免重複送出。所有有副作用的操作都適用。

**理由**　後端對同一筆資料的重複操作會以條件式 UPDATE 拒絕第二筆（後端規範 §4.4）。網路慢時連按兩下，第二次請求可能剛好落在第一次完成之後 —— 產生重複的紀錄，或反向操作掉自己剛完成的事。後端擋得住，但使用者會看到一個莫名其妙的錯誤。

**檢查**　掃描測試：帶 `@click` 且觸發 API 的 `el-button` 必須同時綁 `:loading` 或 `:disabled`。

### 6.3 失敗後的欄位錯誤呈現 ✅（部分）

**規則**　`code === '300'` 時，逐筆讀 `errors`，以 `errors[].data.field` 對應回表單欄位就地顯示 `errors[].msg`，並捲動到第一個錯誤欄位；`data` 中沒有 `field`（或找不到對應欄位）的錯誤才用全域提示。禁止只跳一個 `ElMessage.error('儲存失敗')` 了事。`errors` 只在 `code === '300'` 時存在（後端規範 §1.3），其他 `code` 依 3.6 處理，**不得**在表單上顯示。

**`field` 是路徑式（dot-path），必須依路徑定位到「該列該格」。**　後端的 `field` 一律是從 request body 根層寫下來的完整路徑，陣列以索引表示、0 起算（後端規範 §1.3）：`detail.startDate`、`items.2.startTime`。因此：

- **主路徑是解析 dot-path**：拆出路徑段，依段逐層走進表單資料結構，數字段即陣列索引，定位到**陣列中第 3 筆的那一格**並標紅、捲過去。不是拿整串 `field` 去跟某個扁平欄位名做等值比對。
- **解析與對應必須寫在統一函式內**（與 `el-form-item` 的 `prop` 對接），不是各頁自己 `split('.')`。Element Plus 的 `prop` 本來就吃 `items.2.startTime` 這種路徑，統一函式的工作是把後端路徑對到表單的 `prop` 命名，並處理對不上的情況。 ✅（掃描測試：表單錯誤呈現必須經該統一函式，禁止頁面自行 `split('.')` 或以 `field` 直接查自訂的欄位對應表）
- **找不到對應欄位時仍走全域提示**（保底路徑，不可拿掉）：後端可能回一個純業務層級、不對應任何輸入格的錯誤，或前端表單結構已改名。保底不存在時，這種錯誤會**完全不顯示**——請求失敗了，畫面卻一片安靜。
- `data` 內可能另帶指向其他位置的路徑（例如 `conflictWith: "items.1"`），可用來一併標示衝突對象；**但 `conflictWith` 不是 `field`**，不得拿它當主要定位依據。

**理由**　本系統多處畫面會出現「同一種欄位在陣列中重複出現」的結構。若把 `field` 當扁平欄位名處理，`startTime` 在一張五列的表格上**指不到任何一列**，前端唯一能做的是退化成全域提示「時間格式錯誤」，等於這個 `field` 白給，使用者得自己逐列比對找出是哪一筆錯。這也是後端規定 `field` 必須帶索引的原因：帶了索引卻在前端被當字串比對，等於兩邊都做了工卻沒有人得到好處。

另外，一張二十幾個欄位、分佈在多個區塊的表單，只說「儲存失敗」等於要使用者自己逐欄找。而 `errors[].data` 除了 `field` 之外還帶該錯誤的具體細節（例如 `remaining` / `requested`），這些是使用者自行修正的依據——「剩餘額度不足」與「剩餘 3、你要求了 5」對使用者的價值差很多。

### 6.4 大型表單的拆分與草稿

**規則**　「任一失敗整筆取消」的建立流程維持單頁單次送出，但必須按區塊拆成子元件，每個子元件只接收與回傳自己那段資料；可分段獨立更新的編輯流程按分頁拆分，**每個分頁獨立送出**。未送出內容一律**不**做自動儲存草稿，改為在離開有未儲存變更的表單時攔截確認。

**理由**　建立流程若是「任一失敗整筆取消」的交易，就不能拆成多次送出，只能靠子元件降低單一檔案的複雜度。草稿方面：這類表單可能含敏感個資，暫存 localStorage 會把敏感資料留在使用者裝置上，裝置換手即外洩；暫存到後端則需要一套「半成品資料」的狀態，資料模型沒有這個東西。

## 7. 表格與清單

### 7.1 分頁、排序、篩選參數與後端統一 ✅

**規則**　所有列表使用同一組查詢參數型別，型別一律取自 OpenAPI 產生的型別（同 3.2）。欄位名**固定**如下，與後端規範 §1.4 完全一致，禁止各頁自取別名：

| 用途 | Request 欄位 | Response 欄位 |
|---|---|---|
| 目前頁碼（1 起算，預設 1） | `currentPage`（平鋪） | `data.pagination.currentPage` |
| 每頁筆數（預設 20） | `perPage`（平鋪） | `data.pagination.perPage` |
| 總筆數 | — | `data.pagination.totalCount` |
| 排序 | `sort: { field, order }`（單欄，不支援多欄） | `data.sort` |
| 篩選條件 | 平鋪於 request 根層 | `data.search` |
| 清單本體 | — | `data.data` |

**總頁數由前端計算**：`Math.ceil(totalCount / perPage)`，後端不提供、也不得要求後端提供。分頁元件的 `total` 綁 `totalCount`，不要自己再存一份頁數。

查詢、排序、分頁**一律由後端執行**，前端不得對「當前頁資料」再排序或篩選後呈現。篩選條件變更一律回到第 1 頁（`currentPage = 1`）。

**理由**　前端對當前頁再排序時，使用者看到的是「這 20 筆之中的排序」，畫面卻顯示「共 340 筆」，排出來的第一名並不是全體第一名 —— 沒有任何報錯，使用者也不會察覺自己看錯了。條件變更不歸零頁碼則會出現「查詢有結果但畫面空白」（停在第 5 頁而新條件只有 2 頁）。總頁數不由後端給，是因為 `totalCount` 與 `totalPages` 並存時只要有一邊算錯，就會出現「共 137 筆、14 頁」但第 14 頁是空的 —— 而兩個數字都來自後端，前端沒有依據判斷該信哪一個。

**檢查**　查詢參數型別取自 OpenAPI 產生型別；掃描測試禁止列表頁對取回資料呼叫 `.sort(` / `.filter(` 後直接渲染；掃描測試禁止出現 `totalPages` / `pageTotal` / `pageCount` 等本地欄位名。

### 7.2 空／載入中／錯誤三種狀態都必須實作 ✅

**規則**　每個列表必須實作四種畫面：載入中、有資料、空結果、載入失敗（含重試按鈕）。空結果必須區分「本來就沒資料」與「篩選後無結果」，後者提示可清除篩選。

**理由**　只做「有資料」時，三種失敗長得一模一樣：都是一片空白。使用者無法分辨「這組條件真的沒有資料」「網路掛了」「篩選條件互斥」，只能回報「系統壞了」。空白畫面在 HR 系統特別危險 —— 該處理的清單顯示空白，使用者就真的不去處理了。

**檢查**　掃描測試：使用列表資料來源的頁面必須同時出現 error 分支與 empty 分支的渲染。

### 7.3 list 回應必須比對 `search` / `sort` 回聲，不符即丟棄 ✅

**規則**　收到 list 回應後，**必須先比對 `data.search` 與 `data.sort` 是否等於「目前畫面上的查詢條件與排序」**，不相等就整包丟棄：不寫入 `rows`、不更新 `pagination`、不關閉 loading（仍有較新的請求在途）。這段比對寫在統一的列表 composable 內，**不是各頁自己判斷**。禁止用「後送的一定後到」為前提直接賦值。

**理由**　使用者快速切換篩選條件（連點三個頁籤、邊打字邊查詢）時會連續送出多次請求，而**回應到達順序不保證** —— 第一次查詢走到一台比較慢的節點，可能比第三次晚回來。直接賦值的結果是**舊回應蓋掉新回應**：畫面上的篩選器停在 A 條件，列表卻是 B 條件的資料，`totalCount` 也是舊的那一次。這種 bug **不會報錯、不會有紅字**，測試也很難碰到（本機網路太快），只在客戶端偶發，而使用者唯一能得到的結論是「這個系統的數字不能信」。後端把 `search` / `sort` 原樣回聲就是為了讓這件事可判斷（後端規範 §1.4）—— 這兩個欄位不是冗餘資料，**拿掉它們等於把 race condition 放回來**。

**檢查**　掃描測試：列表資料的賦值必須發生在回聲比對函式的分支內（禁止在 API 呼叫的 `then` / `await` 之後直接賦值給列表 ref）。

```ts
// ✅ 統一 composable：回聲不符就丟棄（client 已拆掉 envelope，回的就是 data）
const page = await api.recordList({ ...search, sort, currentPage, perPage })
if (!isEcho(page.search, search) || !isEcho(page.sort, sort)) return   // 舊回應，丟掉
rows.value = page.data
pagination.value = page.pagination
// ❌ 舊回應會蓋掉新回應，畫面與篩選條件對不上
rows.value = (await api.recordList(query)).data
```

## 8. 測試

**本專案的前端測試分三層**：(a) **把值得測的邏輯抽成純 TS 函式再測**（8.1，來源見 1.3）；(b) **掃描型測試**（8.2）；(c) **E2E 測試**（8.3，Playwright，數量有硬上限）。**不做 `.vue` 元件測試**（8.1），這條維持不變。

三層的分工必須分清楚，否則會互相重複而沒有人負責真正的缺口：

| 層 | 證明什麼 | 抓不到什麼 |
|---|---|---|
| 純函式測試（8.1） | **算得對** —— 狀態矩陣、工時換算、payload 組裝 | 這個函式有沒有被接到正確的元素上 |
| 掃描型測試（8.2） | **東西有被接上、沒有孤兒** —— 路由可達、API 有呼叫端、權限碼存在 | 接上去之後跑起來對不對 |
| E2E（8.3） | **一條真實流程在瀏覽器裡從頭到尾走得通** —— 跨頁導向、跨角色互動、cookie 與重新整理、狀態機的完整轉移 | 沒被納入 E2E 覆蓋範圍的任何東西 |

**第三層補的正是 8.1 承認的那個缺口**：「函式對但模板接錯」（把某個判斷函式綁到另一顆按鈕上）在前兩層都是綠的，只有真的把畫面跑起來按下去才會紅。但**它只在被納入 E2E 的那幾條流程上補得到**——E2E 有嚴格的條數上限，缺口是被縮小，不是被消滅。剩下的部分仍由發版前的人工測試負責，人工測試的重點應放在**沒有被 E2E 經過的畫面**。

### 8.1 不做 `.vue` 元件測試

**規則**　本專案**不寫** `.vue` 元件單元測試，不引入 `@vue/test-utils`。值得測的邏輯先抽成純 TS 函式（見 1.3），再對函式寫測試。

**理由**　這是取捨，不是偷懶。要跑起一個稍有份量的頁面元件，得先 mock HTTP client、Pinia、router、Element Plus 的彈窗與 teleport，測試檔裡 mock 比斷言長；最後斷言的往往是「按鈕文字是某某」這種改個字就紅、真的壞掉卻不會紅的東西。相對地，「某些狀態下操作必須被停用」抽成純函式後，一個參數化表格就能把整張狀態矩陣逐格測完，跑得快、改模板不會壞。代價是「函式對但模板接錯」（把某個判斷函式綁到另一顆按鈕上）測不到 —— **這個缺口由第三層的 E2E 補（8.3）**，但 E2E 有條數上限，只覆蓋符合 8.3.2 判準且已被納入的少數流程；**不在那幾條流程經過的畫面上，這個缺口依然沒有任何自動化測試補得上，只能靠人工測試**。這是清醒的取捨，不是遺漏：知道缺口剩下哪一塊，人工測試才知道要重點看什麼。

### 8.2 掃描型測試（必須有）✅

**規則**　CI 必須包含以下掃描測試，任一失敗即擋合併：(1) **路由可達性** —— 每條註冊路由都必須出現在選單，或被某一頁的程式碼連過去，孤兒路由即失敗；(2) **未接端點清單** —— 比對 OpenAPI 的端點清單與前端實際呼叫到的產生函式，把「後端已開、前端尚未接」的端點輸出成一份**進版控的清單檔**；清單內容變動時測試變紅，必須有人明確更新。**這一條不因為有未接端點而失敗**，只在清單與實際狀況不符時失敗；(3) **權限碼有效性** —— 程式碼用到的權限碼必須存在於後端權限目錄；(4) **掃描器自我檢查** —— 每支掃描測試必須斷言「掃到的檔案／函式數量大於下限」。

**理由**　本專案真正的失敗模式不是「函式寫錯」，而是**「函式對、測試綠、沒有人用」**：後端端點做好了、型別對了、單元測試綠了，但 UI 上根本沒有入口，功能等於不存在。這種缺口既有檢查一個都抓不到 —— 型別是對的、測試是綠的、build 也過，因為「沒有人呼叫」不是語法錯誤，只有掃描抓得到。第 (4) 條同理：正則寫壞時掃到 0 個檔案也會顯示通過，比沒測還糟。路由那半可以直接動態 `import()` 路由宣告檔讀真正的物件（純 TS、無執行期相依），比正則硬；API 那半只能掃原始碼，因此更需要自我檢查。

**(2) 為什麼是「清單」而不是「零呼叫端即失敗」**　前端不再有手寫的 API 包裝層（§0.10），唯一的 API 函式來源是 `api/generated/`，而**它包含後端所有端點**。訂成「每支函式都要有呼叫端」的話，只要後端先行開發、有任何一支端點前端還沒接，CI 就是紅的——而那是完全正常的開發節奏，於是這條規則會在第一週就被要求放寬，然後永遠不會收回來。改成清單之後，它擋的東西反而更準：**「後端做好了、前端沒接」這件事必須被寫下來、被看見**，而不是被一個紅燈逼著隨便接一下或加白名單。

**(1) 的輸入是 registry，因此它上游還缺一段**：registry 漏收了哪一頁，這條掃描就看不到那一頁，對它**永遠是綠的**。那一段（檔案系統掃到的 `.route.ts` 數必須等於 registry 載入後的路由數，且兩個數字由兩種不同機制產生）規定在 §0.12，**與本條串起來才是完整的鏈：檔案存在 → 有被註冊 → 註冊後可達**。

### 8.3 E2E 測試（第三層）

本節規定的是 E2E 的**規則**，不是流程清單。E2E 的失敗模式眾所皆知——**無限膨脹、變慢、變不穩、被加上重試、被 skip，最後被移出 CI**——所以工具、選取判準、條數上限、資料前置、執行時機、穩定性政策與維護責任必須全部先寫死，再開始寫第一條測試。**先有這一節，才可以有 `e2e/` 目錄。**

**本節不指定任何一條具體流程。** 要覆蓋哪些流程，待功能範圍確定後依 8.3.2 的判準另行議定；本節先把約束立起來。

#### 8.3.1 工具一律用 Playwright ✅

**規則**　E2E 一律使用 **Playwright**（`@playwright/test`）。**不引入第二套瀏覽器自動化框架**（Cypress、Selenium、WebdriverIO、Puppeteer 皆不得再加），也不得自行用 Puppeteer 手刻一套 runner。瀏覽器目標只跑 **Chromium 一種**。

**為什麼是 Playwright 而不是 Cypress**

- **內建 auto-waiting**：定位器與斷言本身會等待與重試到條件成立或逾時，不需要手寫 `sleep`。手寫等待是 E2E 不穩的頭號來源——寫短了偶爾紅、寫長了每條慢兩秒，十幾條加起來就是每次 CI 白等半分鐘，而那半分鐘正是「E2E 太慢」這個死亡螺旋的起點。
- **trace viewer 讓失敗可回放**：失敗的那一次執行可以連同 DOM 快照、網路請求與回應、console 訊息一起回放。CI 紅了但本機重現不出來時，trace 是唯一的證據；沒有它，唯一的出路就是重跑——而重跑正是 8.3.7 要禁止的行為。**這一點直接決定 8.3.7 的政策做不做得起來。**
- **原生支援多分頁與多 browser context**：依 8.3.2 的判準，本層必然會涵蓋到需要**同時持有兩個身分或兩個裝置**的流程——跨角色的互動、跨租戶的隔離、一個裝置的動作對另一個裝置產生的效果、兩個身分對同一筆資料的併發操作，都屬於前兩層碰不到而只有這一層能驗的東西。Cypress 的架構是把測試碼跑在被測頁面所在的那一個分頁裡，**做不到同時操作兩個獨立 context**，只能靠外掛與 workaround 繞——而繞出來的東西正是日後最不穩的部分。其中「一個裝置改密碼、另一個裝置立即失效」這類驗證對應的是後端規範 §5.4.5「改密碼作廢所有 session」，那在本系統是「沒有 step-up 驗證」（後端規範 §5.4.4）之下的唯一防線；工具選型若讓它驗不到，這一層的價值少掉一大塊。
- **平行執行與 CI 整合成熟**：worker 層級平行、內建 HTML／JUnit reporter、官方 Docker image。配合 8.3.4「每條測試自建租戶」的隔離策略可以直接開平行，這是把整個 E2E job 壓在時間預算內的前提。

只跑 Chromium 的理由：多瀏覽器矩陣讓 job 時間乘上倍數，換到的是本專案不需要的東西——最小支援寬度 1280px 的內部 HR 系統（5.4），客戶端瀏覽器是可控的。要驗跨瀏覽器相容性時用人工，不用把每次 PR 都乘以三。

**檢查**　`package.json` 掃描：`cypress` / `selenium-webdriver` / `webdriverio` / `puppeteer` 出現在任何 workspace 的相依中即失敗（單一工具原則，同 general 規範 §4.1）。

#### 8.3.2 覆蓋範圍的選取判準與總數上限（**≤ 12 條**）✅

**選取判準（只測前兩層碰不到的東西）**　一條流程要進 E2E，必須至少命中下列其中一項，且必須是「壞了會讓使用者做不了事」的主線：

1. **跨頁流程** —— 需要連續經過兩個以上的頁面，中間有導向或會改變後端狀態的閘門；
2. **跨角色互動** —— 需要同時或先後持有兩個不同身分（例如一筆資料的發起者與處理者、兩位同權限的處理者、同一個帳號在兩個租戶下）；
3. **跨裝置行為** —— 一個裝置上的動作必須在另一個裝置上產生可觀察的效果；
4. **瀏覽器層行為** —— cookie、重新整理、回跳網址、多分頁、上一頁；這些不是純函式，也掃描不出來；
5. **狀態機的完整轉移** —— 一筆資料從建立走到終態、再被反向操作回中間狀態，且每一步的可用操作都跟著變。

**單一畫面內的邏輯一律不進 E2E** —— 那是 1.3 抽出來的純函式的守備範圍（8.1）。判準很直接：**這件事能不能只給一個函式幾個參數就測出來？能，就不准進 E2E。** 同理，**單純的單一畫面 CRUD 不進 E2E**：它命中不到上列任何一項，應由純函式測試加上後端端點測試覆蓋。

**總數上限**　E2E 的**總數上限 12 條**。**本節不預先定義任何一條流程**——要覆蓋哪些流程，待功能範圍確定後依上列判準另行議定並寫入本節；**上限先行約束**。**要加超過上限的流程，必須在同一個 PR 裡先刪掉一條，並說明被刪那條的缺口由誰接手。**

**為什麼要設上限**　E2E 最常見的失敗模式不是寫得不好，是**無限膨脹**：每修一個 bug 都很想「順手加一條 E2E」，而每一條單獨看都合理。加到跑一次要半小時之後，就沒有人願意在 PR 上等它——接著它會被移到 nightly，然後沒有人看 nightly，最後被移出 CI。**上限不是為了省時間，是為了讓這一層活下來。** 上限也強迫做取捨：名額滿了還想加，就必須回答「哪一條比它更不重要」，那個問題本身會篩掉大部分不該進來的測試。

**檢查** ✅　掃描測試：(1) `e2e/` 下的 spec 檔數量不得超過 12；(2) 每支 spec 檔開頭必須有註解標明**它覆蓋的是哪一條已議定的流程**，缺少即失敗；(3) 各 spec 標註的流程不得重複；(4) 掃描器自身須斷言掃到的檔案數大於 0（general 規範 §7.2）。

#### 8.3.3 明確不測什麼

**規則**　下列項目**明確排除在 E2E 之外**，不得因為「順手」或「這樣比較保險」而加進來：

| 不測 | 理由 | 由誰負責 |
|---|---|---|
| 樣式、版面、間距、色票、RWD 斷點 | 沒有穩定的自動判準 | stylelint／掃描測試（5.2、5.3）＋ 人眼 |
| **截圖比對（visual regression）** | 字型渲染、動畫時序、捲動位置的微小差異都會讓它變紅，是 flaky 的最大單一來源，最後必然被整組關掉 | 明確不做 |
| 單一元件的互動細節（下拉開合、日期選擇器、表格排序箭頭） | 那是 Element Plus 的責任，測它等於測第三方套件 | 不測 |
| 每個欄位的驗證訊息與長度上限 | 6.1 已規定驗證規則從 OpenAPI schema 產生，前端沒有第二份規則可以漂移 | 型別 ＋ 後端欄位定義 |
| 所有錯誤分支（每個錯誤碼、每種業務拒絕） | 後端規範 §7.1 已要求每個端點覆蓋成功／業務拒絕／無權限／不存在／跨公司五條 | 後端端點測試 |
| 單一畫面內的計算與顯示規則（數值換算、空值的呈現方式、按鈕可否按的狀態矩陣） | 給函式幾個參數就能測完，放進 E2E 只是用一百倍成本測同一件事 | 純函式測試（1.3、8.1） |
| 權限矩陣的每一格 | 格數等於角色數 × 端點數，放進 E2E 會直接撐爆上限 | 後端每端點的 403 測試（後端規範 §5.2）；E2E 至多取少數代表性角色 |
| 效能、負載、無障礙自動掃描 | 與流程正確性無關，混進來會讓 E2E 紅燈的意義變模糊 | 不在此層 |

**理由**　**沒有這一節，範圍一定會膨脹。** 8.3.2 的條數上限是硬約束，這一節是判準；只有上限而沒有判準時，名額滿了之後被刪掉的不會是最沒價值的那條，而是**最難維護的那條**——而最難維護的往往正是跨角色、跨裝置那幾條，也就是最有價值的那幾條。先寫清楚什麼不該進來，上限才會砍在對的地方。

#### 8.3.4 資料前置狀態與登入

**這是 E2E 最大的維護成本，規則必須具體到可以照做。**

**規則**

- **每條測試自建自己的公司（租戶）與員工**，公司代碼與員工編號帶隨機後綴避免碰撞；**測試之間不得共用任何資料**，也不得假設執行順序（沿用後端規範 §7.4）。
- **前置狀態一律走正式 API**，不得直接寫資料庫 —— **E2E 不持有 DB 連線，沒有例外**（沿用後端規範 §7.3，並比它更嚴格）。這不只是紀律：前置狀態走正式流程，等於順便驗證那幾支端點真的存在且可用；直接改 DB 造出來的狀態，則可能是正式流程根本產不出來的形狀，測到的東西在真實使用中不會發生。**確實無法由正式流程產生的狀態**（例如舊版遺留資料）只有一條路——請後端提供**僅在測試環境生效**的專用端點，並在測試檔內註明理由；不得繞過 API 層自行寫入。
- **禁止共用一份 seed 資料。** 理由：共用 seed 會產生兩種都很難查的失敗。其一是**互相污染**——一條測試把某筆資料的狀態改掉了，另一條測試預期它還在原本的狀態，於是後者在「單獨跑會過、整批跑會紅」之間反覆；其二是**改一處炸一片**——有人為了自己那條測試在 seed 裡多加一筆資料，別條測試的「清單第一列」就換人了，而失敗訊息完全不會指向那個改動。自建公司則讓每條測試的世界裡只有它自己放進去的東西，斷言可以寫死，也天生可以平行跑。
- **清理不是必要條件，隔離才是。** CI 每次從空 DB 跑完整 migration（general 規範 §7.4），因此測試結束不刪資料也不會污染下一次；有刪除端點時順手清掉即可，**不得為了清理而寫直接操作 DB 的程式碼**，那會把 8.3.4 第二條打破。
- **登入：只有「驗證登入流程本身」的測試才走 UI 登入，其餘測試一律程式化取得 session。** 程式化的作法是：呼叫登入端點取得後端下發的 **refresh token cookie**，存成 Playwright 的 `storageState` 再套進 browser context；前端啟動時會自己打一次 refresh 換回 access token（3.1），所以**只需要植入那個 cookie**。
  - **禁止**在程式化登入時往 `localStorage` / `sessionStorage` 塞任何 token —— 那不只違反 3.1，更糟的是它會讓測試走一條**正式環境根本不存在的啟動路徑**，於是「啟動時 refresh 換票」這段永遠不會被 E2E 走到，而那正是重新整理會不會掉線的關鍵。
  - 理由：每條都走 UI 登入，慢（每條多好幾秒，十條就是一分鐘）且脆弱（登入頁改個欄位名，十條測試一起紅，但壞的只有一條該紅）。**登入這件事只需要被驗證一次**，其餘測試要的是「已經登入」這個前提，不是再驗一次登入。
- **平行執行**：worker 數固定寫在設定檔（CI 與本機同一份），因為每條測試自建公司，平行不需要額外協調。**禁止**以 `--workers=1` 讓不穩的測試變綠 —— 需要序列化才會過的測試，代表它偷偷依賴了別條測試的狀態，屬於 8.3.7 的「當天修好或當天刪掉」。

#### 8.3.5 時間相依的處理

**規則**　**禁止任何測試依賴「今天是幾號」。** 具體作法：

- **前置資料的日期一律由測試自己推導出來，不寫死日曆日。** 需要某種性質的日期（例如「符合某條件的那一天」）時，先透過 API 把該條件查出來再挑一天，不要假設今天就是。寫死某個日曆日的測試會在該日之後永遠錯，寫「今天」的測試會在週末、假日、月底當天壞掉——而且**壞的那幾天通常沒有人在上班**。
- **查詢一律明確指定期間，不依賴畫面的預設區間**——除非那條測試的斷言本身就是「預設區間」。混用兩者會讓一條測試在月初與月底表現不同。
- **「現在」由後端的可注入 clock 決定（後端規範 §6.2），不是由前端偽造。** 因此需要固定「現在」的流程，**必須有後端提供的測試用 clock 機制**（例如僅在測試環境生效的固定時間設定）；沒有這個機制時，**凡是結果取決於特定時點的流程一律不進 E2E**，留給後端單元測試（後端規範 §7.1 已要求邊界值）。這是刻意的取捨：與其寫一條只在某些日期會過的 E2E，不如明確不寫。
- **禁止用 `waitForTimeout` / `sleep` 等待業務時間流逝**，也禁止用瀏覽器端假時鐘去影響業務判定 —— 前端顯示與計算用的時間字串全部來自後端（9.2），偽造前端時鐘不會改變任何業務結果，只會製造「前端顯示 A、後端算 B」的假象，讓測試綠得毫無意義。**唯一例外**是純前端的 session 倒數顯示（3.7），那個判斷本來就完全發生在前端，可用 Playwright 的假時鐘推進；但它本身命中不到 8.3.2 的判準，不因此成為一條 E2E。

#### 8.3.6 執行時機：只在 CI ✅

**規則**

- **E2E 只在 CI 跑，不進 pre-commit、不進 pre-push。** 它需要真實 MariaDB、需要 build 前端、需要起後端服務，三項都直接違反 general 規範 §7.3「需要資料庫、需要啟動服務、或耗時超過 30 秒的檢查一律不得放進 git hook」。
  **理由**　把這種檢查塞進 hook，結果不是大家變嚴謹，而是**所有人都學會 `--no-verify`**——而且一旦學會，他們會對所有檢查都用它，連原本 1 秒跑完的格式與 secret 掃描也一起被略過。hook 的價值完全建立在「快到不值得繞過」之上。
- **在 CI 中排在最後**：獨立 job，`needs` 前面所有快檢查（ESLint + Prettier、`vue-tsc`、單元測試、掃描測試、後端測試）通過之後才啟動。
  **理由**　快的先跑、快的先紅。E2E 排在前面時，一個 typo 也要等整組瀏覽器測試跑完才知道，而回饋一慢，開發者就會改成「先推上去讓 CI 跑」，本機檢查隨之荒廢。
- **E2E job 的時間預算 ≤ 6 分鐘**（含 build、migration 與瀏覽器啟動）。超過就是必須處理的問題，處理順序是：先檢討有沒有流程該被刪（8.3.2）、再調平行度；**不得靠放寬預算解決**。 ✅（CI 量測 job 時間，超時即紅）
  **理由**　general 規範 §7.3 的 CI 總預算是「目標 10 分鐘」，E2E 排在其他檢查之後，兩者相加已經接近上限。這正是 8.3.2 條數上限存在的原因——想要更多流程時，先刪，不是先加時間。
- **環境**：與後端測試共用同一個真實 MariaDB service container，從空庫跑完整 migration（general 規範 §7.4）。**禁止對開發或正式環境跑 E2E**。 ✅（E2E 啟動時檢查 API base URL 與資料庫連線字串為測試環境，否則中止，沿用後端規範 §7.4）
- **E2E job 失敗一律擋合併**，不得設為 `continue-on-error`、不得標記為 optional。 ✅（CI 設定掃描）
  **理由**　允許它紅著合併的那一天，它就正式變成裝飾品；而且沒有人會回頭修一個不擋任何事情的紅燈。
- 本機可以跑（`bun run test:e2e`），但**不是必須**。本機跑不起來不得成為擋 PR 的理由，也不得反過來成為把它從 CI 移除的理由。

#### 8.3.7 穩定性政策 ✅

**這一節決定整個計畫成不成立。E2E 不是死於寫不出來，是死於沒有人再相信它的顏色。**

- **禁止設定任何 retry。** `retries` 必須為 `0`，CI 與本機同一份設定；也不得在 CI 指令列加 `--retries`，不得用「紅了就重跑這個 job」代替。 ✅（設定檔與 CI 設定掃描：出現非 0 的 `retries` 或 `--retries` 即失敗）
  **理由**　重試會把「偶爾壞掉的功能」和「不穩的測試」變成**同一種顏色**——而前者正是這一層唯一存在的理由。本系統偶發失敗的典型來源恰恰是真的會偶爾壞的東西：兩個身分對同一筆資料的併發操作、refresh token 一次性輪替下的併發換票（3.1）、以及任何「先後順序會影響結果」的時序。開了 retry，「第一次紅、第二次綠」會被記錄成通過，而那正是最該被看見的訊號被丟掉的瞬間。這條也與 general 規範 §7.4「禁止以 CI 不穩定為由重跑到綠燈後合併」同源。
- **紅燈一律先當成真的壞掉，直到有證據證明不是。** 判斷依據**必須寫進 PR 描述**，且必須具體到：trace 中的哪一步、哪一支請求、回應的 `code` 是什麼、跟預期差在哪。只寫「這條偶爾會紅」「重跑就好了」不算依據。
  **理由**　沒有這條要求時，「測試不穩」會變成萬用擋箭牌——它不需要證據、不需要負責，而且每次都有效。要求附上 trace 的判讀，等於強迫至少有一個人真的看過那次失敗。
- **不穩定的測試：當天修好，或當天刪掉。沒有第三個選項。** 禁止 `test.skip`、`test.fixme`、註解掉、以 tag 排除在 CI 之外，也禁止「先標記起來下個 sprint 處理」。 ✅（掃描測試：`e2e/` 下不得出現 `test.skip` / `test.fixme` / `test.only` / `.skip(` / `.fixme(`）
  **理由**　**被 skip 的測試會留在程式碼裡假裝有覆蓋。** 它出現在檔案清單裡、出現在「我們有 E2E」這句話裡，但它一行都沒跑；而看到它的人會合理推論那條流程有防護，於是人工測試也不看了——**缺口沒有消失，只是變成沒有人知道的缺口**。刪掉至少是誠實的：條數少一條，已議定的流程少一條，缺口明確地攤在文件上，下一個人看得到。
- **刪掉一條時，必須在同一個 PR 記錄下來**，並說明刪了哪一條流程、缺口由誰接手（人工測試清單或後端測試）。 ✅（spec 數量與 8.3.2 的上限比對）
- **失敗時必須留下可回放的證據**：設定 `trace: 'retain-on-failure'`，失敗時一併保留影片與 console 輸出，並上傳為 CI artifact，保存期不少於 14 天。 ✅（設定檔掃描：`trace` 設定存在且非 `off`；CI 設定含 artifact 上傳）
  **理由**　沒有 trace 時，「本機重現不出來」的唯一出路就是重跑，而重跑是這一節禁止的。禁止重跑卻不提供證據，等於要求開發者用猜的——最後一定會有人去改設定。**這條是禁止 retry 這條規則的配套，不是加分項。**
- **每條測試的 timeout 固定 90 秒，寫在設定檔而非個別測試裡**；逾時視為失敗，**不得靠拉長 timeout 解決**。 ✅（設定檔掃描：`timeout` 存在且個別 spec 不得覆寫）
  **理由**　拉長 timeout 是掩蓋不穩的另一種形式，而且它同時讓 job 變慢——兩個問題一起變嚴重，卻只解決了顏色。

#### 8.3.8 維護責任

- **什麼情況必須補 E2E**：一律依 8.3.2 的判準判斷——新功能同時滿足 (a) 命中 8.3.2 的任一判準、(b) 屬於「壞了會讓使用者做不了事」的主線、(c) **名額還有剩**。名額滿了就必須先回答「刪哪一條」，答不出來就不加——**這不是妥協，這就是上限的作用**。
- **什麼情況不必補**：命中不到 8.3.2 任一判準的東西，包括單一畫面內的邏輯（純函式測試）、單一畫面的 CRUD；只是多一個欄位、多一個篩選條件、多一個排序欄；只有文案或錯誤訊息改變；後端規則變更但 UI 流程不變（那是後端測試的事）；只是修一個不在既有 E2E 流程上的 bug（補一條純函式測試即可，見 general 規範 §7.5「修 bug 先補會失敗的測試」）。
- **既有 E2E 因功能變更而失敗時，禁止直接改斷言讓它變綠。** 必須先回答一個問題：**是需求變了，還是東西壞了？** 判斷依據只有一個 —— 該流程的畫面規格文件。規格改了才可以改斷言，且該 PR 必須同時更新規格文件（general 規範 §8「文件變更與程式碼變更同一個 PR」）；**規格沒改就是壞了，要修的是程式碼**。
  **理由**　改斷言是讓紅燈消失最快的方法，而且它看起來非常像在維護測試——commit 訊息可以誠實地寫「更新 E2E 斷言」，review 也很難看出不對。但一旦允許，這一層就從「驗證規格」退化成「記錄目前行為」的快照：它永遠是綠的，因為它的期望值總是等於實際值，而它也就永遠不會再告訴你任何事。
- **每條 E2E 的檔案開頭必須註明它覆蓋的是哪一條已議定的流程，以及對應的畫面規格檔名**（8.3.2 的檢查）。這不只是給掃描器看的——**規格檔名寫在測試裡，才有人在改規格時想得起來要來看這裡**。

### 8.4 測試檔本身 ✅

**規則**　禁止 `it.only` / `test.skip` 進主線；禁止沒有斷言的測試；測試名稱用繁體中文描述行為（「前置狀態不允許時該操作不可執行」），不用函式名。本節適用於所有測試檔；**E2E 另有更嚴格的規定**（8.3.7：連 `test.fixme` 與長期 skip 都禁止，且不得設 retry）。

**理由**　`only` 進主線會讓同檔其他測試全部靜默不跑，CI 依然全綠。

## 9. 無障礙與國際化的最低要求

### 9.1 無障礙最低線 ✅（部分）

**規則**　所有表單控制項必須有可及標籤（`el-form-item` 的 `label` 或 `aria-label`），純圖示按鈕必須有 `aria-label`。互動元素必須是 `button` / `a` / Element Plus 元件，禁止 `div` + `@click` 當按鈕。不得只用顏色表達狀態，狀態標籤必須同時有文字。彈窗開啟時焦點進入彈窗、關閉後回到觸發元素（Element Plus 預設行為，不得關掉）。

**理由**　`div` + `@click` 無法 Tab 到、無法 Enter 觸發 —— HR 大量鍵盤輸入的場景下等於要求使用者在鍵盤與滑鼠間反覆切換。只用顏色表達狀態則讓色覺障礙使用者分不出不同狀態。

**檢查**　`eslint-plugin-vuejs-accessibility` 可涵蓋標籤缺失與 `div` 點擊；「不得只用顏色」靠 review。

### 9.2 文案與格式 ✅

**規則**　介面語言 zh-TW，使用者可見字串一律走語系檔 key，禁止在 `.vue` 內寫死中文（`aria-label` 亦同）。日期 `YYYY-MM-DD`、日期時間 `YYYY-MM-DD HH:mm`（24 小時制）、年月 `YYYY-MM`。時間長度以「小時，小數一位」呈現（`170.1 小時`），由統一函式從分鐘換算，禁止各頁自己除 60。金額千分位無小數（TWD），比率以百分比呈現並標明小數位。所有格式化必須經統一 format 函式，禁止直接呼叫 `toLocaleDateString` / `toFixed`。

**時區：前端不做任何時區換算。** 全系統一律台北時間（`Asia/Taipei`, UTC+8），API 傳來的 `datetime` 就是台北牆鐘時間、格式為 `YYYY-MM-DD HH:mm:ss` 且**不帶時區標記**，`date` 為 `YYYY-MM-DD`（見後端規範 §6.1）。因此：

- 顯示日期時間時，**直接對字串做裁切／重排**（取前 16 個字元即 `YYYY-MM-DD HH:mm`），不要為了格式化而先轉成 `Date`。
- **禁止**把 API 回來的時間字串丟進 `new Date()`／`dayjs()` 再輸出、禁止 `toISOString()`、禁止任何 `timeZone` 相關參數。送給後端的**業務時間**同樣是這兩種字串格式，不得送出帶 `Z` 或 `+08:00` 的值（唯一例外是 envelope 的 `rqTS`，由統一 client 產生，頁面碰不到，見下表與 3.1）。
- 需要「現在」時（例如預設查詢區間）由統一的 clock 函式提供台北時間字串，不在頁面裡各自 `new Date()`。

**兩種時間格式必須分清楚**（後端規範 §6.1 是唯一定義處）：

| 類型 | 格式 | 誰負責 |
|---|---|---|
| 傳輸層時戳 `rqTS` / `rspTS` | ISO 8601 **帶時區偏移**（`2026-04-14T14:30:00+08:00`） | **只有統一 client 碰得到**（3.1）；僅供 log 對時與除錯，**不上畫面** |
| Session 截止時刻 `exp` | ISO 8601 **帶時區偏移**（`2026-08-19T18:28:28+08:00`） | **只有 session 模組碰得到**（3.7）；僅供 log 與除錯，**禁止用於過期判斷，也禁止顯示給使用者** |
| 業務時間 / 日期 | `YYYY-MM-DD HH:mm:ss`、`YYYY-MM-DD`（**無時區標記**） | 頁面顯示與計算用 |

**帶時區偏移的時間字串一律不上畫面，沒有例外。**　`rqTS` / `rspTS` / `exp` **三者都只供 log 與除錯**，不得出現在任何顯示路徑上（模板、以及任何 format 函式的輸出）；它們也一律禁止拿來當業務時間計算。`exp` 另外還禁止用於過期判斷（走 `expiresIn`，見 3.7）——也就是說 `exp` 在前端只剩「寫進錯誤回報與 log」一種用途。畫面需要呈現剩餘登入時間時，一律由 `expiresIn` 推導的 `deadline` 倒數而來（3.7），顯示成相對說法。

零例外的理由：本節的判準是「**格式決定用途**」——看到帶偏移的字串就知道它不上畫面，不必去查它是哪一欄。一旦其中一欄被允許顯示，判準就退化成「要看是哪一欄」，而那是會被記錯的東西。

一般頁面程式碼看到任何帶 `+08:00` 或 `Z` 的時間字串就是錯的 —— 要嘛是後端違反 §6.1，要嘛是有人把 `rspTS` 當成「這筆資料的時間」在用（那是「回應產生的時刻」，跟該筆業務事件實際發生的時刻是兩回事，在重試或排隊時會差好幾秒），要嘛是有人把 `exp` 從 session 模組漏了出來。

**理由**　同一批數字若在統計區與明細列表各自換算與四捨五入，就會出現「總計 170.1，但逐筆加起來是 170.0」這種對不起來的帳，使用者會合理懷疑整套系統的數字。日期格式不統一（`2026/8/1` vs `2026-08-01`）則讓排序與跨頁比對都變困難。時區的部分更嚴重：`new Date('2026-08-26 09:30:00')` 會被當成**瀏覽器所在時區**的時間，之後任何輸出都可能被再換算一次——使用者把筆電時區設成東京，整批時間就多一小時，畫面上不會有任何錯誤提示，而使用者會據此做出判定。字串進、字串出，這個失敗模式就不存在。

**檢查**　掃描測試禁止 `.vue` 出現裸露中文字串（白名單除外）；ESLint `no-restricted-syntax` 禁止直接呼叫 `toLocaleDateString` / `toLocaleString` / `toFixed` / `toISOString`，並禁止在 format 模組以外出現 `new Date(` / `Date.now(`（例外只有兩處且須列在白名單：統一 client 產生 `rqTS`、session 模組換算 `expiresIn` 的 `deadline`，見 3.7）；掃描測試禁止 session 模組以外的程式碼引用 `exp`，禁止 session 模組在過期判斷路徑中引用 `exp`，並禁止**任何顯示路徑**引用 `exp`（`.vue` 一律不得出現 `exp`；format 模組不得有以 `exp` 為輸入或輸出的函式）（3.7）；掃描測試禁止頁面顯示邏輯處理帶 `+08:00` / `Z` 的時間字串。
